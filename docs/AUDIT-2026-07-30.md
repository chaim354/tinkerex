# Audit — performance + security, Rails app (2026-07-30)

> **HISTORICAL — not re-verified.** Written before the repository split of 2026-08-20, when the
> sync engine and the Rust client still lived here (they are `chaim354/tinkerex-sync` and
> `chaim354/tinkerex-client` now). Kept for its reasoning and its measurements; it does not
> describe what this repository contains today. The current map is `docs/README.md`.


**Scope:** the Rails server — web controllers/views/helpers, the v1 API, models, `Sync::*`,
`FileLayer`, jobs, and `config/`. The Rust client crates are out of scope (different threat
model: local, single-user, no network trust boundary of its own).

**Baseline at audit time:** branch `claude/todo-audit-tests-baf3f9`, merge-base `5051404`.
Suite **1690 runs / 5918 assertions / 0 failures / 0 errors / 11 skips** in 6.5 s.
`bin/bundler-audit` clean. `bin/brakeman` **0 warnings** (4 ignored, each a documented false
positive — verified, see "What was checked and is fine").

**Method note.** Every performance finding here is a **measurement**, and the web-coverage
figure is instrumented rather than eyeballed: a temporary `process_action.action_controller`
subscriber recorded which `controller#action` each test actually drives, and the query figures
come from a `sql.active_record` subscriber counting the same page at two data sizes. Reading
code finds what you thought to look for; counting finds what you didn't. Two findings below
(P1, S9) were invisible to reading and fell straight out of the counts.

## Severity ladder used here

| | Meaning |
|---|---|
| **HIGH** | Exploitable now, or silently losing/exposing user data now. |
| **MEDIUM** | Real exposure, but bounded by another control, by deployment shape, or by needing a precondition. |
| **LOW** | Defence-in-depth, or a gap only reachable under concurrency / an unusual deployment. |
| **INFO** | Recorded so the next reader doesn't re-derive it. Not work. |

Nothing in this audit is HIGH. That is the finding to lead with: the tenancy model, the
byte-delivery policy, and the parameter handling are all sound, and the automated gates are
genuinely green rather than green-because-unrun. What is left is hardening, one N+1, and one
piece of infrastructure that was provisioned and never switched on.

## Security

### S1 — No SSL enforcement: no HSTS, and the session cookie never gets `Secure` — MEDIUM

**Evidence.** `config/environments/production.rb:28,31` — both `config.assume_ssl` and
`config.force_ssl` are commented out. Repo-wide, nothing else enables them:

```
grep -rn "force_ssl\|assume_ssl" --include='*.rb' --include='*.yml' . | grep -v ^./client
config/deploy.yml:23:# Using an SSL proxy like this requires turning on config.assume_ssl and config.force_ssl…
config/environments/production.rb:28:  # config.assume_ssl = true
config/environments/production.rb:31:  # config.force_ssl = true
```

**Consequence.** For the internet-facing deployment (tinkerex.com, HTTPS terminated ahead of
the app): no app-layer HTTP→HTTPS redirect, no `Strict-Transport-Security`, and — the one that
matters most — `force_ssl` is what marks the session cookie `Secure`, so **the session cookie
is sent on a plain-HTTP request to the same host**. A single downgraded request leaks a live
session.

**Why it is MEDIUM and not HIGH.** `assume_ssl` being off also means Rails does not believe it
is on HTTPS, so this is one setting, not a compromise in progress; and the LAN deployments are
genuinely plain HTTP, so the current state is *wrong for one host*, not for all three.

**Fix must be env-gated, not simply enabled.** The three Unraid backends are reached by IP over
plain HTTP on the LAN. An unconditional `force_ssl` redirects them to a URL nothing serves and
takes all three down. This is almost certainly why the line was left commented — the fix is to
make the intent explicit rather than to flip it.

### S2 — User enumeration: `config.paranoid` is off — MEDIUM

**Evidence.** `config/initializers/devise.rb:93` — `# config.paranoid = true`, commented.

**Consequence.** An attacker learns which addresses are registered, which is the input to
credential stuffing and to targeted phishing.

**CORRECTED DURING THE FIX, and the correction is the useful part.** This finding originally
said login *and* password reset both leak. **Login does not** — measured: an unknown address and
a wrong password both return `422` with the identical flash `"Invalid email or password."`, so
Devise is generic there by default. **Reset was the whole leak**, and the channel is not what a
reader would check first:

| | Known address | Unknown address |
|---|---|---|
| Status | **303** (redirect) | **422** |
| Body | — | contains `"not found"` |
| `flash[:notice]` | "You will receive an email…" | **identical** |

The flash text was *already* the same in both cases. The oracle was the **status code and the
body** — so an audit that read only the flash copy would have concluded this was fine. That is
why the test asserts status, location and flash together.

**Consequence for reset specifically:** it is the cheap oracle. No password guess, no rate-limit
interaction — POST an address, read the status code.

**Note on the fix's blast radius, also corrected:** the plan warned that `paranoid = true` would
change user-visible copy and that tests asserting flash text would need to move with it. It did
not — the existing 12-test auth flow suite passes untouched, because it asserts status codes and
redirects rather than copy.

### S3 — No rate limiting on any endpoint — MEDIUM

**Evidence.** `grep -rn "rate_limit" app/ config/` returns nothing. `ActionController::Base`
does respond to `rate_limit` on this Rails (8.1.3) — verified — so the facility is present and
unused.

**What is already covered, so the finding stays honest.** Devise `:lockable` **is** enabled —
`app/models/user.rb:41-43` includes it, the `failed_attempts` / `locked_at` / `unlock_token`
columns exist (`db/schema.rb:486,490,496`), and `devise.rb` sets `maximum_attempts = 10`,
`lock_strategy = :failed_attempts`, `unlock_in = 1.hour`. So a **targeted** password guess
against one known account is already bounded at 10 tries per hour.

**What is genuinely unbounded:**
1. **Password spraying** — one attempt each against many accounts never trips a per-account
   lock.
2. **Mail flooding** — `passwords#create` and `confirmations#create` each send a real email per
   POST, unthrottled. That is both an abuse vector aimed at a third party's inbox and a fast
   way to get the sending domain classified as a spam source.
3. **Lockout as denial of service** — the flip side of `:lockable`. Anyone who knows a user's
   email can lock that account for an hour, repeatedly, indefinitely. Per-IP throttling is the
   control that makes lockable safe rather than weaponisable.

**Depends on S9.** A `rate_limit` counter lives in `Rails.cache`. Read S9 first: today that is
a container-local `FileStore`, so a throttle added now would reset on every deploy, and in the
test environment (`:null_store`) it would **do nothing at all** — a rate-limit test would pass
without the throttle existing. Wire the cache first, or the fix and its test are both theatre.

### S4 — No Content-Security-Policy — LOW

**Evidence.** `config/initializers/content_security_policy.rb` is 100 % comments (no
uncommented line).

**Why LOW rather than MEDIUM, argued rather than assumed.** The obvious stored-XSS route in an
app that serves user-uploaded bytes is already closed **deliberately and in the right place**.
`app/controllers/files_controller.rb:361-369` computes the type with `Marcel`, then serves
`inline` only for a raster allowlist plus `application/pdf`, forcing everything else —
explicitly naming SVG and HTML — to `attachment`, with `X-Content-Type-Options: nosniff` on
both non-redirect branches. Rich text is sanitised by Action Text *and* stripped of attachments
server-side by `Maker::TextOnlyRichText`. `grep` finds exactly one `sanitize(` in the view
layer (`app/helpers/notes_helper.rb:7`, wrapping Kramdown output) and no `html_safe` or `raw`
anywhere in `app/views`.

So CSP here is a genuine second layer, not the only one. Worth having — it is what catches the
*next* inline-serving mistake — but it is not load-bearing today.

### S5 — No upload size cap and no per-user quota — MEDIUM (managed) / LOW (self-host)

**Evidence.** `files_controller.rb#create` is `params.require(:file)` handed straight to
`FileLayer.current.write`, with no size check; `projects/uploads_controller.rb:27` is the same
shape; no Rack request-body limit is configured anywhere in `config/`.

**Consequence.** Any authenticated user can write files of unbounded size and unbounded total
volume. Self-hosted that is the user's own disk and arguably their business. On the managed
plan it is unbounded storage and egress cost with no ceiling, and no mechanism to express one.

**Deliberately not fixed blind.** The right cap is a product decision (per-file limit, per-user
quota, or both, and at what numbers), and a wrong number is worse than none because it rejects
legitimate CAD files. Recorded with a recommendation, not a value.

### S6 — `maker_file_attachments` has no uniqueness index — LOW

**Evidence.** `db/schema.rb:203-204` carries two non-unique indexes and no unique one on
`(user_id, attachable_type, attachable_id, node_id)`.

**Measured before reporting, and it downgrades the finding.** Two sequential POSTs of the same
node to the same project create **one** row — the application-level guard works. The gap is
therefore TOCTOU under genuinely concurrent requests only (double-click, retried fetch), not a
routine duplicate.

**If fixed, the migration needs a dedupe pass first**, since existing rows may already violate
the constraint and `add_index unique:` would fail on a live database.

### S7 — Password floor is 6 characters, with no complexity or breach check — LOW

**Evidence.** `devise.rb:183` — `config.password_length = 6..128`.

Six characters is below any current guidance. Note the honest counterweight: NIST now
deprecates composition rules in favour of length plus a breached-password check, so the fix is
"raise the floor (10–12) and consider a breach check", **not** "add symbol/digit requirements".

### S10 — Irreversible account deletion with no re-authentication — MEDIUM

**Evidence — driven, not reasoned.** `DELETE /users` is routed to
`users/registrations#destroy` and the controller adds no override, so Devise's default
`resource.destroy` runs. A single request carrying only the session cookie:

```
before: users=1 projects=1 nodes=1 tasks=1
DELETE /users with NO password -> 303 → /
after:  users=0 projects=0 nodes=0 tasks=0
```

**Consequence.** One request permanently destroys the account and, via 31 `dependent: :destroy`
associations, the entire library catalog — projects, nodes, tasks, build log, attachments,
previews, sheets, devices. There is no server-side confirmation step, no password check, and no
undo.

**What is NOT wrong here, checked rather than assumed:**
- **The cascade is complete.** `app/models/user.rb:2-31` declares `dependent: :destroy` on
  every association, so deletion does not orphan DB rows or trip a foreign key. A great many
  apps get this wrong; this one does not.
- **Tenancy holds.** A signed-in user deleting their own account leaves other users untouched
  (verified: A deletes A, B survives).
- **CSRF is protected**, so this is not a one-click attack from another origin.
- **Chunk bytes are not leaked.** The `chunks` rows go, leaving storage objects with no DB row
  — which is exactly what `Sync::ChunkReaper` sweeps weekly. On share/s3 library backends the
  user's own files are deliberately left alone; that is their storage, not ours.

**So the exposure is narrow but the blast radius is total:** it needs an authenticated session,
and given one it is unrecoverable. The standard control is requiring the current password on
destroy, which Devise supports directly.

### S8 — Preview blobs are URL-capability, not user-scoped — INFO

`Maker::Preview` uses `has_one_attached :asset` served through `url_for`. An Active Storage
signed blob URL is a bearer capability: unguessable, but not tied to the signed-in user, so
anyone holding the URL can fetch the image. This is standard Rails behaviour and the exposure
is one thumbnail. Recorded so nobody reports it as a finding later; not work.

Worth noting the related hole **is already closed**: `ActiveStorage::DirectUploadsController`
descends from `ActiveStorage::BaseController`, not `ApplicationController`, so it shipped
unauthenticated — and `config/routes.rb` now shadows it with a 404, pinned by
`test/integration/web/direct_uploads_gate_test.rb`.

## Performance

### P1 — `projects#show` has an N+1: one `ActionText::RichText` load per build-log entry — MEDIUM

**Evidence — measured, then named.** Query count for the same page at two sizes:

| Data size | Queries |
|---|---|
| 3 attachments / 3 tasks / 3 entries | **14** |
| 15 / 15 / 15 | **26** |

Exactly +1 per added entry. Tallying the SQL at N=10 names it outright:

```
 10x  ActionText::RichText Load   SELECT … FROM "action_text_rich_texts" WHERE "record_id" = ? AND "record_type" = ?
  4x  Node Load                   SELECT … FROM "nodes" WHERE "user_id" = ? AND "deleted" = ? AND "node_id" IN (…)
  1x  … (nine more, all constant)
```

**Cause.** `app/controllers/projects_controller.rb:40` eager-loads
`build_log_entries.includes(:file_attachments)`. Rich text bodies arrived with the project-page
overhaul (PR #91) and the `includes` was never extended to `:rich_text_body`, so rendering each
entry's body triggers its own query.

**Why it went unnoticed, and the generalisable part.** `models#show` loads the same *shape* of
data — attachments plus a child collection — and is **flat at 11 queries**. So the codebase
already contains the correct pattern; this page diverged from it. Nothing in the suite asserts
query counts on any web page, which is precisely why a page could regress from flat to linear
without a single test changing colour. The fix is one line; **the guard is the valuable part.**

### P2 — Four identical `Node Load` queries on `projects#show` — LOW

Same page, same node-id list, four times (see the tally above). `@att_nodes`, `@entry_nodes`,
and `Maker::Previews::ThumbnailMap` each resolve nodes independently. This is **constant, not
N+1** — it does not grow with the page — so it is a tidiness/latency item worth roughly three
round-trips, not a scaling bug. Listed because a reader looking at the tally will notice it and
should know it was seen and classified.

### P3 — `files#index` folder view is unpaginated — LOW, and a decision rather than a defect

Already documented in `docs/STATUS.md` under "Open, and shipped knowingly": ~160 ms of render
at 2000 nodes, and **identical on all three backends**, which is the evidence that the port's
cost is gone and the residual is HTML generation. The flat `?ext=` mode *is* bounded
(`FLAT_LIMIT = 2000`, with an announced truncation). Pagination for the folder view is a
file-browser product decision on its own merits. Carried forward unchanged; no new evidence.

### S9/P5 — Solid Cache is installed, provisioned, and not switched on — MEDIUM

Filed under both headings because it is a performance facility that is also a **precondition
for S3**.

**Evidence.** The substrate is complete: `solid_cache` is in the `Gemfile:39`; `config/cache.yml`
configures it (256 MB, per-env namespace); `config/database.yml` declares the `cache` role for
both the SQLite and Postgres profiles; `db/cache_schema.rb` exists, so the table is
provisioned; and the storage volume is persisted (`config/deploy.yml:125`,
`tinkerex_storage:/rails/storage`). But `config/environments/production.rb:86` still carries
the untouched Rails scaffold line, `# config.cache_store = :mem_cache_store`. Resolved for
real, rather than inferred:

```
RAILS_ENV=production bin/rails runner 'puts Rails.application.config.cache_store.inspect'
[:file_store, "…/tmp/cache/"]
```

**Consequence.** `Rails.cache` is a `FileStore` inside the container's `tmp/`. It is wiped by
every Kamal deploy, it is invisible to any second app container, and it is not the durable
store the deployment already pays for. Nothing in the app depends on the cache for correctness
today, which is why this has been harmless so far — and exactly why adding `rate_limit` on top
of it would quietly inherit all three properties.

**Sharpening what is and isn't wrong.** Solid **Queue** and Solid **Cable** are both correctly
wired (`production.rb:82-83`; `config/cable.yml:12-13`). Two of three were done deliberately
and the third was missed. Also checked and **not** a finding: `database.yml` points the Solid
roles at `migrations_paths: db/cache_migrate` etc., which do not exist — Rails 8 loads
`db/<name>_schema.rb` for these stores instead, and those files are all present. That one looks
alarming and is cosmetic.

**Doc drift, worth correcting with the fix:** `CLAUDE.md` §4 lists the stack as "Rails 8 (Solid
Queue/Cache/Cable)". The Cache third of that claim is not in effect.

## What was checked and is fine

Recorded deliberately. An audit that lists only faults tells the next reader nothing about
where not to spend their attention, and several of these are places a reasonable person would
expect to find a bug.

- **Tenancy / authorization.** Every web controller scopes through `current_user.*`. No
  unscoped `.find` on a user-owned model. The v1 API has a dedicated isolation test per
  resource (`test/integration/v1/maker/*_isolation_test.rb`, plus `tenant_isolation_test.rb`
  and `cross_tenant_fk_test.rb`).
- **Stored XSS via uploaded bytes.** Closed on purpose, with the reasoning in-code —
  `files_controller.rb:361-369`, raster-plus-PDF inline allowlist, everything else
  `attachment`, `nosniff` on both non-redirect branches. See S4.
- **Strong parameters.** Every mutating web action uses `params.require(...).permit(...)` with
  an explicit column list. The one open-shaped permit — `projects/sheets_controller.rb:72`,
  `data: {}` — is deliberate (a spreadsheet blob) and **bounded**: `Maker::Sheet::MAX_DATA_BYTES`
  is 1 MiB, enforced by a `validate`.
- **CSRF.** Exactly one `skip_forgery_protection`, in `dev_blobs_controller.rb:9`, on a
  controller that is only routed when `!Rails.env.production?` (`config/routes.rb:187-191`).
- **Open redirect.** No `redirect_to` takes a user-supplied URL. The one
  `allow_other_host: true` is `files_controller.rb:383`, redirecting to a presigned storage URL
  the app itself minted.
- **SSRF / outbound HTTP.** The two sidecar clients call env-configured base URLs, never
  user-supplied hosts, and both set timeouts (`boxes_client.rb:40,62` — open 3 s, read 10/30 s;
  `openscad_client.rb:82`).
- **Log hygiene.** `filter_parameter_logging.rb` filters `:passw`, `:secret`, `:token`, `:_key`,
  `:crypt`, `:salt`, and `:email` among others.
- **Share-link tokens.** SHA-256 digested at rest, looked up **by digest** so there is no
  string-compare timing surface, with `live?` re-checked on every redeem *and* every presign
  mint (`app/models/share_link.rb`).
- **Automated gates are green and genuinely run.** `bundler-audit` clean; `brakeman` 0
  warnings; all four ignore entries re-read and confirmed as false positives (two
  `Open3.capture3` ARGV-array calls, one integer interpolation Brakeman's own `user_input`
  field admits is an integer, one enum label). All three scanners sit in **one** `bin/ci` gate
  by design, because splitting them is what let brakeman's exit 3 mask bundler-audit for weeks.
- **Duplicate attachments.** Prevented at the application level — measured, 2 POSTs → 1 row.
  See S6 for the residual concurrency gap.

### S4-a — `frame-ancestors 'none'` contradicted a shipped feature — found by the browser

The report-only policy as first written set `frame-ancestors 'none'`. The app embeds its **own**
PDF previews in same-origin iframes (`app/views/files/show.html.erb:94`,
`app/views/models/show.html.erb:89`), and Rails' default is already
`X-Frame-Options: SAMEORIGIN` — so `'none'` was stricter than the app's own behaviour and,
enforced, would have refused to let our page frame our blob endpoint. **Every PDF preview would
have gone blank.** Now `'self'`.

### S4-b — the nonce was empty for anonymous visitors — found by the browser

`content_security_policy_nonce_generator` was `request.session.id.to_s`, and `session.id` is nil
until a session exists. Every sign-in, sign-up and reset page therefore emitted `'nonce-'`, which
Chrome reports as *"an invalid source"* and responds to by **discarding the entire `script-src`
directive**. Enforced, that policy would have protected nothing on precisely the pages reachable
without credentials — and the header would still have looked present and correct in every
integration test. Now falls back to `SecureRandom.base64(16)`.

**The lesson both share, and it is the one worth carrying forward:** these were found because
`bin/ci`'s system-test gate asserts on **SEVERE browser console messages**, and because the policy
shipped **report-only** rather than enforcing. An integration test can confirm a header is
present and well-formed by its own reading; only a browser will tell you the header is being
*ignored*. Both are now pinned in `test/integration/web/content_security_policy_test.rb` so the
next occurrence does not need a browser to catch.
