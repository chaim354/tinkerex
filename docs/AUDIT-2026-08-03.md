## 1. Architecture & data model

### A-H1 — The chunk-GC grace window is dead code: refcount `update_all`s never refresh `updated_at`, so `sweep_orphans!` can free a concurrently re-referenced chunk — HIGH (managed/tiered only)

**Evidence (all re-verified directly, not just reported by the stream):**
`Sync::Gc.sweep_orphans!` frees chunks matching `refcount: ..0` AND `updated_at <= cutoff`
(`app/services/sync/gc.rb:105`), under the stated contract "Never frees a still-referenced
**or freshly-zeroed** chunk" (gc.rb:91). But every refcount mutation in the codebase is a raw
`update_all`, which does not touch `updated_at`: the decrement (gc.rb:31) and all three
increments (`sync/commit.rb:208`, `sync/restore.rb:20`, `sync/conflicts.rb:112`).
`updated_at` is set exactly once, at `insert_all` time (`commit.rb:203-205`). So the grace
filter tests **creation age, not zeroing age** — for any chunk older than an hour (i.e. every
real chunk), the protection does not exist. Compounding it: `sweep_orphans!` takes **no user
lock** (unlike `prune_version!`, gc.rb:26) and `chunk.destroy` (gc.rb:107) never re-checks
`refcount` at delete time.

**Consequence.** Managed/tiered deployments only (`RETENTION_POLICY` defaults to `keep_all`,
which never decrements — verified in `app/jobs/retention_job.rb`). Interleaving:
`RetentionJob` prunes a version → chunk hits refcount 0 → sweep fetches its batch → a
concurrent `Sync::Commit#finalize` dedups against the still-present row (client uploads
nothing; refcount 0→1 under the user lock the sweep doesn't take) → sweep destroys the row
and deletes the bytes → **a live version references a chunk with no row and no bytes.
Silent, permanent data loss.** `finalize`'s verify closes only orderings where the row is
already gone at verify time. `Restore` and `Conflicts.split` re-referencing a zeroed chunk
share the exposure.

**Fix (violates no §14 invariant):** (1) every refcount `update_all` also sets
`updated_at = ?` (four sites), making the grace window mean what its comment says; (2) the
sweep becomes compare-and-delete —
`user.chunks.where(id:, refcount: ..0).delete_all == 1` before `store.delete`; (3) optionally
mirror `PendingCommitReaper`'s `last_modified` guard before the byte delete. Mutation-check
per §15: revert (1), watch a frozen-clock sweep test go red.

### A-M1 — No job-overlap protection anywhere; overlapping `RetentionJob`s double-decrement, overlapping `ScanJob`s violate the Reconciler's sequential-pass assumption — MEDIUM

Zero `limits_concurrency` declarations in `app/jobs/` (verified); `config/queue.yml` runs 3
worker threads, so same-user job overlap is real. `Gc.apply_retention!` loads version lists
outside any lock, and `prune_version!` on an already-deleted version still runs its decrement
(the `WHERE refcount > 0` guard prevents negatives, not wrongful decrements of a chunk shared
with a surviving version) — two overlapping retention passes zero a chunk a live version
references, feeding A-H1's sweep. A first-pass scan on a big NAS (>15 min of hashing)
overlaps its successor, a state the Reconciler's crash-repair design never argues about
(`reconciler.rb:47-55` argues sequential passes). **Fix:** Solid Queue
`limits_concurrency to: 1` keyed per user on `ScanJob`/`ProjectIntakeJob`, keyed globally (or
per user) on `RetentionJob`; independently make `prune_version!` overlap-safe
(`delete_all == 1` before decrementing).

### A-M2 — The changelog is unbounded: `prune_changelog!` exists, is tested, and is never called in production — MEDIUM

Verified: the only non-test reference to `prune_changelog!` is its definition (gc.rb:86).
`changelog_entries` grows one row per mutation per user forever — `SubtreeDelete` mints one
**per node**, so one big folder delete adds thousands — while the client-side pruned-gap
machinery (`oldest_seq`, full-resync detection) is fully built and permanently idle. **Fix:**
wire it into `RetentionJob` under the tiered policy (keep N days or `head_seq - K`);
self-host/`keep_all` untouched.

### A-M3 — `manifest_chunks` rows are never reclaimed — the second unbounded accumulation under tiered retention — MEDIUM

Verified by grep: `ManifestChunk` is inserted (`commit.rb`) and read; no delete site exists.
When the last version referencing a manifest is pruned, its rows (up to 100 k per manifest)
persist forever — in the table the pull/snapshot hot path queries. **Fix:** in
`prune_version!`, delete manifest rows when no remaining version and no live share link
references that `manifest_id` (both indexed lookups; add `versions[user_id, manifest_id]` if
needed) — or a periodic orphan-manifest sweep in `RetentionJob`.

### A-M4 — Maker referential integrity: deleting a supplier/location/inventory-item via the live v1 API strands references, then locks the referencing rows against future edits — MEDIUM — **CLOSED 2026-08-10**

`DELETE /v1/maker/suppliers/:id` and `locations/:id` hard-destroy with no `dependent:`
handling and no DB FKs (the schema's `add_foreign_key` list covers only addon tables), while
`InventoryItem`/`BomLine` validate `*_belongs_to_user` **whenever the id is present** — so
after a supplier delete, every referencing row fails validation on its next save ("must
reference your own supplier") until a field the not-yet-built UI may not even show is
cleared. Bites exactly when the inventory/BOM UI (§12.9, the named next slice) ships.
**Fix:** `dependent: :nullify` on `Supplier`→items/bom_lines, `Location`→items, and
nullify-or-refuse on `InventoryItem`→bom_lines (where a dangling id also still satisfies
`exactly_one_target`, leaving a ghost target); DB FKs with `on_delete: :nullify` pin it on
both adapters.

**CLOSED 2026-08-10** (branch `claude/maker-referential-integrity`; full entry in
`docs/STATUS.md`). One column beyond the three named was in scope: `maker_bom_lines.supplier_id`.
`dependent: :nullify` on `Supplier`→items/bom_lines and `Location`→items; `InventoryItem`→bom_lines
instead **converts the line to a free-text part**, carrying the item's name *and its supplier* into
`part_name`/`supplier_id` before dropping the pointer — the "nullify-or-refuse" note above is right
that a nulled line breaks `exactly_one_target`, and measurement confirmed nullify merely swaps one
permanent lock for another. (`part_number` is not carried: `maker_bom_lines` has no column for it.)

**The DB FKs were deliberately NOT taken**, and not for effort — but the reason first recorded here
was half wrong, and the correction matters because the wrong half is the scarier one. The
measurement stands: on SQLite, `add_foreign_key ... on_delete: :nullify` over already-violating
data **is accepted** at migration time and the bad row survives (`pragma_foreign_key_check` lists
it afterwards). The stated consequence — "then raises `ActiveRecord::InvalidForeignKey` on the next
write" — **does not follow for the ordinary path**: SQLite re-checks a child row only when the
statement names a child key column, and Rails' partial UPDATE does not name the FK, so the write is
refused earlier and identically to today, by the `*_belongs_to_user` validation → `RecordInvalid` →
**422**. `InvalidForeignKey` appears only on a write that names the FK column while skipping
validations (probed: `SET supplier_id = 999` errors, `SET supplier_id = NULL` does not), and this
app has none. So **"turns this finding's 422 into a 500 on self-host" is false** — strike it.

What holds is the other half: **Postgres validates existing rows on `ADD CONSTRAINT` and errors**,
which would abort the managed deploy. Stated honestly, two opt-outs went unmentioned: `NOT VALID`
skips that validation, and the violating rows could be cleared by a two-line
`UPDATE ... SET fk = NULL WHERE fk NOT IN (SELECT id FROM ...)` prelude **in the same migration**
rather than a separate pass. The deferral is therefore a judgement about cost and timing, not an
impossibility. **It still stands**: nothing bypasses Active Record on these three deletes
(independently re-verified), and the lock is an Active Record validation no constraint can lift, so
the FKs buy defence-in-depth rather than the fix. Carried forward as **ledger row 24**.

### A-M5 — No per-user storage accounting or quota exists at all — MEDIUM (managed)

Zero hits for any quota/usage concept in `app/`. `chunks.size` exists per row, so
`user.chunks.sum(:size)` is computable, but nothing computes, caches, or enforces it — §5's
keep-versions plus per-user dedup means a managed user's footprint is unbounded and
*invisible*; the prior audit's "upload quota needs a number" has no measurement substrate
under any number chosen. **Fix:** a `users.storage_bytes` counter maintained where refcounts
cross 0↔1, nightly reconciled from `sum(:size)` in `RetentionJob`, enforced at
`Sync::Commit.begin` (which already knows the missing-hash sizes).

### A-M6 — `SubtreeDelete` is one unbounded transaction holding the per-user `FOR UPDATE` lock, one `next_seq!` round-trip per node — MEDIUM

Deleting a 50 k-node folder ≈ 150 k statements in one transaction while holding the user-row
lock — every device commit for that user blocks for the duration (Postgres) or all writes
stall (SQLite). Correct but the worst-case write-path latency spike and a plausible
pooler-timeout casualty on managed. **Fix:** reserve a seq *range* with one `head_seq` bump,
`insert_all` the changelog entries, `update_all` the tombstones — same lock, same atomicity,
~3 statements instead of 3N, preserving "seq first, one entry per node."

### A-M7 — Composite indexes lead with `user_id` but the hot associations query by bare child FK — the index never applies — MEDIUM

Verified for `maker_build_log_entries`: only index `[user_id, project_id, logged_at]`
(schema.rb:169), queried as `@project.build_log_entries` → `WHERE project_id = ?`
(`projects_controller.rb:43`) — a btree can't seek without its leading column (Postgres has
no skip-scan). Same shape: `maker_sheets`, `maker_bom_lines`, `maker_inventory_transactions`,
`maker_collection_items` (deleted by bare `item_id`). Contrast `maker_boms
[project_id, revision]` and `maker_print_runs [model_id, printed_on]`, which got it right —
the convention is inconsistent, which is how the wrong shape got copied. Full scans land on
exactly the tables that grow monotonically (build log, inventory ledger), and the
query-budget guard asserts count, not plan, so it degrades silently. **Fix:** migration-only
— add bare-FK-leading indexes (or user-scope the associations so the composites apply).

### A-LOW (verified by the stream; spot-checked)

- **L1** Eight redundant bare `[user_id]` indexes fully covered by sibling composites on the
  hottest write-path tables (`changelog_entries`, `chunks`, `manifest_chunks`, `nodes`,
  `pending_commits`, `share_links`, `versions`, `maker_addon_states`) — pure write
  amplification; `manifest_chunks` takes up to 100 k-row `insert_all`s per manifest. Drop
  them; keep `devices`/`maker_print_runs` (no covering composite).
- **L2** `PendingCommitReaper` TOCTOU: a >TTL-stale commit finalizing between the reaper's
  `committed` snapshot and its per-hash delete loses just-committed chunks (the
  `last_modified` guard can't help — the object *is* older than the cutoff). Narrow window;
  re-check `chunks.exists?` immediately before each `store.delete`.
- **L3** `Maker::PrintRun` is the only ownership-carrying maker model without a
  belongs-to-your-own validation — defense-in-depth today (controller scopes correctly), a
  cross-tenant write the day a controller bug ships. Add for symmetry.
- **L4** Per-file ActionCable broadcasts on bulk flows (see P5 — one finding, two lenses: a
  500-file device push is 500 broadcasts/Solid Cable inserts from `v1/commits_controller`).
- **L5** Account deletion instantiates every row of every table (~30 `dependent: :destroy`
  incl. `manifest_chunks`/`chunks`/`versions`); at SaaS scale, millions of AR objects — and
  the `chunks/<user>/` object-storage keyspace has **no deletion story at all** on account
  close. Split into `delete_all` for pure-sync tables + `destroy` where
  ActiveStorage/ActionText callbacks are real, and add the keyspace sweep.
- **L6** Row accumulation with no reaper: resolved `conflicts`, expired/revoked
  `share_links`. Fold into `RetentionJob`.
- **L7** `t.json` is `json`, not `jsonb`, on Postgres (`addon_states.data`,
  `models.print_settings`, `previews.metadata`, `sheets.data`) — read-whole blobs today, but
  the first naive `WHERE data->>...` behaves differently across adapters. `jsonb` on PG is
  invisible to SQLite.

### A-INFO — architecture assessments (no action required now)

- **FileLayer port / 4th backend fit:** the verb set is coherent (5 reads + 5 writes,
  per-op refusals). A path-shaped 4th backend (remote SMB/WebDAV) fits cleanly — the loud
  dispatch points all raise rather than skip. An id-shaped store (Google Drive) breaks first
  at `Observation`/`storage_path` (path is the identity key for scanned backends), not at the
  port — it needs a third observer and an identity story before any new verb. The five
  capability flags are sustainable *because* each pair's independence is argued in
  `capabilities.rb`; the real risk is the scattered gates (12 `require_capability!` + 11
  inline `port_writable?` sites) keyed on today's coincidences — a notification-driven
  backend (`scannable: false, syncable: false, port_writable: true`) would silently not be
  indexed by anything. That's the sixth capability (`notifiable`) waiting to happen.
- **Sync↔Maker boundary: clean, verified.** Controllers touch `Sync::` in exactly the
  recorded places; the §14c single-`ChunkStore`-hit proof still returns exactly
  `library_output.rb`. No new coupling since the invariants were written.
- **Duplicate sibling names are representable server-side in chunk mode** (no uniqueness on
  `(user, parent, name)` for live nodes; scanned backends are protected by the
  `storage_path` partial unique index). Deliberate — the *client* adjudicates collisions
  (`fs-provider`) — but the server-never-adjudicates fact deserves one sentence in
  `docs/sync-protocol.md` so a future "fix" (a unique index) doesn't break the client's
  displacement model.
- **`Sync::Search` is O(tree) per query** (recursive CTE materializing every path, then
  LIKE) — correct, tenant-safe, injection-safe (verified); FTS5/pg_trgm is the recorded
  follow-up. Known ceiling at 100 k nodes.
- **Client crates: clean split**, no duplicated sync logic (the one shared computation,
  `manifest_id`, is protocol-mandated on both sides); 5 TODOs total, all in the stubbed
  `fs-fskit`. One naming smell: the maker-app API client lives in `sync-client/src/maker.rs`
  (1,791 LoC) — structure fine, name misleading.
- **Doc drift, three small:** CLAUDE.md §4 says no `client/fs-fskit` crate exists on `main`
  — it does (stubbed FFI; the paid-dev-account half is still true). §14a's write-verb list
  omits `mkdir`. `maker/preview.rb:2` still opens with the retired per-version keying its
  own line 22 contradicts.

### 2.1 — A malicious or compromised addon bundle owns the account — HIGH as a design property; accepted for self-host, **unacceptable as-is for SaaS**

`addon_controller.js:15-23` `import()`s remotely-fetched ESM into the authenticated page and
**hands it the CSRF token explicitly**. No iframe, no separate origin, no permission model.
A hostile bundle can, with no bug required: read every library file, project, BOM and note;
write/delete/move arbitrary library files; read *any* addon's saved state (it can just call
`/tools/<other-key>/states` — no `states_key` needed); and **exfiltrate all of it, because
CSP is report-only** (§2.4) so `connect-src` is not enforced. It persists by re-running on
every visit to its own page. The one real backstop holds: account deletion and password
change both require the current password.

Two things sharpen this beyond "trusted source": (a) **publishing the bundle image IS the
deploy** — a compromise of the addons registry reaches every user's authenticated session
with no Rails redeploy, no CI, no review (the feature working as designed); (b) the accessory
uses a **floating `:latest` tag, not a digest**, and `Maker::Addons::Source` does **no
integrity check** on manifests or bundle bytes — no SRI, no signature, no pinned hash.

**Self-host: coherent accepted risk** (one operator, private repo, LAN). **SaaS: this is the
single largest security decision in the delta** — one shared addon source × N tenants means
one bundle compromise = every tenant's library. Cheap hardening available today: digest-pin
the accessory, add per-asset `sha256` to `manifests.json` and verify in `Source#asset`, flip
CSP to enforcing. The structural answer is the API plan's Ring 2 (sandboxed null origin +
postMessage + scoped tokens).

### 2.2 — Addon save: chunk mode accepts a traversing filename; no transaction; port errors uncaught — MEDIUM — probed on both backends

`parse_files` (`addons_controller.rb:172-181`) checks only presence, string-ness, count ≤ 8,
total ≤ 4 MB — **no name validation**. Three verified defects:

**(a) Chunk accepts a traversing node name.** Probed: saving `"../../escape.txt"` on chunk
returns 302 with a live node of that name; on share it raises `FileLayer::NotFound`
(uncaught → 500). **Verified in tree:** share and s3 both call `leaf!`
(`share.rb:184`, `s3.rb:265`); `Sync::Commit.begin` validates the manifest exhaustively and
the name not at all, and `Node` validates `name` **presence only** (`node.rb:7`). So the
most-used write backend is the one with no name check — and that name flows into the
changelog and out to every device mount, where FUSE/CfAPI/WebDAV must materialize it. The
same gap is already documented for `V1::CommitsController`; the addon save is a **new
web-facing door onto it**.

**(b) No transaction, port refusals uncaught.** Probed on share: saving 4 files where #2 and
#3 collide leaves **2 of 4 written, an orphan `AddonState`, and a 500**. Saving the same name
twice → 500 + orphan state. This is §2.2 of the earlier draft generalized: `FilesController`
maps `FetchError → 503` and `UnsupportedOperation → 422` centrally; this controller inherits
none of it.

**(c) Chunk's mirror-image defect:** the same duplicate save *succeeds twice* and produces
**two sibling nodes with the same name in one directory** — POSIX-illegal on a mount.
(Related to §12 item 11, but at the *same* parent, not project-wide.)

**Fix:** validate the leaf name in `parse_files` (backend-neutral, mirroring
`MoveNode#leaf!`); wrap state + writes in a transaction; rescue
`UnsupportedOperation`/`NotFound`/`FetchError` → 422/503 with a flash. **Mutation-check each
guard** — (a) is a live example of a guard that exists on two backends and silently doesn't
on the third.

### 2.3 — Service proxy echoes the sidecar's `Content-Type` verbatim, inline, same-origin — MEDIUM (latent XSS channel)

`addons_controller.rb:101` — `send_data res.body, type: res.content_type,
disposition: "inline"` with **no allowlist**, unlike its sibling `#asset:78`, which maps
through `content_type_for`. Reaching `text/html` is not hypothetical: the route is
`via: %i[get post]` while boxes' `/generate` is POST-only, so a GET proxies to a POST-only
Flask route → Werkzeug's **405 page, `Content-Type: text/html`**, served inline under the
app's origin. Bodies are static today so there is no working XSS, but the channel is open and
any future sidecar endpoint that reflects input becomes same-origin script execution.
`image/svg+xml` also passes `#asset`'s map unchanged and is served inline — SVG is
script-capable and `nosniff` does not help. **Fix:** allowlist proxied types
(`application/json`, `image/png|jpeg`, `model/*`, `text/plain`); force `attachment` otherwise.

### 2.4 — `URI::InvalidURIError` escapes both HTTP clients → 500 — MEDIUM — probed

`Source#get` and `ServiceProxy#call` each rescue the same five network errors; **neither
rescues `URI::Error`**, and `URI.parse` is the first thing both do.
`validate_asset_path!` rejects `..`/`.`/empty/leading-`/` but **not** spaces, newlines, NULs,
or non-ASCII. Probed: `GET /tools/<key>/asset/caf%C3%A9.js` and `/a%20b.js` both raise out of
the action → 500 for any authenticated user, and an addon shipping a non-ASCII asset filename
fails as a 500 rather than the intended 404 — exactly the "my fix didn't deploy" confusion
the asset action's own comment wants to avoid. **HTTP mode only** — `Source::Local` (dev/test)
uses `Pathname#read`, which is why the suite is green over it: the same shape as §14a's
`STORAGE_BACKEND` 500, a guard whose precondition is never established in test. **Fix:** add
`URI::Error` to both rescues (→ 404), or tighten `validate_asset_path!` to a URL-safe class
(more in keeping with §14a's "reject, never normalize").

### 2.5 — No rate limit on any `/tools` endpoint; the proxy pins a Puma thread — MEDIUM (managed) / LOW (self-host)

`rate_limit` appears in exactly four places, all Devise. Nothing on `/tools/*`, while
`ServiceProxy::READ_TIMEOUT = 30` and `OpenscadClient::RENDER_READ_TIMEOUT = 90` hold a Rails
thread that long, and both sidecars run `gunicorn -w 2` shared across all three backends. Any
authenticated user can saturate the sidecars and exhaust the (3-thread — see **P1**) web pool.
**Fix:** `rate_limit` on `#service`, `#create`, and the OpenSCAD render/preview actions;
consider moving renders to a job with a polled result.

### 2.6 — Smaller verified items

- **`Source#get` has no response size cap** (`source.rb:79` returns the whole body) while its
  sibling `ServiceProxy` caps at 20 MB *while streaming* and explains why. Unargued asymmetry;
  a compromised addon host can hand Rails an arbitrary-size body per asset request. — LOW
- **`states_key` write side enables cross-addon DOM-XSS**: addon A can *inject* rows that
  addon B's bundle renders — a real path if B uses `innerHTML` on `state.name`. Inside one
  trust boundary today; the tenant boundary itself holds (confirmed by an existing test). —
  INFO (see §2.1 earlier draft, and the API plan's mutual-declaration constraint)
- **Unbounded `name`/`data` on saved states**, no cap on row count per user — feeds the still
  open quota decision (**A-M5**). — LOW

### 2.7 — Project intake: no security findings

The destination is `["Projects", slug, dest]` where `slug` is sanitized to `[a-z0-9-]` at
`maker/project.rb:74` (no separator survives) and `dest` is one of **ten fixed literals** via
`fetch` with no default. A crafted filename influences *which* of ten folders, never the path
shape. Symlink nodes are neither `file?` nor `dir?`, so they are ignored rather than followed.
Both walks are `MAX_DEPTH`-bounded with visited sets. **Clean.**

### 2.8 — Sidecars

**openscad** — arbitrary code execution **by design** (stated in its own docstring), with real
bounds: 60 s subprocess timeout under a gunicorn timeout deliberately set *above* it,
`RLIMIT_AS` 2 GiB applied between fork and exec, fresh temp dir per render, non-root user,
1 MB `.scad` cap, catalog path regex-gated **and** `realpath`-confirmed. The one gap is named
in the code itself: OpenSCAD's `include`/`import`/`surface` can walk **up** out of the temp
dir, so container file-read is possible — contained because nothing sensitive lives there.
**Accepted, and honestly so.**

**boxes** — no shell; argv built only from registered argparse actions with unknown params
refused **by name**; `FileType` params dropped by rule (closing a server-side `open()`
primitive); `/sample/<name>` regex-gated before `os.path.join`. **Clean.**

**Both:** no `port:` in `deploy.yml` → internal Kamal network only, unreachable from host or
internet. **SaaS implication, separately:** neither sidecar has *any* authentication — the
network is the whole boundary — and both are shared multi-tenant compute with 2 workers and no
rate limit. For managed hosting that is a cross-tenant DoS surface, and openscad's "arbitrary
execution is fine, nothing sensitive here" argument **needs re-deriving once "here" is shared
infrastructure.**

### 2.1 — `states_key` is a documented, deliberate trust widening — **CLOSED 2026-08-07** (was INFO today, HIGH the day the trust model widens)

**Evidence.** `app/services/maker/addons/registry.rb:56-65` — the in-code comment states it
plainly: a manifest declaring `states_key: "other-addon"` grants itself read AND write access
to that addon's saved states, for every user, unconditionally. Safe only because manifests
come from a repo the operator controls. **Verified in tree.**

**Consequence.** Nothing to fix now — the comment already names the fix (host asserts
`states_key == key` unless allow-listed) for when third-party sources exist. Recorded here
because the addon API plan (`docs/plan-addon-api.md`) must carry this constraint into the
manifest permission model rather than inherit the unguarded default.

**CLOSED** by branch `claude/addon-api-pr2-manifest-metadata` (commits `787c675`, `da75f34`,
`0faffe1`) — PR 2 of the Addon API v1 arc, which is the plan this finding asked to carry the
constraint. `Maker::Addons::Registry.states_key_permitted?` now refuses a `states_key` pointing at
another addon unless that addon names the claimant back in `shares_states_with`, **and** unless the
target manifest is itself one `build` accepts. A claim on an addon absent from the index is refused
too — the permissive reading would let a typo reserve a namespace and collide the day the real
addon shipped. A refusal SKIPS the addon (it does not appear in the gallery), deliberately rather
than greying it out: `Tools::AddonsController` never gates on `available?`, so a greyed-out addon
would still resolve through `load_addon` and still serve `@addon.states_key` from `#states` and
`#create` — closed-looking, open in fact.

**What is closed, exactly.** A manifest can no longer, **by declaration alone**, redirect its own
saves and state reads into another addon's namespace. That is the whole of it.

**What is NOT closed, and must not be read into this.** `states_key` was never an inter-addon
*runtime* boundary and this does not make it one: a bundle runs same-origin in the authenticated
session and can call `/tools/<other-key>/states` directly — the controller resolves whatever key is
in the URL, no `states_key` involved. **The other §2.1 in this document** ("A malicious or
compromised addon bundle owns the account", §2 above, HIGH) states that same fact as part of its own
evidence and **remains open**; §5 item 8 still stands. The manifest metadata PR 2 also shipped
(`permissions`, `min_host`) is **display, not enforcement** — nothing on the server refuses a
request because a manifest failed to declare something.

### 2.2 — Addon save: duplicate output filename on share/s3 is an unrescued 500 — MEDIUM (robustness, not exploit)

**Evidence.** `Tools::AddonsController#create` rescues only `Source::Error`,
`ServiceProxy::Error`, and `JSON::ParserError` (`app/controllers/tools/addons_controller.rb:79,102,179,186`);
`ApplicationController` has no `rescue_from`. `Maker::Addons::LibraryOutput.write` on a
port-writable backend calls `FileLayer#write`, whose clobber answer is
`FileLayer::UnsupportedOperation` (§14a: "a clobber is `UnsupportedOperation`"). **Verified:
no rescue exists on this path.**

**Consequence.** A user who saves an addon output twice under the same name on a share/s3
deployment gets a 500, not the 422-with-message the `FilesController` upload path gives. Same
condition, two answers — exactly the shape §14a's clobber bullet warns about, one layer up.
This is also the recorded `TrashController` failure shape (a controller-level rescue gap no
adapter suite can see).

**Fix.** Rescue `FileLayer::UnsupportedOperation` in `Tools::AddonsController#create` → 422
with a JSON error body (the fetch()-driven bundles currently get body-less failures — see the
API plan's error-contract item).

### 2.3 — Sidecar-proxy read timeout (30 s) is below the OpenSCAD sidecar's own render cap (60 s) — MEDIUM (latent)

**Evidence.** `Maker::Addons::ServiceProxy::READ_TIMEOUT = 30`
(`app/services/maker/addons/service_proxy.rb:21`); the openscad sidecar allows renders up to
60 s (`sidecar/openscad/render.py` RLIMIT/timeout) and the legacy `OpenscadClient` deliberately
reads at 90 s for renders (`app/services/openscad_client.rb:19,63`). **Verified in tree.**

**Consequence.** Latent, not live — OpenSCAD still runs on its legacy controller. But the
recorded migration plan (design spec §7, step 2) moves it onto the generic service proxy,
where any render slower than 30 s would time out at the proxy while the sidecar keeps
computing. The generic surface needs per-service (manifest- or env-declared) timeout ceilings
before that migration, not after it fails.

## 3. Performance delta

Baseline (measured, this worktree): `bin/rails test` = 1893 runs / 6498 assertions / 0
failures / 0 errors / 9 skips in ~8.7 s. Findings are labeled **measured** or **reasoned**.

### P1 — Sidecar proxy holds one of THREE production Puma threads for up to 30–90 s — HIGH (SaaS) / MEDIUM (self-host) — reasoned from config + code

`config/puma.rb:28` defaults to 3 threads via `RAILS_MAX_THREADS`; `config/deploy.yml` never
sets it and sets `SOLID_QUEUE_IN_PUMA: true` (line 57) — so production is **3 web threads in
one process that also hosts the job supervisor**. §14e recorded `RAILS_MAX_THREADS=16` as the
dev fix; production never got the knob. **Verified in tree.** Meanwhile
`ServiceProxy::READ_TIMEOUT = 30` and the legacy OpenSCAD render read at 90 s run
synchronously inside request threads, and the boxes bundle fires a proxied render on a 600 ms
debounce per param drag (the browser's `AbortController` frees the browser, not the Rails
thread). Three users dragging sliders can consume the entire web pool; everything else —
including the v1 sync control plane — queues. There is no reentrancy deadlock (sidecars never
call back; bundle assets come from the accessory), so the failure mode is **starvation, not
deadlock**.

**Fix, cheapest first:** (1) `RAILS_MAX_THREADS: 16` in `deploy.yml` (one line, already
validated in dev per §14e); (2) shorter per-endpoint proxy timeouts (a boxes render finishing
in <5 s does not need a 30 s ceiling — and see §2.3 for the per-service manifest knob going
the other direction for OpenSCAD); (3) longer term, render via a job + poll, off Puma.

### P2 — Addon assets: zero caching at any layer; every module is a full Rails request + a fresh accessory fetch — MEDIUM — measured + reasoned

Measured with the disk source: the boxes bundle is **12 ES modules**; each is a full Rails
request (0.8 ms + 1 query locally). In production each one *additionally* costs a Solid Cache
DB read (registry), a **fresh TCP connection + GET to the accessory** (`source.rb` uses
`Net::HTTP.start` per call, no keep-alive), and full-body buffering — the generators bundle
re-proxies its 180 KB `makerjs.js` through Ruby on **every page view**. No
`Cache-Control`/`ETag` is set anywhere on the asset action (deliberate "not in this phase",
`addons_controller.rb:73-75`); stock `Rack::ETag` gives the browser 304s but Rails still
re-fetches and re-digests the full body per module per navigation. Burst shape (4–6 parallel
module fetches on page load) is exactly the §14e incident's load profile, now landing on P1's
3-thread pool.

**Fix:** content-hash asset URLs + `Cache-Control: immutable` (the API plan's §5.6 — the
manifest index is already the versioning source), and a persistent upstream connection or
`If-None-Match` pass-through. This also kills the design doc's named risk #3 (stale bundle
reads as "my fix didn't deploy").

### P3 — Standing item #8 re-measured: `files#index` is render-bound and folder view has no cap at all — MEDIUM — measured

At 2000 nodes in one folder: wall 225–307 ms, `view_runtime` 175–278 ms, **5 queries**, db
≈ 0 ms — same shape as the prior audit (the port N+1 stays closed; cost is per-row ERB). Flat
mode is capped (`FLAT_LIMIT = 2000`); folder mode has **no cap** — a 10 k-child NAS folder
extrapolates to >1 s of render and a multi-MB payload. **Recommended fix: SQL-side keyset
pagination of the folder view** (the query already runs on
`index_nodes_on_user_id_and_parent_node_id` ordered `kind DESC, name ASC`; page ~250 with the
truncation banner flat mode already has). Not Turbo lazy frames — they defer the same total
render; pagination removes it. Every downstream batch (stat_all, note counts, thumbnails)
shrinks automatically because they all take `@nodes`. Wrinkle: non-name sorts order by port
mtime in Ruby; `nodes.mtime` exists on all three backends, so SQL-sort the page or ship
name-sort-only as v1.

### P4 — Project intake sweep instantiates the whole project subtree as AR objects every 15 min — LOW today / MEDIUM at NAS scale — measured + reasoned

Measured steady-state (3000 attached files, nothing loose): ~20 ms, 6 queries — the
BFS-per-level design and its indexes are right. But `subtree_files` materializes **full Node
models** for every file under every project folder, and `attach` plucks the entire attachment
set into a Ruby Set, every sweep, even when nothing changed. At 100 k files that is ~10⁵ AR
instantiations per user per 15 min inside the Puma-hosted worker. **Fix:**
`select`/pluck the four columns the sweep actually reads — one line, behavior-preserving.

### P5 — Chunk-mode sweep broadcasts per move, against the channel's own coarse contract — LOW — verified (repo's own measurement)

`LibraryChannel`'s header says "one event per commit — never per-operation," and
`project_intake.rb:76-87` records 26 broadcasts for filing 25 files (each also taking the
`next_seq!` row lock in its own transaction). On managed Postgres a 500-file sweep = 500
serialized lock transactions + 500 Solid Cable rows + 500 nudges per device. Devices converge
fine (pull is incremental); the waste is server-side. **Fix:** batch/debounce — one broadcast
per sweep with the final `head_seq`; the pull protocol already makes one nudge sufficient.

### P6 — Thumbnail storm on first index: full-file reads, 256 MiB ceiling, billed S3 egress — LOW (self-host) / MEDIUM (S3 cost) — reasoned

First index of a large library enqueues one `GeneratePreviewJob` per renderable file; each
buffers the whole file (`FileLayer::MAX_BYTES` = 256 MiB) — worst-case 3 × 256 MB transient in
the web process, and on S3 a **full billed download of every renderable object** — the same
cost §14a's identity ladder explicitly refused to pay for hashing, paid silently by previews.
**Fix:** a much smaller per-preview byte ceiling (skip/defer above ~32 MB), and job priority so
a storm can't starve other background work.

### P7 — Smaller, verified items

- **Eager intake on S3** (§14f already documents it): 25 moves × 3 sequential S3 calls ≈
  6–15 s inside one upload response at the repo's own measured per-call latency. Make the
  eager default backend-aware (e.g. 5 on s3) or run the filing half async on s3 — the attach
  half can stay inline. — LOW
- **Standing item #10** (no eager nudge on device push): the 15-min bound is right, but a
  **deduplicated** `ProjectIntakeJob.perform_later(user_id:)` from `Sync::Commit#finalize`
  (Solid Queue concurrency key per user, short delay) coalesces a 500-file push into one
  sweep seconds after the batch lands. Better than both recorded alternatives. — LOW
- **Addon shell inlines the entire folder tree** into a data attribute per page view
  (`Tools::LibraryFolders#folder_options` — hundreds of KB at NAS dir counts), and the label
  builder's recursive lambda has **no cycle guard** — a parent-cycle in `nodes` (a hazard
  `ProjectIntake` explicitly defends against) is a `SystemStackError` here. Fix: lazy
  filechooser endpoints (API plan §5.4 moves folders behind `pickFolder`) + a seen-set. — LOW
- **`GET /tools/:key/states` is unbounded** — all saves, full `data` hash each; 2 queries, no
  N+1. Paginate when it matters (API plan §5.3). — INFO

### Scaling ceilings (analysis)

- **Self-host Solid stores:** production SQLite is four separate files (primary/cache/queue/
  cable) — polling never contends with primary at the file level. The real ceiling is
  `SOLID_QUEUE_IN_PUMA: true`: scan hashing + preview rendering share the GVL and RSS with the
  3 web threads. Fine for one user; the escape hatch (`JOB_CONCURRENCY`, separate job host)
  already exists in `deploy.yml` comments.
- **Scan at 100 k files:** no quadratic has re-entered since the Reconciler work (diff
  verified by the stream); the ceiling is now the walk itself — ~100 k `lstat`s over SMB/NFS
  per cycle ≈ 1–3+ min wall. Inherent to polling; cadence is the knob.
- **ActionCable fanout:** per-user streams, tiny payloads, 2–5 devices — fine at 50 SaaS
  users. The one wart is P5.

### Checked and fine (performance)

Registry caching (rescue outside `fetch`, one cached read per gallery); addon shell 3
queries/~4 ms; `#states` constant-query; `LibraryOutput` bounded (8 files/save, single-chunk
commits); ServiceProxy 20 MB cap enforced **while streaming**; ProjectIntake query design
(every query index-covered, caps re-read per call); ProjectIntakeJob gating (no double sweep
with ScanJob); `files#index` batching (stat_all constant-in-N, grouped counts, capped
backfill/poll); preview enqueue idempotence; query-budget guards (gap: `/tools` pages not
covered — constant-query by construction, add when convenient).

## 4. Comparison to similar projects

Full research (with sources) was produced by the comparative stream; condensed here to what
changes decisions. Three sub-areas: sync layer, maker layer, plugin APIs.

### 4.1 Sync/file layer — position: data plane is competitive; the gaps are policy, not engine

The 2026-06 research (`docs/research-sync-competitors.md`) already established the
architecture ranking; the delta from re-checking the field in 2026-08:

| System | What it does better than us | What we do better | Adopt? |
|---|---|---|---|
| Syncthing 2.0 (MPL) | **Untrusted-device encryption** (published spec: per-file keys, block-offset-bound nonces) | Authoritative tree, real versioning, CDC dedup, hydration/placeholders | Yes — the best blueprint for our at-rest encryption arc |
| Seafile (AGPL core) | Encrypted libraries shipped; virtual repos = sharing + selective sync in one primitive | Permissive stack; native mounts; no CE/Pro split | Study virtual-repo primitive for sharing arc |
| oCIS / OpenCloud (Apache) | **Spaces** — subtree-scoped membership/quota, the best sharing primitive in the field | CDC dedup (they have none); their community just forked (Kiteworks → OpenCloud) | Yes — model sharing on Spaces, not per-file ACLs |
| Nextcloud (AGPL) | App-platform breadth, sharing, groupware | The entire data plane (they re-upload whole files, bytes through PHP) | No (breadth comes via our addon story) |
| Dropbox Nucleus | Three-tree planner; **Trinity-style randomized fault-injection harness** | Self-hostable at all; keep-versions vs their 30 days | Yes — the fault-injection harness idea (already queued in prior research) |
| rclone bisync (MIT) | 70+ storage backends | Everything else (it's snapshot-diffing, not a sync engine) | Only as BYO-storage ChunkStore idea |
| Resilio (proprietary) | Peer/LAN block swarming | Open, versioned, server of record | Defer — differentiating but not now |
| ente (AGPL) | **Key-wrapping ladder** (file→collection→master) that keeps per-user dedup working under E2EE, audited | General-file sync (they're photos-first) | Yes — crib the ladder for `docs/plan-encryption.md` |

Standing conclusions unchanged: no competitor combines CDC dedup + immutable versions +
native per-OS mounts + permissive licensing + self-host; that intersection is the moat. The
client pull path should also gain a mass-delete guard mirroring the Reconciler's (a
server-side mass-tombstone should not silently empty a mount) — new suggestion, see §5.

### 4.2 Maker layer — position: the file↔BOM↔project join is unique; the UI breadth is behind

- **Manyfold** (AGPL, Rails) is the direct competitor and moved fast in 2026: ActivityPub
  federation, printer handoff (OctoPrint/Moonraker), remix/provenance graphs, and now its own
  plugin system. It has **no sync engine** — it scans a directory; we *are* the directory on
  every device. Assume its features keep coming; the moat is the sync+catalog join.
- **InvenTree** (MIT, Django) is years ahead on inventory/BOM UX (part→stock→BOM→build-order,
  barcodes) and has the most mature plugin model in the space (mixin classes). Our
  inventory/BOM models exist with no UI (§12.9) — copy InvenTree's information architecture
  when building it; keep the versioned-CAD-file join as the differentiator (no competitor can
  link a BOM line to a file at a specific version).
- **Spoolman** (MIT) owns filament inventory + printer-firmware integrations; consume its
  API rather than compete.
- **Printables/MakerWorld/Thangs**: upstream, not competitors. Gap: our zip import discards
  provenance (source URL, creator, license, remix-of) that Manyfold and 3MF metadata both
  model. Cheap to persist now, painful to backfill.
- **LightBurn**: `.lbart` art/material libraries are machine-local and unversioned — indexing
  and previewing them would make us the sync/backup layer LightBurn lacks (we already parse
  `.lbrn2`).

Ranked feature gaps: (1) inventory/BOM web UI, (2) printer handoff (HTTP POST to
OctoPrint/Moonraker — small, visible, Manyfold just shipped it), (3) import provenance
metadata, (4) Spoolman API consumption, (5) watch-don't-build on federation.

### 4.3 Plugin-API models — position: our delivery is Figma-shaped, our trust is Obsidian-shaped

Survey conclusion (full detail in the API plan): our current model — remotely-fetched ESM
executed same-origin in an authenticated page — is the **Obsidian/OctoPrint full-trust
model**, which Obsidian itself retreated from in May 2026 (automated review of every version,
open-source-only, after concluding full trust doesn't scale past first-party). Our *delivery*
(manifest + JS bundle into a host page) is the **Figma** shape, and Figma is the existence
proof that CAD-grade tools work behind a sandbox + postMessage RPC + typed host API +
manifest-declared permissions (`networkAccess.allowedDomains` with mandatory `reasoning`).
Shopify contributes the server-edge pattern (short-lived signed tokens carrying an explicit
scope set); Home Assistant/HACS contributes the honest two-ring distribution model (curated
core + caveat-emptor community ring); VS Code contributes declarative contribution points +
`engines`-style host-version ranges. These become the skeleton of `docs/plan-addon-api.md`.

    stale-bundle trap). 19. Keyset pagination on the files folder view (P3 — the only real fix;

    `Sync::Commit#finalize` (P7 — better than both alternatives §12.10 records).

### Product direction (from §4)

24. **Inventory/BOM web UI** — the biggest gap against every competitor in the field.
25. **Printer handoff** (HTTP POST to OctoPrint/Moonraker) — small, visible, and Manyfold just
    shipped it. 26. **Import provenance** (source URL, creator, license, remix-of; 3MF metadata)

    mass-delete guard mirroring the Reconciler's — a server-side mass-tombstone should not
    silently empty a mount.

### Deliberately NOT recommended

- **Don't** "fix" the two §14a invariant departures (share/s3 current-state-only; share's
  `send_file`), collapse the two tombstone kinds, or re-derive `port_writable?` as
  "accepts uploads". All recorded, all cost a real bug already.
- **Don't** build federation speculatively — watch whether Manyfold's ActivityPub work gets
  traction first (§4.2).
- **Don't** add a server-side unique index on `(user, parent, name)` to fix the duplicate-
  sibling issue — the *client* adjudicates collisions by design; fix it at the write doors
  (2.2) and document the server-never-adjudicates fact in `docs/sync-protocol.md`.
