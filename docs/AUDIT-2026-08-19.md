## 2. Confirmed opportunities

### F-01 · S04 · Chunk's write-refusal surface is a hand-copy that has drifted — and drifted toward the swallowable failure §14a designed against
**Status:** ACCEPTED (coordinator-verified end to end). **Confidence:** high.

Evidence (every line re-checked by the coordinator, not taken from the worker):
- `app/services/file_layer/chunk.rb` defines exactly 14 methods; `grep -n "def "` shows refusal stubs for `write:205`, `delete:209`, `move:213`, `mkdir:217`. **There is no `undelete`.**
- `app/services/file_layer/share.rb:419` and `app/services/file_layer/s3.rb:509` both `def undelete(user, node_id: nil)` — so the port's write surface is five verbs, and Chunk implements four.
- `app/services/file_layer/chunk.rb:77-79` asserts the opposite in prose: *"unlike `undelete`, which is a write and so raises here (chunk-mode restore is Sync::Trash.restore, driven by TrashController's port_writable branch)."* It does not raise here — it is `NoMethodError`.
- Signature drift: `chunk.rb:205` takes `(_user, parent_node_id:, name:, io:)`; `share.rb:200` and `s3.rb:273` take an additional `replace: false`. A live caller passes it — `app/services/maker/addons/library_output.rb:86` calls `FileLayer.current.write(..., io:, replace:)`.

Why this is a representation problem and not a nit: §14a chose `NotImplementedError` deliberately because it is a **`ScriptError`, not a `StandardError`** — so `rescue => e` and ActiveJob's `retry_on` cannot swallow it. The two verbs that fell out of the hand-copy fail as `NoMethodError` and `ArgumentError`, both `StandardError`s. The drift therefore inverts the exact property the design exists to guarantee. Both are latent today only because a capability gate sits one frame away (`library_output.rb:44-47` branches on `caps.port_writable?`; `app/controllers/trash_controller.rb:74-75` gates `undelete` the same way) — i.e. the gate-before-the-call rule is the only thing holding, and §14a is explicit that the gate is supposed to be belt *and* braces.

Proposed representation: complete the set in place — add `UNDELETE_MSG` naming `Sync::Trash.restore`, a 3-line `undelete` stub, and `replace:` to the `write` stub. Explicitly **not** a registry or a `refuses :write, MSG` DSL: §14a forbids a shared refusal message ("One shared refusal message is how an earlier draft sent delete/move callers to `Sync::Commit`… Keep them separate"). This *restores* the documented model rather than replacing it.

Scope: `app/services/file_layer/chunk.rb` only (one constant, one method, one keyword). Optionally extend the per-op table at `test/services/file_layer/chunk_test.rb:113-135`.
Risks: `respond_to?(:undelete)` flips false→true — coordinator grepped `app/` and `test/` for `respond_to?(:undelete)`: **zero hits**, so no duck-typed branch changes. `replace:` moves from rescuable `ArgumentError` to uncatchable `NotImplementedError` (intended).
Validation: existing `test/services/file_layer/adapter_contract.rb:208,238` and `chunk_test.rb:113-135` pin write/delete/move per-op with `not_names: /Sync::Commit/`. **`undelete` and `mkdir` are unpinned on this adapter** — add the same per-op assertion for both.

### F-02 · S07 · `Commit#finalize`'s verify probes the chunk table one hash at a time, contradicting its own documented cost model
**Status:** ACCEPTED (coordinator-verified). **Confidence:** high.

Evidence:
- `app/services/sync/commit.rb:79-81` — `manifest.map { |c| c["hash"] }.uniq.reject { |h| user.chunks.exists?(chunk_hash: h) || store.exists?(user.id, h) }`. One `SELECT … LIMIT 1` **per hash**, distinct bind values, so Rails' query cache never coalesces them.
- The same class answers the same question in one batched query twice: `commit.rb:63` (`user.chunks.where(chunk_hash: hashes).pluck(:chunk_hash).to_set`) and `commit.rb:198` in `upsert_chunks!`.
- `MAX_MANIFEST_CHUNKS = 100_000` (`commit.rb:22`), header sizes chunks at "~1 MiB avg FastCDC target".
- It is on by default in production: `config/initializers/finalize_verification.rb:23` → `ENV.fetch("SYNC_VERIFY_FINALIZE", "1") == "1"`; `app/controllers/v1/commits_controller.rb:30` passes it; `app/controllers/files_controller.rb:498` hard-codes `verify: true`.
- **The initializer documents a cost this code does not meet** — `finalize_verification.rb:9-11`: *"It costs one storage HEAD per *first-seen* hash only (already-known chunks are satisfied from the DB), so the write hot path pays nothing for dedup hits."* True of the storage half (the `||` short-circuits); false of the DB half, which is the N+1. That is why no store-level test sees it.

Impact: a fully-deduped re-commit of a 1 GB file — precisely the "pays nothing" case — issues ~1000 sequential DB round-trips inside the finalize request. On managed Postgres over a network that is ~1 s of pure latency per file on the sync hot path.

Proposed representation: one private `known_hashes(user, hashes)` returning a `Set`, used by `begin` and by the verify block; HEAD only what the DB does not know. The class then holds one model of chunk presence instead of two divergent ones.
Scope: `app/services/sync/commit.rb` only (lines 63-64 and 79-81). No public interface change.
Risks: (a) `ChunksMissing#hashes` ordering is consumed by `v1/commits_controller.rb:47-48` and `files_controller.rb:518` — reject from the ordered array against the set, don't iterate the set; (b) **must `each_slice`** — 100k binds exceeds Postgres' 65535 limit and SQLite's `SQLITE_MAX_VARIABLE_NUMBER`. Omitting the slicing trades an N-query loop for a hard failure on huge manifests.
Validation: existing `test/integration/v1/sync_flow_test.rb:41`, `node_guards_test.rb:132`. Add a query-count assertion using the `count_queries` helper at `test/services/sync/scale_test.rb:146-157` (it runs `uncached`, which is what makes this measurable) asserting the count does not grow with manifest size, plus a case above the bind-slice threshold.

### F-03 · S07 · The seq/changelog ledger is re-implemented at every write site, so §14e's ordering rule is enforced by comments only
**Status:** ACCEPTED, with a coordinator note on scope. **Confidence:** medium-high.

Evidence — coordinator census of every `next_seq!` **call expression** under `app/` (the worker said "6 sites"; the precise count is **8 expressions across 6 services**, all inside S07):
`sync/commit.rb:95`, `sync/mutation.rb:17`, `sync/restore.rb:15`, `sync/subtree_delete.rb:20`, `sync/subtree_delete.rb:23`, `sync/conflicts.rb:37`, `sync/conflicts.rb:60`, `sync/conflicts.rb:71`. (Remaining `next_seq!` greps in `app/` are prose comments — `tools/addons_controller.rb:501`, `library/reconciler.rb:40`, `maker/project_intake.rb:83` — plus the definition at `app/models/user.rb:167` and two comments in `lib/postgres_pooler_check.rb`.)

All repeat the same four-step ledger: `transaction` → `next_seq!` → work → `updated_seq = seq; save!` → `changelog_entries.create!`. Two hand-roll a "first seq pre-minted, rest mint on demand" branch with *different* ad-hoc predicates:
- `subtree_delete.rb:23` — `seq = i.zero? ? first_seq : user.next_seq!`
- `conflicts.rb:71` — `this_seq = new_node_ids.empty? ? seq : user.next_seq!` (keyed on an **output accumulator**, so reordering the `new_node_ids <<` push silently breaks seq allocation)

The invalid state this permits: §14e's rule — *"`next_seq!` must be the FIRST statement … or concurrent commits deadlock on a `FOR KEY SHARE`→`FOR UPDATE` lock upgrade"* — is enforced by **nothing executable**. `commit.rb:88-94` is a nine-line comment explaining it. A seventh write path with the lock second compiles, passes the full suite (the default gate runs SQLite per §13, where the deadlock cannot reproduce), and deadlocks only on production Postgres under concurrency.

Proposed representation: a `Sync::Journal.write(user:) { |j| … j.record!(node:, op:, version_id:) }` whose first in-transaction statement is `next_seq!`. Ordering becomes structural rather than advisory; both first-vs-rest conditionals vanish; the `updated_seq`/`save!`/`changelog_entries.create!` triple gets one definition. **This implements §14e rather than contradicting it.**

**Coordinator scope note:** this is the largest-blast-radius finding in the audit and touches the deadlock-sensitive path. ### F-04 · S03 · `nodes.content_hash` serves as both a scan identity and a live wire ETag; `move`/`undelete` never refresh it

- `s3.rb:483` — the row update is `node.update!(storage_path: rel, name: new_name, parent_node_id: new_parent_node_id)`. **No `content_hash`, no `mtime`.**

- `s3.rb:628-633` — `copy!` discards the `copy_object` response, which carries `copy_object_result.etag`.

After a `move` or `undelete`, `node.content_hash` names an ETag no object has, so the next `delete`/`move` sends a stale `copy_source_if_match` → `PreconditionFailed` → `FetchError` → **503 "try again", forever**, until a scan re-indexes. `move`-then-`delete` is an ordinary UI sequence.

That precedent is why this finding is ranked high despite no red test.

Proposal: one private `object_attrs(etag:, last_modified:, size: nil)` fed by the response each verb **already holds** (`put.etag`, `copy_object_result.etag`, `head.etag`), used by all four mutating verbs; move the identity *decode* into `ObjectIdentity` so encode and decode live in one file. Validation: `s3_test.rb:673-684`, `:697-729` exist but cannot fail on this. Proposal: `put` delegates to `write` (mirroring `memory_chunk_store.rb:72`, which already has one write path); move the temp to `<dir>/.tmp/` so the enumerated directory *is* the keyspace; belt-and-braces, `list` skips names failing the same regex `path_for` enforces — today `list` and `delete` disagree on the alphabet, and that disagreement **is** the defect.
Scope: `local_chunk_store.rb` only (`initialize`, `put`, `write`, `list`). No interface change, no caller edits.
Risk: `File.rename` across `<dir>/.tmp` → `<dir>/chunks/...` needs same-device; both are under `@dir`, but `@dir` is operator-supplied via `CHUNK_LOCAL_DIR`, so a bind-mounted subpath would `EXDEV` — worth an explicit comment. Existing `.tmp` leftovers on a deployed box need a one-time sweep (a deploy note, not code).
Validation — **nothing in the suite can see either half today**: `test/services/storage/local_chunk_store_test.rb` never calls `put` and never calls `list`; `chunk_store_put_test.rb` tests `put` on the **memory** store only; `chunk_reaper_test.rb`'s 8 tests run against the memory store, which has no temp files. Add: `put`-then-`read` round-trip on Local asserting `Dir.children` holds only the hash; a hand-planted `<hash>.abc123.tmp` that `list` excludes and the reaper neither reaps nor warns about; and a "every `list` hash survives `delete`" assertion.

### F-48 · S30 · `staging` has no owner, and the lock order between it and `conn` is already inverted — a reachable hard deadlock
**Status:** ACCEPTED — **the most severe finding in this audit.** **Confidence:** high (coordinator reproduced the inversion by reading both paths).

Coordinator-verified in `client/fs-provider/src/lib.rs`:
- Three independent mutexes with **no documented order**: `conn: Mutex<Connection>` (`:437`), `staging: Mutex<HashMap<u64, Vec<u8>>>` (`:441`), `locks: LockManager` (`:447`, itself a `Mutex<HashMap<..>>`). `grep -rn "lock order\|deadlock" client/fs-provider/src/` → **no hits**.
- **staging → conn**, in `getattr` (`:1926-1936`):
  ```rust
  if let Some(buf) = self.staging.lock().unwrap().get(&ino) {
      let conn = self.conn.lock().unwrap();
  ```
  The `staging` guard is the `if let` **scrutinee temporary**, so it is live for the whole block — and it must be, because `buf` borrows from it. So `conn` is acquired while `staging` is held.
- **conn → staging**, in `unlink` (`:2170` → `:2196`): `let mut conn = self.conn.lock().unwrap();` is a **function-scope binding**, live to end of function; `purge_inode_state` (`:686-695`) then takes `let mut staging = self.staging.lock().unwrap();`. Note `tx.commit()?` runs first, but committing the transaction does not drop the `conn` guard. The same shape repeats in `rmdir` (`:2201`→`:2238`), `rename` (`:2246`→`:2360`) and `apply_remote` (`:930`→`:1121`).
- Exactly one site gets it right, by scoping the guard in an explicit block — `apply_remote_delete_signaled` (`:1194-1239`). **Nothing enforces that.**
- Both orders run concurrently by design: `sync-engine/src/daemon.rs:287-289` puts the FUSE session on its own thread while the sync loop is another.

Failure: the mount thread in `getattr` on any inode open for write holds `staging` and blocks on `conn`; the sync thread in `apply_remote`, or any thread in `unlink`/`rmdir`/`rename`, holds `conn` and blocks on `staging`. **The mount wedges and only a remount clears it.**
Why this belongs in a simplification audit rather than a bug list: the representational cause is that "is this inode open for write?" is re-derived by **15 inline probes** (`:690,698,1905,1928,1974,2001,2018-2027,2037,2124,2135,2144,2159,2165`), each choosing its own guard scope, so correctness depends on every future edit picking the right one.
Proposal: a private `StagingArea` whose every method acquires and releases the lock internally and returns **owned** values, never a guard or a borrow (`len`, `slice`, `snapshot`, `put`, `take`, `resize`, `discard`, `purge_many`). Then `staging` is a **leaf lock by construction** — no caller *can* hold it across a tree query, so the inversion becomes unrepresentable rather than merely avoided. `getattr` becomes `staged.len(ino)` then the row read.
Scope: `lib.rs` plus a new private `staging.rs`. **No public API change** — `staging` is a private field and `purge_inode_state` a private method — so S31/S33/S34 are untouched.
Risk, and it must be named in the commit: `getattr` currently reads staged length and node row under one held guard; splitting them lets a concurrent `flush` land between, so `getattr` would report the committed size instead of the staged one. That read is already unsynchronized against `flush` in every other respect, so this **narrows an existing race rather than creating one**. Keep `write`'s (`:2018-2027`) drop-and-relock seed behaviour identical.
Validation: `tests/concurrency.rs` claims "must not panic, deadlock, or corrupt" but **never pairs `getattr` on a staged inode with a concurrent removal**; `adversarial_reliability.rs:245-283` is same-file writers only; `removal_state.rs` is single-threaded. ### F-65 · S39 · `FakeS3#do_copy` inherits the source's ETag — and the repo already caught this exact shape on a different field of the same struct, at the same line
**Status:** ACCEPTED. **This is the single most important finding in the audit's test-infrastructure lane**, because it is what makes F-04 invisible. **Confidence:** high on the blindness; medium on production severity, gated on a real-store probe.

Coordinator-verified:
- `test/support/fake_s3.rb:183-184` — `@objects[key] = o.dup.tap { |c| c.last_modified = Time.now }` then `{ copy_object_result: { etag: o.etag } }`. `Obj` is a 5-field struct (`:24`), so `o.dup` carries `etag`, `checksum_sha256`, `checksum_type` forward verbatim. **Exactly one of five fields is re-derived on copy.**
- **The field that IS re-derived was forced by this same bug.** `test/jobs/library/trash_purge_job_test.rb:396` reads, verbatim: *"A fake that copied the source's timestamp forward would invert it… **FakeS3#do_copy did exactly that, and nothing could see it**: no test reached delete. **This is the CGI.escape shape again** (a fake disagreeing with reality where the suite cannot look), so the link is asserted end-to-end rather than reasoned about."*
So the repo diagnosed this pattern, at this line, and fixed **`last_modified` only** — leaving `etag`, the field F-04 depends on, still inherited.

The fake holds **two contradictory rules for one field**: `seed!`/`do_put` **derive** `etag` as `Digest::MD5.hexdigest(body)`; `do_copy` **inherits** it. The inherited rule is precisely the adapter's implicit assumption, so **neither the bug nor its fix is observable** — adding `content_hash: ObjectIdentity.for(etag: head.etag)` to `restored_stat` would pass identically to omitting it. That is strictly worse than a missing test.
Real S3 re-tags a copy whenever the source ETag is not `md5(bytes)` — multipart objects and SSE-KMS — and that population **is this backend's premise**: `fake_s3.rb:92`'s own comment says an overridden ETag "models the object a real bucket is full of: anything uploaded MULTIPART." The adapter's own `write` is single-part and safe; only the pre-existing objects the backend exists to serve are exposed.
Traced live defect: seed a multipart-ETag object → scan → `content_hash = "etag:aaa…-7"` → `move` (precondition matches source, copy re-tags destination, `content_hash` untouched at `s3.rb:483`) → `delete` sends `copy_source_if_match: "\"aaa…-7\""` against an object now tagged `"<md5>"` → `PreconditionFailed` → `FetchError`. **The user cannot delete or re-move a file they just moved, until the next scan.** Same for `undelete`, where `restored_stat` (`s3.rb:765-770`) discards the `head.etag` it already holds while its own comment says its purpose is "so the next scan skips it" — and `Reconciler#unchanged?` (`reconciler.rb:348-350`) tests `content_hash` **first**.
Blind spot is total: the only `etag:` overrides in the suite are `s3_observer_test.rb:434,454`, neither of which copies; the only test reading a fake object's ETag reads a written, never-copied object.
Proposal — **a reduction, not an addition**: a copy mints its own identity from its own bytes, so `seed!`, `do_put` and `do_copy` all say "ETag is the md5 of the bytes unless a test seeded an override," and the override correctly does not survive a copy.
Scope: two lines plus a comment. Every existing test stays green (no test copies an object with a non-default ETag). Then **one** new test — seed `etag: "a"*32 + "-7"`, scan, `move`, `delete` — which **goes red today** and is the mutation-check evidence.
**Before choosing the default, probe a real store** — the repo's own precedent (`fake_s3.rb:169-171` verified `copy_source` against SeaweedFS 4.39) says probe rather than reason; SeaweedFS/MinIO may relink parts and preserve a composite ETag where AWS does not.
Do **not** also drop `checksum_sha256`/`checksum_type` in the same change without checking `LIBRARY_S3_HEAD_FOR_CHECKSUM`.

## Coordinator calibration — read this before treating it as a §9 breach
The worker flagged severity as pending SPDX confirmation, and **that caution is correct and must survive into any action taken.** Two facts I established that narrow it:
- **The WinFsp DLL is not bundled.** `tauri.conf.json` has no `resources`/`externalBin` entry matching `winfsp-x64.dll`. §9's actual wording targets exactly that — *"FUSE drivers (WinFsp GPL, macFUSE) are **user-installed**, never bundled"* — and on that literal reading the invariant **holds**.

A Rust *bindings* crate is frequently permissive even when the product it binds is GPL — the driver and the bindings are different artifacts.

**Therefore: what is proven is a broken feature gate and a false statement in CLAUDE.md §4/§9's supporting text. What is NOT proven is that any copyleft code ships.** Anyone acting on this must check the two crates' licences first; that check decides whether this is urgent or merely correct. ### F-81 · S50 · The "no orphaned nodes" assertion cannot fail — three copies of it, all reading a field that structurally cannot express the condition
**Status:** ACCEPTED. **Confidence:** high — **the tautology is provable from the SQL; no execution needed.**

Coordinator verified the proof end to end. `fs-provider/src/lib.rs:797-801`:
```sql
CASE WHEN n.parent_ino = ?1 THEN NULL ELSE p.node_id END, …
FROM nodes n LEFT JOIN nodes p ON p.ino = n.parent_ino
WHERE n.ino != ?1
```
A missing parent row makes the LEFT JOIN yield NULL, so `parent_node_id` is `None`; a present parent row is necessarily `n.ino != ROOT_INO` (the root case is the `CASE`'s NULL arm) and is therefore **itself in the exported set**. So `parent_node_id` is `Some(x)` **iff** the parent row exists and is exported.
Which makes `fault_injection.rs:810-818` — `if let Some(pid) = &n.parent_node_id { assert!(id_set.contains(pid), "orphaned node …") }` — **true by construction**. It cannot fail. The same check is inlined a second time at `:1944-1957`, run after **every** op on **both** devices as the 150-seed sweep's per-step invariant, and a third variant sits in `fs-provider/tests/adversarial_reliability.rs:356-375` whose docstring claims it panics if a node "is in a cycle **or orphaned**" — its walk ends `cur = by_id.get(&pid).cloned().flatten()`, so a missing parent terminates it cleanly.
The schema permits the state the guards cannot see: coordinator confirms `fs-provider/src/lib.rs:468` declares `parent_ino INTEGER` with **no foreign key and no cascade**. An orphan (`parent_ino` → deleted row) exports as `parent_node_id: None` — **indistinguishable from a root child** — and is skipped by all three.
What slips through is exactly the corruption `apply_remote`'s cycle guard exists to prevent; `fs-provider/src/lib.rs:1006-1024` promises "never leaving a detached cycle **or an orphaned subtree** locally". A regression in the recursive delete that removed a parent but not its descendants produces rows that still count in `export_tree`, still hold chunk refcounts, are unreachable from `readdir`, and pass every guard plus the sweep. Note `apply_remote_cyclic_reparent_must_not_orphan_subtree` (`:378`) is **named for the orphan case its own helper cannot detect.**
Proposal: stop deriving reachability from `parent_node_id` — that field is a lossy projection. Walk `readdir` from `ROOT_INO`, collect inodes, assert `reachable.len() == export_tree().len()`. Reachability from root is the real invariant, and **one traversal decides orphans *and* cycles** (a detached cycle is simply unreachable) — replacing a HashMap build plus a per-node ancestor walk, with no 10 000-hop magic bound.
Risk: land it first as an `eprintln!` diff on one seed sweep before making it a panic, in case any provider legitimately holds unreachable rows.
Validation: **the current assertion cannot be mutation-checked at all** — that is the finding. Mutation-check the replacement: build a two-level tree, `apply_remote_delete` the intermediate dir, confirm the new check fires while the old body does not.
