### F-26 · `Maker::Item` has no `has_many :tasks`

**Assessed: NECESSARY (NARROWED)** — confidence high. 11/11 citations resolved.

The assessor reproduced the defect live (`bin/rails runner -e test`, rolled back): destroy an
item that owns a task, and the task row survives pointing at a gone owner, so
`taskable_belongs_to_owner` — guarded `if: taskable_id.present?` — fires on every subsequent save.
`t.update(title:)` returns **false** (`"Taskable must reference your own item"`); `t.complete!`
raises. That is CLAUDE.md §14d's recorded lock-the-whole-row shape, verbatim, and reachable from a
real route (`routes.rb:318` exposes `items#destroy`, driven at `items_test.rb:62`).

**Correction to the audit, found by probing rather than reading.** The audit proposes
`dependent: :destroy`. The assessor ran both values and showed `:destroy` contradicts the audit's
own required test — under it the task row is deleted, so the "PATCH an unrelated field and assert
success" check the audit asks for is a 404 and cannot be written. `:nullify` is correct here and
does **not** hit §14d's `Maker::BomLine` trap: Rails nulls *both* polymorphic columns, `taskable` is
already `optional: true`, and a task with no owner is an existing blessed state
(`task_test.rb:10-14`). `:nullify` also preserves user data where `:destroy` destroys it.

**Product call surfaced, not decided:** under `:nullify` an item's checklist outlives the item.
Called out here rather than settled silently.

- **Scope:** `app/models/maker/item.rb` — one logical line, mirroring `project.rb:13`.
  `test/integration/v1/maker/referential_integrity_test.rb` — ~12 lines.
- **Out of scope, deliberately:** the registry (§9.4 REJECTED list), and the half-orphan
  `taskable_type`-set/`taskable_id`-nil state reachable via the API.
- **Mutation check (two, per §15):** delete the association → RED with 422 on the *unrelated-field*
  PATCH; flip `:nullify`→`:destroy` → RED with 404 on the same PATCH. Both must fail, for different
  reasons — if only the first does, the test asserts existence rather than editability.

### F-65 · `FakeS3#do_copy` inherits the source's ETag

**Assessed: NECESSARY (NARROWED)** — confidence high. 10/10 citations resolved (three off by a few

The assessor ran the fake standalone: seeded `etag: "a"*32+"-7"`, copied it, and the copy came back
carrying the source's multipart ETag while the md5 of its bytes was something else — then a second
copy using the scanned precondition **succeeded**. On AWS and R2 a single-part `CopyObject` re-tags,
so that second call is a 412 → `FetchError`. **The fake cannot express the defect**, which is why
F-04 is invisible today. CLAUDE.md §14e's "A FAKE THAT SHARES THE CODE'S MISUNDERSTANDING CONFIRMS
IT" — third field of the same struct, after `copy_source` and `last_modified`.

**Zero-churn claim verified exhaustively rather than sampled:** 77 `seed!` calls outside the fake,
exactly two pass `etag:` (`s3_observer_test.rb:434,454`), and that file performs no copy at all.

1. The audit's "probe a real store before choosing the default" becomes a **comment, not a

   survives a store which preserves.
2. `checksum_sha256` / `checksum_type` are **explicitly out of scope**: `LIBRARY_S3_HEAD_FOR_CHECKSUM`

- **Scope:** `test/support/fake_s3.rb:183-184` (2 lines + comment);

### F-04 · S3 `content_hash` is never refreshed on `move`/`undelete`

**Assessed: NECESSARY (NARROWED)** — confidence high. 11/11 citations resolved.

`move` sends `if_match: etag_precondition(node.content_hash)` then updates only
`storage_path, name, parent_node_id`; `restored_stat` holds `head` and drops `head.etag`. After a
re-tagging copy the row names an ETag no object has, so the next `delete`/`move` gets
`PreconditionFailed` → `FetchError` → 503.

**Severity narrowed by probing the real predicates.** `etag_precondition("sha256:…")` returns nil
(immune), and real S3 re-derives the *same* md5 for a single-part unencrypted copy — so plain rung-2
is unaffected. **The defect reduces to rung 3 (`etag:`, multipart-origin) and SSE-KMS objects
mis-classified into rung 2.** "Forever" is also wrong: `library_scan` runs every 15 minutes and
`Reconciler#unchanged?` repairs the row, so the blast radius is a **≤15-minute 503 window** on
delete/move plus one spurious thumbnail re-render. Still a live defect on an ordinary UI sequence,
still worth fixing at zero request cost.

**Five constraints the assessor extracted, each a real trap:**
1. Refresh must go through `ObjectIdentity.for` — a raw ETag keeps its quotes and gives one object
   two identities (§14a IDENTITY LADDER).
2. The guard must be a **`presence` test, not a `rescue`**. `ObjectIdentity.for` raises
   `ArgumentError`, which `:479`'s rescue does **not** match, and `delete_object` runs *before* the
   update — so an unguarded call raises **with the source already deleted and the row never
   updated**, which is §14a's orphaned-attachment landmine.
3. **Do not refresh `mtime` in `move`.** `FakeS3#do_copy` returns no `last_modified`, so `nanos(nil)`
   would be green-against-the-fake and wrong against real S3 — *a brand-new instance of the very
   §14e defect these two findings are about.* This is the sharpest catch of the batch.
4. Leave `etag_precondition` where it is — relocating it is cohesion, not correctness, inside the
   hunk F-05 will restructure.
5. Zero billed requests; an added HEAD violates `s3.rb:676-681`'s explicit ruling.

- **Scope:** `move` and `undelete` only — `write` already sets it, `delete` tombstones with a null
  path. ~15-25 lines + 3 tests via `stub_responses(:copy_object)`.
- **Shipping with F-65 as one commit** (F-65's e2e test is red until this lands; §15 forbids a red
  branch).

## LANDED — F-26 · a destroyed item locked every task that named it

**Commit `c3b688e`.** Reviewer verdict: **ACCEPT WITH NOTE** (no change required).

`Maker::Item` declared no `has_many :tasks` while `Maker::Project` did, so
`DELETE /v1/maker/items/:id` left each task holding a dangling `taskable_id`.
`Task#taskable_belongs_to_owner` is guarded on `taskable_id.present?`, and a dangling id **is**
present — so it fired on every later save and refused it. The row became permanently unsaveable
(`update` false, `complete!` raised), with no web UI for item tasks to escape through. CLAUDE.md
§14d, verbatim.

**Fix:** `has_many :tasks, as: :taskable, class_name: "Maker::Task", dependent: :nullify` —
**not** the `:destroy` the audit proposed. `:destroy` deletes a to-do the user wrote as a side
effect of deleting an item that merely mentioned it, and makes the required "PATCH an unrelated
field, assert success" test unwritable. `taskable` is already `optional: true` and an ownerless
task is an already-blessed state (`task_test.rb:13`); nothing here plays `exactly_one_target`'s
role, so §14d's `Maker::BomLine` trap does not apply.

**Accepted consequence:** an item's checklist outlives the item, visible only in the flat
`GET /v1/maker/tasks` list. Stated in the model comment and the commit message.

**Verified independently by the reviewer:** 370 runs / 865 assertions / 0 failures; rubocop clean.
Both mutations reproduced, each RED on the **editability** PATCH at test line 165 and for
**different** reasons — association removed → 422 `"Taskable must reference your own item"`;
`:nullify` → `:destroy` → 404 `not_found`. The 422 message is itself proof the fixture wired the
association up, which closes the "green because the association never took" hole. `Item` and
`Project` are now the complete set of `TASKABLE_TYPES`, both carrying a `dependent:`.

**Deliberately left:** the half-orphan `taskable_type`-set/`taskable_id`-nil state; `Maker::Model`'s
absence from `TASKABLE_TYPES`; and the item below, which the reviewer escalated.

### NEW FINDING raised during review — not in the audit

**`Maker::Task#taskable_belongs_to_owner` fails open on an unresolvable type.** `TASKABLE_TYPES`
and the method's `case`/`when` are two independent enumerations of one set, and
`return unless owner_class` means an unmatched type performs **no tenant check at all**.

Unreachable today — `validates :taskable_type, inclusion: { in: TASKABLE_TYPES }` rejects anything
the `case` lacks an arm for. **That is what makes it dangerous:** the one-line edit that makes a
third model taskable (adding it to the constant) is exactly the edit that opens the hole, and the
`case` is elsewhere in the file. The result would be an open cross-tenant write — a user attaching
a task to a stranger's row. `cross_tenant_fk_test.rb` contains **no task coverage at all**, and the
only cross-tenant task assertion (`tasks_test.rb:63`) is hardcoded to `Maker::Item`, so a third type
would ship green over it. This repo's signature shape: a guard everyone believes in that silently
does not run.

Fix is to derive the class from the constant and **fail closed** on an unresolvable type. Needs its
own mutation checks; correctly not bundled into F-26.

## NEW FINDING (N4) — escalated out of F-12's review, and the most serious of the session

`Sync::Commit.begin` accepts a manifest entry with **no `hash` key**, because the guard is

`destroy_all` and `reap_all!`'s per-user rescue swallows it as a log line.

**The compound probe is what makes it serious.** One nil-hash row plus one *normal* expired row naming

- every run returned **0**; **both rows survived all three**
