### F-26 · `Maker::Item` has no `has_many :tasks`

**Assessed: NECESSARY (NARROWED)** — confidence high. 11/11 citations resolved.

The assessor reproduced the defect live (`bin/rails runner -e test`, rolled back): destroy an
item that owns a task, and the task row survives pointing at a gone owner, so
`taskable_belongs_to_owner` — guarded `if: taskable_id.present?` — fires on every subsequent save.
`t.update(title:)` returns **false** (`"Taskable must reference your own item"`); `t.complete!`
raises. That is CLAUDE.md §14d's recorded lock-the-whole-row shape, verbatim, and reachable from a
real route (`routes.rb:318` exposes `items#destroy`, driven at `items_test.rb:62`).

**Correction to the audit, found by probing rather than reading.** The audit proposes
`dependent: :destroy`. The assessor ran both values and showed `:destroy` contradicts the audit's
own required test — under it the task row is deleted, so the "PATCH an unrelated field and assert
success" check the audit asks for is a 404 and cannot be written. `:nullify` is correct here and
does **not** hit §14d's `Maker::BomLine` trap: Rails nulls *both* polymorphic columns, `taskable` is
already `optional: true`, and a task with no owner is an existing blessed state
(`task_test.rb:10-14`). `:nullify` also preserves user data where `:destroy` destroys it.

**Product call surfaced, not decided:** under `:nullify` an item's checklist outlives the item.
Called out here rather than settled silently.

- **Scope:** `app/models/maker/item.rb` — one logical line, mirroring `project.rb:13`.
  `test/integration/v1/maker/referential_integrity_test.rb` — ~12 lines.
- **Out of scope, deliberately:** the registry (§9.4 REJECTED list), and the half-orphan
  `taskable_type`-set/`taskable_id`-nil state reachable via the API.
- **Mutation check (two, per §15):** delete the association → RED with 422 on the *unrelated-field*
  PATCH; flip `:nullify`→`:destroy` → RED with 404 on the same PATCH. Both must fail, for different
  reasons — if only the first does, the test asserts existence rather than editability.

### F-28 · A failed task update still nulls `completed_at`

**Assessed: NECESSARY** — confidence high. 14/14 citations resolved.

`PATCH {task: {status: "bogus"}}` on a done task: `task.update` returns false (DB keeps
`status="done"`), but line 41's condition reads *params* and the *in-memory* stamp rather than the
success of the write, so `update_column(:completed_at, nil)` fires anyway and writes only that
column. Persisted result: **`status="done", completed_at=NULL`**. The two existing tests
(`:72`, `:97`) both send a valid status, so they structurally cannot go red on this — CLAUDE.md
§14e's "green suite over something that never worked", again.

**A second defect in the same method, folded in:** the `"done"` branch does `complete!` (which
commits) and then a second `task.update(...)` that can fail silently, leaving the task marked done
with the old title and no alert rendered.

**Sequencing question resolved.** The audit's hard-sequencing table says F-40 (drop the redundant
timestamp columns) should be decided first. The assessor established it is **not a blocker**: the
`if/else` + `alert:` half is identical under either F-40 outcome, and F-40 would later delete only a
four-line `case`. Doing F-28 first makes F-40's edit to this file smaller, not larger. The audit's
"they collide" is a textual overlap in one method, not a semantic dependency.

**The correct pattern already exists one file over** — `v1/maker/tasks_controller.rb:23-29` computes
attributes in memory and does a single `update!`. This brings the web door to the door beside it,
and uses `Time.current` specifically so it does not add a *fourth* spelling of the `completed_at`
rule (§14d).

- **Scope:** `app/controllers/projects/tasks_controller.rb#update` (14 lines → ~10);
  `test/integration/web/project_tasks_test.rb` (+3 tests, ~25 lines).
- **Out of scope, deliberately:** F-40 itself (unranked product decision); `Maker::Task#complete!`,
  which becomes test-only but is a model edit outside this boundary.
- **Recorded, not fixed:** `completed_at` has **zero readers** repo-wide — four writers, one
  serializer, no `where`, no `order`, no branch. That corroborates F-40's schema claim.
- **Mutation check (three, per §15), plus a trap the assessor caught:** assertion (a) must be
  written `assert_not_nil task.reload.completed_at`, **never** as "unchanged" compared at `.to_i` —
  the request lands in the same whole second as the fixture, so that spelling stays green under the
  mutation and is a guard that cannot fail. This is §15's recorded timestamp trap.

### F-65 · `FakeS3#do_copy` inherits the source's ETag

**Assessed: NECESSARY (NARROWED)** — confidence high. 10/10 citations resolved (three off by a few
lines, all landing in the correct block).

The assessor ran the fake standalone: seeded `etag: "a"*32+"-7"`, copied it, and the copy came back
carrying the source's multipart ETag while the md5 of its bytes was something else — then a second
copy using the scanned precondition **succeeded**. On AWS and R2 a single-part `CopyObject` re-tags,
so that second call is a 412 → `FetchError`. **The fake cannot express the defect**, which is why
F-04 is invisible today. CLAUDE.md §14e's "A FAKE THAT SHARES THE CODE'S MISUNDERSTANDING CONFIRMS
IT" — third field of the same struct, after `copy_source` and `last_modified`.

**Zero-churn claim verified exhaustively rather than sampled:** 77 `seed!` calls outside the fake,
exactly two pass `etag:` (`s3_observer_test.rb:434,454`), and that file performs no copy at all.

**Two narrowings, both accepted:**
1. The audit's "probe a real store before choosing the default" becomes a **comment, not a
   precondition**. AWS and R2 — the managed deployment — both re-tag; the fake must model the
   contract, not the most forgiving store, and re-tagging is the strictly harder case that also
   survives a store which preserves.
2. `checksum_sha256` / `checksum_type` are **explicitly out of scope**: `LIBRARY_S3_HEAD_FOR_CHECKSUM`
   has no production reader (§14a records it as not implemented) and zero of the 77 `seed!` calls
   pass either field, so changing their copy behaviour is unobservable in both directions — the exact
   anti-pattern this audit's headline warns against.

**Plan change this forces.** The end-to-end test F-65 needs is **red until F-04 lands**, so F-65
cannot be its own commit without leaving the branch red, which §15 forbids. **F-65 and F-04 ship as
one commit.** F-65 also needs its own direct assertion in `s3_test.rb` or it has no teeth: reverting
`do_copy` would make F-04's mutation check *falsely green*.

- **Scope:** `test/support/fake_s3.rb:183-184` (2 lines + comment);
  `test/integration/library/s3_library_test.rb` (~20 lines); `test/services/file_layer/s3_test.rb`
  (~6 lines). Nothing in `app/` for F-65 itself.
