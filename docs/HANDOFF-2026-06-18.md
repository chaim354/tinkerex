## 🟡 WebDAV concurrent-copy data loss — ROOT CAUSE FOUND + FIXED (2026-06-18, pending live re-verify)

**Symptom (user-reported, live, macOS desktop app v0.2.0):** copying **two files at once** to the
mounted drive → the **second** file is created but truncated to **~1 KB** when it's actually ~11 MB.
A data-integrity bug in the file layer (which "cannot fail"). Single-file copies appear fine.

**Mount path on macOS = WebDAV:** macOS `webdavfs` (kernel client) → HTTP → `client/fs-webdav`
(`dav-server`) → `Provider` (`client/fs-provider` `SqliteProvider`).

### ✅ Root cause + fix (commit pending)

The Provider/adapter *concurrency* is clean (below), but that wasn't the whole story — our code was
**committing partial PUT bodies**. `dav-server`'s `handle_put` (`handle_put.rs:244-278`) writes the
request body frame-by-frame, calls `DavFile::flush()` to **commit**, and only *afterward* checks
`total < count` for a premature EOF. So when the second concurrent connection's body ends early (the
leading transport hypothesis (a) below — early-closed keep-alive under concurrent PUTs), our
`Provider::flush` had **already chunked + committed the ~1 KB that arrived as a durable version**.
dav-server then returned `BAD_REQUEST`, but the truncated version was live and synced. A transport
hiccup was being turned into permanent data loss — and `fs-webdav`'s `open()` was **throwing away
`OpenOptions.size`** (the declared `Content-Length` / macOS `X-Expected-Entity-Length`), so `flush`
had no idea the body was short.

**Fix (test-first, TDD):**
- `fs-webdav`: capture `OpenOptions.size` (only for full truncating PUTs — `truncate == true`, so
  ranged/append PUTs whose staged length ≠ declared count are *not* guarded) into `WebdavFile`.
  `WebdavFile::flush` now refuses to commit when the staged length ≠ declared size: it **discards the
  partial write (prior committed content stays intact)** and returns an error → the PUT fails cleanly
  → macOS `webdavfs` retries with a complete body. Tests:
  `short_put_does_not_commit_truncated_file`, `complete_put_commits_full_content`.
- `fs-provider`: new `Provider::discard(ino)` primitive (default no-op; `SqliteProvider` drops the
  uncommitted staging buffer; forwarded through `impl Provider for Arc<P>`).
- All green: fs-webdav 3/3, fs-provider full suite, sync-engine builds.

**Still TODO:** re-verify on the live macOS mount (copy two 11 MB files at once → both intact). The fix
makes a short transfer *fail-safe + retry-able* rather than *silently truncating*; if macOS turns out
NOT to retry a failed PUT, the user would see a 0-byte/absent second file (obvious + non-corrupt, and
it never syncs) instead of a 1 KB corrupt one — still strictly better, but worth confirming the retry
actually fires. The HTTP-level repro below is the way to nail down *why* the body ends early.

**Systematic-debugging progress (Phase 1 — concurrency ruled out; the real bug was partial-commit):**
- **Ruled OUT — ino collision:** `create` does `INSERT … ; conn.last_insert_rowid()` under the
  `conn` mutex → unique inos. Not the bug.
- **Ruled OUT — the Provider:** wrote `client/fs-provider/tests/repro_concurrent_copy.rs` (committed)
  that reproduces the *exact* macOS-WebDAV sequence — `create → truncate(ino,0) → many write(ino,off,chunk)
  → flush`, two files concurrently, 40 rounds. **It PASSES** — content stays intact. The core
  write/flush/manifest path (`staging: Mutex<HashMap<ino, Vec<u8>>>`, keyed by ino; `flush` chunks +
  commits) is concurrency-correct.
- **Ruled OUT — the `fs-webdav` adapter:** `WebdavFs` holds only `Arc<provider>` + `hydrate` (no shared
  buffer/handle map); each `WebdavFile` is independent `{ino, pos}` writing straight to `provider.write`.
  No shared mutable state between concurrent files.

**⇒ The corruption is at the dav-server / macOS-webdavfs boundary, NOT our core logic.** Leading
hypotheses: (a) HTTP body-framing / early-close on a **reused keep-alive connection** under concurrent
PUTs (would corrupt the *second* request — fits the symptom), or (b) macOS `webdavfs` flakiness for
large/concurrent writes (a known weakness — a major reason the project wants off WebDAV on macOS toward
FSKit). "Exactly ~1 KB" smells like one write-buf chunk / a truncated body.

**NEXT STEPS for the takeover:**
1. **HTTP-level repro:** boot a local `fs-webdav` server (`client/fs-webdav/src/bin/maker-webdav.rs` or
   `client/sync-engine/src/bin/maker-webdavd.rs`) and fire **two concurrent large PUTs** via curl — once
   on separate connections, once pipelined/keep-alive on one connection. If the second truncates → it's
   `dav-server`/our HTTP serving (fixable in our code). If both are intact → it's macOS `webdavfs`.
2. **Awaiting user repro details** (asked, not yet answered): how copied (Finder drag vs `cp` vs `cp -R`),
   reproducible every time?, does a *single* large copy work?, is the bad file exactly 1024 bytes with a
   correct-but-truncated header?
3. If macOS-`webdavfs`-specific: mitigation options (disable keep-alive / force `Connection: close` in the
   WebDAV server, tune the body reader) and/or accelerate the FSKit path (`night`/`fskit-skeleton` already
   landed a `client/fs-fskit` crate skeleton on a prior merge; see `docs/plan-macos-fskit-migration.md`).

The transport may still be what *triggers* the short body (hypotheses (a)/(b) above) — worth the
HTTP-level repro to pin down — but our code no longer *loses data* when it happens: a short PUT is now
rejected, not committed. The Provider/adapter concurrency was genuinely clean; the bug was the
commit-before-completeness-check (fixed above).

## Ops / how to operate

- **Deploy:** on `main`, `export KAMAL_REGISTRY_PASSWORD="$(op read 'op://Personal/ghcr.io/password')"` +
  `export CHUNK_SECRET_ACCESS_KEY="$(op read 'op://Personal/seaweedfs/secret key')"` then `bin/kamal deploy`.
  (1Password desktop integration prompts Touch ID; `RAILS_MASTER_KEY` auto-sources from `config/master.key`.)
  Build is the Mac → ghcr → Unraid pulls. The image now includes the Rust `stl-thumbnailer` stage.
- **Test account (on the deployed box):** `demo@maker.test` / `MakerDemo2026!` (created via the seam).
  More via `curl -X POST http://192.168.1.95/v1/test/users -d '{"email":…,"password":…}'`.
- **Stuck previews:** an `unsupported` preview is terminal (won't auto-retry). To make the user's existing
  STL render after the fix, either re-upload, or reset on the server:
  `current_user.maker_previews.where(status:"unsupported").update_all(status:"pending")` + re-enqueue.
