## Opportunity 1: One reading of LIBRARY_BACKEND with "unset" and "unknown" as explicit states (retire the `chunk` sentinel and the dead `LibraryBackend` module)
1. Verdict: recommend
2. Evidence:
   - app/services/file_layer.rb:169 `backend = ENV.fetch("LIBRARY_BACKEND", "share")`; :202-203 `else raise ArgumentError, "unknown LIBRARY_BACKEND ..."`. This is the only place an unknown value is refused.
   - lib/library_backend_check.rb:107 `def self.check!(env: ENV, backend: env.fetch("LIBRARY_BACKEND", "chunk"))`, and :108-114 a `case` with no `else`, commented "an unknown backend is FileLayer.build's ArgumentError to raise, not this guard's". The default is a retired backend name. It works as a "check nothing" sentinel because it matches no arm.
   - lib/library_backend_check.rb:123-130 `required_in_production!`: `return nil if env["LIBRARY_BACKEND"].to_s.strip.present?`, so any non-blank value passes. Its message hand-writes `(share | s3 | chunk_remote)`.
   - config/initializers/library_backend_check.rb:20-25: the boot runs `required_in_production!` and then the no-argument `check!`. Line 19 says "no test can catch it, because the test env skips this file".
   - lib/library_backend.rb:18 `DEFAULT = "chunk"` and :22 `def self.name(env: ENV) = env.fetch("LIBRARY_BACKEND", DEFAULT)`. Nothing in app/, lib/ or config/ calls it. Its only callers are three tests (test/system/uploader_test.rb:49, test/services/file_layer/chunk_remote/upload_test.rb:91, .../mutation_contract_test.rb:96). It is still kept loaded by a hand `require_relative` (config/application.rb:14) and an autoload-ignore entry (:24).
   - lib/tinkerex/registration.rb:47 `backend = env["LIBRARY_BACKEND"].to_s` is a fifth reading, with no default.
   - test/deploy_hygiene_test.rb:810-814 holds the only `{ backend => required knobs }` table, as a test-local copy, because LibraryBackendCheck exposes none (share's `LIBRARY_PATH` is hard-coded inside `check_share!`).
   - Two comments describe a boot that does not exist: app/services/file_layer/s3.rb:39 ("The factory runs this at boot") and test/services/file_layer/factory_test.rb:120 ("the factory runs at boot"). The boot runs `check!`, never `build`.
   - History. 0fd8c8e0 (2026-08-26): the factory and guard defaults had drifted apart (`share` vs `chunk`), and "the one backend reachable without setting LIBRARY_BACKEND was the one the guard never checked". 287ddac5 (2026-10-13): a blank backend "booted cleanly and then answered 500 to every request, /up included, because the CSP header's connect_src lambda resolves FileLayer.current per response" (config/initializers/content_security_policy.rb:53-54). Each bug was fixed by patching one reader.
   - config/puma.rb:56-60: the boot-time scan rescues StandardError, so its own ArgumentError is only logged as a warning.
3. Current complexity or invalid states:
   - Four readers of one variable apply four different normalisations: default `share` (factory), default `chunk` (guard), `strip.present?` (production guard), and raw `to_s` (Registration). Each reader carries its own copy of the name list: the factory's `case`, the guard's `case`, the production message, and a test-local registry.
   - Unset, development: the boot check sees `chunk`, matches nothing, and boots; the factory then builds share. This is correct, but only through the sentinel.
   - Unset, production: refused at boot. Correct.
   - Unknown, typo'd, retired or space-padded values (`chunk`, `S3`, `chunk-remote`, ` share`), in any environment: `required_in_production!` passes because the value is not blank, `check!` matches no arm, and the boot (including `bin/rails db:prepare` in bin/docker-entrypoint:72) succeeds. The first `FileLayer.current` then raises ArgumentError. That call is the CSP lambda on every HTML response (/up included) and the first call in every job, so every page and job fails. This is the exact symptom 287ddac5 fixed, but it was fixed only for the blank case. The factory's deliberate refusal of `chunk` (factory_test.rb:26-34) therefore never happens at boot. It happens on every request.
   - Explicit blank (`LIBRARY_BACKEND=`): the production guard treats it as unset, but the factory treats it as unknown (`fetch` returns `""`). In development that means it boots and then raises on every request.
4. Proposed representation and why it is simpler. One reader returns one of three explicit states: nil (unset or blank), a known name, or a raise for an unknown value. The boot and the factory both consume it. They still answer different questions (§14a), but they now read the same fact.
   ```ruby
   # lib/library_backend_check.rb  (absorbs lib/library_backend.rb)
   NAMES = %w[share s3 chunk_remote].freeze
   UnknownBackend = Class.new(ArgumentError)   # ArgumentError: factory tests and RepoMetadataPurge keep their contract

   def self.configured(env: ENV)               # THE one reading
     raw = env["LIBRARY_BACKEND"].to_s
     return nil if raw.strip.empty?            # unset or blank: nothing named
     return raw if NAMES.include?(raw)         # exact; reject, never normalise
     raise UnknownBackend, "unknown LIBRARY_BACKEND #{raw.inspect} (#{NAMES.join(' | ')})"
   end

   def self.boot!(env: ENV, production: Rails.env.production?)   # the initializer's question, now testable
     name = configured(env:)                            # unknown: the boot is refused
     return check!(env:, backend: name) if name         # named: today's per-backend check
     required_in_production!(env:, production:)         # unset: production refuses, development boots (unchanged)
   end

   def self.check!(env: ENV, backend:)                  # no default; the `chunk` sentinel is gone
   ```
   ```ruby
   # app/services/file_layer.rb
   backend = LibraryBackendCheck.configured || "share"   # unset: the hermetic dev/test default (unchanged)
   # config/initializers/library_backend_check.rb
   Rails.application.config.after_initialize { LibraryBackendCheck.boot! unless Rails.env.test? }
   ```
   Why this is simpler:
   - One reading, one list, and three named states replace a retired backend name doing duty as "skip".
   - The boot decision becomes a pure function with a unit test, replacing an initializer that "no test can catch".
   - lib/library_backend.rb, its hand-require and its autoload-ignore entry are deleted.
   - The closing of the gap is a by-product, not an extra mechanism.

   Variant B: the boot calls `FileLayer.build` when a backend is named, which would make the s3.rb:39 and factory_test.rb:120 comments true. It is not needed for the fix. If it is not adopted, those two comments should be corrected.
5. Smallest credible implementation scope, in order:
   1. lib/library_backend_check.rb: add `NAMES`, `UnknownBackend`, `configured` and `boot!`; make `check!`'s `backend:` required; build the `required_in_production!` message from `NAMES`.

   3. app/services/file_layer.rb:169: read `configured || "share"`. Keep the `case`, and keep its `else raise` as a guard for a NAME the case lacks.

   5. Tests, as listed in item 7.
   6. CLAUDE.md §14a: reword the two bullets ("FileLayer.build TELLS check! ..." and "PRODUCTION REFUSES TO BOOT ... the lib default stays chunk-shaped") to describe the explicit unset state instead of a `chunk`-shaped default. The behaviour both bullets pin is kept.

   Optional, in other rows:

## Considered and rejected
- **Collapsing `Capabilities`' six booleans into a backend enum or discriminated union.** This violates §14a and §14b. S3 is the recorded counterexample (presignable true, versioned false). scannable, port_writable and !syncable are kept separate on purpose ("agreement across three samples is not identity"). Each flag is pinned against an independent fact by adapter_contract.rb:224-376, and all six vary, which is §14a's "a capability earns its place by varying".
- **A `storage_kind` capability (folder / bucket / sync server) to replace the three-arm ladders** in layouts/_library_unreachable.html.erb:13-19, shared/_where_files_come_from.html.erb:30-45 and help/show.html.erb:31-48. The ladders agree today, and the views deliberately ask capabilities rather than names. This would move branching behind a new type for a hypothetical fourth backend.
- **Encoding the upload flow as one `upload_flow` value instead of port_writable plus syncable.** The only invalid combination (both false) is hypothetical. files_controller.rb:66-76 records why the endpoints gate on `syncable` rather than `!port_writable`.
- **Turning `LibraryBroadcast.batch` into a port verb** (Share and S3 `def batch(_user) = yield`, then deleting the module and its `is_a?`). The branch already sits in exactly one place and has two callers (project_intake.rb:271 and :470). The payoff is naming, not structure. The module is misnamed (this app broadcasts nothing, §14e), and its header at library_broadcast.rb:3-35 still describes the retired engine arm. A doc or rename pass only.
- **Replacing the `is_a?(FileLayer::ChunkRemote)` checks** (library_broadcast.rb:50, remote_changelog_pull_job.rb:110) with `syncable?`. §14a records that the class check stays "because a future syncable backend faces the same ambiguity".
- **A shared `FileInfo.from_node`, or a base class for the three `file_info` / `live_node!` copies** (share.rb:865-888, s3.rb ~1290-1312, chunk_remote.rb:463-479). This is a recorded deliberate trade: independent implementations of one port, with the read contract keeping them equal. The gain would be line count only.
- **Making `UploadFinalized#info` non-nullable.** It is load-bearing. On a sync-server conflict, `current_version_id` "does not move" (docs/sync-protocol.md ~549), so `ChunkRemote#finalize_upload`'s `find_by(current_version_id: version_id)` (chunk_remote.rb:386-387) returns nil. Note that upload_finalized.rb:11-18 ("should be un-reachable in practice") and :20-27 (the conflict description) are stale; they describe embedded Chunk.
- **One concern for the per-controller `rescue_from FileLayer::*` blocks** (files 148-163, trash 59-67, models 169-184, projects/uploads 30-36, tools/addons 131-190, public/base 23-25). The statuses already agree. Redirect targets and copy differ per surface on purpose, so a concern would only parameterise them.
- **`Subtree.node_ids`'s `MAX_DEPTH`** (subtree.rb:24, 37-48). Not a material simplification, but worth a ticket. The `seen` filter (:45) already guarantees termination: every pass adds at least one unseen id or stops. subtree_test.rb:59-69's "cycle" test passes on `seen`, not on the cap. The cap's only remaining effect is to return a silent SUBSET for a tree deeper than 64 levels, which is the "tombstone a subset" wedge the module's own header names. A one-line fix would raise instead, as S3's `DIR_DELETE_MAX_OBJECTS` refusal does. It sits below this audit's bar because no real library is 64 levels deep.
- **Removing the dead `CAPABILITY_ABSENT[:versioned]`** (library_capabilities.rb:35-36). No `require_capability! :versioned` caller exists, and the concern's header (1-3, 21-24) still says the v1 API uses it, which §14j says no v1 controller does. A dead entry plus doc staleness; line count only.
- **Stale prose in boundary.** file_layer.rb:1-6 (the Chunk adapter, `Storage::ChunkStore.current`); capabilities.rb:53-65 (describes DIR_DELETABLE as live, though it was retired 2026-09-10); upload_begun.rb:11-17 (`Storage::ChunkStore`); library_broadcast.rb:3-35. Docs only.
- **The process-wide `FileLayer.current` memo with `attr_writer` and `reset!`** (92 test setters, 158 resets). This is test-harness territory (S27). The port's seam itself is fine.
- **Merging `write`'s `replace:` and `expect_token:` into one argument.** Both adapters ignore `expect_token` unless `replace` is set (share.rb:237, s3.rb:341), and callers pass them consistently. It would be a new type for no gain.
