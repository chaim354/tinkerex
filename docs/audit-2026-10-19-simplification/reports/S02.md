## Opportunity 1: Record which trash entry a tombstone belongs to instead of inferring it — the folder cascade rewrites tombstones it does not own, and folder restore guesses which rows to revive

1. Verdict: recommend
2. Evidence:
   - `app/services/file_layer/share.rb:422-424` — the cascade writes EVERY row the walk returns:
     `ids = FileLayer::Subtree.node_ids(user, node.node_id)` / `user.nodes.where(node_id: ids).update_all(deleted: true, storage_path: nil, updated_at: Time.current)`.
     `app/services/file_layer/subtree.rb:17-18` returns tombstones on purpose: "TOMBSTONES ARE INCLUDED … so `undelete` has the full set to revive."
   - `share.rb:694-712` (`revive_subtree!`) — a row is revived if it is anywhere in that walk and `File.exist?(parent.storage_path/child.name)` (`:705`); it writes `deleted: false, storage_path: rel, size:, mtime:` (`:708`) and never `content_hash`; the candidate query (`:698`) has no ORDER.
   - `share.rb:81-82` — `trashed` = `where(deleted: true, storage_path: nil)` ("`storage_path: nil` IS THE FILTER", `:59`).
   - `share.rb:554-558` — membership inferred from the parent row (`parent&.deleted? && parent.storage_path.nil?`); `:560` assumes an own entry at `.trash/<id>/<name>`.
   - `db/schema.rb:507` — `index_nodes_on_user_id_and_storage_path` unique `WHERE deleted = false`; `app/models/node.rb:6-8` validates nothing about it, so a clash is a raw `ActiveRecord::RecordNotUnique`, which `app/controllers/trash_controller.rb:36-67` does not rescue.
   - The recorded premise this broke: `docs/superpowers/plans/2026-07-16-file-layer-share-phase2b.md:89-96` — scan tombstone "revivable by the reconciler's revive-by-path (keep it)", and "The trash path stays derivable from the node alone: `.trash/<node_id>/<name>`. No column needed." True while delete refused directories; since the cascade (`ae996173`, 2026-09-10) a member's bytes sit at `.trash/<root id>/<root name>/…`, which nothing on the member's row records.
   - The rule is pinned only at the top level: `test/integration/web/share_trash_test.rb:127-140` and `test/services/file_layer/share_test.rb:1104-1120` ("a file deleted on the NAS is not offered for restore"). No test puts any tombstone inside a folder that is later deleted.
3. Current complexity or invalid states — a share row's trash state is the product of four signals (`deleted`, `storage_path IS NULL`, the parent row, whether `.trash/<own id>/` exists on disk), and the cascade writes the member shape onto rows that are not members:
   - (a) A scan tombstone becomes trash. `F/c.stl` removed in Finder → the scan tombstone KEEPS its path (`app/services/library/reconciler.rb:161-162`). The user then deletes folder F in the browser → `share.rb:423` nulls C's path → C is listed in /trash. Its Restore says "Restore "F" first, and its contents come back with it" (`trash_controller.rb:121-122`); after F is restored C is not revived (no bytes), stays listed forever, and answers "Couldn't restore that item." (NotFound "purged?", `share.rb:574`). That is exactly what the pinned rule forbids.
   - (b) Folder restore collides on a name. The ordinary replace workflow on share — delete `x.stl` (A: trash tombstone under F, kept indefinitely — the trash purge removes `.trash` dirs and never a row, `app/jobs/library/trash_purge_job.rb:98-102`), upload a corrected `x.stl` (B, live at `F/x.stl`; the clobber check is on disk only, `share.rb:233`) — leaves two rows named `x.stl` under F. Delete F, restore F: `revive_subtree!` reaches both, both pass `File.exist?("F/x.stl")`, the second `update!` violates the partial unique index → RecordNotUnique → 500, after the bytes are renamed back and F is already live. Rows the BFS had not reached keep NULL paths over bytes that are back on disk, so the next scan cannot revive them by path and mints new node_ids (`reconciler.rb:535-548`) — every attachment, BOM line and tag on them orphaned silently (§14a's landmine). If A is reached first it goes live over B's bytes with A's OLD `content_hash`; size/mtime were re-stamped from B's stat, so the scan's (mtime, size) skip (`reconciler.rb:372-375`) never re-hashes it and `stat`/previews keep describing A's content. The same pair also arises from a scan tombstone plus a browser upload, because `write` never revives (`share.rb:294`).
   - (c) Every older tombstone inside F has `updated_at` re-stamped by the cascade: its "Deleted" date changes and `Maker::DeadNodes.reapable?` (`app/services/maker/dead_nodes.rb:32-37`) restarts its 30-day grace.
   - (d) `undelete` needs those four signals to answer two different questions (is this row inside another entry? is its destination folder trashed?) and spends 28 lines (`share.rb:526-553`) arguing which proxy separates them.
4. Proposed representation and why it is simpler — one nullable column, written when membership is KNOWN (at delete) and read back, never re-derived:
   ```ruby
   # nodes.trash_root_id: node_id of the `.trash/<id>/` entry that holds this row's bytes.
   #   NULL = live, or a scan tombstone (not trash).  == node_id = an entry root.  other = moved with that root.
   def delete(user, node_id: nil)
     # … rename into .trash/<node_id>/<name>, unchanged …
     ids = FileLayer::Subtree.node_ids(user, node.node_id)   # walk unchanged: by edge, tombstones included
     user.nodes.present.where(node_id: ids)                   # only rows that were LIVE travel with it
         .update_all(deleted: true, storage_path: nil, trash_root_id: node.node_id, updated_at: Time.current)
   end

   def undelete(user, node_id: nil)
     node = user.nodes.find_by(node_id:, deleted: true) || raise(NotFound, "…")
     raise NotFound, "… removed outside the app; nothing in the trash" unless node.trash_root_id
     raise UnsupportedOperation, "… restore the folder first" if node.trash_root_id != node.node_id
     # destination check unchanged: parent&.deleted? && parent.storage_path.nil? (folder trashed AFTER this row)
     # … observable!, clobber check, rename back, unchanged …
     node.update!(deleted: false, storage_path: rel, trash_root_id: nil, size:, mtime:)
     revive_members!(user, node) # today's top-down BFS, over user.nodes.where(trash_root_id: node.node_id)
   end
   ```
   Simpler because membership becomes a recorded fact instead of a guess assembled from four signals: `revive_subtree!`'s `File.exist?` stops being the membership test (it can remain as a consistency check, or go with its per-row NAS stat); `undelete`'s essay becomes two one-line checks with distinct meanings; and the cascade can no longer turn a scan tombstone into trash, so §14a's two tombstone kinds are kept by construction instead of eroded on the folder path. Every trash row still has a NULL `storage_path`, so revive-by-path still cannot fire (§14a; `test/services/file_layer/adapter_mutation_contract.rb:216-217`).
5. Smallest credible implementation scope (in order):
   1. Migration: `add_column :nodes, :trash_root_id, :string` + index `[:user_id, :trash_root_id]`; backfill share/s3 data — each `deleted AND storage_path IS NULL` row gets the topmost ancestor in its chain of such rows (today's inference, run once, depth-capped like Subtree). chunk_remote rows stay NULL.
   2. `share.rb`: `delete` (`:422-424`), `undelete` (`:521-610`), `revive_subtree!` (`:694-712`); `trashed` (`:81-82`) may read the field (same rows once the cascade stops converting).
   3. `app/services/file_layer/s3.rb` in the SAME change, because the read and mutation contracts run on both legs: file `delete` (`:510`), `delete_directory!` (`:531-532` and `:568` — live rows only; see cross-notes for the live S3 bug this also fixes), `trashed` (`:144-145`), orphan check (`:726`).
   4. Optional: `TrashController#restore_refusal_message` (`:114-123`) names the entry root rather than the direct parent.
   A no-migration first step exists — `.present` on `share.rb:423`, plus `revive_subtree!` skipping rows that kept a path or own a `.trash/<id>` entry — and closes (a), (c) and the half of (b) where A's entry still exists. It cannot close (b) after the default `LIBRARY_TRASH_DAYS=30` purge removes A's entry, and "replace a file, then delete and restore the folder months later" is the realistic timeline; that case is what forces a recorded fact.
6. Regression risks and migration concerns:
   - Data: rows ALREADY converted by (a) cannot be told apart by the backfill and stay listed, as today; the backfill set is everything ever trashed (the trash purge never removes a row), each walk depth-capped.
   - API/port: `TrashEntry` and every port signature unchanged. chunk_remote must never read the column — its trash is the server's (`chunk_remote.rb:134-139` lists every deleted mirror row).
   - UI: /trash keeps listing folder members (parity with chunk_remote) minus converted scan tombstones; old tombstones inside a deleted folder now age (DeadNodes grace) from their own deletion.
   - Legs: new tests go in share_test/s3_test, which run on all three legs, so the run counts stay identical (§15). The Reconciler never sees members (NULL path) and never writes the column.
   - Do not narrow `Subtree.node_ids` itself (S01; including tombstones is still right for the WALK) — narrow the adapters' UPDATE.
7. Existing and additional validation required:
   - Must stay green: share_test.rb:757-775, :1104-1120, :1159-1227; share_trash_test.rb:45-155; adapter_mutation_contract.rb:154-218; adapter_contract.rb:416-431; s3_test.rb:1646-1665, :1713-1776; subtree_test.rb:41-48.

## Opportunity 2: A directory move rewrites its descendants' storage_path in the same call, so the path and the parent edge never disagree after a port write

1. Verdict: recommend
2. Evidence:
   - `share.rb:499` — `node.update!(storage_path: rel, name: new_name, parent_node_id: new_parent_node_id)`: the moved row only.
   - `share.rb:440-452` — "Only the moved node's own row is rewritten, so a moved directory's descendants keep a STALE storage_path until the next scan … Cascading the prefix rewrite to descendants here would close both. It is the right end state and it is NOT in this phase's plan".
   - `app/controllers/files_controller.rb:1013-1022` (`FOLDERS_NOT_YET`, enforced at `:1046`, `:1079`): "FOLDERS ARE REFUSED BY #rename AND #move UNTIL Share#move REWRITES THE SUBTREE'S PATHS IN THE SAME CALL … nested folders come back from that scan under new node_ids … lift it with that port change, as its own slice."
   - `subtree.rb:12-15` — the same staleness, given as the reason the walk is by edge.
   - `share_test.rb:860-886` pins it: `assert_equal "cad/gear.stl", @user.nodes.find_by!(node_id: gear.node_id).storage_path` after `cad` → `cad2`.
   - `reconciler.rb:605-608` finds/revives a directory only by exact storage_path and `:665-674` tombstones the unmatched one → a moved sub-directory is re-minted; files re-pair only by re-hashing every byte (`:392-438`, `hash_for` `:769-777`).
   - `share.rb:232` and `:337` find "the row already at rel" by storage_path → inside a moved folder `write(replace: true)` and `mkdir` mint duplicates.
   - `share.rb:694-712` already rebuilds descendant paths top-down from the parent edge, for undelete.
3. Current complexity or invalid states: `move` is the one port write that leaves live rows whose `storage_path` contradicts `parent.storage_path/name`. Until the next scan every descendant reads/downloads as NotFound ("File not found."), and `write(replace: true)`/`mkdir` inside the moved folder mint a second node for an existing file/dir, which the scan resolves by tombstoning the original (§14a: a replace "MUST reuse the existing node"). At the scan every nested directory gets a new node_id (dir ids carry project `folder_node_id` anywhere since adopt-anywhere, and model `folder_node_id`, §14k), every byte of the subtree is re-read from the NAS to re-pair files, and a file unreadable at that moment is tombstoned and re-created (`share.rb:446-448`). No production door reaches this today — FOLDERS_NOT_YET, `AttachToProject#refusal_for` (`:not_a_file`) and `ProjectIntake#place` (files only) keep directories out — so the present cost is a known-bad mode in a port verb plus a blocked browser feature.
4. Proposed representation and why it is simpler:
   ```ruby
   def move(user, node_id: nil, new_parent_node_id: nil, new_name: nil)
     # … guards and clobber check unchanged …
     refuse_into_own_subtree!(user, node, new_parent_node_id) if node.dir? # today rename(2) EINVAL -> FetchError "try again"
     # … rename unchanged …
     from = node.storage_path
     node.update!(storage_path: rel, name: new_name, parent_node_id: new_parent_node_id)
     rebase_descendants!(user, node, from:) if node.dir?
     stat(user, node_id: node.node_id)
   end

   # ONE statement. The SET is the parent-edge walk (Subtree, §14a); the rewrite is by prefix, and only
   # rows that still agree with the old prefix move — a descendant already stale from an unscanned
   # Finder change is left for the scan, as today. NULL-path trash rows are untouched (undelete
   # rebuilds them from their parent, which now carries the new path).
   def rebase_descendants!(user, dir, from:)
     old = "#{from}/"
     user.nodes.where(node_id: FileLayer::Subtree.node_ids(user, dir.node_id).drop(1))
         .where("substr(storage_path, 1, ?) = ?", old.length, old)
         .update_all(["storage_path = ? || substr(storage_path, ?)", "#{dir.storage_path}/", old.length + 1])
   end
   ```
   Equivalent alternative: lift `revive_subtree!`'s BFS into one path-rebuild walk used by both move and undelete, with the row writes in one transaction (the "no transaction" argument at `share.rb:454-455` is about the rename, not rows written after it). Simpler because, after every port write, storage_path agrees with the parent edge for every row the port touched; move's two-residual docstring, the controller's blanket refusal and the next-scan repair pass (re-hash + directory re-minting) stop being needed.
5. Smallest credible implementation scope: `share.rb#move` + helper + the self-nesting refusal; rewrite `share_test.rb:860-886`; update `share.rb:440-452` and `subtree.rb:12-15`. Separate slice outside this row: FilesController lifts FOLDERS_NOT_YET where the port accepts a directory (s3 still refuses via `movable_file!` → UnsupportedOperation → 422).
6. Regression risks and migration concerns: stale LIVE rows under the destination prefix would make the statement hit the partial unique index (the moved row already has this exposure at `:499`) — atomic, so descendants stay exactly as stale as today and the scan heals; `||`/`substr` behave identically on SQLite and Postgres and are character-based like Ruby's `length`; stored paths are valid UTF-8 (`app/services/library/scanner.rb:194` skips others); scan tombstones inside the folder move with it (their kept path is rebased), so revive-by-path fires at the new location — what a Finder rename means; no data migration; no leg divergence (s3 refuses dir moves; chunk_remote mirror rows have NULL paths).
7. Existing and additional validation required: existing — share_test.rb:787-886, adapter_mutation_contract.rb:88-126, adapter_write_contract.rb (taken-destination / directory-occupies / OS-clutter tests), subtree_test.rb:30-39. New — (1) after a folder move every descendant, including a nested sub-folder's file, reads back immediately; (2) across the next scan the nested sub-folder keeps its node_id and no file is re-hashed (spy `Digest::SHA256.file` with the house `#replacing` helper — the suite has no `Object#stub`); (3) `write(replace: true)` into the moved folder reuses the node; (4) a move into its own subtree is UnsupportedOperation and renames nothing; (5) a descendant whose path was already stale is left alone. Mutations: delete the `rebase_descendants!` call → 1-3 red; drop the prefix guard → 5 red; drop the refusal → 4 red (FetchError instead).
8. Confidence: medium — mechanics high and entirely in-file, but the payoff lands when FOLDERS_NOT_YET is lifted, since no production door moves a directory on share today.

## Considered and rejected
- Make `write`/`mkdir` revive a scan tombstone at `rel` like the scan does (`share.rb:294-295`, `:337`/`:347` vs `reconciler.rb:535-548`, `:605-608`). A real two-door divergence: a browser upload or New Folder after a Finder deletion mints a new node_id where a Finder re-creation revives the old one (that mkdir mints because its idempotence lookup is `.present` is recorded, in the chunk context, at docs/superpowers/plans/2026-08-20-widen-the-file-layer-port.md:876; a project whose folder was removed in Finder is not re-linked when the folder is re-made in the browser, since `app/models/maker/project.rb:270` answers nil for the tombstoned id and nothing revives it). Not taken: it is a product decision (should a browser upload inherit a Finder-deleted file's attachments?) and its clean form is one "node at rel" ladder shared with the Reconciler and S3 — S05/S03's call. In cross-notes.
- A `destination!` helper for the `leaf!`/`parent_dir_rel!`/`observable!`/`resolve_inside!` chain (`share.rb:228-231`, `:334-340`, `:457-462`, `:580-592`): consistent today and the variations are deliberate (undelete uses `live: false` and no `leaf!` on a stored name; `revive_subtree!` omits `observable!` because the indexed `.git` marker must come back with its folder). Line-count only.
- One method-level `SystemCallError → FetchError` mapping instead of per-call `begin` blocks: the blocks carry per-phase cleanup (`rm_f(tmp)`, `discard_empty`), so not simpler. It did surface a real defect, to fix on its own: `write`'s `FileUtils.mkdir_p(dest.dirname)` (`share.rb:257`) sits OUTSIDE the `begin` at `:273` — the exact bug class delete/move/undelete record fixing (`:368-372`, `:483-485`, `:598`) and test (share_test.rb:737, :1068, :1082; none for write). A write under a catalog folder missing on disk whose re-creation fails (a file now at that path; a read-only remount) raises a raw Errno → 500 instead of FetchError → 503. One-line move into the `begin`. (The post-rename `File.stat` calls at `:285`, `:349`, `:606`, `:707` are also unmapped; narrower.)
- A shared base/module for the Share/S3 twins (`live_node!`, `file_info`, `leaf!`, `join_rel`, `nanos`, `parent_dir_rel!`, `read_capped!`, `library_present?`): the recorded standing trade (`share.rb:863-868`, `:874-878`; `s3.rb:140-143`); the contracts keep the answers equal.
- Store a trash row's real `.trash/<root>/…` location in `storage_path` instead of NULL (membership without a column): reverses §14a's "a trash tombstone NULLs it", the mutation contract's `assert_nil` (`adapter_mutation_contract.rb:216-217`) and RepoMetadataPurge's reliance on NULL + parent chain (`repo_metadata_purge.rb:48-55`). Rejected.
- Derive `storage_path` from the parent edge (drop the column on share): the scan's identity, the partial unique index, revive-by-path and the Reconciler's live index all key on it (S05; §14a/§14b).
- `trashed` listing entry roots only: tidier page, but chunk_remote lists every deleted mirror row and TrashController's refusal message is built around listed members — a three-backend UX decision, not a Share simplification.
- Make `Share#move` refuse directories like S3's `movable_file!` (deletes the stale-path mode today): contradicts the recorded direction (`share.rb:449-452`, `files_controller.rb:1013-1021`).
- `TrashPurgeJob`'s `case adapter when FileLayer::Share / S3` (`trash_purge_job.rb:63-72`) as a port verb: moving existing branching behind an interface; S05.
- Drop the inner `<name>` level of `.trash/<node_id>/<name>`: it keeps the NAS-side trash legible and is what undelete renames back; nothing gained.
- `write`/`mkdir` do not ask `library_present?`, so an upload during an unmount lands on the empty mount point's own disk: an empty root is also a fresh library, so that heuristic cannot gate writes; needs a real mount signal — robustness, not simplification.
- Share has no `put_chunk` refusal (begin/finalize get named refusals per `share.rb:300-313`; a direct `put_chunk` is a NoMethodError): trivial, and gated by `port_writable?` at `library_output.rb:90`.
- `resolve_inside!` is lexical (`expand_path`), so a file swapped for a symlink between scans is followed by read/download: hardening outside a simplification audit; the scanner never indexes symlinks and the threat model is the NAS owner.
