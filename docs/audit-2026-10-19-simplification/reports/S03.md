## Opportunity 1: Give an S3 trash entry ONE shape and drive delete and undelete from one subtree walk

The shape is Share's: the root's subtree lives under `.trash/<root id>/<root name>`. A file is the subtree of one.

1. Verdict: recommend.

2. Evidence
   - **There are two trash layouts, and `undelete` reads only one of them.**
     - A file entry is `trash_key(node)`, which is `.trash/<node id>/<name>` (s3.rb:842-844). Both `delete` (:486) and `undelete` (:731) use it.
     - A folder entry is built differently: `trash_root = ".trash/#{node.node_id}"`, then `pairs = files.map { |f| [ key_for(f), key_for_rel("#{trash_root}/#{f.storage_path}") ] }` (s3.rb:545-546). It is keyed by the cascade root's id plus each file's FULL `storage_path`. That is the column the same method NULLs at :568.
     - `undelete` knows only the file layout (`src_key = trash_key(node)` :731, then `object_exists?(src_key)` :739). Its own comment describes the folder layout as "`.trash/<dir id>/<path under the dir>`" (:721-724), which is not what the code writes.
   - **The folder's object set is `user.nodes.where(node_id: ids).where.not(storage_path: nil).where(kind: "file")` (s3.rb:532).** It has two problems:
     - It has no `present`. `Subtree` includes tombstones by design (subtree.rb:16-17), and a SCAN tombstone keeps its path (reconciler.rb:162, `node.update!(deleted: true)`; §14a). So a file whose object is already gone is still in the set.
     - It keeps `kind: "file"` only. The dir markers that `mkdir` puts (`marker = "#{key}/"`, s3.rb:417 and :425) are objects too, but nothing copies them (:551) or deletes them (:556).
   - **Share has the inverse operation; S3 does not.** Share has `undelete` plus `revive_subtree!` (share.rb:521-610 and 694-714), pinned by share_test.rb:1185-1214 ("restoring a directory returns the subtree with the same node ids and the same bytes", "an empty directory deletes and restores too").
     - S3 has no folder-restore code and no folder-restore test. s3_write_test.rb:171-186 asserts only the tombstones.
     - The shared mutation contract has no folder-restore case (adapter_mutation_contract.rb:183-218).
     - In git, Share's cascade and revive landed in ae996173. S3's cascade landed 16 minutes later in 5fc9b7e1, delete only.
   - **The product promises the restore.**
     - trash_controller.rb:121-122: "Restore X first, and its contents come back with it."
     - help/show.html.erb:56-58.
     - §14a: "a refusal is recoverable — restore the folder, then the file".

3. Current complexity and invalid states. Each was traced statement by statement, and FakeS3 models every wire step they depend on.
   - **(a) A folder can become permanently undeletable from the app.** This happens when the folder holds any file the scan tombstoned:
     - A file removed out-of-band (the S3 console, rclone) is scan-tombstoned.
     - So is an `etag:`-rung object renamed out-of-band, which §14a says "degrade[s] to delete+create".
     - Its copy from a source that no longer exists fails. That is NoSuchKey on AWS and in FakeS3, and InvalidArgument on SeaweedFS (fake_s3.rb:159-161). The failure becomes FetchError, shown as "Couldn't reach your library. Try again." (files_controller.rb:148-153), on every retry. Nothing ever clears that tombstone's path.
     - For the same reason, the phase-2 comment's recovery claim is false (s3.rb:552-555: "the next scan … tombstones them … and a retry of this delete completes it"). The scan tombstones it creates keep their paths, so they re-enter the copy set.
   - **(b) A deleted folder comes back after the next scan.**
     - Its markers stay in the bucket.
     - S3Observer treats a marker as positive evidence of a directory (s3_observer.rb:154-160).
     - `Reconciler#ensure_dirs` cannot revive the tombstone (its path is NULL), so it mints a NEW node (reconciler.rb:605-606). s3_test.rb:1693-1698 pins exactly this marker-keeps-folder behaviour.
     - So every folder the app makes (via mkdir/LibraryFolder: project folders, New folder) and every console folder reappears empty within 15 minutes, under new node_ids. Meanwhile its contents sit in the trash.
   - **(c) A deleted folder cannot be restored.**
     - `undelete(dir)` HEADs `.trash/<dir id>/<name>`, an object no code writes. The check answers false, `library_present?` answers true, and the result is NotFound ("its trashed bytes are gone (purged?)"). The user sees "Couldn't restore that item."
     - Restoring any child gets "restore the folder first" (s3.rb:725-729).
     - That is a dead end. The bytes sit in `.trash/<dir id>/…` until the purge job removes them (default 30 days).
   - **Nested folders have a further problem.** Their entry location depends on the root's former path, which the cascade NULLs and which an out-of-band ancestor rename (re-homed by the scan) rewrites. So even a correct restore could not always find the entry.

4. Proposed representation and why it is simpler
   - **The rule (Share's layout).** An entry is `.trash/<root id>/<root name>`. A file root is the object at exactly that key, which is byte-identical to today. A directory root's members keep their ROOT-RELATIVE path beneath it, markers included as `<rel>/`.
   - **How the relative path is computed.** It comes from node names along the parent edge, the walk `revive_subtree!` already uses. So the location depends only on facts the catalog keeps (root id, root name, the descendants' names) and never on `storage_path`.
   - **The object set.** It is the subtree's LIVE nodes: each file's key, plus each directory's marker when one exists. Ask existence with `object_exists?`, a HEAD, whose "missing" answer is the same on every store (s3.rb:1078-1082). Never infer absence from a failed COPY: SeaweedFS answers a missing copy source with InvalidArgument.

   ```ruby
   def entry_key(root, rel = nil) =
     key_for_rel([Library::Scanner::TRASH_PREFIX, root.node_id, root.name, rel].compact.join("/"))

   def delete(user, node_id: nil)              # a file root is the walk of one
     root  = live_node!(user, node_id)
     moves = subtree_objects(user, root)       # [src_key, entry_key(root, rel), if_match], LIVE nodes only
     # cap (counting files, as today) + copyable_size! — unchanged
     # copy every move -> delete every source (markers included) -> update_all(deleted: true, storage_path: nil)
   end

   def undelete(user, node_id: nil)
     # tombstone lookup, orphan refusal, restored rel, observable! — unchanged
     # vacancy: destination_vacant!, and for a dir root also list_objects_v2(prefix: "#{key}/", max_keys: 1)
     # copy back each entry object that exists (on failure: best-effort delete what was copied, then FetchError)
     # revive top-down, rebuilding storage_path from the parent (share.rb:694-714's walk) -> sweep the entry last
   end
   ```

   - **Why it is simpler.**
     - One entry shape replaces two.
     - One delete path replaces `delete`'s file branch plus `delete_directory!`.
     - `undelete` reads exactly what `delete` wrote.
     - Today's file behaviour is the degenerate case. Root-level folder entries are also byte-identical (`.trash/<id>/parts/stl/a.stl` either way), so the key assertions at s3_test.rb:1713-1741 still hold.
     - Net code is roughly flat: the delete side shrinks and the restore side grows a directory branch. The simplification is in the representation, and the payoff is (a)-(c).

5. Smallest credible implementation scope. Code changes are in s3.rb only, in this order:
   1. **Delete side (fixes a and b).** Add `.present` and markers to the object set, root-relative destination keys via `entry_key`, and markers deleted in phase 2 alongside the sources. No interface changes. This step can ship alone.
   2. **Undelete side (fixes c).**
      - A directory root goes through the same walk.
      - For a directory root, the vacancy check also asks the bucket prefix (Share's `File.exist?(dest)`). Otherwise an unindexed object already there would be clobbered.
      - The revive mirrors share.rb:694-714. A node revives only if its object came back, or if it is a directory on the path to one.
   3. **Cleanup.**
      - Fold the file branch into the subtree path.
      - Delete the dead `trashable_file!` (s3.rb:947, no caller since 5fc9b7e1) and the stale "So BOTH verbs refuse" block (s3.rb:912-946).
      - Correct s3.rb:721-724.

   Nothing else changes: not `TrashPurgeJob` (it groups only by the first segment after `.trash/`, trash_purge_job.rb:139-149), not the observer, not the controllers, not `trashed`, and not the port signature. A directory delete of the root keeps using `Subtree.node_ids` for the tombstone set (§14a's parent-edge rule).

6. Regression risks and migration concerns
   - **Data.** Old-layout entries for NESTED folders (`.trash/<id>/<ancestors>/<name>/…`) would be missed by the new restore. They are unrestorable today anyway and age out under LIBRARY_TRASH_DAYS. File entries and root-level folder entries are layout-identical.
   - **Billing.**
     - Delete: one extra HEAD per directory, plus a copy and a delete when its marker exists.
     - Folder restore: a HEAD, a COPY and a DELETE per object, bounded by DIR_DELETE_MAX_OBJECTS.
     - Keep the cap counting files. s3_test.rb:1743-1754 asserts the file count in the refusal message.
   - **Behaviour: one explicit decision.** Today only the single-file path sends `copy_source_if_match` (s3.rb:489 vs :551). One uniform rule is simpler. It means a folder whose child changed since the last scan refuses (FetchError) until the next scan, which is the single-file path's existing behaviour.
   - **Ordering invariants are preserved.**
     - Delete: copy, then delete, then tombstone LAST (§14a's landmine).
     - Restore: copy first, revive second, sweep last.
     - A partial restore must never leave a copied-back object without a live row, because the scan would mint a new node_id. Hence the compensating delete.
     - The residual is a compensation that itself fails. That is the same class as the scan race already accepted at s3.rb:700-703.
   - **Backend legs.** Every S3 test injects FakeS3, so all three legs run them identically. Nothing depends on the ambient `LIBRARY_BACKEND`.
   - **Semantics.** Share revives the whole subtree. chunk_remote's journey restores the child with a second POST after the folder (chunk_remote_journey_test.rb:286-293). Matching Share is what the TrashController copy promises. A shared contract test must accept both behaviours.

7. Existing and additional validation
   - **Existing tests that pin the surrounding behaviour:**
     - s3_test.rb:775-1060 (delete ordering, preconditions, wire encoding), :1220-1360 (caps, orphan refusal), :1487-1667 (undelete), :1713-1779 (folder delete).
     - adapter_mutation_contract.rb:183-218.
     - s3_write_test.rb:124-241.
     - s3_library_test.rb:179-305.
     - trash_purge_job_test.rb:245-470.
   - **New tests in s3_test.rb; each is red today:**
     - "a folder holding a file the scan tombstoned still deletes". Create `cad/a.stl` and `cad/b.stl`, call `delete_file!(b)` (s3_test.rb:143 already produces the scan-tombstone shape), then delete the dir. Today it raises FetchError. Mutation: drop `.present` → red.
     - "a deleted folder stays deleted across a scan". Use `make_dir`, write a file, delete the dir, run `scan!`, then assert there is no live node at "parts" and `refute stored?("parts/")`. Today a new directory node appears. Mutation: drop markers from the object set → red.
     - "restoring a directory returns the subtree with the same node ids and the same bytes" and "an empty directory deletes and restores too". Port share_test.rb:1185-1214 as written. Today both raise NotFound. Mutation: send a directory root down the file-only branch → red.
     - "a nested folder's entry is root-relative". Assert `.trash/<id>/<name>/…` for a directory inside a directory. Today the key carries the ancestors.
     - "a folder restore whose copy fails partway revives nothing and leaves no copied-back object", using `fault_after!(:copy_object, 1, …)`. Mutation: drop the compensation → an object sits at a live key with no live node.
   - **Optional, owned by S01:** a backend-agnostic contract case. Delete a folder, restore it, restore the child only if it is still trashed, then assert both are live with the same node_ids and the child's bytes.

8. Confidence: high that (a)-(c) are real and reachable on the deployed s3 backend. Medium-high on the design: S3 offers no atomicity, so the restore inherits a narrow compensation residual.

## Opportunity 2: One rule for the facts a store response carries

Two parts: `ObjectIdentity` owns the blank-ETag answer, and FakeS3's copy result carries LastModified as the wire does.

1. Verdict: recommend, at lower priority than Opportunity 1.

2. Evidence
   - **Three hand-rolled guards answer "the store gave no usable ETag":**
     - `move`: `ObjectIdentity.for(etag: copied_etag) if copied_etag.present?` (s3.rb:675-676).
     - `restored_stat`: `… if head.etag.present?` (s3.rb:1002). Its rescue covers only ServiceError and NetworkingError (:1004).
     - `store_identity`: `return nil unless head.etag.present?` plus `rescue ArgumentError` (s3.rb:1120-1129).
   - **A review fix reached one site of three.** Commit b3741f76 found that a literally quoted-empty ETag `""` passes `present?` and still raises in `normalize_etag` (object_identity.rb:107-116). It fixed `store_identity` only.
     - Its comment calls skipping "the direction #move and #restored_stat already take" (s3.rb:1106-1112). Those two still use the `present?` test that the same review showed is insufficient.
     - They are also the two sites whose failure the code calls the worst. `move` raises after `delete_object` has removed the source ("the orphaning landmine", s3.rb:660-667). `restored_stat` raises after the copy-back and before the revive (s3_test.rb:1174-1179).
   - **FakeS3 leaves LastModified out of the copy result.** It returns `{ copy_object_result: { etag: copy.etag } }` (fake_s3.rb:205).
     - The SDK's `CopyObjectResult` has `:last_modified`, mapped from `<LastModified>` (types.rb:3177-3179, client_api.rb:1046-1047).
     - `PutObjectOutput` has none (types.rb:17944-17966), which is why `write` HEADs.
     - `move`'s comment reaches the opposite conclusion by citing the fake: "copy_object's response carries no last_modified, and the fake returns none either" (s3.rb:669-673).
     - So the adapter's own rule, "FROM THE RESPONSE WE ALREADY HOLD. Never a HEAD afterwards" (s3.rb:651-653), is applied to the ETag but not to the date.

3. Current complexity and invalid states
   - One decision has three spellings, and only one handles `""`. A store that answers a copy or a HEAD with `""` causes two failures:
     - `move` raises with the bytes only at the new key while the row still names the old one.
     - `undelete` strands a restored object behind a trashed row. The next scan then mints a new node_id, orphaning the node's attachments.
   - After every move, the row keeps the source's mtime until the next scan rewrites it: one UPDATE and one enqueue per moved file (reconciler.rb:315-338).
   - The comment justifying that is wrong about the wire. This is §14e's shape: a fake that shares the code's misunderstanding confirms it.

4. Proposed representation. Put the second answer next to the one place the quotes come off:

   ```ruby
   class BlankEtag < ArgumentError; end   # raised by normalize_etag; still an ArgumentError
   # -> String, or nil when the store reported no usable ETag. For the adapter's REFRESH sites,
   # where keeping the previous value is safe. The observer keeps `for`, whose raise is §14a's
   # totality guard.
   def self.for_reported(etag:)
     self.for(etag:)
   rescue BlankEtag
     nil
   end
   ```

   - `move`, `restored_stat` and `store_identity` call `for_reported`. Their `present?` tests and `store_identity`'s `rescue ArgumentError` go away.
   - FakeS3's `do_copy` returns `last_modified:` in the copy result, and so does s3_test.rb's `retag_copies!` helper.
   - `move` takes the mtime from the copy result when it is present, guarded the same way the ETag is.

5. Smallest credible implementation scope:
   - object_identity.rb: add `BlankEtag` and `for_reported`.
   - s3.rb: lines 669-676, 999-1006 and 1120-1129.
   - fake_s3.rb: line 205.
   - s3_test.rb: lines 1080-1090.
   - `write`'s unguarded `ObjectIdentity.for(etag: put.etag)` (s3.rb:370) stays raising, because a created node needs an identity. Falling back to the ETag on the HEAD it already makes is a separate decision.

6. Regression risks and migration concerns
   - No data or API change. The observer path is untouched, so totality holds and `Reconciler#plan_moves`'s nil-drop stays unreachable.
   - The mtime half depends on stores filling `CopyObjectResult.LastModified`. Keep the presence guard. Before relying on it, compare its precision with the listing's on the self-host SeaweedFS (the write path already pairs a HEAD date with a listing date, s3.rb:1268-1272).
   - The change touches FakeS3 only, so all three backend legs behave identically.

7. Existing and additional validation
   - **Existing:** s3_test.rb:1100-1210 (the F-04 refresh tests and the blank-ETag tests) and object_identity_test.rb:74-81.
   - **New in object_identity_test:** `for_reported` returns nil for nil, `""` (empty), the quoted-empty `""` and whitespace, and equals `for` otherwise. Mutation: make it plain `for` → red on the quoted-empty case.
   - **New in s3_test:**
     - A move with `retag_copies!('""')` keeps the previous identity and lands. Today it raises ArgumentError. Mutation: restore `present?` → red.
     - An undelete whose HEAD answers `etag: '""'` completes. Today it raises.
     - A FakeS3 self-test that a copy result carries the new object's `last_modified`, beside s3_test.rb:1057. Mutation: drop the field → red.
     - A move sets the row's mtime to the copy's. Mutation: drop the refresh → red.

8. Confidence: high on the facts (code and SDK read). Medium on value: the quoted-empty case needs a misbehaving store, and the mtime half is cosmetic and heals at the next scan.

## Considered and rejected
- **A shared base or module for Share and S3's duplicated helpers** (`live_node!`, `leaf!`, `join_rel`, `parent_dir_rel!`, `read_capped!`, `file_info`, `trashed`). This is a recorded standing trade (s3.rb:139-143, 1289-1292, 1298-1302), and the three contracts keep the two answers equal. The gain would be line count only; S01 rejected the same thing.
- **A `transient(label) { }` wrapper for the seven `rescue ServiceError, NetworkingError → FetchError` blocks** (s3.rb:198, 352, 427, 491, 557, 638, 768). Line count only. Each site's comment carries a site-specific argument, and no state becomes unrepresentable.
- **One `resolve_destination!` for the `leaf!` → `parent_dir_rel!` → `join_rel` → `observable!` → `key_for_rel` sequence** (write :304-307, mkdir :410-416, move :592-599, undelete :731-736). Each verb interleaves its own steps:
  - mkdir's idempotence short-circuit must come before `destination_vacant!`.
  - move has its no-op short-circuit.
  - undelete passes `live: false`.

  Every guard is already pinned per verb (s3_test.rb:364-430 and 1412-1470; write contract :292-447). Note: undelete never applies `leaf!` to the restored name. That is reachable only through a poisoned row, and `key_for_rel` still refuses `..`.
- **An explicit tombstone-kind or `trash_root_id` column so a cascaded child can name its entry.** The NULL `storage_path` is the mechanism that disarms revive-by-path (§14a), and S05 rejected the same column. Opportunity 1's root-relative keys make the entry location derivable without a new column.
- **Moving `etag_precondition`'s rung rule into ObjectIdentity.** It is a wire concern (re-quoting a value for If-Match), not an identity question, and it sits next to its only use.
- **Collapsing `destination_vacant!`'s two namespaces into one.** Both halves are needed (s3.rb:1020-1064); the cross-kind bug fixed in 9996ce6f is the evidence.
- **A background job to lift `DIR_DELETE_MAX_OBJECTS`.** The code already rejects this (s3.rb:472-477): the job would have to decide what the catalog says while it runs.
- **FakeS3 gaps that do not matter today:**
  - `do_get` ignores `range:`, but the adapter's dependence on the range is pinned at the wire (s3_test.rb:752-762).
  - `do_list` ignores `delimiter`/`start_after`, which nothing sends.
  - A missing copy source answers NoSuchKey where SeaweedFS answers InvalidArgument (fake_s3.rb:159-161). That is harmless today because nothing branches on a copy's error code. It does constrain Opportunity 1: do not infer "absent" from a failed copy.
  - The `checksum_*` fields are modelled but unused, as fake_s3.rb:78-87 documents.
- **`write(replace: true)` looks the same path up twice** (`existing` at s3.rb:308, `occupant` at :1066). That is one query, not material.
- **Stale prose that should ride along with Opportunity 1 rather than stand alone:**
  - s3.rb:912-946 says delete refuses directories, and `trashable_file!` (:947) has no caller.
  - s3_test.rb:1263-1279's "WHY REFUSE RATHER THAN CASCADE" paragraph describes the retired refusal.
  - s3.rb:721-724 misdescribes the cascade layout.
