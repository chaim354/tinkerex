## Opportunity 1: The tombstone-revive lookups can use no index, so every file a scan CREATES costs a scan of the user's whole `nodes` table — a first scan or large import is quadratic

1. Verdict: recommend
2. Evidence:
   - `reconciler.rb:165-167` — every leftover observation (every new file) goes through the revive lookup: `leftovers.each do |o, hash| enqueue_thumbnail(create_or_revive!(o, hash), hash)`.
   - `reconciler.rb:536-537` — the first statement of `create_or_revive!`: `@user.nodes.where(storage_path: o.rel_path, deleted: true, kind: "file").order(id: :desc).first`.
   - `reconciler.rb:605` — `ensure_dirs`' revive, reached for every new or changed directory: `@user.nodes.where(storage_path: o.rel_path, kind: "dir").order(id: :desc).first` (no `deleted` term).
   - `db/schema.rb:507` — the ONLY index containing `storage_path`: `t.index ["user_id", "storage_path"], …, unique: true, where: "deleted = false"`. A `deleted = true` (or unfiltered) query cannot imply that predicate, so the planner falls back to `db/schema.rb:509` `index_nodes_on_user_id` and filters every row of the user.
   - `reconciler.rb:729-732` and the `c5ca25bd` body ("vanished_nodes and the two tombstone-by-path lookups stay LIVE queries") — F-07 deliberately kept these as per-row live queries. I found no measurement of their per-query cost in the code, the commit bodies, or the 2026-08-19 audit/fix-log (F-07 measured no-op passes, which reach neither lookup; `fa1676e5` timed the 50k rename, not the 50k create that set it up).
   - `s3_observer.rb:510` — S3 identity comes free from the listing, so an S3 first scan hashes nothing: the create path IS its cost. `fa1676e5`'s body: "S3 is where someone actually points 2M objects at this".
   - `scan_job.rb:45-49,55-56` — the per-user semaphore `duration: 1.hour` "has to exceed a realistic slow pass or it lets exactly the overlap this prevents back in"; `config/recurring.yml` fires `library_scan` every 15 minutes.
   - Probe (in-memory, see Files read). Plans, identical with and without `ANALYZE`: create_or_revive! shape with `deleted` bound to 1 → `SEARCH nodes USING INDEX index_nodes_on_user_id (user_id=?)`; ensure_dirs shape → the same; a `present` lookup with `deleted` bound to 0 → `index_nodes_on_user_id_and_storage_path (user_id=? AND storage_path=?)`. Cost of a no-match lookup is linear in the user's rows: 100 lookups = 0.30 s at 25k rows, 0.61 s at 50k, 2.57 s at 200k (~0.125 µs/row/lookup); 200 lookups at 100k = 2.47 s (12.4 ms each).
3. Current complexity or invalid states:
   - A first scan of N files performs N revive lookups whose cost grows with the rows already inserted: ≈ 0.125 µs × N²/2 in memory (a lower bound for the on-disk DB) — ~10 min at 100k files, ~1 h near 240k (where the ScanJob semaphore expires and the next 15-minute tick can start a second, overlapping pass over the same library, the state `scan_job.rb:30-34` says the pairing logic assumes away), ~17 h at 1M, ~69 h at 2M objects.
   - The same applies to any large import into an indexed library (copying a big archive onto the share, or `aws s3 sync` into the bucket), and to every new directory via `:605`.
   - It is invisible at today's real scale (the 2026-09-07 share snapshot: 3,830 live + 1,455 tombstones ≈ 0.6 ms/lookup) and in every test (the query-count guard at `reconciler_test.rb:651` counts queries, which stay linear; it is the rows each query visits that grow).
4. Proposed representation and why it is simpler — a complementary partial index over exactly the rows these lookups ask for, and the one missing word that lets the dir lookup say what it already means:
   ```ruby
   # db/migrate/<ts>_index_node_tombstones_by_path.rb
   add_index :nodes, [:user_id, :storage_path], where: "deleted = true",
             name: "index_nodes_on_user_id_and_storage_path_tombstones"

   # reconciler.rb:605 — `row` was nil, so no PRESENT row sits at this path; only a tombstone can match
   node ||= @user.nodes.where(storage_path: o.rel_path, kind: "dir", deleted: true).order(id: :desc).first
   ```
   - Probe with that index: both revive shapes → `SEARCH nodes USING INDEX …_tombstones (user_id=? AND storage_path=?)`; 200 lookups at 100k rows: 2.47 s → ~0.0001 s. The `present` lookups and the no-op `#live` pluck keep their current plan (the unique partial).
   - Simpler because nothing in the Reconciler's control flow or state changes: F-07's "tombstone lookups stay live queries" decision stands, no second in-memory index has to be kept fresh, and §14a's two tombstone kinds stay distinguished exactly as today (a trash tombstone has a NULL `storage_path`, so it sits in this index under NULL and still cannot match a path lookup). The per-written-node cost the file's comments already claim ("one SELECT per written node", `:281-285`) becomes true of the create path.
   - Alternative: a NON-partial `(user_id, storage_path)` index serves both lookups as written (no edit at `:605`) and needs no bound-parameter implication on Postgres; but in the probe, with no statistics (this repo's production configuration, per `architecture_invariants_test.rb:1240-1247`), the planner moved the no-op `#live` pluck onto it (`storage_path>?` range that also walks scan tombstones) — a small regression on the every-15-minutes path — and it indexes every row.
   - Side benefit, plan-verified only: `Share#trashed`/`S3#trashed` (`share.rb:82`, `s3.rb:145`, `where(deleted: true, storage_path: nil)`) move from the user_id scan to the new index.
5. Smallest credible implementation scope:
   1. New migration + `db/schema.rb` + regenerate `docs/schema-map.html` (`test/schema_map_test.rb` "the checked-in map is the current schema") — these files are S23's (see Cross-subsystem notes).
   2. `reconciler.rb:605` add `deleted: true`; amend the comments at `:599-605` and `:729-732` to name the index.
   3. One test in `test/services/library/reconciler_test.rb`.
6. Regression risks and migration concerns:
   - The `:605` edit is equivalent on every input a pass produces itself (`row` nil ⇒ no present row at that path as of the pluck, and `ensure_dirs` visits each dir path once). It differs only if a web `mkdir` creates a live dir at that exact path between the `#live` pluck and this line: today the query adopts that row; with the term, the insert hits the unique partial index → `RecordNotUnique` → that one ScanJob execution fails, and the next pass sees the row in `#live`. The non-partial alternative avoids even that.
   - Postgres: a partial index is used only when the planner sees the bound `deleted` value (custom plans). Every scannable deployment is SQLite today (`config/deploy.{share,s3,ovh}.yml` set no `DATABASE_URL` → the SQLite branch of `config/database.yml`), and there is no local Postgres; if share/s3 ever run on PG, EXPLAIN both lookups there or take the non-partial variant.
   - Write cost: one more index entry per tombstone (tombstoning is rare relative to scans). Migration: CREATE INDEX over tombstones only — fast. chunk_remote's tombstones (NULL path) are indexed under NULL, harmless.
   - `test/architecture_invariants_test.rb:1267-1310` treats only NON-partial indexes as supersets, so no new prefix pair; with the non-partial variant `index_nodes_on_user_id` is already exempt (`:1262-1265`).
   - Backend legs: all three CI legs run SQLite; no behaviour change, +1 test on each, run counts stay identical.
7. Existing and additional validation required:
   - Must stay green (they pin revive semantics): `reconciler_test.rb:184` (a restored file revives its node_id), `:204` (a move onto a tombstoned path wins over the revive), `:250` (kind change both ways — the reverse pass revives the original FILE tombstone at "thing"), `:624` (tombstoned dir revived, S3 shape), `:651` (no-op query constancy), `s3_observer_test.rb:564`, `scanner_test.rb` ScannerTest, `scan_job_test.rb:12`.
   - New, following `test/services/maker/addon_origin_test.rb:155-171` (skip unless the adapter is SQLite): drive one pass that creates one file and one new directory, capture the two revive statements AND their type-cast binds from `sql.active_record`, `EXPLAIN QUERY PLAN` each with those binds, assert the plan names the new index and does not read `USING INDEX index_nodes_on_user_id (user_id=?)`.
   - Trap to avoid: that precedent's `explain_plan` (`:239-242`) EXPLAINs WITHOUT binds. For a partial index keyed on a boolean, an unbound `?` cannot prove the predicate (probe: literal `0` does not match `deleted = false`; a bound `0` does), so a bind-less EXPLAIN reports the user_id scan even where production uses the index.
   - Mutations: drop the migration's index → both assertions red; remove `deleted: true` at `:605` → only the dir assertion red (so each carries its own weight).
8. Confidence: high that the cost is real and the index fixes it (plans and timings probed; SQLite's partial-index rule). Materiality scales with library size: negligible at the measured real library, minutes at 100k, past the 1-hour semaphore near 240k, hours to days at the 1M–2M-object buckets the S3 phase was built for.

## Opportunity 2: Give the Reconciler's pass state one owner — route its eight `nodes` writes through two `#live`-maintaining helpers, and drop the redundant `@dir_ids`

1. Verdict: recommend
2. Evidence:
   - `reconciler.rb:717-727`: "THE INVARIANT: this mirrors `present`. Every site that tombstones, revives or re-stamps a node maintains it — FIVE of them … an earlier version of this very comment enumerated only four while claiming "every" — probed in review, one stale key. Count them against the code, not against this sentence."
   - `0a160454` closed the missed fifth site (the doomed loop) and changed only `reconciler.rb`: nothing tests the invariant.
   - The write sites, each pairing a DB write with a hand-written mirror update: `:161-164` (doomed files), `:306-313` (file obs at a non-file row), `:327-332` (in-place re-stamp `row.size = …; row.mtime = …; row.content_hash = …`), `:443-455` (move: `live.delete(was)` + new row), `:543-556` (create/revive), `:578-584` (dir obs at a non-dir row), `:607-621` (dir write-back, "THE ONE LINE THAT MAKES THE MEMOIZED INDEX SAFE"), `:665-674` (vanished dirs).
   - Three verbatim 8-field `LiveRow.new(… from node …)` blocks: `:450-453`, `:552-555`, `:618-621`. `LiveRow` is a mutable Struct only "because the write sites below re-stamp the fields they just wrote" (`:59-65`).
   - `@dir_ids` (`:98`) predates `#live`: in `63544ee8` `parent_id_for`'s fallback was a per-file `present.find_by(storage_path: dir)`. F-07 (`c5ca25bd`) added `#live` and writes every observed dir back into it in the same loop that stamps `@dir_ids` (`:595` skip path, `:609` + `:618-621` write path), so for every observed dir both maps hold the same node_id. `parent_id_for` (`:686`) is `@dir_ids[dir] || live[dir]&.node_id`.
   - `:591-594` "THE `@dir_ids` STAMP IS NOT OPTIONAL ON THE SKIP PATH … DB fallback at best, and to nil at worst" describes the pre-F-07 fallback; today the fallback is `live[dir]`, which already holds that very row.
3. Current complexity or invalid states:
   - Three representations of overlapping facts — `present` in the DB, `@live`, `@dir_ids` — synchronized by hand at eight plus two sites.
   - A missed site is silent: the doomed-loop stale key was "harmless today by luck" (`:152-157`), the invariant has no test, and adding a `LiveRow` column means editing four constructors (a `keyword_init` Struct silently defaults a forgotten key to nil).
   - About 45 lines of comments (`:150-160`, `:549-551`, `:591-596`, `:610-617`, `:717-727`) exist to remind writers of obligations the structure could discharge.
4. Proposed representation and why it is simpler:
   ```ruby
   LiveRow = Data.define(:id, :node_id, :kind, :name, :mtime, :size, :content_hash, :parent_node_id) do
     def self.from(n) = new(id: n.id, node_id: n.node_id, kind: n.kind, name: n.name, mtime: n.mtime,
                            size: n.size, content_hash: n.content_hash, parent_node_id: n.parent_node_id)
   end

   # THE ONLY TWO WAYS A PASS WRITES `nodes` — #live mirrors `present` because of that, not by count.
   def write!(node, **attrs)              # create, revive, move, re-stamp
     was = node.storage_path
     node.update!(**attrs)
     live.delete(was) if was && was != node.storage_path
     live[node.storage_path] = LiveRow.from(node)
     node
   end

   def tombstone!(path, node = nil)       # kind collisions, doomed files, vanished dirs
     row = live.delete(path)
     (node || @user.nodes.find(row.id)).update!(deleted: true)
   end

   def parent_id_for(rel) = (dir = File.dirname(rel)) == "." ? nil : live[dir]&.node_id
   ```
   - Each of the eight sites becomes one call. For example `create_or_revive!` becomes `write!(tomb || @user.nodes.new(node_id: SecureRandom.uuid), **attrs)`, and the doomed loop becomes `doomed.each { |n| tombstone!(n.storage_path, n) }`.
   - `ensure_dirs`' skip becomes a bare `next`, and `@dir_ids` and its two stamps are deleted.
   - The invariant becomes a property of the two writers, and the row type becomes immutable because nothing re-stamps it in place.
5. Smallest credible implementation scope: `app/services/library/reconciler.rb` only, all private.
   1. `LiveRow` → `Data` + `.from`, and the pluck at `:737-740` builds through it.
   2. Add `write!`/`tombstone!` and rewrite the eight sites.
   3. Delete `@dir_ids` (`:98`, `:595`, `:609`) and reduce `parent_id_for` (`:683-687`).
   4. Trim the obligation comments.
   - Public surface (`new`, `#call`, `#vanished_paths`) is unchanged.
6. Regression risks and migration concerns:
   - Identical output on every input an observer can produce. It differs only on CONTRADICTORY input: a dir AND a file observation at one rel_path, which S3Observer stopped emitting in `083ce11` and a filesystem walk cannot produce.
     - There a child's parent resolves to the live FILE row at the parent path instead of `@dir_ids`' already-tombstoned dir. Both leave the child unreachable from the tree.
     - Traced two passes by hand: no raise, one live row at the path, the same 4-writes-per-pass oscillation as today, so `reconciler_test.rb:683`'s survival property holds.
     - Requiring `kind == "dir"` in `parent_id_for` is possible but is a behaviour change on partial input, and not needed.
   - Query count unchanged: the no-op path writes nothing, and `tombstone!` takes the already-loaded node in the doomed loop, so no SELECT is added.
   - No data, schema, API or UI change; share and s3 run this one code path; chunk_remote never runs it.
7. Existing and additional validation required:
   - Existing tests that must stay green: `reconciler_test.rb` `:98`/`:110` (rename/move keep node_id), `:119` (edit in place), `:145` (delete tombstones), `:184`/`:204` (revive vs move), `:225` (tree parenting, which is `parent_id_for`), `:239` (vanished dir), `:250` (kind change both ways), `:594`/`:611`/`:624`/`:636` (dir skip, repair and revive), `:651` (no-op query constancy), `:683` (dir+file survival); `s3_observer_test.rb:211` (two-pass stability with a live parent).
   - New property test: one fixture sequence drives a pass through each of the eight sites (new file, edit, rename, delete, revive, file→dir, dir→file, vanished dir). After every `call`, assert `rec.instance_variable_get(:@live)` equals a fresh `present.where.not(storage_path: nil)` pluck mapped through `LiveRow`.
   - Mutations:
     - drop `live.delete` from `tombstone!` → red (exactly `0a160454`'s stale key);
     - drop `live.delete(was)` from `write!` → red on the rename pass;
     - drop the `live[…] =` assignment → red on the create pass;
     - make `parent_id_for` return nil → `:225` red.
8. Confidence: medium. Behaviour preservation is high (traced site by site), but the payoff is preventive: it retires a bug class that has already happened once, plus a redundant map, rather than fixing a live defect.

## Considered and rejected
- **Make the tombstone kind an explicit column/enum (scan vs trash).** The NULL `storage_path` is not an encoding accident: it is the mechanism that makes revive-by-path unable to reach a trash tombstone (`share.rb:403-408`, `s3.rb:503-510`, §14a). An explicit kind would either duplicate that NULL (two representations of one fact) or replace it and make every revive query remember a filter, which re-arms the landmine. The discriminating call sites are S02/S03's.
- **Fold the tombstone lookups into `#live`, or into a second pass-scoped tombstone map** (the in-boundary alternative to Opportunity 1). F-07 decided the lookups stay live (`reconciler.rb:729-732`). A snapshot map is one more hand-maintained mirror, the opposite of Opportunity 2. On contradictory input it would also mint a fresh node per pass instead of oscillating over two rows. The DB index keeps the query live and fresh.
- **Have `vanished_nodes` (`:379-383`) read `#live` instead of re-querying.** Vanished sets are small except in reorganizations, where the per-move UPDATE dominates. F-07 recorded it as deliberately live.
- **`Scanner::Report = Data.define(:observations, :unreadable_dirs)`.** The Reconciler weighs and declines this itself (`:82-83`): one caller, and S3Observer's `unreadable_dirs` is a literal `[]` (`s3_observer.rb:97`).
- **Split `Observation` into a FileObservation/DirObservation union.** `dir` is consumed by two partitions only, and the positional 4-arg form and nil-hash equality are pinned (`reconciler_test.rb:721`).
- **A registry for the per-backend dispatch in ScanJob/TrashPurgeJob** (`observer_for`, `purge_share!`/`purge_s3!`, the serializable-args split at `scan_job.rb:129` / `trash_purge_job.rb:252`). That is four two-arm sites of boring local code, and moving them would be moving branching behind a type. The raise-on-unknown dispatch vs capability-gate split is argued at `scan_job.rb:175-197`. The 2026-08-19 audit rejected the fan-out duplicate as fail-safe.
- **Collapse ScanJob's three post-reconcile steps into a list.** The order is load-bearing and pinned per step (IntakeOrderTest, DiscoveryOrderTest), so this would only save lines.
- **One composed "unobservable path" predicate shared by both observers, both write guards and `ReservedNames`.** The primitives (`OsClutter`, `RepoMetadata`, `TRASH_PREFIX`, `TEMP_PREFIX`) are already single-sourced. The compositions differ on purpose: S3 omits `TEMP_PREFIX`, the guards are one segment stricter at `.git`, and the doors take leaves. A shared predicate would need parameters to restate those differences, and the guard sites are S02/S03's.
- **Unify the two trash reapers.** They are two mechanisms enforcing one rule (`trash_purge_job.rb:7-19`), and the earlier audit rejected the same idea.
- **Simplify `RepoMetadataPurge`** (for example, read `storage_path` instead of walking the parent chain). It is a run-once deploy migration that has already run. Trash tombstones need the chain (their path is NULL). No payoff.
- **Merge `content_hash` (share/s3) and `current_version_id` (chunk_remote) into one content-token column.** This crosses S02/S03/S04/S08, and `current_version_id` is a real version reference on chunk_remote.
- **Stale prose (doc drift, not a simplification; recorded for whoever owns comments):**
  - `reconciler.rb:39-53` (Sync::Mutation, SubtreeDelete, Gc);
  - `reconciler.rb:70-73` and `scanner.rb:91-94` (the deployment default is "Chunk");
  - `scan_job.rb:151-152` (`ENV.fetch("LIBRARY_BACKEND", "chunk")`);
  - `trash_purge_job.rb:69-71` (the operator error names `Sync::Gc`/`Sync::ChunkReaper`, which have not been in this process since 2026-08-25);
  - `reserved_names.rb:5-24` (`chunk_mkdir`, `write_chunk` and `Sync::Commit` no longer exist; the probe table's `chunk` column is the retired embedded backend).

## Cross-subsystem notes
- **S23 (schema):** Opportunity 1's index lives in S23's files (`db/migrate/*`, `db/schema.rb`, `docs/schema-map.html`). The access pattern that needs it is S05's (`reconciler.rb:536-537,605`). Coordinator to dedupe if S23 independently flags `db/schema.rb:507`'s partial index.
- **S03/S05 race (reasoned, not probed): an S3 listing is not a snapshot against concurrent web writes.**
  - The trigger: an object is listed, then trashed by `S3#delete` (or moved by `S3#move` when the listing also saw the destination) before the Reconciler's `#live` pluck. `create_or_revive!` (`reconciler.rb:535-548`) then mints a ghost live node at the old key. (When the listing did NOT see the destination, pairing instead moves the node back to the old key for one pass — the self-healing shape §14f records for the intake race.)
  - Share has the same window but survives it: `hash_for` re-reads the bytes and gets ENOENT (`reconciler.rb:769-777`). S3 observations carry their identity (`s3_observer.rb:510`), so no read happens.
  - On the next pass the ghost is doomed. On a library small enough that one file exceeds 20%, the scan refuses permanently — §14b's ghost shape.
- **Tombstones of both kinds are never destroyed on share/s3** (only with their user, `user.rb:3`, or by the one-shot `RepoMetadataPurge`). The 2026-09-07 share snapshot had 1,455 tombstones against 3,830 live nodes. Every user_id-scoped scan walks them, including the lookups in Opportunity 1. The lifecycle owner is unclear (S02/S03 trash, S06 reapers).
- **`Share#trashed` and `S3#trashed` (`share.rb:82`, `s3.rb:145`) also run as a user_id scan plus a temp B-tree today.** Opportunity 1's partial index would serve them (plan-verified only).
