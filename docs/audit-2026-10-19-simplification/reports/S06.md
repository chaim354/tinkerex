## Opportunity 1: ProjectIntake::Result as one row per inbox file, not three parallel collections + a String|Symbol pun + a side channel
1. Verdict: recommend
2. Evidence:
   - `app/services/maker/project_intake.rb:32` — `Result = Data.define(:attached, :moved, :skipped, :skips, :plan, :status, :conflict_folders)`;
     `:45-48` adds `def initialize(conflict_folders: {}, **) = super` "so the three construction sites in this file and the three
     in project_scan_button_test.rb did not have to change".
   - `:722-737` `#file_all` keeps four accumulators: `moved += 1` and `plan << [ node.name, outcome ]` run in the same branch
     (`:732-733`), and it returns the positional tuple `[ moved, skips.size, skips, plan ]` — `skipped` is literally `skips.size`.
     The tuple is destructured positionally at `:470` (`moved, skipped, skips, plan = LibraryBroadcast.batch(@user) { file_all(inbox) }`)
     and rebuilt by the FetchError rescue at `:746`, which also needs a separate `processed` counter (`:726`, `:735`, `:739`).
   - `:683-687` + `:729` — "#place ANSWERS A STRING (the destination folder) ON SUCCESS OR A SYMBOL (the skip reason) ON FAILURE",
     dispatched by `if outcome.is_a?(Symbol)`.
   - A Symbol cannot also carry the folder, so the conflict arm writes a side channel from inside a rescue: `:849`
     `conflict_folders[node.name] = dest`, a lazily built ivar `:874-878`, surfaced as the 7th member at `:473`.
   - `#call` builds Result four times, three spelling out zeros (`:428`, `:441`, `:455`, `:473`).
   - Consumer, `app/controllers/concerns/project_folder_intake.rb`: `:111-115` scans `skips` pairs for `[name, :conflict]`;
     `:203-206` `intake_result.conflict_folders[filename].presence || Maker::ProjectFolders.folder_for(current_user, filename)` —
     a re-derivation fallback "for a Result built without the map (a test double, an older caller)"; `:217-228` scans `plan` pairs.
   - History: the side channel arrived in 521bfb30 to fix a shipped wrong flash — a board zip filed into `pcb/` while the sentence
     said `archives/`, because `skips` had dropped the folder and the concern re-derived it from the name
     (`test/integration/web/project_folder_intake_test.rb:78-94`). The fix added a parallel hash instead of giving the skip its folder.
   - Hand-built Results: `test/integration/web/project_scan_button_test.rb:129,156,177,199,226,250`; the conflict stub (`:250-262`)
     carries no `conflict_folders`, so its assertion only passes through the fallback.
3. Current complexity or invalid states: the shape can represent `moved != plan.size`, `skipped != skips.size`, a `:conflict` skip
   with no folder, and a `conflict_folders` key with no matching skip. Production keeps them consistent only by construction in one
   method; every hand-built Result must do it by hand. One fact ("file X collided trying folder F") lives in two structures written
   at two moments, and the reader re-derives when the second is absent — the exact derivation that was wrong for board zips.
   The fallback also MASKS a broken side channel: delete `:849` today and only the board-zip test reddens, because for every
   name-keyed destination the fallback recomputes the same folder (reasoned from the code, not run). Readers must know three
   shapes (pairs in `skips`, pairs in `plan`, a name-keyed hash) to answer "what happened to file X".
4. Proposed representation and why it is simpler:
   ```ruby
   # One row per inbox file #file_all reached. `folder`: where it was filed (dry run: would be), or for
   # :conflict where #place TRIED; nil for a refusal decided before a destination existed.
   Filing = Data.define(:name, :folder, :skip) do
     def filed? = skip.nil?
   end

   Result = Data.define(:attached, :status, :filings) do
     def initialize(attached:, status:, filings: []) = super
     def plan    = filings.select(&:filed?).map { |f| [ f.name, f.folder ] }  # same shape as today
     def skips   = filings.reject(&:filed?).map { |f| [ f.name, f.skip ] }    # same shape as today
     def moved   = filings.count(&:filed?)
     def skipped = filings.size - moved
     def conflict_folder(name) = filings.find { |f| f.skip == :conflict && f.name == name }&.folder
   end
   ```
   `#place` always returns a Filing (Collision arm: `Filing.new(name:, folder: dest, skip: :conflict)`); `#file_all` becomes
   `inbox.each { |n| filings << place(n) }` with the FetchError rescue appending `:unavailable` Filings for `inbox[filings.size..]`
   (the `processed` counter and the tuple disappear); `#call` ends `result = Result.new(attached:, status: :ok, filings:)` then
   `record_sweep!(result.moved)` — still below the `unless @move` return, so §14f's "an attach-only pass is not a sweep" holds; the
   early returns become `Result.new(attached:, status:)`. In the concern, `#left_unfiled_by_conflict?` asks
   `!r.conflict_folder(name).nil?` and `#conflict_folder` loses its fallback. Simpler because: one collection, one return type, no
   side channel, no fallback, and counts that cannot disagree with their lists — while `plan`/`skips`/`moved`/`skipped` keep their
   exact current shapes, so `lib/tasks/projects.rake:45-54`, `ProjectIntakeJob#report` (`project_intake_job.rb:135-140`),
   `Projects::ScansController#scan_notice` (`:141-146`) and ~60 test assertions read unchanged. Keep every new name off
   `ENGINE_ASSOCIATIONS` (`test/architecture_invariants_test.rb:116-117` — never `conflicts`). Optional, same rule, not required:
   `ProjectDiscovery::RunResult#created` is always `names.size` (`project_discovery.rb:129-130`).
5. Smallest credible implementation scope:
   1. `app/services/maker/project_intake.rb` — add `Filing`; reshape `Result`; `#place`/`#skip` return Filings; `#file_all` returns
      `Array<Filing>`; `#call`; delete the `#conflict_folders` memo and the comments defending the old shape (32-48, 683-687,
      846-849, 874-878).
   2. `app/controllers/concerns/project_folder_intake.rb` — `#left_unfiled_by_conflict?`, `#conflict_folder` (no fallback);
      `#filed_sentence`/`#unfiled_by_conflict` unchanged (they read `plan` and skip names).
   3. `test/integration/web/project_scan_button_test.rb` — six hand-built Results → `filings:`; the conflict stub carries `folder:`.
   4. `test/services/maker/project_intake_test.rb:512` — assert `result.conflict_folder("Gerber_lamp.zip") == "pcb"`.
   5. `docs/invariants/project-intake.md:383-393` — `Result#conflict_folders` → the conflict Filing's folder; drop "falls back to
      ProjectFolders.folder_for"; keep the "not called `conflicts`" warning for the new names.
6. Regression risks and migration concerns: no schema, no wire format (FilesController's JSON carries the sentence, not the Result —
   `files_controller.rb:869-871`). Pure backend-neutral Ruby: share/s3/chunk_remote run identical code and run counts are unchanged.
   Risks: (a) a missed hand-built `Result.new(moved: …)` raises ArgumentError — loud and test-only; (b) removing the fallback is a
   deliberate behaviour change only for Results built without a folder, i.e. test doubles; (c) the FetchError abort must keep marking
   exactly the unanswered files: `inbox[filings.size..]` equals today's `inbox[processed..]` because one Filing is appended per answered
   file and none for the one that raised; (d) `plan`/`skips` become computed per call — negligible, bounded by MAX_MOVES.
7. Existing and additional validation required: existing pins — `project_intake_test.rb` (moved/skipped/skips/plan across conflicts,
   bad names, refusals, README, working tree, dry run, and the FetchError cases ~886-978 incl. "a move that succeeds once keeps its
   result when a later file aborts the sweep"); `project_folder_intake_test.rb:84-94` (board zip names `pcb/`, never `archives/`) and
   `:111-127` (exact dup.stl conflict sentence); `project_upload_attach_test.rb:140`; `project_scan_button_test.rb:248-262`; the save
   door's conflict tests in `test/controllers/tools/addons_controller_test.rb` (~1120-1200); `project_intake_job_test.rb`. New: replace
   the `conflict_folders` assertion with "a conflict's Filing carries the folder #place tried" (board zip → `pcb`). Mutation that shows
   the new shape carries weight: in `#place`'s Collision arm record `folder: nil` — with no fallback, EVERY conflict-sentence test
   (dup.stl exact string, board zip, scan door) goes red; under today's shape the equivalent mutation (delete `:849`) reddens only the
   board-zip test.
8. Confidence: medium — high that it is behaviour-preserving (one service, one concern, two test files, no backend or schema
   surface); medium on payoff: it removes a side channel, a fallback, a type pun, a positional tuple and two derivable counters — a
   real but local win, not a mechanism change.

## Considered and rejected
- **A closed outcome vocabulary for `Maker::AttachToProject` with an exhaustive table at the doors.** Rejected: the symbols are
  worded at exactly one door, so a registry only moves a `case` behind a type. **DEFECT found while checking it (in boundary, not a
  simplification):** `#refusal_for` answers `:in_working_tree` unconditionally (`attach_to_project.rb:192`) and `#relocate` returns it
  (`:148`), but `Projects::AttachmentsController#relocate`'s exhaustive `case` has no arm for it (`attachments_controller.rb:118-128`)
  → `else raise ArgumentError` → HTTP 500. Introduced by 2217257f, which did not touch the controller. The UI never offers the button in
  that state (`move_conflicts.rb:89`), so it needs a crafted POST or a stale prompt (a `.git` appearing after the prompt rendered); no
  test drives a working-tree refusal through the relocate door (`attach_auto_move_test.rb` covers bundle/elsewhere/not-attached/dir).
  Fix: one `when :in_working_tree` arm plus a test driving every `#refusal_for` symbol through `#relocate`.
- **One adoption policy for the three places that answer "may this folder become a project?"** — the sweep
  (`project_discovery.rb:166-187`: name + own claim), the door (`adoptions_controller.rb:67-162`: name, `Projects/` root,
  own/ancestor/descendant claim, unresolvable chain, working tree), and the folder-view gate (`app/views/files/index.html.erb:32-34`:
  name + root, the root rule spelled a second time). Rejected as a simplification: the view must stay cheap (FilesController#index is
  hot) and applying the working-tree rule to the sweep is a product call. **Divergence worth a targeted fix:** the sweep can adopt a
  direct child of `Projects/` that already CONTAINS an adopted subfolder (adopt `Projects/lamp/firmware` by hand before discovery
  reaches `Projects/lamp`, or a form project's `ensure_path!` claiming an existing folder) — exactly the nesting the door refuses at
  `adoptions_controller.rb:140-143`. A contains-claimed filter in `.adoptable` over a lazily built LibraryTree would close it. Do NOT
  copy the door's `destroy_auto_model` into the sweep: unattended destruction was rejected on purpose (`model_intake/prune.rb:8-13`).
- **Replace `ProjectIntake.owning_project`'s per-level query walk (`project_intake.rb:359-374`) with `Maker::LibraryTree`**, as
  `Tools::AddonsController#owning_project_folder` does (`addons_controller.rb:690-696`). Rejected: it runs inside every upload request
  (`.for_node`), where 2-6 point queries are not obviously costlier than a whole-library dir pluck; both are bounded and cycle-safe.
  (It walks `user.nodes` — through tombstones — unlike every other walk; that is the only source of `.for_node`'s documented "third
  return shape", `:284-288`. Minor.)
- **Replace `#subtree_files`' BFS (+ MAX_DEPTH, `#warn_if_truncated`, WALK_COLUMNS, `#full_records`) with the listing's
  LibraryTree-derived dir set and one files query.** Rejected here: it crosses into S15 (`ProjectFolderListing#collect_dirs`) and changes
  what gets attached (the listing hides dot/build-output dirs) — see cross note 3.
- **Fold `@dry_run`/`@move`/`autofile?` into one mode enum.** Rejected: the only unreachable combination (dry_run && !move) is harmless,
  and an enum removes none of the three checks (`:675`, `:826`, `:897`).
- **Give `Maker::FilingRules` a `#folder_for(name)`** so `ProjectIntake#folder_for` (`:514-516`) and `ProjectFolders.folder_for`
  (`project_folders.rb:118-120`) stop both spelling `fetch(ext_of(name), "other")`. Rejected: two one-liners; the per-instance memo is
  the real reason for the second copy and is documented.
- **One bulk-attach writer on `Maker::FileAttachment`** for `ProjectIntake#attach` (`:666-679`), `AttachToProject#attach_bundle`
  (`:307-344`) and S07's `ModelIntake.attach_all` (`model_intake.rb:152-171`). Rejected: three short sites with legitimately different
  extras (dry run, bundle membership, RETURNING delta, dismissal); the shared part is ~6 lines. See cross note 5.
- **Return a nil-or-chain array from `LibraryTree` instead of yielding the `:broken` sentinel** (`library_tree.rb:42-71, 100-113`).
  Rejected: two private callers, both mutation-checked; cosmetic.
- **Derive `role` instead of storing it on `maker_file_attachments`.** Rejected: not purely derived — the v1 API permits a client-set
  role (`v1/maker/file_attachments_controller.rb:33`) and EntryPhotosController writes `"image"` (`entry_photos_controller.rb:16`);
  a schema + API change.
- **Move FolderDestination's `primary` off the Destination** (`folder_destination.rb:16, 33-38`). Rejected: 39-line concern, one reader.
- **AttachmentReaper's whole-table loads (`attachment_reaper.rb:57-81`) → a SQL anti-join.** Rejected: performance, not
  simplification; the current shape is clear and shared with `Maker::DeadNodes`.
- **Drop `ProjectDiscoveryJob`'s `limits_concurrency`** now that the partial unique index exists (`db/schema.rb:376`). Rejected: one line
  that still saves duplicate work; the index is now the correctness guard (cross note 4 for the stale comment).
- **Dead code:** `Maker::ProjectIntakeJob.nudge` (`project_intake_job.rb:86-90`) has no production caller since ChangelogSync moved to
  `.nudge_parents` (`changelog_sync.rb:124`); only `test/jobs/maker/project_intake_job_test.rb:39-68` calls it. Trivial, below the bar.

## Cross-subsystem notes
1. (S06/S07/S24) **chunk_remote has no discover → file → catalogue sequence.** share/s3 run it inline in `Library::ScanJob#perform`
   (`scan_job.rb:96-98`) because "the order changes the ANSWER" (`docs/invariants/project-intake.md:134-146`,
   `docs/invariants/model-intake.md:88-93, 205-211`; `ModelIntake.claimed_folders` relies on it, `model_intake.rb:126-145`). On
   chunk_remote they are three independent 15-minute recurring entries (`config/recurring.yml:93-95, 158-160, 192-194`) served by 3
   worker threads (`config/queue.yml`), chained only discovery→intake and only when discovery created something
   (`project_discovery_job.rb:45, 80-87`). A folder pushed under `Projects/` can therefore be catalogued as one auto folder model
   before (or while) discovery claims it — the permanent wrong row those docs describe. Not reproduced (read-only audit).
2. (S06/S07) **Discovery's cap leaves the same hole on share/s3.** ScanJob runs discovery capped at MAX_PROJECTS=50
   (`project_discovery.rb:58, 77-78, 94`) and ModelIntake in the same perform; folders beyond the cap that hold a model-role file outside a `models/` subfolder
   are still unclaimed when ModelIntake classifies, become auto folder models, and are adopted on the next scan — project AND model, the
   state `adoptions_controller.rb:197-242` repairs for the door only. One fix for notes 1 and 2: let `ModelIntake.claimed_folders` also
   treat discovery's adoptable candidates (the positional claim; today `private_class_method :adoptable`, `project_discovery.rb:166-188`)
   as claimed, so the catalogue stops depending on discovery's cap or schedule.
3. (S06/S15) **The intake and the project page disagree about what is in a project folder.** `ProjectIntake#subtree_files`
   (`project_intake.rb:573-589`) descends into every live dir and attaches every file; `ProjectFolderListing#collect_dirs` skips dot-dirs
   and node_modules/__pycache__ (`project_folder_listing.rb:320, 343-345`). So the sweep attaches `.git/**` on chunk_remote (those rows
   exist there — `node.rb:20-27`, `repo_metadata_purge.rb:22-25`) and dot/build-output contents on every backend. Those rows are loaded
   by every project card's derived cover (`projects_controller.rb:63`, `home_controller.rb:30`, `public/users_controller.rb:59`,
   `project.rb:198-201`), serialized by the v1 project JSON (`v1/maker/projects_controller.rb:46`) and re-read daily by the reaper
   (`attachment_reaper.rb:57`); the sweep also builds IN lists over the whole subtree (`project_intake.rb:579, 669`) where the listing caps
   its own "on SQLite" (`project_folder_listing.rb:41`). Decide whether the intake should share the listing's hidden-dir rule.
4. (docs/comments) The folder-claim index exists (`db/schema.rb:376`, tinkerex#281) yet three places say otherwise:
   `project_discovery_job.rb:11-15` ("NONE on folder_node_id"), `scans_controller.rb:104-105` and `docs/invariants/project-intake.md:228-231`
   ("open work"). Also `project-intake.md:327-330` says the §14d `port_writable?` count "stays five" (§14d now says one);
   `project_intake.rb:93-103, 463-469` cost the chunk path in embedded-engine terms (`Sync::Mutation.apply`, `Sync::LibraryChannel`,
   `User#next_seq!`) retired by §12.12; `project_intake.rb:599-602` says inbox order decides which files a capped run files, but both caps
   are all-or-nothing per project (`:266/273`, `:320/326`) — order only decides which files become `:unavailable` after a FetchError abort.
5. (S07) `model_intake.rb:152-154` says "insert_all bypasses timestamp autofill, hence the explicit stamps", contradicting
   `project_intake.rb:631-632` and `attach_to_project.rb:321-323` ("insert_all DOES stamp created_at/updated_at"); the three bulk attach
   writers also name the unique index differently (index name vs column list).
6. (S15/S07/S16) `has_many :file_attachments, -> { order(:position) }` (`project.rb:91`, `model.rb:44`, `item.rb:28`,
   `build_log_entry.rb:13`) orders on a column that is 0 for every row the web writes (`attach_to_project.rb:271-277`), so association
   order is plan-dependent on Postgres; `order(:position, :id)` would make it deterministic.
