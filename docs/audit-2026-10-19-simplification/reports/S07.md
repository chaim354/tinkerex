1. Verdict: recommend
2. Evidence:
   - `model_intake.rb:145-150` — `claimed_folders` is import-model `folder_node_id` ∪ project `folder_node_id`: claims that EXIST at the moment of the sweep. `for_user` drops claimed keys before `existing` (`:88-95`). Its own comment delegates the rest to ordering: "Library::ScanJob already runs discovery before this sweep (§14k)" (`:137-138`).
   - The seeded `*` shelf makes `Projects` a shelf (`shelf.rb:13-24`), so every file under `Projects/<x>/` that is not under `models/` keys to `<x>` (`owner_key`, `:255-268`; `library_tree.rb:75-84` chain ends in `nil`).

With 63 project folders, 13 are still unclaimed when `intake_models` runs in the same perform; each holding a mesh becomes an auto folder model; the next scan adopts it.

Order within a tick is not defined. (Reasoned from the code, not reproduced.)
   - Result in both cases: an `origin: "auto"` row keyed on a folder that becomes a project. The claim then only stops accretion (`:89-93`); the row stays listed (`files/models_controller.rb:24, 46`) and keeps its page (`model_folder.rb:35`). That is the "project AND model" state `adoptions_controller.rb:197-242` repairs for its own door only and the docs call permanent (`model-intake.md:205-211`, `project-intake.md:134-146`).
   - The defaults test pins the hole as the seeded behaviour: `model_intake_defaults_test.rb:22` "`cad/mount.stl -> the project is the model, "desk-lamp"`", asserted at `:51` and `:80-81`, with no project row. In production that state appears only through the holes above.

So "project intake before catalog" changes only the timing under the seeded shelves. `scan_job_test.rb:390-396` ("turns this RED with ["desk-lamp"]", re-measured 2026-08-26) now goes red with `[]`. `scan_job_test.rb:653-660` ("verified against BOTH mutations") still holds for the reconcile mutation only: the discover↔intake swap leaves the folder claimed before the catalog runs, so `assert_nil swallowed` (`:673`) stays green and the test fails later.
3. Current complexity or invalid states: in time, a folder under `Projects/` has three states: claimed (a row exists), pending (discovery will adopt it), and unclaimed. Only the first and third are represented. "Pending" is handled by sequencing, and sequencing fails in three ways. It is capped on every backend. It does not exist on chunk_remote. It is described as correctness-critical in five places (`scan_job.rb:239-249, 320-333`; `model-intake.md:88-93, 205-211`; `project-intake.md:134-146`; `recurring.yml:162-166`), backed by two tests whose mutation claims predate the claim rule. The wrong row it produces lasts until someone runs `rake models:prune APPLY=1`.
   The claim FACT has one representation: `maker_projects.folder_node_id`, with the partial unique index at `schema.rb:376`. The catalog consults it in three ways:
   - exact-key pluck sets in `claimed_folders` and `adoptable`;
   - `exists?` in `landing_folder_id`;
   - `find_by` in `FilesController#index:262`.
   The adoption door also walks ancestry both ways (`adoptions_controller.rb:114-162`). Those differences are boring local code. What is missing is the pending state.
4. Proposed representation and why it is simpler: discovery publishes its own positional rule as a read-only set, and the catalog treats it as a claim.
   ```ruby
   # project_discovery.rb (S06's file) — the ONE definition, now public; `adoptable` = this minus claimed
   def self.positional_claims(user)   # every folder discovery owns by position, UNCAPPED
     root = projects_root(user)
     return [] unless root
     user.nodes.present.where(parent_node_id: root.node_id, kind: "dir")
         .pluck(:node_id, :name).select { |_, name| adoptable_name?(name) }.map(&:first)
   end

   # model_intake.rb
   def self.claimed_folders(user, model_keys)
     (user.maker_models.where(origin: "import", folder_node_id: model_keys).pluck(:folder_node_id) +
      user.maker_projects.where(folder_node_id: model_keys).pluck(:folder_node_id) +
      Maker::ProjectDiscovery.positional_claims(user)).to_set   # claimed now, or at discovery's next run
   end
   ```
   A positional claim always becomes a real one: `adoptable` is "unclaimed and `adoptable_name?`". Archiving keeps the claim, and a v1 hard delete is re-adopted on the next sweep (`project-intake.md:32-42`). So "pending" means "claimed later", and the catalog's eventual answer stops depending on job order, the cap, or pull timing on every backend. Discovery-before-catalog drops from correctness to latency. With the claim rule already in place, the only ordering that still changes the catalog's answer under the seeded shelves is reconcile-first. ScanJob keeps its order for latency.
   The policy stays in discovery, so the intent of `model-intake.md:88-93` survives ("ask the claimant, never re-test the path here, keep ProjectDiscovery's policy in one place"). Only its dependence on ScanJob ordering goes. Prune inherits the change through `prune.rb:35`.
   **Verdict on S06's suggestion: the right shape, with two conditions.**
   - (a) It must be discovery's own uncapped reader, never a path test inside ModelIntake. If discovery gains S06's proposed "contains-claimed" refusal, the reader must follow it.
   - (b) It only prevents NEW wrong rows. Rows that predate the claim still need repair: legacy rows, a folder MOVED into `Projects/` while already an auto model, and a top-level folder renamed to `Projects`. Prune repairs them today; Opportunity 2 makes it automatic. Copying `destroy_auto_model` into discovery stays rejected (unattended destroy; S06 already rejected it).
   **Better than the structural alternative** (one sequenced discover→file→catalogue pipeline on chunk_remote, driven by ScanJob and RemoteChangelogPullJob; S01/S06):
   - that pipeline cannot close the cap hole, which exists inside ScanJob's own sequence;
   - at the pull's 2-minute cadence it multiplies the catalog's linear steady-state payload by 7.5, which `model-intake.md:244-248` warns about;
   - it keeps three jobs' correctness tied to their order, which is exactly what broke.
   Optional step 2 uses the same claim set: consult it for every folder between a file and its nearest shelf (`chain[0...index]` in `owner_key`), not only at the key. Today a project adopted by hand three levels down (`3D/Printers/Voron`, key `Printers`) still has its meshes swallowed by the `Printers` folder model through the `model_dirs` arm (`:227-234`). That is a different reach from the door's ancestry checks. This costs no extra query, and the `Projects/*/models` one-file models are unaffected because the nearest shelf is their parent.

## Opportunity 2: An auto model's attachment rows are a function of the plan; let the sweep reconcile them and retire Prune
1. Verdict: recommend
2. Evidence:
   - The sweep only inserts: `model_intake.rb:152-172` is one `insert_all … unique_by`, and nothing in the sweep removes a row.
   - Prune exists only because of that (`prune.rb:3-13`; `model-intake.md:177-192`). Its sole stated premise is that a sweep that deleted would "also delete what a user attached BY HAND through `Models::AttachmentsController#create`".
   - That door has no UI path to an AUTO model:
     - its only caller is `importer_controller.js:106-122`, which posts to the `attach_url` that `ModelsController#create` returns (`models_controller.rb:124-133`), always for a just-created IMPORT;
     - no view references `model_attachment(s)_path` (grep);
     - the detail page's detach link went in fdaa2660 (2026-07-22), a month before auto models existed (085f3fa5, 2026-08-25). `Models::AttachmentsController#destroy` (`:43-47`) has had no UI caller since;
     - the v1 door cannot name a Model (`v1/maker/file_attachments_controller.rb:6-10`);
     - `Maker::AttachToProject` writes only Project rows (`attach_to_project.rb:314`).
   - Prune's guard 3 rests on a premise that moves break. `prune.rb:57-60` says "The sweep can only ever have attached from inside it, so anything else was attached by hand". But a moved file keeps its node_id (`model-intake.md:17-22`). Take a mesh the sweep attached under `Enclosure/` that the user moves to `Lamp/`:
     - the sweep inserts a Lamp row;
     - nothing removes the Enclosure row;
     - Prune keeps it as "outside the model's own folder" (`prune.rb:81`).
     The file is now in both models.
   - Prune skips one-file models entirely (`prune.rb:28-32`). Moving `3D Models/benchy.stl` into `3D Models/Boats/` leaves the one-file `benchy` row holding a LIVE attachment, so it stays listed (`files/models_controller.rb:46` hides only rowless autos) beside `Boats`, which also holds `benchy.stl`.
   - Stale rows are read as membership: `AttachToProject#model_owning` (`attach_to_project.rb:226-230`; oldest row wins, dismissed or stale alike) feeds `#attach_bundle` (`:256-257`). Attaching the moved mesh to a project drags in the OLD model's bundle.
3. Current complexity or invalid states:
   - Four actors own an auto model's rows:
     - the sweep inserts;
     - Prune detaches or destroys on demand, behind four independently mutation-checked guards;
     - the reaper destroys rows on dead nodes;
     - the adoption door destroys the model.
     None handles "the file is live but the plan no longer gives it to this model".
   - Reachable stale states:
     - a file in two models;
     - ghost one-file models;
     - auto models over claimed folders that stay listed (`model_intake.rb:89-93`: "clearing that row out is Prune's job");
     - a rule change that is not self-applying, which is why Prune exists (98 lines, plus `models.rake:12-30`, plus a 121-line test).
   - Steady state: every tick re-sends one `INSERT … ON CONFLICT DO NOTHING` carrying every owned file (`model-intake.md:244-248`). On SQLite that is a write statement, so it takes the write lock to write nothing. `ProjectIntake` avoids exactly this with pluck-and-reject (`project_intake.rb:636-640`).
4. Proposed representation and why it is simpler:
   - **Make the premise structural.** `Models::AttachmentsController#create` refuses an auto model (`return render(json: { error: "auto_model" }, status: :unprocessable_entity) if @model.auto?`). The importer never targets one, so nothing visible changes. An auto model's rows then have one writer, and `maker_models.origin` *is* the "which door wrote this row" column that `model-intake.md:182` says is missing. No attachments schema change is needed.
   - **The sweep reconciles rows for non-dismissed auto models only.**
     - The desired set is `plan.owners` grouped by key, for unclaimed keys. A claimed key, or one absent from the plan, wants ∅.
     - Delete rows whose node is LIVE and not desired.
     - Keep rows on tombstones; that is the reaper's grace window and Prune's guard 2.
     - Keep rows on broken-chain files (Prune's guard 4). For that, `classify` must tell `:broken` from `:no_shelf`; today both are recorded as `:no_shelf` (`:197-201, 255-260`).
     - Insert only the missing pairs.
   ```ruby
   want = plan.owners.group_by(&:last).transform_values { |ps| ps.map(&:first).to_set }
   have = Maker::FileAttachment.where(user:, attachable_type: "Maker::Model", attachable_id: autos.map(&:id))
                               .pluck(:id, :attachable_id, :node_id)
   gone = have.filter_map { |id, mid, nid| id if plan.live.include?(nid) && !plan.broken.include?(nid) &&
                                                 !want.fetch(key_of[mid], EMPTY).include?(nid) }
   # delete_all(gone) when any; insert_all only the (model, node) pairs `have` lacks
   ```
   - An emptied row hides by the EXISTING rule (`files/models_controller.rb:46`, `model_folder.rb:24`) and returns when the plan gives files back. So "hidden, not dismissed" (`model-intake.md:54-60`) holds unchanged, and this is not a second reaper: the reaper's population is dead nodes, this one is live nodes. Import rows and dismissed rows are never touched, and no model is ever destroyed.
   - Simpler because:
     - each row population has one owner: the sweep for live nodes on auto models, the reaper for dead nodes;
     - `prune.rb`, the `models:prune` task and its test go;
     - "a rule change here is not self-applying" stops being true;
     - the steady state becomes one SELECT and zero writes.
   - With Opportunity 1 in place, ScanJob's post-reconcile order becomes purely a latency choice even under non-default shelves: a stale attachment written in the "wrong" order is removed by the next sweep.
5. Smallest credible implementation scope:
   1. `app/controllers/models/attachments_controller.rb`: the auto guard. Optionally delete the UI-less `#destroy` and its route.
   2. `app/services/maker/model_intake.rb`:
      - `classify` also returns the live file set and the broken-chain set;

   4. Delete `app/services/maker/model_intake/prune.rb`, `lib/tasks/models.rake:12-30` and `test/services/maker/model_intake_prune_test.rb`.
   5. Prose:

      - `adoptions_controller.rb:203-218`, which cites Prune (S06's file; behaviour unchanged).

The argument is code evidence that the only hand door is unreachable for auto models, plus the guard that makes that structural. It never destroys a model. The rows it deletes are pure functions of the plan: position 0, no label or version (`model_intake.rb:162-164`). A wrong deletion is re-derived by the next correct sweep. **It needs the owner's sign-off.**

## Considered and rejected
- **Model state as a discriminated union** (`kind: import|auto_folder|auto_file` plus one node id, replacing `origin`/`auto_node_id`/`folder_node_id`/`dismissed_at`).
  - The columns do permit invalid rows: an import with `auto_node_id`, an auto with no key, a dismissed import, a folder auto with folder ≠ key.
  - But each column has one writer that never produces them: ModelIntake writes origin, key and folder together (`model_intake.rb:105-117`); `dismissed_at` is written only for autos (`models_controller.rb:158-159`); the folder is set only at import (`model.rb:82-90`, `models_controller.rb:197`).
  - The two node columns are a recorded deliberate split (`model-intake.md:151-158`; `adoptions_controller.rb:224-230`).
  - The reachable contradictions are between tables, not within a row; those are Opportunities 1 and 2. A migration on three live databases would buy nothing.
- **`print_status` derived-only from print runs:** the manual override is deliberate (`print_run.rb:1-5`) and pinned (`print_run_test.rb:39-45`).
- **Merging `Maker::Item` into `Maker::Model`, or including `Maker::Taggable` in Item:** settled by tinkerex#153 (`model-intake.md:253-283`). Item is wire-only (`item.rb:8-14`; the v1 items and collections controllers are its only readers). Taggable excludes Item on purpose (`taggable.rb:8-10`). Stylistic.
- **Shared partial for the destroy-button branch** duplicated at `models/show.html.erb:27-34` and `files/_model_strip.html.erb:48-55`: real duplication with a recorded shipped bug, but it is 8 lines and both copies are pinned (`models_catalog_test.rb:128-146`, `model_strip_test.rb:54`).
