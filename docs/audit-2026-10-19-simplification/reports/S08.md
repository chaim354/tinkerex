## Opportunity 1: One owner for "does this row need a job?" — the STALLED_AFTER heal is unreachable from every door that renders a wedged row

1. Verdict: recommend

2. Evidence
- The lifecycle decision is written once, inside `Enqueue.call` — enqueue.rb:91-98:
  `stalled = preview.persisted? && %w[pending processing].include?(preview.status) && preview.updated_at < STALLED_AFTER.ago`
  / `return preview unless preview.new_record? || content_moved || rebuilt || preview.status == "failed" || stalled`.
- It is documented as reached by the read paths: enqueue.rb:46-48 ("the 15-minute scan, `backfill_thumbnails`,
  `#show` and the addon door all no-op'd on it forever"), :53-57 ("`backfill_thumbnails` calls this once per row on
  every Files page render … a wedged row self-heals on the next scan at the latest"); measure-view.md:320-333
  repeats it ("the backfill calls `Enqueue` per row on every Files render").
- But every lazy door decides first, with a coordinates-only copy (status-blind by the rule at enqueue.rb:182-189),
  and never calls `call` for a coordinate-current row — so it never reaches the `stalled` arm:
  - thumbnail_map.rb:140 `next if fi.content_token.nil? || map.current?(node_id)`; :161
    `def current?(node_id) = !thumb(node_id).nil?`; :108-117 keeps every coordinate-current row whatever its status.
  - files_controller.rb:1231-1234 `row = …current_preview(…)` / `return row if row` (file page AND inspector).
  - files_controller.rb:467-483 `#geometry` enqueues only `if preview.nil?`.
  - public/files_controller.rb:161-163 `return if …current_preview(…)` before `Enqueue.call`.
  - missing_backfill.rb:89-90,109 `pluck(:node_id, :version_id, :renderer_revision)` / `next if seen.include?(…)`.
  - reconciler.rb:313-318 skips an unchanged file (`next true`); it enqueues only at :166 (create/revive) and :340
    (content changed). config/recurring.yml has no preview sweep.
- So the only callers that can heal a current wedged row are `V1::Maker::PreviewsController#create`
  (previews_controller.rb:53, unconditional) and an eager door re-writing identical bytes. The tests agree: every
  stall test calls `Enqueue.call` directly (enqueue_test.rb:188-243); the one door-level stall test is the v1 API
  (previews_renderer_revision_test.rb:105). inspector_test.rb:105-107 even says a `failed` row is "the ONE state
  where the two spellings differ" — a stalled row is a second one nobody listed.
- It was already so when the heal shipped: at c3bc2f57, `backfill_thumbnails` skipped `existing` rows
  (`next if token.nil? || existing.key?([node.node_id, token])`, `thumbnails_for` status-blind) and
  `current_thumbnail` already did `return row if row`.
- Wedge producers that still exist: generate_preview_job.rb:65-70 (`retry_on FetchError … attempts: 5`; "the
  preview stays non-terminal ("processing") so a later manual/scheduled re-enqueue can still succeed") — an
  unmounted share (Share#read answers the retryable FetchError when the root looks unmounted,
  generate_preview_job_test.rb:457-466), an S3 credential/endpoint blip, or an unreachable sync server during any
  backfill burst; a job lost between claim and :90; and the start write itself, :90
  `preview.update!(status: "processing", error: nil)`, which is not compare-and-set (it writes through the object
  loaded at :75, so a superseded job can flip a newer `ready` row back to `processing`).

3. Current complexity / invalid states
- `pending`/`processing` are unverified assertions ("a job is coming"). The verifier exists but only `call` holds
  it; five doors re-decide "does this row need a job?" with a weaker copy that drops `stalled` (and, on purpose,
  `failed`). A row wedged on current content therefore stays wedged until its content or renderer revision moves:
  every grid view spins 40 polls (~80 s) then thumbs_controller.js:46/111-113/130 resolves it to "Preview not
  supported" (a wrong label); the file page sits on "Generating preview…" (show.html.erb:98); `rake
  previews:backfill_missing` reports 0.
- The read doors' deliberate "never retry `failed` from a read" policy (inspector_test.rb:110-126;
  public/files_controller.rb:112-118 and :154-157; files-preview.md:612-620) exists only as an emergent side-effect of
  those pre-filters — which is how the `stalled` arm was lost along with it.

4. Proposed representation — one predicate, with the read policy as a named argument
```ruby
# enqueue.rb — THE answer, used by `call` and by every caller that already holds a row
def needs_job?(preview, version_id:, revision:, retry_failed: true)
  return true if preview.nil? || preview.new_record?
  return true if preview.version_id != version_id || preview.renderer_revision != revision
  return retry_failed if preview.status == "failed"
  %w[pending processing].include?(preview.status) && preview.updated_at < STALLED_AFTER.ago
end

def call(user:, node_id:, name:, version_id:, kind: "thumbnail", skip_unrenderable: true, retry_failed: true)
  …
  return preview unless needs_job?(preview, version_id:, revision:, retry_failed:)
  …                                   # repoint / restamp / perform_later exactly as today
```
- `FilesController#current_thumbnail` → one `Enqueue.call(…, retry_failed: false)` (it returns the existing row when
  nothing is needed — the same row the two-step returns today, minus one query on a miss).
- `Public::FilesController#enqueue_geometry` → `Enqueue.call(…, retry_failed: false)`, guard deleted.
- `ThumbnailMap.backfill!` → `next unless Enqueue.needs_job?(map.thumb(id), version_id: fi.content_token,
  revision: Enqueue.revision_for_name(fi.name, "thumbnail"), retry_failed: false)` (in memory; a query only for a
  row that actually needs a job).
- `MissingBackfill` → load the batch's rows (`index_by(&:node_id)`, still one query per batch) and ask the same
  predicate, replacing the hand-kept triple whose own comment (missing_backfill.rb:16-17) warns it must be edited in
  step with `current_preview?`.
- `FilesController#geometry` → enqueue `if preview.nil? || Enqueue.needs_job?(preview, …, retry_failed: false)`
  (collapses to one `Enqueue.call` once Opportunity 2 lands).
Why simpler: one transition table instead of one plus five partial restatements; the read-door policy is a
parameter instead of an accident of each pre-filter; `current_preview?` stays status-blind (enqueue.rb:182-189
untouched); the window and restamp (enqueue.rb:118-124) do the stampede-prevention job they are documented to do.

5. Smallest credible implementation scope (in order)
1. enqueue.rb: extract `needs_job?`, add `retry_failed:` (default true → behaviour-neutral for all 9 callers).
2. thumbnail_map.rb `backfill!`. 3. missing_backfill.rb. (all three in S08)
4. Call sites: files_controller.rb `#current_thumbnail`, `#geometry` (S10's file); public/files_controller.rb
   `#enqueue_geometry` (public row).
5. Correct the factual claims in enqueue.rb:43-63 and measure-view.md:320-333 (S09's doc) — the rule stands, the
   list of doors that reach it was wrong.

6. Regression risks and migration concerns
- Writes-on-GET grow only for rows already ≥15 min in flight; each heal restamps (enqueue.rb:124), so ≤1 job per row
  per window per door, and ThumbnailMap's BACKFILL_LIMIT still bounds a render. A share unmounted for days re-tries
  each wedged row it renders once per 15 min (5 backed-off attempts each) — the trade enqueue.rb:59-62 already accepts.
- The polled doors keep their no-write rule: `#thumbnails` stays `backfill: false` and never asks the predicate; the
  public geometry poll (public/files_controller.rb:122-150) stays read-only.
- `retry_failed: false` must be passed at every read door, or a `failed` row re-renders on every view (the S4-5
  asymmetry). Pinned for the inspector (inspector_test.rb:110) and the public page.
- No schema, wire or UI change; identical on share/s3/chunk_remote (version_id is the port's content_token on all).

7. Validation
- Must stay green: enqueue_test.rb:188-243 (window, processing, restamp); inspector_test.rb:110 (failed never
  re-enqueued); maker_page_thumbnails_test.rb:137 (current row shown, nothing enqueued); thumbnail_map_test.rb:255
  (query constancy); missing_backfill_test.rb:122; previews_renderer_revision_test.rb:105.
- New, request-level (the repo's own lesson, maker_page_thumbnails_test.rb:4-10), all RED today:
  (a) `get files_path(folder:)` re-enqueues a coordinate-current thumbnail row created at `processing` inside
  `travel_to 3.days.ago`; (b) `get file_path(node)` does the same; (c) `MissingBackfill.call` returns 1 for it;
  plus the negative (d): a row made `processing` now is NOT re-enqueued by (a)/(b).
- Mutations: delete the stall line from `needs_job?` → (a)(b)(c) red; drop `retry_failed: false` at
  `current_thumbnail` → inspector_test red; drop the restamp → a second page load enqueues again.
- Extend missing_backfill_test.rb:122's "agreement" test with `failed` and stalled fixtures (it asserts only `ready`,
  which is the one state where the sweep and `Enqueue` already agree).

8. Confidence: high — every pre-filter read at HEAD and at c3bc2f57; the only door-level stall coverage is the v1
   API. Not executed (read-only brief), so (a)-(c) being red today is reasoned from the code, not run.

## Opportunity 2: `ready` means two things during a renderer rebuild — give that window its own status and name the status classes once

1. Verdict: recommend

2. Evidence
- enqueue.rb:100-117: a renderer-only rebuild stamps the NEW revision (`preview.renderer_revision = revision`) and
  leaves `status` alone (`preview.status = "pending" if preview.new_record? || content_moved || preview.status ==
  "failed"`), so the row reads (current token, current revision, `ready`) while asset/metadata/width/height were built
  by the old revision. The coordinates are the job's TARGET (generate_preview_job.rb:87 `target = [ preview.version_id,
  preview.renderer_revision ]`), yet every reader treats them as the artifact's provenance (enqueue.rb:157-159 "was it
  made by the CURRENT CODE?").
- Private Measure door, files_controller.rb:467-492: the first GET finds no current row → `Enqueue.call` → "pending".
  The client polls again 250 ms later (measure_controller.js:49 `POLL_DELAYS_MS = [250, …]`, :152-169); now
  `current_preview` matches (Enqueue stamped the revision) and `case preview.status when "ready"` returns the OLD
  build's `url_for(preview.asset)` until the job reaches generate_preview_job.rb:90. The door's own comment
  (files_controller.rb:477-478) says reading status "would hand back the stale blob URL — exactly the bug the revision
  check exists to stop"; measure-view.md:286-291 makes the same claim; lbrn_geometry_test.rb:133 asserts only the
  first response.
- Public: `#view` enqueues at render (public/files_controller.rb:74, :158-167), so the visitor's FIRST poll (:128-142)
  and `#preview` (:94-97) can already serve the older build.
- The window is the job's queue wait: config/queue.yml runs one worker, 3 threads, `queues: "*"`; any backlog (the
  100-job ThumbnailMap backfill from the Library page just visited, a scan import, `previews:backfill_missing` after a
  bump) holds it open for seconds. Geometry revisions do move (lbrn_geometry.rb:48 `FORMAT_REVISION = 5`; bumps in
  d5c662c6, cc2340ff, 5ce97ac0, f55a7f45) — each bump re-opens the scar measure-view.md:343-348 records ("four
  already-measured files kept serving mangled curves").
- A lost rebuild is permanent: `ready` is not in the stall set (enqueue.rb:95), MissingBackfill's triple calls it
  covered (missing_backfill.rb:109), ThumbnailMap calls it current — an older build served as current, forever.
- The picture is not actually kept through a rebuild: the job's start write (generate_preview_job.rb:90) flips the row
  to `processing`, which files/_thumb.html.erb:28, viewers/_static.html.erb:20 and _measure.html.erb:172 render as a
  spinner for the whole render — contradicting enqueue.rb:113-116 ("the old artifact stays visible until the job swaps
  it") and measure-view.md:278-285.
- An `unsupported` row hit by a renderer bump keeps the terminal `unsupported` while its job runs (same branch).
- The status→display classification is hand-spelled ~15 times: `status == "ready" && asset.attached?` at
  application_helper.rb:52, files/_thumb.html.erb:26, viewers/_static.html.erb:18, _measure.html.erb:170,
  _model3d.html.erb:39, _gerber.html.erb:63, public/_project_card.html.erb:31, public/projects/_page.html.erb:141,
  files_controller.rb:386, public/files_controller.rb:97; `%w[pending processing]` at _thumb.html.erb:28,
  _static.html.erb:20, _measure.html.erb:172, show.html.erb:98, enqueue.rb:95. preview.rb:19 has `STATUSES` and no
  classification (its `ready` scope, :30, has no caller).
- show.html.erb:188-193 renders the thumbnail row's `metadata` (Laser/CNC panel) with no status check, so after a
  CONTENT change it shows the previous content's settings beside the pending poll — the `pending` rule applied to the
  picture and not to the rest of the artifact.

3. Current complexity / invalid states
One string column encodes both "what is in flight" and "what the attached artifact is", so "artifact is an older
build of these coordinates, rebuild queued" is indistinguishable from "artifact matches these coordinates". Every
reader re-derives meaning from literals; the one reader that must refuse an older build (Measure, both doors) cannot
tell, and the one row that should stall-heal (a queued rebuild) cannot.

4. Proposed representation — the missing discriminant, plus the three classes named once
```ruby
# preview.rb
STATUSES  = %w[pending processing rebuilding ready failed unsupported].freeze
IN_FLIGHT = %w[pending processing rebuilding].freeze          # a job is believed coming; STALLED_AFTER applies
def in_flight?     = status.in?(IN_FLIGHT)
def showable?      = status.in?(%w[ready rebuilding]) && asset.attached?   # a picture OF THIS CONTENT, any build
def current_build? = status == "ready" && asset.attached?                  # what a data consumer (Measure) needs
```
- Enqueue: new / content moved / failed → `pending` (unchanged); renderer-only rebuild → `rebuilding` if
  `showable?`, else `pending` (covers the `unsupported` case); stall set = `IN_FLIGHT`.
- Job: start transition `pending → processing` only, written through `commit_if_current` (which also closes the
  non-CAS start write); `rebuilding` stays while rendering; terminal writes unchanged.
- Readers: picture surfaces ask `showable?`; data surfaces ask `current_build?`. Both geometry doors need NO code
  change — their `case … when "ready"` already sends every other status to "pending". `#thumbnails` answers
  `{status: "ready", url}` for a showable row, so thumbs_controller.js is unchanged; v1 `preview_json` maps
  `rebuilding` → `"ready"` to keep the wire behaviour pinned at previews_renderer_revision_test.rb:97.
Why simpler: each value means one thing; measure-view.md:286's "a consumer that cannot tolerate an older build says so
itself" becomes `current_build?` instead of an argument about when status may be read; ~15 literal classifications
become three predicates; with Opportunity 1 the private `#geometry` special-casing (files_controller.rb:450-483, the
current_preview → nil → Enqueue → early-return dance and its comment) reduces to one `Enqueue.call(…, retry_failed:
false)` plus the existing `case`. "Content repoint blanks; renderer rebuild does not" (measure-view.md:278) and "do
not unify" (:291) both hold — better than today, since the picture now survives the render too.

5. Smallest credible implementation scope (in order)
1. preview.rb: `rebuilding`, `IN_FLIGHT`, three predicates (behaviour-neutral while nothing writes `rebuilding`).
2. Move consumers onto the predicates, still behaviour-neutral: application_helper.rb#preview_src, the seven partials
   above, files_controller.rb#thumbnails, public/files_controller.rb#preview (thumbnail kind `showable?`, geometry kind
   `current_build?`), v1 previews_controller.rb#preview_json — cross-row files (S10/S22/public/v1).
3. enqueue.rb writes `rebuilding`; 4. generate_preview_job.rb start transition.
5. Optional: show.html.erb:188 gates the settings panel on `showable?`. 6. Docs: enqueue.rb:102-116, measure-view.md:278-291.

6. Regression risks and migration concerns
- Ordering: a consumer still comparing `status == "ready"` when step 3 ships renders _thumb's terminal "Preview not
  supported" badge during a rebuild (visible wrong label, not data loss). Do step 2 first and add a grep/template guard
  refusing raw `"ready"` comparisons on a preview outside the model.
- Wire: v1 clients (tinkerex-client) keep seeing `ready`; check the sibling before exposing `rebuilding` instead.
- No migration: `status` is a plain string with a model-level inclusion (schema.rb:312, preview.rb:23); rows mid-rebuild
  at deploy keep today's behaviour until their jobs land.
- Backend-neutral (all three legs); `Public#preview` serves both kinds by param, so it needs the one kind split above.

7. Validation
- Representation pins to update (they assert the raw string, not the behaviour): enqueue_test.rb:93,
  thumbnail_map_test.rb:244, lbrn_geometry_test.rb:215, previews_renderer_revision_test.rb:96 → `rebuilding` (keep
  :97's wire `"ready"`), each paired with a behavioural assertion (the page still renders `.thumb img`/the poster).
- New, RED today: lbrn_geometry_test — a stale-revision `ready` geometry row with a JSON asset; GET (enqueues →
  "pending"); GET again without performing jobs → today `"ready"` + the old URL, must be `"pending"`. Public twin: GET
  `#view`, then GET public geometry → `"pending"`. Mutation: revert Enqueue's `rebuilding` branch → both red.
- New: a `rebuilding` row stays `showable?` while its job renders (hook `render` as generate_preview_job_test.rb:76
  does); a `rebuilding` row aged past STALLED_AFTER is re-enqueued (through a page render once Opportunity 1 lands).
  Mutation: drop `rebuilding` from `IN_FLIGHT` → red.
- Must stay green: lbrn_geometry_test.rb:155, :219, :241 (content axis blanks), maker_page_thumbnails_test.rb:112-137,
  failed_preview_tile_test.rb:41, public_preview_test.rb:125-175.

8. Confidence: medium-high on the defect (traced line by line, not run); medium on the exact shape (the status name,
   the v1 mapping, whether to gate the settings panel).

## Considered and rejected
- Folding `stalled` (or any status) into `Enqueue.current_preview?` — smallest diff for Opp 1, but violates
  enqueue.rb:182-189 ("DO NOT FOLD `status` INTO EITHER OF THESE") and makes "which row is current" clock-dependent.
- Desired/observed split (wanted_version_id/wanted_revision/wanted_at; artifact coordinates written only by the job) —
  the textbook model for Opp 2, but a migration plus a change to what v1's `version_id` means, for what one status
  value and three predicates achieve.
- Geometry-only blanking in Enqueue (`rebuilt && kind == "geometry"` → pending) — closes the Measure window in one
  line, but puts a consumer's policy in the shared writer against measure-view.md:286-291, and leaves `ready`
  overloaded (lost rebuild unhealable, picture still blanked during processing).
- Stamping the build onto the asset blob's metadata for the geometry doors to compare — hides a third coordinate where
  no query or sweep can see it; fixes only the geometry read.
- Deriving `Registry::RENDERERS` from each renderer's `EXTENSIONS` (the keys are exactly their union today) — removes a
  doubled list, but renderer_contract_test.rb:61-69 already reddens the harmful drift direction and the registry hash
  is where the per-extension reasoning lives; line-count only.
- A shared renderer base module for the optional `available_for?`/`payload_revision`/kwarg capabilities
  (registry.rb:155-173, enqueue.rb:139-143) — moving two-line `respond_to?` fallbacks behind a type; not material.
- `Registry.render`'s `method(:render).parameters` introspection (duplicated in renderer_contract_test.rb:90-95) —
  small, local, deliberate (keeps simple renderers' signatures); not material.
- Collapsing `pending`/`processing` — no server reader distinguishes them, but `processing` is v1 wire and its start
  write refreshes the stall clock; minor gain for a wire change.
- `ThreeMf::THUMBNAIL_REVISION` kept in lockstep with `Stl` by hand — a relationship pin exists (stl_test) and the
  embedded-thumbnail branch could legitimately diverge; not material.
- The job's exception→status mapping (Unsupported / FetchError / StandardError, renderers raising the job's
  `Unsupported`) — argued at mesh.rb:47-68, clean; left alone.
- DeadNodeReaper loading every preview of a user weekly (dead_node_reaper.rb:42) — DB-only, weekly, fine at this scale.
- Deleting app/views/active_storage/blobs/_blob.html.erb (recorded unreachable, config/application.rb:41-45) and
  preview.rb:30's unused `ready` scope — dead-code removal, not a representational change.
