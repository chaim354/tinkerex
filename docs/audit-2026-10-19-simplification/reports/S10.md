## Opportunity 1: One bounded content-read door for the two zip readers — cache what the bytes said, never what the port said
1. Verdict: recommend
2. Evidence:
   - app/services/maker/gerber_archive.rb:83-97 — `for` gates on `node.size`, derives `token = node.content_hash.presence || node.current_version_id.presence`, then `Rails.cache.fetch([ "gerber-archive", node.node_id, token ], expires_in: CACHE_TTL) do read(user:, node:) end`; `read` is `listing_from(FileLayer.current.read(...))` with `rescue FileLayer::NotFound, FileLayer::FetchError` → nil. The port failure becomes nil INSIDE the cache block.
   - app/services/maker/three_mf_manifest.rb:86-107 — the same wrapper (its header, :21, calls it "Maker::GerberArchive's shape and its argument"), `rescue FileLayer::FetchError` → `Current.library_unreachable = true; nil`, `rescue FileLayer::NotFound` → nil, again inside the block.
   - activesupport 8.1.3.1 cache.rb:1123 — `write(name, result, options) unless result.nil? && options[:skip_nil]`: a nil block result IS written. No `skip_nil` anywhere (config/cache.yml; production.rb:108 `:solid_cache_store`, which persists across deploys). CACHE_TTL is 30.days in both classes.
   - The repo already records the rule this breaks: app/services/maker/addons/registry.rb:159-161 — "A fetch failure returns [] for THIS request and caches nothing — rescuing outside `Rails.cache.fetch` is deliberate. Rescuing inside would cache the empty result, so a two-second blip would grey every addon out for the whole TTL."
   - The two copies have already diverged: GerberArchive's FetchError arm (gerber_archive.rb:95) does NOT raise `Current.library_unreachable`, although it degrades output exactly like the four setters app/models/current.rb:10-13 / CLAUDE.md §14d (last bullet) list; commit 9f395929 split Readme/RepoCard/GerberSets/ThreeMfManifest and missed this reader.
   - The suite cannot see it: config/environments/test.rb:47 is `:null_store`; three_mf_manifest_test.rb:265 says so ("The test cache is the null store, so each `for` really reaches `read`"); the two MemoryStore cache tests (gerber_archive_test.rb:259, three_mf_manifest_test.rb:310) feed only parser-nil inputs ("firmware.zip", "not an archive"); GerberArchive has no FetchError test at all.
   - A consumer reasons from the wrong premise: app/services/maker/project_intake.rb:531-534 — "AN UNREACHABLE LIBRARY ANSWERS 'not a board' … That costs nothing: the move that follows raises the same FetchError one line later … so the zip is never filed to the wrong place".
3. Current complexity or invalid states: `nil` from `.for` stands for five facts — wrong name and over/unknown size (both answered before the cache), "the bytes say no" (cached — correct, and the recorded intent: files-preview.md:171), "the store did not answer" (cached — wrong), "the path is not there right now" (cached — wrong). The last two are facts about one REQUEST persisted as facts about the CONTENT for up to 30 days, under a key that does not change when the store comes back:
   - a Gerber zip whose page is opened during an outage (unmounted share, S3 5xx, sync server restarting) renders as a plain `:thumbnail` instead of the board on both file pages;
   - a 3MF opened during one loses its slicer colours and unit factor on the file, public and model pages (models_controller.rb:86) — an inch/metre export then measures 25.4x/1000x short;
   - ProjectIntake: an outage during sweep N caches "not a board"; sweep N+1, store back, files the board zip into the source-archive folder instead of pcb/ — a real move on the maker's NAS that the comment above says cannot happen (reached by reading, not reproduced: read-only audit);
   - NotFound is not a content fact either: Share#read answers NotFound for ENOENT with the root mounted (share.rb:114-118), which is also the stale-path window after an outside move until the next scan pairs it — and pairing keeps node_id AND content_hash, so the cached nil outlives the repair.
   Plus the wrapper (size gate, token, key, read, rescue split) and its test helpers (`counting_reads`, `with_memory_cache`) are each written twice and have already drifted once.
4. Proposed representation — one door owns the wrapper; the cache stores only what the PARSER answered (nil included); a port failure is this request's answer and is never written:
   ```ruby
   module Maker
     module ContentRead # name illustrative
       def self.cached(namespace, user:, node:, limit:, ttl:)
         return nil if node.size.nil? || node.size > limit

         token = node.content_hash.presence || node.current_version_id.presence
         Rails.cache.fetch([ namespace, node.node_id, token ], expires_in: ttl) do
           yield FileLayer.current.read(user, node_id: node.node_id) # only the parse result is stored
         end
       rescue FileLayer::FetchError # OUTSIDE the fetch: nothing is written (Registry.manifests' rule)
         Current.library_unreachable = true
         nil
       rescue FileLayer::NotFound
         nil
       end
     end
   end
   # GerberArchive.for:   return nil unless archive?(node.name)
   #   ContentRead.cached("gerber-archive/2", user:, node:, limit: READ_LIMIT, ttl: CACHE_TTL) { |b| listing_from(b) }
   # ThreeMfManifest.for: the same with "threemf-manifest/2" and manifest_from. Both `self.read` methods go.
   ```
   Simpler because the cache rule and the banner rule are stated once; each reader keeps only its name test, its bound and its pure parser; and a nil in the cache means exactly one thing. The parsers keep their own narrow rescues — the door rescues only the port's two classes, so a NoMethodError stays loud.
5. Smallest credible implementation scope: (a) new app/services/maker/content_read.rb; (b) gerber_archive.rb:83-97 → the door, delete `read`; (c) three_mf_manifest.rb:86-107 → the door, delete `read`; (d) bump both cache namespaces so nils already poisoned in production's Solid Cache stop being served (otherwise they live up to 30 more days); (e) prose: app/models/current.rb:10-13 setter list, both class headers, docs/invariants/files-preview.md:171 and :518 ("nil cached" → "nil from the bytes cached; a port failure never"). Call sites unchanged: files_controller.rb:537-546, public/files_controller.rb:57-60, models_controller.rb:86, project_intake.rb:547.
6. Regression risks and migration: during an outage each zip/3MF page view re-attempts one bounded read instead of serving a poisoned hit — on chunk_remote one Transport failure per view, the cost Readme/GerberSets already pay uncached. Zip pages begin raising the unreachable banner on FetchError (what §14d's rule implies). The namespace bump costs one read per zip/3MF on first view after deploy. No schema/API change. Backend legs: the readers go through the port on all three; the existing suites pin share and the new tests stub the adapter's `read`, so they are leg-neutral.
7. Validation: must stay green — gerber_archive_test.rb:182, :194, :207, :259; three_mf_manifest_test.rb:255, :266, :290, :310 (parser-nil is still cached). New, for each reader (or once at the door): under a MemoryStore, make the adapter's `read` raise FetchError → `.for` is nil and `Current.library_unreachable` is set; remove the stub → `.for` returns the real Listing/Manifest and `counting_reads` records a SECOND read; repeat with NotFound (no banner). Mutation 1: move the rescue back inside the `Rails.cache.fetch` block (today's shape) → the second call answers the cached nil → red. Mutation 2: delete the banner line → the new GerberArchive banner assertion reds (it has none today). Optional end-to-end for the intake owner: one sweep whose zip read raises, then a clean sweep → the board zip lands in pcb/.
8. Confidence: high on the defect (read off the code and the gem source; the test cache is the null store, so nothing in the suite exercises it); high that one door beats two diverged copies; medium only on placement/naming — the fallback is to move each rescue outside its `fetch` in place (two small edits plus the missing banner arm), which fixes the bug but keeps two copies to drift.

   - The public copy is unpinned: gerber_preview_test.rb:184 pins the zip board on the private page only; public_file_view_test.rb covers a .gbrjob (:99) and a single layer (:119) but no zip and no 3MF colours/unit (files_flow_test.rb:293-322 pins those on the private page).

3. Current complexity or invalid states: five ivars (@kind, @gerber_archive, @gerber_layers, @gerber_single, @viewer_manifest) whose valid combinations are fixed by one rule but assembled twice. Wrong-but-representable states are avoided only by convention (kind :gerber with nil layers would raise in `_gerber`'s `layers.empty?`; a provisional kind can be read mid-action). Any change to the zip rule, the single/stack rule or the manifest defaults must land in two controllers and two templates, and the public half has no test that would notice a miss.
4. Proposed representation:
   ```ruby
   # FilePreview
   Viewer = Data.define(:kind, :gerber_layers, :gerber_single, :colors, :unit_factor)

   def viewer_for(user:, node:, url:)
     archive = Maker::GerberArchive.for(user:, node:)       # nil unless a zip whose BYTES are a board
     kind = archive ? :gerber : preview_kind(node.name)     # preview_kind stays name-only (files-preview.md:191)
     layers =
       if archive then [ helpers.gerber_archive_entry(name: node.name, url: url.call(node), members: archive.stacked) ]
       elsif kind == :gerber then gerber_layers_for(user:, node:, url:)
       end
     manifest = Maker::ThreeMfManifest.for(user:, node:)
     Viewer.new(kind:, gerber_layers: layers,
                gerber_single: kind == :gerber && !archive && !gerber_job?(node.name),
                colors: manifest&.colors || [], unit_factor: manifest&.unit_factor || 1.0)
   end
   # FilesController#show:          @viewer = viewer_for(user: current_user, node: @node,
   #                                                     url: ->(n) { named_blob_file_path(n.node_id, filename: n.name) })
   # Public::FilesController#view:  @viewer = viewer_for(user: owner, node: @node, url: ->(n) { @pub.layer_url_for(n) })
   ```
   One lambda suffices per side: the private page already uses `named_blob_file_path` for both the archive entry and the layers, and on the public page `layer_url_for(@node)` equals `file_url_for(@node.node_id, filename: @node.name)` because @node has already passed `deliverable!` (public_project.rb:518-523, 568-570). The kind is assigned once, final, before anything reads it; the templates read `@viewer.*` with the defaults applied once.
5. Smallest credible implementation scope: (a) file_preview.rb: `Viewer` + `viewer_for`; (b) files_controller.rb#show: replace :510 and :537-575 with one call and compute `@editable` from `@viewer.kind`; (c) files/show.html.erb chain (:109-182) reads `@viewer`; (d) S14-OWNED, coordinated: public/files_controller.rb#view :46/:57-74 → one call (`enqueue_geometry` keys on `@viewer.kind`), public/files/view.html.erb :64-101; (e) files-preview.md:191 and :200 location sentences. `preview_kind`, `gerber_layers_for`, `FilesHelper#gerber_archive_entry` (still the one wire shape) and every viewer partial's strict locals are unchanged.
6. Regression risks and migration: behaviour-preserving; no data/API change; no backend-leg difference (both readers go through the port exactly as today). A public zip page asks `permits?` once more for the archive URL (constant; page_query_budget_test.rb:504 asserts constancy only). ## Considered and rejected
- A "listing location" value object (folder | ext+q, selected) parsed once and serialized once — rejected: the per-control subsets are deliberate and documented (files_helper.rb:175-189 `ext_toggle_path` omits folder/sort; chips, Clear filter and the search form drop `selected`), so the object would mostly rename them. The one real drift it would have caught is a DEFECT worth a one-line fix: `#rescan` rebuilds `{ folder:, ext: }` from params (files_controller.rb:1135) although the button posts `files_query_base` (index.html.erb:89), so a rescan started from a search lands at the unfiltered root and the scanreload URL then drops `q` too — add `q: resolve_query` (and arguably `selected:`).
- Typed listing modes (Flat / FolderPaged / FolderAll) replacing @flat/@paged/@pages/@page/@child_count/@match_count/@truncated — rejected: no reachable invalid combination (index.html.erb:169-173, :249, :266 guard on @flat/@paged); it would move branching behind a type.
- One table for `resolve_view` / `resolve_hidden` / `resolve_sort` (files_controller.rb:1300-1375) — rejected: three ~10-line resolvers with real differences (compound key:dir cookie, boolean hidden, `?dir=` alone ignored); a table is line-count only.
- One sort authority — rejected: flat_order (SQL, selects under LIMIT), folder_page_order (SQL, paging) and sort_nodes (Ruby, port mtime) are each argued in place (§5.2 portability; port mtime vs nodes.mtime) and pinned by files_sort_test/files_pagination_test. Trivia: `sort_key`'s name branch (files_controller.rb:1498) is now unreachable — `paged_folder?` (:1458) sends every name sort to SQL.
- Folding the ancestry walks (folder_crumbs :1733, LibraryBrowseController#crumbs :103, Maker::LibraryTree#path_for via library_path_for :1203 / folder_paths_for :1698) — rejected: library_browse_controller.rb:100-102 defends its copy, and moving #index's crumbs onto LibraryTree adds a whole-library dir pluck to the busiest page. Observation: on a broken chain they disagree on one page — #show's breadcrumb and FolderDestination label (:613-616) show the partial chain folder_crumbs stops at, while the Path row (library_path_for → nil) shows nothing and _rename_move says "Current folder"; #show also walks the same chain twice (one pluck + one find_by per level). - A Maker::Preview display-state predicate — `status == "ready" && asset.attached?` appears in _thumb:26, _static:18, _model3d:39, _gerber:63, files_controller.rb:386 (+ public views); pending/processing in show:98, _thumb:28, _static:20 — rejected: `preview_src` (application_helper.rb:51) already owns the URL half, the nil-row answers differ by surface on purpose (files-preview.md, "the two no-row cases"), and Maker::Preview is outside S10.
- Dropping `crumbs` from `/library/children` — LibraryBrowseController#children pays a per-ancestor query walk per request (:27, :103-113) that lib/file_chooser.js#childrenOf never reads (it takes `entries` only) — rejected: the endpoint is also handed to addon bundles as `ctx.urls.children` (tools/addons_controller.rb:817) and library_browse_test.rb:55/:70 pin `crumbs`; that is an addon-contract decision, not a simplification.
- SearchController's own `QUERY_MAX = 80` and six copies of `LOWER(…) LIKE ? ESCAPE '\'` — rejected: line-count only. Observation: the Files group's "See all N" (search_controller.rb:35) opens /files?q=, whose flat search also counts folders/symlinks and honours the dot-file cookie (files_controller.rb:224), so N and the landing page's "M matches" can disagree.
- `#thumbnails` vs `#geometry` poll shapes — deliberately different (§14h; files_controller.rb:460-466 forbids unifying `current_thumbnail`'s and `#geometry`'s use of the row).
- A remembered `type` sort in a search with no types silently falls back to name (files_controller.rb:241) while the header/select still say Type — a known limitation, not a representation problem.
