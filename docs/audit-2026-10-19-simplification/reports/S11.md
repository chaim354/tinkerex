## Opportunity 1: Record which save wrote each `maker_addon_files` row, so a state's current output set is stored rather than guessed

1. Verdict: recommend

2. Evidence
   - Today the row cannot tell which save wrote it, and the code says so:
     - `app/services/maker/addons/library_output.rb:107-112`: "`position` IS NOW ONLY UNIQUE WITHIN ONE SAVE, AND NOTHING ON THE ROW SAYS WHICH SAVE THAT WAS … the relative order of a stale row and a current one is arbitrary and unrecoverable."
     - `:113-116`: `upsert_file!` writes `role:, content_type:, position:` and nothing else.
     - `test/controllers/tools/addons_controller_test.rb:592-603` records this on purpose ("Asserted so the wart is recorded rather than discovered"): `assert_equal [ 0, 0 ], state.files.pluck(:position)`.
   - Two definitions of output order, and both put the stale row first:
     - `app/models/maker/addon_state.rb:23`: `has_many :files, -> { order(:position, :id) }`.
     - `app/controllers/tools/addons_controller.rb:681-682`: `latest_output_folder` orders by `"… maker_addon_files.position ASC, maker_addon_files.id ASC"`. At a position tie the OLDEST row wins.
   - Reader 1, where a save starts:
     - `addons_controller.rb:651-660` (`destination_from_outputs`, steps 2 and 3 of `tool_destination_node_id`) reads `rows.first` of that order.
     - Step 2 is documented as "the folder THAT state's output lives in now" (`docs/invariants/addons.md`, the "WHERE A SAVE STARTS" bullet).
   - Reader 2, the `#states` JSON:
     - `addons_controller.rb:271-276` serializes `s.files` in that order.
     - `docs/addon-api-v1.md:626-627` promises: "that is the order `state.list()` reports them back in".
     - The shipped boxes bundle already works around the gap. `../tinkerex-addons/addons/boxes/gallery.js:165-176`: "NOT NECESSARILY THE CURRENT ONE … after a rename this can be the drawing from an earlier name", then `const first = state.files?.[0]`.
     - The openscad bundle (`addons/openscad/editor.js:406`): `state.files?.find((f) => f.role === "output")`. This is the oldest row.
   - Reader 3, the revision label:
     - `app/views/files/_meta.html.erb:10-17` and `app/views/projects/_generated_group.html.erb:49` print `state.revision` (the item's CURRENT number).
     - `addon_origin_surfaces_test.rb:127-128` describes it as "the revision the file came out of", which is false for a file an earlier revision wrote.
   - How a state gets stale rows in the normal flow:
     - The boxes folder field always starts at `ctx.defaultFolder` (`folder_field.js:38`).
     - Revising a box picked from the bundle's own gallery sends that folder together with `stateId` (`editor.js:358, 363`). That folder is step 3, the newest box's folder.
     - So revising an older box that lives elsewhere CREATES new files there, and the old rows stay in the old folder (on purpose, `library_output.rb:102-105`).
     - Renaming while revising leaves stale rows too, as documented in `docs/addon-api-v1.md:564-570`.

3. Current complexity and invalid states
   - `maker_addon_files` mixes two things: "every file this state ever produced", which the code needs for ownership (`owned_destinations`, `addons_controller.rb:899-907`, where "A STALE ROW STILL COUNTS") and for provenance (`AddonOrigin`), and "this state's current output set", which three readers need.
   - It can only store the first. The second is approximated with `(position, id)`, and at a tie that approximation picks the stale row. A concrete case:
     - Box A has rows r1 and r2 in folder FA from revision 1. A revision made from the gallery adds r3 and r4 in folder FB.
     - "Edit in Boxes" on r3's file goes to `?state=A`. Step 2 orders r1 (pos 0, lowest id) first, so the save starts in FA.
     - Saving there hits `resolve_placements`' owned arm 2 (`addons_controller.rb:1066-1067`), which rewrites r1, the stale FA file. The FB file the user clicked "Edit" on is left alone.
     - Step 3 has the same tie, so after that revision a plain `/tools/boxes` visit also starts in FA.
     - Meanwhile `#states` lists [r1, r3, r2, r4]: stale and current interleaved. Both bundles' "open the file" links go to r1. The file page labels r1 "· v2" although r1's bytes are from v1.
   - The cost in prose: three "not test-pinned, this tiebreak cannot fail" arguments (`addon_state.rb:9-22`, `library_output.rb:107-112`, `addon_origin.rb:94-104`) and a caveat inside a published bundle (`gallery.js:165-171`). Each one exists only because the row lacks this one fact.

4. Proposed representation and why it is simpler
   - Stamp each row with the per-state revision whose save last wrote it. The only writer is `upsert_file!`, called inside the save's transaction right after `state.revision` was bumped (`addons_controller.rb:510/516/523` happen before `LibraryOutput.write`):
     ```ruby
     # migration (new; never rewrite an old one, CLAUDE.md §10)
     add_column :maker_addon_files, :revision, :integer, null: false, default: 1
     execute <<~SQL  # adapter-agnostic correlated update; legacy rows tie exactly as today
       UPDATE maker_addon_files SET revision = (SELECT s.revision FROM maker_addon_states s
                                                WHERE s.id = maker_addon_files.addon_state_id)
     SQL
     # LibraryOutput#upsert_file!
     row.update!(role:, content_type:, position:, revision: state.revision)
     # Maker::AddonState — ONE order: the latest save's files first, in save order; earlier saves after
     has_many :files, -> { order(revision: :desc, position: :asc, id: :asc) }, ...
     # Tools::AddonsController#latest_output_folder
     "…, maker_addon_files.revision DESC, maker_addon_files.position ASC, maker_addon_files.id ASC"
     ```
   - Why this is simpler:
     - "Which outputs are current" becomes one stored fact, `revision = MAX(revision)` for the state, instead of a tiebreak every reader has to argue about.
     - `position` keeps its one honest meaning: the index within a save.
     - `(revision, position)` is unique per state, so both orders become assertable, and the three "cannot be pinned" caveats can be deleted rather than maintained.
     - Stale rows keep every job they have today (ownership, provenance, "never delete user bytes").
   - Alternatives considered:
     - A `current` boolean needs an extra `update_all` on every save, and it loses the number reader 3 wants.
     - An FK to the `maker_addon_state_revisions` row is globally monotonic, but it is more machinery than any present reader needs.
     - A timestamp ordering is not used: `upsert_file!` does not bump `updated_at` on an unchanged row, and a timestamp cannot group the rows of one save.
     - Deleting stale rows is refused by the documented ownership and provenance rules.

   5. Docs:

This touches S10 and the projects views.

6. Regression risks and migration concerns
   - Data: the column is additive, with a backfill and no row deletion.
     - Legacy rows all get their state's current revision, so for existing data the order falls back to today's `(position, id)`. Behaviour changes only for saves made after the deploy.
     - The correlated UPDATE runs on SQLite and on Postgres.
   - API: the `#states` file order changes only for states that acquire stale rows after the deploy, where today's order is documented as arbitrary.
     - Both shipped bundles want the current output at `files[0]` or as the first `output` (`gallery.js:176`, `openscad/editor.js:406`). This is a fix for them, not a break, and no bundle release is needed (§14c: Rails and bundles deploy independently).
     - Key sets do not change unless the optional per-file key is taken.
   - UI: a tool's default "Save into" folder changes only in the stale case, and only toward the current output's folder.
   - Backend legs: no port verb or adapter changes. `latest_output_folder` is SQL over `nodes` (the mirror on chunk_remote). `addon_destination_test.rb` builds rows directly, so share, s3 and chunk_remote run the same assertions and keep identical run counts.
     - `page_query_budget_test.rb`'s "tools#show's default folder does not grow with saved states" sees no new query.
   - Invariants:
     - Untouched: "a save door must not delete user bytes", "A STALE ROW STILL COUNTS" for `owned_destinations`, and "`maker_addon_states.revision` … NO COUNT COLUMN". This is a per-row fact, not a second copy of the count, and it is written in the same transaction by the one writer.
     - CLAUDE.md §10's "never rewrite a migration" is respected.
   - Residual: the folder half of the problem could also be attacked bundle-side, by starting the folder field at the edited state's folder. That would not fix reader 2's order or reader 3's label. The host-side stamp fixes all three, and it also gives a future per-state `folderNodeId` in `#states` a correct definition.

## Considered and rejected
- **One per-file "save plan" value in place of `refuse_taken_names!` + `resolve_placements` + `render_would_replace` + `.slice` (the closest runner-up).**
  - Today a file's outcome is split across a whole-save raise, a flag hash (`{folder:, parent_node_id:, replace:, owned:}`, three valid shapes out of many), a parallel `placements[i]` array, and an absent-vs-nil `fetch` in `LibraryOutput.write`.
  - One method returning `:taken | :replace_asks | :replace_owned | :create` would remove the documented order dependency ("`.key?` arm is safe only because it runs AFTER", `addons_controller.rb:994-997`) and the "`owned` REQUIRED on both" pairing.
  - Rejected for now because there is no present defect, a save is ≤8 files, request-level tests pin every arm across backends, and §14c names the two checks by method. The gain is structural only.
  - It would tip into a recommendation the day a third collision question is added.
- **Extracting the save door or the destination resolver from the 1351-line controller into services.** CLAUDE.md §14d's rule is that a verb gets a named service when more than one controller performs it. Both have exactly one caller, so this is organisation only.
- **Removing `maker_addon_states.data`/`revision` as a copy of the newest `maker_addon_state_revisions` row.** This is a deliberate denormalisation with one writer in one transaction. `#states`, `AddonParamsController` and `record_source_links` would each pay a latest-per-group read, and the docs promise that the two agree.
- **A single resolution pass in `Registry`.**
  - `all` and `problems` each rebuild the served list, so `build` runs about 3 times per manifest per request, plus inside `states_key_permitted?`.
  - With n≈4 manifests, two adjacent copies, and 610 lines of `registry_test.rb` pinning both, the gain is minor.
  - Caching the built list would also change the documented per-request warn cadence (`registry.rb:299-306`).
- **Folding the ctx blob, the nine legacy `data-addon-*` attributes and the raw `mount` ctx into one**, and **dropping `@folders`** (every live dir, rendered for a select the boxes bundle no longer builds, per `folder_field.js:3-15`). Both are pinned for the life of `api_version: "1"` (§14c).
- **The double `find_addon_state(params[:state])` in `#show`** (once via `launch_state_id`, once via `destination_from_outputs`): one extra primary-key query, not material.
- **SDK helpers.**
  - The three segment encoders guard three segments with different contracts, and `_serviceUrl` is already the consolidation §14c requires.
  - The `state.list`/`state.revisions` JSON-guard twins are about 8 lines.
  - The lifecycle (module-global `host`, `teardownHost()` not checking ownership) is safe because Stimulus processes removals before additions within a mutation record. A `teardownHost(h)` ownership check would be hardening, not a simplification.
- **Moving `#create`'s byte writes out of the DB transaction.** On chunk_remote the transaction spans the `begin_upload`/`put_chunk`/`finalize_upload` HTTP calls and the changelog pull, so the SQLite write lock (IMMEDIATE transactions per `test/sqlite_concurrency_test.rb`) is held across those network calls. This is a concurrency trade-off, not a simplification, and the "one unit of work / rolls back before any byte lands" argument (`addons_controller.rb:426-441, 497-512`) is explicit. Worth a probe.
- **`Tools::LibraryFolders#chosen_parent_node_id` (`library_folders.rb:53-58`) uses `.presence` with no `is_a?(String)` guard**, unlike `destination_from_param` (`addons_controller.rb:643`) and `find_addon_state`. A hand-rolled `parent_node_id[]=a&parent_node_id[]=b` becomes an IN lookup on the WRITE door: it saves into whichever of the user's own folders the planner returns first, silently. The SDK cannot send this, because FormData stringifies an array. It is a one-line guard fix, not a simplification.
- **`Source#manifests` / `Source::Local#manifests`** have identical 6-line parsing. Trivial.
