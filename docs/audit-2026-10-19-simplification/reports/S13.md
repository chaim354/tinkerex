## Opportunity 1: The commit box computes each path's row once. One per-request row set feeds both #show and #create, `binary` moves onto the Row, and node ids are returned instead of passed through a side-channel ivar

1. Verdict: recommend
2. Evidence:
   - `repo_commits_controller.rb:28` `@rows, @dropped = reconcile` → `:121` `status = @local.status_for(by_path.keys)` builds a Row (a full content read, a HEAD blob lookup and `Rugged::Patch`) for every pending path. `:31` `full = @local.full_status` then builds a Row for every dirty path again (`local_repo.rb:103` `paths.first(limit).map { |rel| row_for(rel) }`), and `:33` `rest = full.rows.reject { |r| @rows.key?(r.path) }` throws away the pending ones it just recomputed. #create does the same twice: `:52` reconcile, then `:152` `@local.full_status`.
   - `:37` `@binary_paths = binary_paths(@rows.values + rest)` → `:205` `File.binread(File.join(@local.workdir, row.path), BINARY_SNIFF_BYTES)` re-opens every listed modified, added or ignored file that `local_repo.rb:264` `current = File.binread(abs)` had just read in full.
   - `:130` `@node_id_by_path = by_path`: `reconcile` returns `[keep, dropped]` and also writes an ivar. `:36` `merge!`s into it, and `:213` `node_ids_for` reads it in #create. #create is correct only because `:52` happens to call `reconcile` first.
   - For each row, the view reads four path-keyed sources: the Row (`show.html.erb:61-85`), the group's literal `checked:` (`:16-23`, `:64`), `@binary_paths` (`:88`) and `@node_id_by_path` (`:90`, `:103`).
   - "What the page offered" has two definitions. One is implicit in #show plus the view: the three groups' rows, with a checkbox only where `row.committable?` (`:63-65`). The other is explicit in #create (`:151-153` `committable_paths`). The two have already disagreed once, and that disagreement shipped. `:45-50` records it: "THE PLAN SAID THIS METHOD NEEDED NO CHANGE. It did: the intersection was against `reconcile` alone ... the commit answered "Nothing selected."" (`repo_edit_flow_test.rb:406-412` repeats it).
   - The cost model is the codebase's own: `local_repo.rb:84-87` and git-editing.md:531-535 say "every row costs a content comparison against HEAD's blob ... over CIFS that is ~15 ms per object". `DEFAULT_STATUS_LIMIT` is 500, and `catan` has 58 dirty paths.
3. Current complexity or invalid states: in #show, each dirty pending file is read in full twice by `row_for`, once more by libgit2's own status hash, and then sniffed again (8 kB). Its HEAD blob is looked up twice. Every other listed file costs one extra open for the sniff. At the ~15 ms-per-object figure above, the extra opens alone are on the order of a second for catan and several seconds at the 500-path cap. That is an estimate, not a measurement. Four parallel path-keyed structures have to agree by key. The rule that #create's authority equals what the page rendered is held by hand across two actions and a template, which is the drift that already shipped once. The side-channel ivar makes `node_ids_for` depend on call order.
4. Proposed representation and why it is simpler: compute each row once, carry everything the box knows about a path on that row, and derive both the render and the authority from the same three lists.
   ```ruby
   # local_repo.rb: decided while the bytes are already in hand (git's rule, unchanged: a NUL in the first 8 kB)
   Row = Data.define(:path, :state, :additions, :deletions, :binary)
   BINARY_SNIFF_BYTES = 8_000   # moved from RepoCommitsController
   #   row_for: binary = current.byteslice(0, BINARY_SNIFF_BYTES).include?("\x00".b)
   #   (the :ignored branch reads 8 kB, as binary_paths does today)

   # repo_commits_controller.rb: ONE builder; both actions call it
   Staging = Data.define(:pending, :other, :clutter, :pending_node_ids, :dropped, :truncated_count) do
     def offered_paths = (pending + other + clutter).select(&:committable?).map(&:path)  # #create's authority IS the render
   end

   def staging
     @staging ||= begin
       node_ids, gone = pending_paths                        # the catalog half of today's reconcile: rel => node_id, no ivar
       full   = @local.full_status
       listed = full.rows.index_by(&:path)
       asked  = @local.status_for(node_ids.keys - listed.keys) # only pending rows full_status did not compute:
                                                               # .gitignore'd-untracked, past the cap, unchanged, missing
       pending, stale = node_ids.keys.map { |rel| listed[rel] || asked.fetch(rel) }
                                .partition { |r| r.state != :unchanged && r.state != :missing }
       clutter, other = full.rows.reject { |r| node_ids.key?(r.path) }
                                 .partition { |r| Library::OsClutter.ignore?(r.path) }
       Staging.new(pending:, other:, clutter:, pending_node_ids: node_ids.slice(*pending.map(&:path)),
                   dropped: gone + stale.map { |r| node_ids[r.path] }, truncated_count: full.truncated_count)
     end
   end
   # #show:   GC staging.dropped; diff node ids = staging.pending_node_ids.merge(catalog_node_ids(other+clutter paths))
   # #create: paths = Array(params[:paths]) & staging.offered_paths
   #          delete RepoEdits for staging.pending_node_ids.values_at(*paths).compact
   # view:    the same literal groups array (checked: stays where it is), reading @staging lists and row.binary
   ```
   This deletes `binary_paths`, `committable_paths`, `node_ids_for`, `@binary_paths` and the ivar write inside `reconcile`. It also keeps every row behaviour: pending order (updated_at), pending rows that git status never lists, and the truncated count. The safety-critical `checked:` literal stays in the view exactly as it is.
5. Smallest credible implementation scope, in order:
   1. `LocalRepo::Row` gains `binary`, set in `row_for`. Delete `RepoCommitsController#binary_paths` and the view's `@binary_paths`. This step stands alone.
   2. Turn `reconcile` into a builder that returns its node-id map and reuses `full_status` rows for pending paths. `#create` intersects with `offered_paths`.
   3. Point git-editing.md's "Binary is decided by CONTENT" reference (line 585) at `LocalRepo::BINARY_SNIFF_BYTES`.

   The changes touch `local_repo.rb`, `repo_commits_controller.rb` and `repo_commits/show.html.erb`. No interface outside S13 changes (`status_for` and `full_status` have no other callers), and there is no schema change.
6. Regression risks and migration concerns:
   - No data or API change.
   - The commit box only renders where `local_worktree?` is true, so the s3 and chunk_remote legs see the existing redirect, pinned by `RepoCommitSurfacePresenceTest`. The share-pinned cases run identically on all three legs, and run counts are unchanged.
   - #create now pays an 8 kB read for `:ignored` rows, which are rare.
   - Within one request, a pending row and its full_status twin can no longer come from two different moments.
   - The one easy mistake is moving `checked:` out of the view at the same time. Don't: the safety property is pinned where it is.
7. Existing and additional validation required:
   - Existing pins in `repo_edit_flow_test.rb`: "the box shows three groups with the right membership", "only the tinkerex-edited group is checked on load", "a binary path is committable and says so instead of mounting a diff", "a path .gitignore covers is listed without a checkbox" (this one exercises the `status_for` fallback), "a row that now matches HEAD is dropped rather than offered", "a truncated list says how many paths it did not show", "a path from Other changes commits, and only it", "a deletion from Other changes can be committed" and "a submitted path in no group is ignored rather than committed".
   - Other existing pins: `local_repo_test.rb`, plus the system tests `repo_staging_test.rb` and `repo_editor_test.rb` (the pending diff mount).
   - New: in `local_repo_test`, "a NUL in the first 8 kB marks a row binary; text, and a NUL after 8 kB, do not". The mutation is to sniff the whole file, or never sniff.
   - New: in `repo_edit_flow_test`, "a ticked OS-clutter path commits" (POST `paths: [".DS_Store"]`). Dropping clutter from the lists turns this test red together with the membership test, and that coupling is the point. No current test posts a clutter path.
   - Optional: during GET of the box, count per-path `File.binread` calls using the house `replacing` pattern and assert at most 1. The mutation is to restore the separate sniff.
8. Confidence: medium-high.
   - High that the duplicate reads, the side channel and the two definitions are real. Each was read directly off the code, and the drift is recorded as having shipped once.
   - Medium on materiality: the I/O saving is estimated from the doc's per-object figure, not measured on the share.

## Opportunity 2: CommitPaths decides each selected path once, and writes both the tree and the index from that one read

1. Verdict: recommend
2. Evidence:
   - `commit_paths.rb:46` `paths.each { |rel| stage(builder, rel) }`, then `:48-52` `Rugged::Commit.create(... update_ref: ref_name ...)` moves the ref, then `:53` `refresh_index(paths)`.
   - `stage`: `:88` `return remove(builder, segments) unless File.exist?(File.join(@local.workdir, rel))` runs again at every recursion level (`:99` re-enters `stage`), even though `:86` says "ASKED ONCE, AT THE TOP OF THE FIRST CALL". At the leaf, `:91` `oid: Rugged::Blob.from_workdir(@repo, rel), filemode: filemode_for(rel)` reads, hashes and stats the file.
   - `refresh_index`: `:160-161` `if File.exist?(...)` / `index.add(path: rel, oid: Rugged::Blob.from_workdir(@repo, rel), mode: filemode_for(rel))` asks the same three questions of the working tree a second time, after the ref has moved.
   - The class's own rule (`:22-24`), git-editing.md:183-185 and spec part 8 rule 3 (2026-08-28 design, lines 288-289) all say: "Keep the write window two operations wide. Objects are content-addressed and safe to write early. Only the ref update and the index update need locks; do everything else first." Today, N file reads, hashes and possible object writes sit between the ref update and `index.write`, on a network mount.
   - `:12-15`: leaving the index out of step with the commit "reads as 'the app half-did something'". That is the state this race produces.
   - git log shows no rationale for the re-read (b0b6cdc3 introduced it).
3. Current complexity or invalid states:
   - Each committed path is read, hashed and stat-checked twice. A path at depth d costs about d+3 stats and two reads, where one read would do.
   - Whether the file exists, its bytes and its mode are each decided twice. The second decision happens after the commit landed.
   - If the maker's editor or desktop sync writes the file over SMB between `stage` and `refresh_index`, the index can record a blob, mode or deletion that the commit did not record. `git status` then shows the path staged-and-different, or as a staged deletion nobody asked for. Nothing errors, and "the committed path reports clean afterwards" cannot see it, because nothing changes the file between the two reads.
   - The doubled reads also explain two of the class's explanatory comments. `:69-75` explains why `stage` must carry both `rel` and `segments`, and `:106-108` explains why `remove` does not. Both exist only because `stage` reads from the working tree mid-recursion.
4. Proposed representation and why it is simpler: decide once per path, then apply that decision to the tree and the index.
   ```ruby
   def call(paths:, message:, expected_head: nil)
     raise NothingToCommit if paths.empty?
     parents = ...; raise RefMoved ... if expected_head && ...      # CAS first, unchanged
     entries = paths.to_h { |rel| [ rel, read_entry(rel) ] }           # rel => { oid:, mode: } | nil (gone)
     builder = tree_builder(parents.first)
     entries.each { |rel, entry| stage(builder, rel.split("/"), entry) }
     oid = Rugged::Commit.create(...)                                   # unchanged
     refresh_index(entries)                                             # in-memory edits + index.write; no file I/O after the ref moved
     oid
   end

   def read_entry(rel)                    # THE one place a selected path is read
     return nil unless File.exist?(File.join(@local.workdir, rel))
     { oid: Rugged::Blob.from_workdir(@repo, rel), mode: filemode_for(rel) }
   end

   def stage(builder, segments, entry)    # no `rel`: it no longer reads, so it is symmetric with #remove
     return remove(builder, segments) if entry.nil?
     return builder.insert(name: segments.first, oid: entry[:oid], filemode: entry[:mode]) if segments.size == 1
     # ... recurse on segments.drop(1) with the same entry, exactly as today
   end

   def refresh_index(entries)
     index = @repo.index
     entries.each do |rel, entry|
       if entry then index.add(path: rel, oid: entry[:oid], mode: entry[:mode])
       elsif index[rel] then index.remove(rel)   # KEPT: Rugged::Index#remove raises on a path it does not hold
       end
     end
     index.write
   end
   ```
   The tree and the index agree by construction, and the write window becomes the two operations the spec names. `refresh_index` stops re-deciding anything. Two comments that only explain the doubled reads go away.
5. Smallest credible implementation scope, in order:
   1. `app/services/maker/git/commit_paths.rb`: `call`, `stage`, `refresh_index`, and a new `read_entry`. `remove` is unchanged.
   2. `test/services/maker/git/commit_paths_test.rb`: the new tests below.
   3. git-editing.md:609-610: "branches three ways — `File.exist?` → `add`" becomes "a recorded entry → `add`".

   The public interface `CommitPaths#call(paths:, message:, expected_head:)` and its only caller are unchanged.
6. Regression risks and migration concerns:
   - Without a concurrent write, behaviour is identical.
   - Every invariant in git-editing.md still holds:
     - no `index.clear`, and the index is touched for exactly the committed paths;
     - an unselected deleted path survives, because staging is still per selected path;
     - the `index[rel]` guard stays;
     - emptied directories are still pruned;
     - the HEAD-seeded builder is unchanged.
   - Reads now all happen before any tree object is written. An unreadable file therefore aborts before more objects are written than today, never after.
   - Commits only run where `local_worktree?` is true, and those tests pin share libraries. There is no backend-leg or schema impact.
7. Existing and additional validation required:
   - Existing: all 16 cases in `commit_paths_test.rb`, especially "the committed path reports clean afterwards", "the committed deletion reports clean to git afterwards", "an executable file keeps its mode", "a selected path in neither the worktree nor HEAD is a no-op, not an error", "a nested deletion prunes only its own entry", "a directory emptied by a deletion is pruned from its parent" and "an UNSELECTED deleted path survives in the new tree with HEAD's bytes". Also the commit cases in `repo_edit_flow_test.rb`, and `repo_staging_test.rb`.
   - New: "the index records exactly the blob the commit recorded, even if the file changes after it was read". Wrap `Rugged::Commit.create` with the house `replacing` helper on its singleton: call the original, then `File.write(path, "raced\n")`. Assert `rugged.index["a.txt"][:oid] == rugged.head.target.tree.path("a.txt")[:oid]`. This is red on today's code and green after. The mutation that turns it red again is restoring the re-read in `refresh_index`.
   - New, deletion twin: `File.delete` inside the same wrapper. Today the index loses the entry (a staged deletion). After the change the index keeps the committed oid, and the worktree shows an unstaged deletion, which is the truth.
   - Optional: count `Rugged::Blob.from_workdir` calls and assert they equal `paths.size`.
8. Confidence: high on correctness and behaviour preservation: one class, a direct code trace, and the class header and the spec both state the target shape. Medium on materiality: the race window is narrow, and the per-path I/O saving over CIFS is estimated, not measured.

## Considered and rejected
- **One "standing" value for a file (repo root, committable here, pending, editable, has history).**
  - Every flag derives from two facts: the catalog root (`WorkingTree#root_for`, files_controller.rb:515) and `local_worktree?`. The doors that open git also ask `LocalRepo#refusal` lazily.
  - Each derived flag is one line: :522, :529 and :530. `TextSave` (text_save.rb:99-100) repeats :529's predicate exactly.
  - The two-ivar encoding cannot represent a contradiction, because `@committable_here` is computed from `@repo_root`. A Standing type would move branching, not remove a state.
  - Nits, not findings:
    - files/show.html.erb:219 `@repo_root && @committable_here` is redundant.
    - :530 queries a count on backends where it never renders.
    - "committable" names two predicates: `LocalRepo#committable?` (refusal is nil) and `@committable_here` (capability only).
- **`LocalRepo.open` returning LocalRepo-or-Refusal, so the "refusal FIRST" ordering rule can't be broken.** That rule is restated in git-editing.md:421-439, files_controller.rb:754-765 and :1804-1807, projects_controller.rb:648-651, release_snapshot.rb:86-88 and repo_card.rb:64-77.
  - Ruby cannot force a caller to branch on the result. A Refusal handed to `History.new` fails with the same NoMethodError the rule exists to prevent.
  - A raising `open!` would turn today's locked-repo sentences into exceptions that all 7 callers must rescue.
  - All 7 callers comply today, and the s3/chunk_remote legs pin the controller paths.
- **TextSave returning one closed Result (saved, stale, removed, taken, unreachable, gone) instead of a Result for two outcomes and exceptions for three.**
  - The divergence is real:
    - door 1 leans on FilesController's HTML-first `rescue_from` for NotFound and UnsupportedOperation (files_controller.rb:129-134, 155-160);
    - door 2 has no NotFound arm (readmes_controller.rb:43-49);
    - door 3 has all three arms, the NotFound one added after a shipped 500 (text_files_controller.rb:33-56).
  - Making the Result total only moves the same arms into per-door status maps. A forgotten map key is the same production failure as a forgotten rescue, unless a hygiene test enumerates statuses per door.
  - It also reverses a recorded choice (text_save.rb:48-55).
  - The live gaps are fixed with two rescue arms and one JS line (see notes). `Result#ok` vs `#status` is cosmetic redundancy: status is `:ok` exactly when ok is true.
- **History wire shape.** `stopped` carries both walk outcomes and refusal codes (files_controller.rb:707-732 and 1831-1833; history_controller.js:33). That is a union in one field, but it is documented as intentional (git-editing.md:336-339), and the JS's default branch makes the modest claim. A separate `refused` member is a wire change that removes no state.
- **A shared CodeMirror mount helper for editor, codeview and diffview.**
  - Each repeats about 25 lines: the abort/disconnected guard, the three dynamic imports, and the basicSetup + theme + language assembly. `this.disconnected` duplicates `this.abort.signal.aborted`.
  - Extracting them saves lines and serves only hypothetical extensibility. codemirror_theme.js:5-9 already names and defers the "follow the theme" change.
  - The parts that differ are the ones that matter: the capped streaming read, the save bar and the two-blob fetch.
- **Routing `FilesController#restore` through `Maker::TextSave`.** Restore is a fourth door performing that save verb.
  - It skips the store-side `expect_token` and the preview re-enqueue, so git-editing.md:366-369's "the same door the editor's Save uses" has been only half true since S4-4.
  - The payoff is modest. Restore has no client-held token. The thumbnail heals itself, because the redirect lands on #show, whose `current_thumbnail` (files_controller.rb:1230-1238) enqueues on a miss.
- **Resolving `repo_relative_path` from `WorkingTree`'s own ancestor walk**, instead of a `LibraryTree` pluck of every live dir on each history, blob or restore request (files_controller.rb:1847-1855).
  - The walk follows tombstoned parents (working_tree.rb:60 has no `.present`), while LibraryTree refuses a broken chain.
  - The method's own comment requires the panel and the commit box to resolve paths from one source.
- **Deriving the pending group from `full_status` alone.**
  - A `.gitignore`'d untracked path that tinkerex edited never appears in git status, and it is pinned as listed but disabled (repo_edit_flow_test.rb:270-283).
  - Pending rows past the 500 cap would vanish.
  - Opportunity 1 keeps `status_for` for exactly those rows.
- **Splitting TextSave's "node XOR (parent_node_id, name)" input.** Door 1 passes both halves (files_controller.rb:687-689). No live invalid combination exists. Splitting into rewrite/create just moves the REMOVED branch into the README door.
- **Small duplicates.**
  - `load_repo` is repeated in RepoCommitsController and RepoHistoriesController: 5 lines, deliberate per repo_histories_controller.rb:24-32.
  - `LocalRepo#other_dirty_count` has no production caller, and git-editing.md:548-555 already says to remove it together with its citation.
  - Three copies of 200_000 (server, editor, codeview) are documented as the courteous halves of the server's cap.
