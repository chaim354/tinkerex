## Opportunity 1: One "shown" answer for a visitor's page. Hiding goes by ancestry and is asked of the layout, and every derived reader uses it, the thumbnail map and the /u/:handle card included
1. Verdict: recommend
2. Evidence:
   - PublicProject answers four page-assembly questions, and it answers them on four different bases:

   - The hidden filter is applied one reader at a time, in seven separate spellings:

     - :313 bundle_path_for

3. Current complexity or invalid states. I reached each of these by reading the code; none is reproduced (read-only audit).
   - (a) **/u/:handle shows a hidden folder's picture as a project card's cover.** `permitted_cover_ids` admits the node, users_controller.rb:77 maps it, and `_project_card.html.erb:31-34` names `public_file_preview_path`. No test covers the card case.
   - (b) **Past FILE_CAP or DIR_CAP, `hidden_file_ids` misses a hidden folder's unlisted files.**
     - The two readers that resolve nodes outside the listing therefore advertise those files: cover_node (:378 `find_by`) and block_image_node (:122 `page_nodes`).
     - An inline image then renders from its bytes as the hero (_page.html.erb:133-134), which is exactly "the Photos leak in its biggest frame" that :379-380 exists to prevent.
     - The header's reason for using ancestry (the listing is capped) is never applied to hiding.

       - backups, which come second in `listing.node_ids` and are never rendered publicly (public_project_test.rb:279-290), although lbrn/lbrn2/mage files have renderers;
       - every hidden folder's files;
       - BOM and release targets, which are painted nowhere (`_bom` and `_releases` render links only).

   - (d) **A BOM line pointing at a `_backup.lbrn2` gets a zip path in the CSV** (bom_csv.rb:46 via :315) for an entry the zip never carries (:298).
4. Proposed representation and why it is simpler. Hidden means "the layout hides the depth-one folder this node sits under". It is decided from the same lineage `claimed?` already walks, and asked of `Layout#hidden?` rather than of a set built from the listing.
   ```ruby
   def self.depth_one_dir(parent_id, tree:, folder_node_id:)   # shared by the page and the card batch
     lineage = Array(tree.ancestors_of(parent_id))              # includes parent_id; nil chain => []
     i = folder_node_id && lineage.index(folder_node_id)
     lineage[i - 1] if i&.positive?
   end

   def hidden_dir?(dir_id)                                      # a file asks about its parent
     (@hidden ||= {}).fetch(dir_id) do
       d1 = self.class.depth_one_dir(dir_id, tree:, folder_node_id: listing.folder_id)
       @hidden[dir_id] = !d1.nil? && layout.hidden?(Maker::ProjectKind.folder_key(d1))
     end
   end
   def hidden?(node) = hidden_dir?(node.parent_node_id)
   def shown?(node)  = permits?(node) && !hidden?(node)         # cover_node, block_image_node

   # WHAT THIS PAGE ADVERTISES OUT OF THE LISTING: every DERIVED reader starts here. AUTHORED prose
   # (README/block links via listing.path_index, BOM/release links via permits?) keeps reading `listing`.
   def shown_rows = @shown_rows ||= listing.all_rows.reject { |r| r.backup? || hidden?(r.node) }
   def shown_row(id) = (@shown_by_id ||= shown_rows.index_by(&:node_id))[id]

   def bundle_files = @bundle_files ||= shown_rows.map { |r| BundleFile.new(...) }.sort_by(&:path)
   def bundle_path_for(id) = (row = shown_row(id)) && bundle_path(row)
   def kicad_rows = @kicad_rows ||= shown_rows.select { |r| kicad?(r) }.sort_by { |r| r.node.name }
   # photo_rows: ProjectPhotos.rows(...).reject { |r| hidden?(r.node) }
   # repo_cards: flatten_dirs(listing.tree).select(&:repo?).reject { |d| hidden_dir?(d.node_id) }
   # THE UNION IS WHAT THE PAGE PAINTS, one term per painting surface, hero first:
   def thumbs = @thumbs ||= Maker::Previews::ThumbnailMap.for(owner,
     [ cover_node&.node_id ] + shown_rows.map(&:node_id) + live_entry_photo_ids + live_block_image_ids)
   ```
   - `permitted_cover_ids` adds one line: `next if (d1 = depth_one_dir(...)) && project.panel_layout(folders: [[d1, false]]).hidden?(folder_key(d1))`. That reads the stored `panels` column the batch already loaded and the tree it already built, so it adds no query.
   - Deleted: `hidden_folder_ids`, `hidden_file_ids`, `hidden_dir_ids`, and the seven inline filters.
   - Why this is simpler:
     - One predicate on permission's own basis replaces two capped sets.
     - One `shown_rows` collection replaces per-reader filtering, so the bundle, the CSV path, the Schematics panel and the map agree by construction.
     - A new derived reader is correct because of what it reads, not because someone remembered the comment at :139-146.

## Considered and rejected
- **Visibility and token model** (`visibility` ∈ private/unlisted/public, plus a nullable `unlisted_token`).
  - This is deliberate. The token survives unlisted → public → unlisted (project.rb:317-322) and rotates only through Projects::UnlistedTokensController.
  - An unlisted row with a NULL token fails closed at `public_project!`'s `blank?` refusal (base_controller.rb:41-58, pinned by public_project_test.rb:59).
  - A `Private | Unlisted(token) | Public` union would discard the survival rule, so it is not a simplification.
- **Threading the token through `default_url_options` instead of `**pub.link_params`** at about nine call sites. That would add `k` to links that leave the project (the `public_user_path` breadcrumb, the explore header) and leak the credential onto other pages' URLs. The per-call form is pinned by "every link an unlisted page renders carries the token" (public_project_test.rb:68) and its feed and manifest twins.
- **S15's pointer that repo_cards repeats ProjectsController#show's batched root query and `RepoCard.for` loop** (public_project.rb:342-348 vs projects_controller.rb:292-302). The shared part is about three lines around the one implementation (`RepoCard.for`), and both copies are pinned by page_query_budget_test's repo-growth seeds, so merging them is line-count only.
  - Observation, not a finding: the public page has no ROOT card (projects_controller.rb:303-317). A project whose folder IS the working tree, which is the common real shape, shows a visitor its README but no head commit or tags. That is a product question.
- **S15's pointer that hidden_file_ids, hidden_dir_ids and flatten_dirs re-walk the tree.** The walks are in memory over at most DIR_CAP dirs and cost nothing measurable. Their real problem is the capped basis and the per-reader application, which Opportunity 1 addresses.
- **One shared viewer chain partial for public/files/view.html.erb:64-102 and files/show.html.erb:109-182.** Rejected because it contradicts the recorded per-page decision (show.html.erb:103-108). The text and Measure branches differ substantively (editor and save locals, the repo banner).
- **One method for the BOM part cell** shared by BomCsv#part_for (bom_csv.rb:72-78) and `_bom.html.erb`:38-56. Both are small, and the privacy rule is pinned on both sides (public_project_test.rb:376; bom_csv_test.rb:54, :64), so this is line-count only.
- **`pub.feed_visible?` for the pair of `build_log || releases` gates** that show.html.erb:42 and _page.html.erb:54 say "must stay in step". Two call sites; a fine cleanup, but not material.
- **The four-cell row duplicated in `_files` and `_folder_panel`.** This is documented ("a third caller is when to extract it") and pinned on both panels.
- **`visible_entry?`'s ivar peek** (`@page_nodes&.key?`, :613-617). It gives the same answer at two costs, it is correct, and it is documented, so it is not contradictory state.
- **Defect, not a simplification: the public `.gbrjob` page has an N+1.** `gerber_layers_for` calls `@pub.layer_url_for` per layer, and that calls `permits?` and then `visible_entry?`, which is one `exists?` per layer on an anonymous GET (bounded by the job's layers, or by FLAT_LIMIT pcb siblings when the job names none).
  - page_query_budget_test.rb:499-527 claims "a .gbrjob's sibling walk is ONE bounded query", but its subject is `hero.stl`, so it cannot see this.
  - Fix: prime visibility once for the sibling set, the way `visible_page_ids` does for `page_nodes`.
- **Defect for the owner to decide, not folded into Opportunity 1 because it narrows permission: deliverable is wider than listable.**
  - `claimed?` refuses only a lineage that contains `.git` (:476).
  - The listing skips every dot-directory and build-output directory it walks into (project_folder_listing.rb:343-345).
  - `Node.visible_entries` tests the leaf name only (node.rb:73-83).
  - So a plainly named file under `.github/`, `.vscode/`, `.pio/` or `node_modules/` inside a published folder is deliverable by node_id, although it is never listed or bundled. The header at :433-436 says "the display rule the folder listing already applies", but that is only the leaf half, and the publish warning promises "every visible file".
  - Exposure is limited because node ids are UUIDs and nothing on the page links these files.
  - Fix: ask the listing's one dir-skip rule for the lineage segment below the folder.
- **Stale prose that Opportunity 1 dissolves or that should be corrected:**
  - public_project.rb:294-296 (the CSV zip path for a hidden file, contradicted by :309-313 and the test).
  - public_project_test.rb:550-553 (says the feed, manifest and CSV "never consult the layout"; tinkerex#283 gated all three).
