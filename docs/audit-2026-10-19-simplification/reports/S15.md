## Opportunity 1: One answer to "which subfolders does this render draw no file cells for", read by both the recent row and the thumbnail union
1. Verdict: recommend
2. Evidence:
   - The page answers that question twice, once per representation. As Dir objects, for the recent row: `projects_controller.rb:196` `@recent_files = @listing.recent_files(skip: dirs_without_tiles)`, and `:638-639` `if !@panel_layout.visible?(key) || @panel_layout.view_for(key) == "browser" then [ dir ] else collect_repo_dirs(dir.children)`. As file ids, for the ThumbnailMap union: `:402-406` `unrolled = @listing.tree.select { |d| d.repo? && …view_for(…) != "browser" }.flat_map(&:subtree_file_ids)`, `hidden_in_repos = @listing.repo_subtree_ids - @generated_ids - unrolled`, `tile_ids = @listing.node_ids.reject { |id| hidden_in_repos.include?(id) } + …`. The second one feeds `project_folder_listing.rb:230-232` `repo_subtree_ids`, whose only caller is this line.
   - The comment on `dirs_without_tiles` (`:626-631`) says its two repository arms are "the exclusion #show's thumbnail union already makes (`hidden_in_repos`)". They aren't. The recent rule was rewritten in review because it keyed on `repo?`. `project_page_test.rb:144-147` says "Both leaked into the row while the rule keyed on `repo?`", covering a browsed plain folder and a nested repository in a tiles-view repository panel. The union still keys on `repo?`.
   - The union is a hand-kept list of everything the page paints, and each new surface was patched in as review found it: `:396-401` ("found in review"), `:407-413` (the pickers' `@folder_images`), `:417-422` (the recent row), giving `:424-427` `recent_ids + tile_ids + entry_photo_ids.select {…} + block_thumb_ids + @folder_images.map(&:node_id) + cover`. The Photos panel never got its own term. It paints `Maker::ProjectPhotos.rows` (`project_photos.rb:13` `listing.all_rows.select { |r| r.role == "image" }`, every image at any depth, inside repositories too), and `_photos.html.erb:7-9` and `_folder_panel.html.erb:25-29` both claim those ids are already in `@page_thumbs`. For an image inside a repository that claim is false, because `hidden_in_repos` removed it. `@photo_rows` is even computed after the union (`:432`).
3. Current complexity or invalid states: the two derivations disagree in four reachable cases on the normal page:
   (a) A hidden depth-one folder panel: the recent row skips it, but the union backfills it.
   (b) A plain folder in browser view: the recent row skips it, but the union backfills it.
   (c) A repository nested inside a depth-one repository panel set to tiles or list: the recent row skips it, but `unrolled` takes the whole outer subtree, so the union backfills it.
   (d) An image inside a browsed repository: Photos paints it, but it is never in the union. `files/_thumb` shows a spinner, the poll door never backfills (files-preview.md: "omit"), and on chunk_remote "nothing but a backfill creates a row", so it ends as "Preview not supported".

   Cases (a) to (c) are the waste the `:385-395` comment calls a defect: ThumbnailMap backfills in the order given under a 100-id budget, and `@listing.node_ids` is name-ordered, so an alphabetically early hidden folder can use up the budget before the visible tiles get theirs. In edit mode the page needs the opposite answer for hidden panels, because the editor draws them ghosted with full tiles. Today the union only gets that right by accident, and the recent row gets it wrong.
4. Proposed representation and why it is simpler: compute the Dir set once, editing-aware, and derive both readers from it. Then add the one surface that paints without being a folder tile (Photos) to the union directly:
   ```ruby
   def dirs_without_tiles                # "on THIS render"
     @listing.tree.flat_map do |dir|
       key = Maker::ProjectKind.folder_key(dir.node_id)
       dropped = (!@editing && !@panel_layout.visible?(key)) || @panel_layout.view_for(key) == "browser"
       dropped ? [ dir ] : collect_repo_dirs(dir.children)
     end
   end
   # #show
   no_tiles = dirs_without_tiles
   @recent_files = @listing.recent_files(skip: no_tiles)
   …
   untiled  = no_tiles.flat_map(&:subtree_file_ids).to_set - @generated_ids   # Generated still tiles in Files
   tile_ids = @listing.node_ids.reject { |id| untiled.include?(id) } + @linked_rows.map(&:node_id)
   @photo_rows  = Maker::ProjectPhotos.rows(listing: @listing, entries: @entries, page_nodes: @page_nodes)
   @page_thumbs = Maker::Previews::ThumbnailMap.for(current_user,
     recent_ids + tile_ids + @photo_rows.map(&:node_id) + block_thumb_ids + (@cover_node ? [ cover_id ] : []))
   ```
   This deletes `unrolled`, `hidden_in_repos`, `ProjectFolderListing#repo_subtree_ids`, and two union terms: `@folder_images` is a subset of the photo rows, and the live entry photos are exactly the photo rows' entry half. Backups need no term, because `Dir#subtree_file_ids` already excludes them. One rule now decides what the page paints, and each union term maps to one painting surface.
5. Smallest credible implementation scope: (1) `ProjectsController#dirs_without_tiles` becomes editing-aware, and #show calls it once; (2) #show swaps `unrolled`/`hidden_in_repos` for `untiled`, moves `@photo_rows` above the union, and drops the two subsumed terms; (3) delete `ProjectFolderListing#repo_subtree_ids`; (4) rewrite the comments at `:385-422` and the stale claims in `_folder_panel`/`_photos`. Steps (1) to (3) are in-boundary; the `_photos` comment is S16's.
6. Regression risks and migration concerns: no data, API or query-count change. The work is in memory over the listing, and it is still one `ThumbnailMap.for` and one `stat_all`. Intended behaviour changes: fewer preview rows and jobs for (a) to (c); new rows for (d). One visible change to confirm with the owner: in edit mode the recent row now includes the files of a ghosted hidden panel, which is the "on this render" reading. List-view panels draw rows with no thumbnail, yet both today's code and this change keep them in the union. Narrowing that further is a separate product call. Identical on all three legs; (d) fixes a hole that shows only on chunk_remote.
7. Existing and additional validation required: these stay green: project_attachments_test "a repository's files enqueue no thumbnails…" (2 jobs), project_page_test "a repository panel switched to tiles…" and the two recent-row tests, page_nodes_test "a node on both surfaces resolves from the one map" (1 job), and the page_query_budget constancy tests.    - A repository nested in a tiles-view repository panel enqueues nothing. Mutation: restore `unrolled`, and it goes red.

## Opportunity 2: The "browser draft is the whole truth of blocks and tabs" rule belongs to `LayoutDocument#from_draft`, not to the Save door alone
1. Verdict: recommend
2. Evidence:
   - `layout_document.rb:295-298`: `merge` takes `base_draft = base || draft`, which for `from_draft` (`:202-207`, base nil) is the saved layout. `:352` `ordered = listed.map(&:last) + (current.keys - listed.map(&:first)).map { |k| current[k] }` re-appends every saved entry the posted draft does not name, blocks and tabs included. That is paste semantics, applied to a document that posts every slot (`layout_editor_controller.js:83-84` `panels: this.slotTargets.map(…)`; `:32-33` "a block skipped here is a block deleted").
   - Only one of the three doors undoes this. `panels_controller.rb:55` `held = held_by_browser(result.draft, posted)` and `:87-90` reject kinded entries the browser did not post, and that happens after `merge` has already run its result checks (`layout_document.rb:353-357` Publish-last, `:364` block cap, `:371` duplicate tab names, `:376` tab cap) on the merged set. The other two doors use the raw merge: `layouts_controller.rb:24-26` (`yaml`) and `:37-39` (`parse`, whose base is `doc.from_draft(parsed_draft)`, with `base.ok? ? base.draft : nil`).
   - This was recorded as a deliberate decision (content-blocks spec §10.9: "The two meet at the door"). The decision's own premise ("it posts every slot it holds, so a block that is absent is one whose slot was deleted") is just as true of the yaml and parse doors, which receive the same `this.draft()` (`js:453`, `:466`).
3. Current complexity or invalid states: a "merged draft" holds blocks and tabs the maker deleted, and it is what caps, duplicate checks, YAML export and Apply all see. Each failure below is traced through the code:
   (a) After a block or tab is deleted, the YAML drawer still lists it, after Publish.
   (b) Apply brings it back. The parse base re-adds it, `adopt` (`js:486-489`) mints a slot from the template, and `adoptBlock` refills its saved content, so the deletion is undone silently.
   (c) Save refuses drafts that would be valid, for example: 38 saved blocks, delete 3, add 4 gives 39 on screen but 42 counted; 7 tabs, delete 1, add 2; or delete tab "Notes" and rename another tab to "Notes" ("Two tabs are named"). Each refusal redirects to the editor and discards the session's draft (spec §8.13). The JS `slotProblem` (`:577-585`) checks only what is on screen, so it cannot warn first.
   (d) Every Save after a delete flashes "Publish is always last; it was moved to the end.", because the carried entry lands after Publish.
   (e) When (c)'s condition holds, `parse` falls back to the saved layout as base, so Apply silently reverts every unsaved hide, width and title on the page.
4. Proposed representation and why it is simpler: the document type owns its semantics. `:yaml` keeps merge-and-never-delete-by-omission; `:draft` is the whole truth of what the browser owns:
   ```ruby
   carried = (current.keys - listed.map(&:first)).map { |k| current[k] }
   carried = carried.reject { |e| e["kind"] } if source == :draft   # blocks and tabs: absence = deleted
   ordered = listed.map(&:last) + carried
   ```
   `held_by_browser` is deleted, and `replace` uses `result.draft` for the rows, the column and the page. Panels and folders keep being carried, so a folder made mid-edit still survives. The checks now run on the set that will actually be written, and all three doors agree.
5. Smallest credible implementation scope: `Maker::LayoutDocument#merge` (one line plus the header note); `Projects::PanelsController#replace` (drop `held_by_browser`, about 10 lines); update the spec §10.9 note. No change to the JS, the views, the column or the YAML grammar.
6. Regression risks and migration concerns: no data or API change. Save's outcome is identical: `held_by_browser`'s set equals "kinded entries listed", because invalid ones already refuse. The yaml and parse doors change exactly in cases (a), (b) and (e). A pasted `id:` naming a block deleted this session now creates a new block, which is the existing "unknown id creates" rule, instead of reviving the deleted one. Existing unit tests that post partial drafts (`layout_document_test.rb:342`, `:436`, `:454`, `:569`) assert nothing about carried blocks or tabs, so they stay green. A folder appearing mid-edit can still trigger the Publish-last note; that is pre-existing and rare. Leg-neutral.
7. Existing and additional validation required: these existing tests pin Save's deletion: project_blocks_test "Save creates, updates and deletes…" and project_tabs_test "…a deleted tab is gone". Deleting `held_by_browser` without the merge line turns them red, which proves the rule moved rather than vanished.

   New tests, each red today:
   - Unit: `from_draft` of a draft that omits a saved block or tab drops it, and raises no Publish note.
   - Integration: `yaml` for that draft does not contain `id: <key>`.
   - Integration: `parse` with that draft and a YAML text that does not name it returns a draft without it.
   - Integration: Save at block-cap churn (delete k, add k) and a reused tab name both save.

   Mutation: drop the `reject` line, and all of these go red.
8. Confidence: high. Every symptom is a direct code trace, the change is two small edits inside the boundary, and existing tests guard the Save half.

## Considered and rejected
- **Turning #show's page assembly (about 41 ivars, at least 8 comment-enforced ordering constraints) into a memoized `Maker::ProjectPage` like `Maker::PublicProject`.** Rejected: it moves the same logic behind a new type with churn across about 20 partials. The §14d named-service rule does not call for it, since there is one controller. The one ordering-sensitive derivation that actually drifted is Opportunity 1. Noted only: the editor's view switch (`layout/panel`) pays the whole assembly per click (README port reads, git reads, `stat_all`).
- **Storing the `panels` column per entry instead of as six maps.** Rejected: deliberate. The `over.key?("hidden")` "maker answered" semantics, Reset-as-nil, and sparse titles all rely on the map shape, and the conversions (`entry`, `column`) are small.
- **One shared rule table for `ProjectKind.layout_for` (read) and `LayoutDocument` (write).** Rejected as an abstraction. It did surface two real mismatches, each a one-line alignment:
  - `stored_views` accepts any of VIEWS for any key (`project_kind.rb:445-450`), where the door uses `offered_views`. A console-stored `views: {attachments: browser}` renders Files with no active toggle and makes the editor's Save refuse.
  - Tab names are read under TITLE_MAX = 60 (`:414`), but written under TAB_NAME_MAX = 30.
- **Splitting `ProjectKind` (kind suggestion plus layout vocabulary) into two modules.** Rejected as rename churn.
- **Typed panel keys or entries in place of prefix strings and the overloaded `kind`.** Rejected as moving branching behind a type. The one drift is a bug with a one-line fix: `addBlock`'s cap counts tab slots (`layout_editor_controller.js:249` `filter((s) => s.dataset.kind)`), so 8 tabs take 8 of the 40 block slots. The server was fixed for exactly this (`layout_document.rb:361-364`).
- **A per-kind block field map driving `entry`, `to_yaml` and `blocks_from`.** Rejected: three short case statements, and `image`/`link` need special arms anyway.
- **A registry for ON_DEMAND, PANEL_ANCHORS and `panel_has_rows?`.** Rejected: already `fetch`-coupled maps (design-system rule 14).
- **One README-region partial for `_readme_card` and `_repo_card` (RepoCard flattens `Readme` into `readme_html`/`readme_note`).** Rejected as cosmetic. Same for `_block_templates` re-spelling `_panel_slot`'s attribute list.
- **JS async ordering.** `fetchYaml` (`:451-460`) and `setView` (`:177-193`) apply responses in arrival order, so a late older response can overwrite newer drawer text, and Apply would then re-apply stale text. This is a sequence-guard bug fix, not a representation change.
- **`Maker::Project#visible_panels`.** Dead in app code (tests only), and its header comment (`project.rb:49-53`) still says show.html.erb loops over it. Trivial cleanup, not a finding.
