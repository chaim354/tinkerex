## Opportunity 1: Sheet autosave saves on five named events, so other grid edits never reach the database — compare the grid with the last saved copy instead
1. Verdict: recommend
2. Evidence:
   - **What triggers a save.** `app/javascript/controllers/sheet_controller.js:77-81` lists exactly five handlers, each `() => this.scheduleSave()`: `onchange`, `oninsertrow`, `ondeleterow`, `oninsertcolumn`, `ondeletecolumn`.
   - **What a save sends.** The whole grid (`:127-132`): `columns: getHeaders(true).map((title, i) => ({ title, width: getWidth(i) }))` and `cells: getData(false, false)`.
   - **Which gestures are switched on.** `:58-76` never sets `columnSorting`, `allowRenameColumn`, `columnResize`, `rowDrag` or `columnDrag`. The bundle gates each one as `0!=e.options.X` (`vendor/javascript/jspreadsheet.js:7` at bytes 154355-154477 and 122731), so with nothing set, all of them are on.
   - **Five gestures change what a save would send but fire none of the five events.** All are on bundle line 7, by byte offset:
     - **Sort.** Double-clicking a column header sorts it: `doubleClickControls` (@119453) runs `if(1==t[1]&&0!=…options.columnSorting){…orderBy(parseInt(t))}`. `orderBy` reorders the data array itself (`t.options.data=s`, @42998) and fires only `"onsort"` (@44876). The context menu's Order ascending/descending works the same way.
     - **Rename a column** (context menu, @122731). `setHeader` writes `options.columns[e].title` and fires only `"onchangeheader"` (@144990).
     - **Resize a column.** `setWidth` writes `options.columns[e].width` and fires only `"onresizecolumn"` (@94147).
     - **Drag a row or column.** `options.data.splice(…)` fires only `"onmoverow"` (@99394); a column drag fires only `"onmovecolumn"`.
     - **Undo and redo** (Ctrl/Cmd+Z, Ctrl+Y). Undo sets `e.parent.ignoreEvents=!0` before re-applying the old value (@13019). The dispatcher drops every event while that flag is set (`if(!r.ignoreEvents&&(…r.config.onevent…r.config[e]…`, @1251). Afterwards it fires only `"onundo"` / `"onredo"` (@14279 / @15524).
   - **The status label never changes for any of these.** `projects/sheets/show.html.erb:70` renders the label as "Saved", and the only call that changes it to "Saving…" is in `scheduleSave` (`sheet_controller.js:104`).
   - **No test covers them.** `test/system/sheet_grid_test.rb:50-99` exercises only cell edits.
3. Current complexity or invalid states:
   - **The database and the grid disagree while the label says "Saved".** Examples:
     - Press Ctrl+Z on a saved value: after a reload, the undone value is back.
     - Double-click a header: the rows are sorted on screen and unsorted in the database.
     - Rename or widen a column: the change is gone after a reload.
   - **Whether such a change survives is a matter of luck.** Every save sends the whole grid, so the next unrelated cell edit persists the sort, rename or undo along with it. If the user leaves before making another edit, the change is lost.
   - **The list fails silently.** The bundle can fire 42 event names. Any edit the controller does not list is a write that never happens, including events a library upgrade adds later.
   - **There is no "unsaved" state to act on.** Related case (traced, not run): `disconnect()` clears the pending timer (`:87`). The Rename form (`show.html.erb:73-77`) is a Turbo submit that redraws this same page without a full reload. So a cell edit followed by Rename within 1 s is dropped, and the redrawn grid shows the stored data. The controller has no explicit unsaved state it could use to save first or warn before leaving.
4. Proposed representation and why it is simpler: decide "is the grid different from what the server last stored?" by comparing values, and re-check after every event.
   ```js
   jss(this.gridTarget, {
     worksheets: [ { data: cells, columns: …, allowInsertRow: true, … } ],
     onload: (workbook) => { this.instance = workbook.worksheets[0]; this.stored = this.snapshot() },
     // EVERY dispatched event re-arms the debounce; save() decides whether anything is sent.
     // BLOCK BODY ON PURPOSE: a dispatch of an event with no handler of its own returns this hook's value,
     // and onbeforechange substitutes any non-null result for the typed value.
     onevent: () => { this.scheduleSave() }
   })

   snapshot() {
     const w = this.instance
     return JSON.stringify({ columns: w.getHeaders(true).map((title, i) => ({ title, width: w.getWidth(i) })),
                             cells: w.getData(false, false) })
   }

   async save() {
     if (!this.instance) return
     const body = this.snapshot()
     if (body === this.stored) return            // the row already holds this; send nothing, and the label stays true
     this.setStatus("Saving…")
     const response = await fetch(this.urlValue, { …, body: `{"sheet":{"data":${body}}}` })
     if (response.ok) { this.stored = body; this.setStatus("Saved") } else { … }   // error branches unchanged
   }
   ```
   Why this is simpler:
   - It deletes the five handlers and the hidden assumption that "a listed event fired" means "there is something to save".
   - Persistence no longer depends on knowing the library's event list. An unknown event now costs one comparison that finds nothing to send, where today it costs a lost write.
   - "Saved" now means the stored row equals the grid.
   - Selecting cells sends nothing, and a failed save is retried by the next interaction.
   - `this.stored !== this.snapshot()` becomes an explicit unsaved flag. Later, one line each could use it to warn on `beforeunload`, save before Rename, or wait for an in-flight save before sending another. None of that is in this scope.
5. Smallest credible implementation scope:
   - `sheet_controller.js`: drop the five handlers; add `onevent`, `snapshot()` and `this.stored` in `onload`; make `save()` compare and return early; move the "Saving…" label from `scheduleSave` into `save()`. Update the handler-placement comment (`:45-56`): `onevent` is top-level like `onchange`, because the dispatcher reads `r.config`. About 20 changed lines.
   - `test/system/sheet_grid_test.rb`: add the tests in item 7.
   - No server, view, route, data or wire change. The PATCH body is the same JSON, give or take key order.
6. Regression risks and migration concerns:
   - **The hook's return value matters.** For any event without its own handler, the dispatcher returns the `onevent` result (`o=r.config.onevent.apply(…)`, @1251). Two call sites read it:
     - `onbeforechange` uses a non-null result as the new cell value (`if(null!=n&&(s=n)`, @24979).
     - `onbeforeinsertrow` cancels on `false`.
     So the hook must return undefined, which a block body guarantees.
   - **Owner decision: should a sort persist?** With this change, a sort or row drag is saved; today it is saved only when an edit happens to follow it. If sorting should not change the data at all, set `columnSorting: false` (and `rowDrag` / `columnDrag: false`) instead. Either choice removes the disagreement between grid and database. Rename, resize and undo still need the value check. Sorting moves formula text with its row without rewriting references; that is what the user already sees on screen.
   - **Clicks now delay saves.** Selection and focus events also re-arm the debounce, so a save waits for a 1 s pause in any interaction, not only in editing. A deny-list of read-only events can tune this, and it fails safe: an unlisted event costs one comparison.
   - **The label lags by up to 1 s.** It switches to "Saving…" when a PATCH is actually sent, not at the keystroke.
   - **Cost.** One `JSON.stringify` of the grid each time the debounce expires. The grid is at most 1 MB (`MAX_DATA_BYTES`), and today's save already pays this once per PATCH.
   - **Same on every backend.** Sheets are app-database rows (`sheets_controller.rb:2-4`).
7. Existing and additional validation required:
   - **Must stay green:** sheet_grid_test "a formula computes in the grid and persists as its raw text" (pins raw-formula persistence and that a cell edit still saves); project_sheets_test and sheets_controller_test (the endpoint is unchanged).
   - **New system tests:**
     - (a) **Undo reaches the row** (red today). Fill A1 with "6" and `assert_persisted_cell(0, 0, "6")`. Click a cell, send Ctrl+Z, then `assert_persisted_cell(0, 0, "")`. Today the poll times out still reading "6".
     - (b) **A header double-click sort reaches the row** (red today). Seed column A with "c", "a", "b", double-click `thead td[data-x='0']`, and poll the stored column until it is sorted.
     - (c) **Selecting cells sends nothing** (green today, pins the early return). Run `@sheet.update_columns(updated_at: 2.days.ago)`, click three cells, wait past the debounce, then assert `@sheet.reload.updated_at < 1.day.ago`. This separates the two times per §15 instead of comparing `.to_i`.
   - **Mutations:**
     - Restore the five handlers in place of `onevent`: (a) and (b) go red.
     - Delete the `body === this.stored` early return: (c) goes red.
     - Make the hook return a value (`onevent: () => true`): `onbeforechange` stores `true` in place of typed values, and the formula test goes red.
8. Confidence: high on the defect. Each gesture was traced to its dispatch site in the vendored bundle bytes, and the option defaults and the event suppression during undo were read from the same file. The system test's own header records that grid bugs are invisible to the server suite. Medium-high on the design: it relies on `onevent` as read from the dispatcher rather than from documentation, it needs the block-body care, and it needs the owner's decision on sorting.

## Opportunity 2: A stock BOM line's unit is stored twice, and only the web create door keeps the two copies in agreement
1. Verdict: recommend
2. Evidence:
   - **Only the web door applies the rule.** `app/controllers/projects/bom_lines_controller.rb:37-42` carries the comment "A STOCK LINE IS COUNTED IN ITS ITEM'S UNIT … (found in review)", then runs `item = current_user.maker_inventory_items.find_by(id: …)` and `attrs[:unit] = item.unit if item`.
   - **The v1 door writes the same model without it.** `app/controllers/v1/maker/bom_lines_controller.rb:9-20,29-34` permits `:unit` and calls `save!` / `update!` with it unchanged. An omitted unit takes the column default `"each"` (`db/schema.rb:106`).
   - **The shipped desktop app hits this path.** Its composer sends the unit dropdown for every kind of line, stock included: `../tinkerex-client/client/maker-app/src/projects.js:424` `unit: $("blUnit").value`, then `:432` `input.inventory_item_id = id`.
   - **An item's unit can change after lines exist.** `app/controllers/inventory_items_controller.rb:160-164` permits `:unit`, the form renders it as a select (`inventory_items/_form.html.erb:31`), and `Maker::InventoryItem` has no unit hook (`inventory_item.rb:25` declares only `before_destroy :release_bom_lines`).
   - **Readers disagree about which copy to use, even within one table row:**
     - Item's copy: the Consume confirm dialog says `#{item.unit}` (`_bom_lines.html.erb:74`); Consume subtracts `line.quantity` from the item's balance and its flash names `item.unit` (`bom_lines_controller.rb:83-85`); the short check and estimated cost compare and multiply `line.quantity` against item-unit figures (`_bom_lines.html.erb:38`, `bom_rollup.rb:22-36`).
     - Line's copy: the Qty cell shows `line.unit` (`_bom_lines.html.erb:64`), as do the public table (`public/projects/_bom.html.erb:58`), the public CSV (`bom_csv.rb:47`) and the API (`v1/maker/bom_lines_controller.rb:38`, `v1/maker/boms_controller.rb:82`).
   - **Only the web door is tested for it:** `test/integration/web/project_bom_test.rb:226-234`.
3. Current complexity or invalid states:
   - **A stock line's unit can disagree with its item's unit.** That is wrong, because Consume, the short check and the cost estimate all treat the line's quantity as being in the item's unit.
   - **Three ways to reach that state today:**
     - Add a stock line from the desktop app with the unit dropdown left at "each" for an item stocked in kg.
     - Send any v1 POST or PATCH that includes a unit, or omits it.
     - Edit an item's unit on the web after lines point at it.
   - **What the user then sees:** the project page shows "2 each" in Qty, while the Consume button on the same row asks "Consume 2 kg of PETG for …?" and takes 2 kg. The public table and the CSV publish "2 each".
   - **The wrong value becomes permanent after the item is deleted.** `release_bom_lines` converts the line to free text, and from then on the stale stored unit is the line's only unit.
4. Proposed representation and why it is simpler: the line's unit column stays a copy, but the model keeps it correct on every write path, so the door no longer has to.
   ```ruby
   # Maker::BomLine
   # A STOCK LINE IS COUNTED IN ITS ITEM'S UNIT (Consume subtracts `quantity` from the item's balance),
   # so for a stock line this column is a copy of the item's, kept true here for every door.
   before_validation :count_in_item_unit
   def count_in_item_unit
     item = inventory_item if inventory_item_id.present?
     self.unit = item.unit if item && item.user_id == user_id     # a dangling or foreign id: leave it to the validations
   end

   # Maker::InventoryItem (S19's file)
   after_update :recount_bom_lines, if: :saved_change_to_unit?
   def recount_bom_lines = bom_lines.where(user_id: user_id).update_all(unit: unit, updated_at: Time.current)
   ```
   - One backfill statement fixes existing rows.
   - The door's lookup and copy (`bom_lines_controller.rb:37-42`) are then deleted.
   - Every reader of `line.unit` (both tables, the CSV and the API) becomes correct with no change of its own.
   - The rule's owner moves from one of three write doors to the model.

   Alternative weighed: override the `BomLine#unit` reader to return the item's unit, following the precedent of `Project#cover_node_id`. It needs no backfill and no item hook, but it costs three things:
   - `validates :unit` would then check the reader, not the stored column. A raw "furlong" could be saved on a stock line and lock the row once it converts to free text, which is the §14d dangling-lock shape.
   - `release_bom_lines` would have to copy the unit at conversion.
   - The v1 index would need `includes(:inventory_item)` to avoid an extra query per line.

   The stored, model-maintained column is the more boring choice.
5. Smallest credible implementation scope:
   1. `app/models/maker/bom_line.rb`: the callback.
   2. A data migration that backfills `maker_bom_lines.unit` from the item for live stock lines, using a correlated `UPDATE … SET unit = (SELECT unit FROM maker_inventory_items WHERE id = inventory_item_id)` that works on both SQLite and Postgres, or a `find_each` over items.
   3. `app/models/maker/inventory_item.rb`: the `after_update`. This is S19's file, so it needs that row's agreement.
   4. `Projects::BomLinesController#create`: delete the lookup and copy, keep the blank-item refusal, and point the comment at the model.
6. Regression risks and migration concerns:
   - **v1 behaviour changes.** A unit sent for a stock line is replaced by the item's unit, and the response shows that. This is the rule the web door already applies. The desktop app needs no change.
   - **The backfill rewrites stored units on rows that disagree.** The display changes to the unit Consume already used. No balance and no ledger row changes.
   - **An item unit edit now relabels its lines** (for example "4 each" becomes "4 pack"). The quantity's meaning changes exactly as the item's own balance already does, and the label stays honest about what Consume will take.
   - **`release_bom_lines` is unaffected.** It uses `update_all`, and the column is already correct when the line converts. Dangling rows planted with `update_columns` give `inventory_item == nil`, so the callback skips them and adds no lock (§14d).
   - **Cost.** One extra item load per stock-line save, on the write path only. Read paths and `page_query_budget_test` are untouched. Same on every backend.
7. Existing and additional validation required:
   - **Proves the rule moved instead of vanishing:** `project_bom_test.rb:229-234` "a stock line takes its item's unit, whatever the composer sent" must stay green after the door code is deleted. Mutation: delete the door code without adding the callback, and it goes red.
   - **Also stays green:** `:289-305`, Consume's flash "Consumed 2 each of NEMA17".
   - **New tests:**
     - Model: `bom.lines.create!(inventory_item: kg_item, quantity: 2, unit: "each")` stores "kg".
     - v1 (red today): POST `/v1/maker/boms/:id/bom_lines` with `{inventory_item_id: <kg item>, unit: "each"}` answers `"unit":"kg"`.
     - Item: `kg_item.update!(unit: "g")` relabels its stock line, and a free-text line is untouched.
     - Conversion (red today): v1-create a stock line on a kg item, destroy the item, and the converted free-text line reads "kg".
   - **Mutations:** drop the callback and the model, v1 and conversion tests go red; drop the `after_update` and the item test goes red.
8. Confidence: high on the disagreement, with every path traced, including the shipped desktop composer. Medium-high on the shape: callback-plus-backfill versus a reader override is the owner's call, and both remove the rule from the door.

## Considered and rejected
- **Task `status` + `completed_at` (a status enum paired with a timestamp, kept in sync by hand).** Not raised again, because it is already recorded as **X6 / F-40** in `docs/AUDIT-2026-08-19.md:993-1019`: ACCEPTED, recommending dropping the column, and still open as a product decision. Three new facts for that record:
  - The web create door permits `:status` (`projects/tasks_controller.rb:105`) but never stamps the time (`:20-29`), so `POST task[status]=done` persists `done` with a NULL `completed_at`. That is a sixth write site X6 does not list.
  - Two rules still coexist for re-sending done on a task already done: the web door re-stamps (`:51`), v1 keeps the old stamp (`v1/maker/tasks_controller.rb:25`).
  - `Task#complete!` is now called only from tests.
- **BOM line's three nullable target columns into one polymorphic or discriminant column.** Rejected:
  - `release_bom_lines`'s conversion and §14d's "targetless filter tests `[nil, ""]`" depend on the three columns being checked with `present?`.
  - The v1 wire format exposes all three ids.
  - `target_kind` (`bom_line.rb:19-25`) already derives the discriminant in one place.
- **The web radio values (`TARGETS = %w[stock file text]`) versus `target_kind`'s symbols.** A second vocabulary for the same three kinds, but it is a UI contract (`project_bom_test.rb:133-135`), and a map between them would be cosmetic.
- **"Short" computed twice** (`_bom_lines.html.erb:38`, `BomRollup#short`). The two agree today; folding them into `rollup.short?(line)` would be a minor tidy-up.
- **BOM panel loading duplicated** in `ProjectsController#show:253-259` and `BomsController#show:13-19`. The two are identical, and a `BomSurface` value object would only move code behind a new type.
- **"Append at end" position assignment repeated in four create doors** (`tasks:22`, `sheets:13`, `connections:10`, `bom_lines:59`). Nothing in the web UI reorders rows, and a concern would only save lines. Wrinkle noted for S18: v1-created rows default to position 0 and so sort first.
- **The task panel's order** is spelled at `projects_controller.rb:439` and `tasks_controller.rb:87`, whereas sheets, connections and releases put their order on the association. Trivial to align; not a finding.
- **Release fields.**
  - `maker_releases.bom_id` and `repo_node_id` are written but never read anywhere in `app/`.
  - On the web, `bom_revision` is always 1, because only v1 ever mints a second revision, and the lines under that revision stay editable. So "BOM rev 1" on a release records nothing a reader can act on.
  - Whether to snapshot BOM lines into a release, or drop the field, is a product question, not a simplification.
- **Release tag state** (`git_tag` / `git_oid` / `repo_node_id` as a nullable trio). Written by exactly one door (`Maker::ReleaseSnapshot`) and read through `short_oid`, so it is consistent by construction.
- **Sheet `data` as one JSON blob versus a cells table.** Decided deliberately in `sheet.rb:4-7`. Perf note: the project page loads every sheet's full blob (up to 1 MB each) only to print `cells.size` (`projects_controller.rb:440`, `_sheets.html.erb:23`). Fixing it needs a stored row count or adapter-specific JSON SQL; this is not a simplification.
- **Tasks answer with a turbo-stream, the other sub-resources redirect.** Documented as deliberate (`bom_lines_controller.rb:10-12`).
- **`TextOnlyRichText`, `ReleaseFile#state_against`, `Connection`.** Small, single-owner and documented; nothing to simplify.
- **A bug, outside this brief: `Projects::EntryPhotosController#destroy`** (`entry_photos_controller.rb:33-38`).
  - It finds any of the user's attachments (`current_user.maker_file_attachments.find`) and then calls `att.attachable.project`.
  - With the id of a project, model or item attachment, it destroys that row and then raises NoMethodError, a 500 after the delete has committed.
  - No view renders this route (`entry_photo_path` appears only in tests).
  - Fix: scope it to `attachable_type: "Maker::BuildLogEntry"`, as `TasksController#project_task!` does, or delete the dead route.
