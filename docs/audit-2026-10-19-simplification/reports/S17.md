## Opportunity 1: One predicate for "can this deployment keep the demo's promise for this account", asked by the door AND by the reset

1. Verdict: recommend

2. Evidence:
   - The door's rule, `lib/tinkerex/demo.rb:48-50`: `!account.nil? && Tinkerex::DemoReset.accounts_sharing_library(except: account).zero?`. Its comment (`:46-47`) says "the button, the links and POST /demo all ask this and nothing else". Callers: `app/views/users/sessions/new.html.erb:9`, `app/views/users/shared/_links.html.erb:8`, `app/controllers/landings_controller.rb:14`.
   - POST /demo does NOT ask it. `app/controllers/demo_sessions_controller.rb:28-46` re-derives `enabled?`, the account, and the co-tenant count, and writes its own sentence (`:43-44`). Both copies landed in the same commit (`f275f0e3`).
   - The reset's rule, `lib/tinkerex/demo_reset.rb:68-88`, has three arms: the seed (`:70-74`); the port, which must be share or s3 (`:75-79`, "only a share or s3 library has; #{port.class} has neither"); and co-tenants (`:81-87`).
   - The co-tenant helper, `demo_reset.rb:93-97`, returns 0 when `port.capabilities.syncable?`. `FileLayer::ChunkRemote` declares `syncable: true` (`app/services/file_layer/chunk_remote.rb:55-56`).
   - Net effect on chunk_remote, with an account at the demo address: `available?` is TRUE, so the button, the "Try the demo" link and POST /demo all sign visitors in. `refusal` refuses on its port arm, so `Tinkerex::DemoResetJob` logs "the reset refused and changed nothing" every night (`app/jobs/tinkerex/demo_reset_job.rb:31-32`). The banner tells each visitor "It resets every night at 04:00 UTC" (`_demo_banner.html.erb:12`).
   - The spec expected chunk_remote to work. `docs/superpowers/specs/2026-10-14-h-public-demo-design.md:64`: "on `chunk_remote` every account has its own library and the demo is just one of them". At `:67` it notes that the Unraid destinations keep "their console demo account". The base Unraid destination is chunk_remote, so pointing `DEMO_ACCOUNT_EMAIL` at that account there produces exactly this state.
   - `tinkerex:demo:setup` asks `refusal` before it mints (`lib/tasks/tinkerex.rake:65-66`), so on chunk_remote the account must come from another door: `tinkerex:owner`, a sign-up (chunk_remote may run `REGISTRATION=open`), OIDC, or a backend switch.

3. Current complexity or invalid states:
   - Three modules (`Demo.available?`, `DemoSessionsController#create`, `DemoReset.refusal`) each compose the admission rule.
   - The three agree on the co-tenant arm: one helper with three callers, and the co-tenant sentence written twice (`demo_sessions_controller.rb:43-44`, `demo_reset.rb:84-87`).
   - They disagree on the port arm, which only the reset asks.
   - So the representation permits a contradictory lifecycle state with no end date: the demo is "live" (door open, banner promising a reset) and also "never reset" (the job refuses nightly).
   - "Every account indexes one library" is spelled as `!syncable?` (`:94`). That is the capability-coincidence §14b warns about: `syncable` means a sync server is behind the port, not that each account has its own library.

4. Proposed representation and why it is simpler: one host predicate, nil or a sentence (this file's existing idiom). The reset adds the seed checks to it; the door asks it alone.
   ```ruby
   # lib/tinkerex/demo_reset.rb
   # NIL WHILE THIS DEPLOYMENT CAN KEEP THE DEMO'S PROMISE FOR `except`: a library the reset can rebuild
   # (only share and s3 have a byte write and a trash of this app's), indexed by no other account.
   def self.host_refusal(except: nil, port: FileLayer.current)
     unless port.is_a?(FileLayer::Share) || port.is_a?(FileLayer::S3)
       return "the demo reset rebuilds the library through the port's byte write and empties its " \
              "trash, which only a share or s3 library has; #{port.class} has neither"
     end
     others = User.where.not(id: except&.id).count  # share/s3: every account indexes the one library
     others.zero? ? nil : "the demo would wipe a library #{others} other ... (today's sentence)"
   end

   def self.refusal(seed_dir: DEFAULT_SEED_DIR, except: nil, port: FileLayer.current)
     why = seed_refusal(Pathname.new(seed_dir)) || host_refusal(except:, port:)
     why && "#{why}; nothing was changed"
   end

   # lib/tinkerex/demo.rb
   def self.available? = (a = account) && Tinkerex::DemoReset.host_refusal(except: a).nil?

   # app/controllers/demo_sessions_controller.rb, replacing :37-46
   if (why = Tinkerex::DemoReset.host_refusal(except: account))
     Rails.logger.warn("[demo] POST /demo answers 404: #{why}")
     return head(:not_found)
   end
   ```
   Why this is simpler:
   - One rule, one sentence, and one place to change it.
   - The door can no longer promise what the reset cannot do.
   - `accounts_sharing_library` and its `syncable?` proxy disappear: after the port arm, every other account shares the library by definition.
   - Cost is unchanged on share/s3 (an `is_a?` before the same one COUNT the sign-in card already pays, `landings_controller.rb:12-13`). On chunk_remote the COUNT is skipped.
   - The seed checks stay reset-only. They walk a directory, and a missing seed is an image defect `test/deploy_hygiene_test.rb` already pins, not a deployment state.

## Safety note (outside this audit's simplification remit; flagged for the owner, not counted above)
`DEMO_ACCOUNT_EMAIL` is a destructive switch that only documentation guards.
- **Whatever row has the address is the demo.** `Tinkerex::Demo.account` is `User.find_by(email: <the setting>)` (`demo.rb:37-40`). Nothing records that the reset minted that row.
- **The demo's three doors act on that row.**
  - The door opens onto it (`demo.rb:48-51`), and signed-out `/` becomes the marketing landing with a one-click button (`routes.rb:61`, `Landing.enabled? = Demo.enabled?`).
  - The nightly job resets it (`demo_reset_job.rb:19-30`).
  - `tinkerex:demo:setup` RESETS an existing account at the address rather than refusing it (`tinkerex.rake:57-71`, pinned by `tinkerex_tasks_test.rb:139-150`).
- **What the reset does to that row:**
  - deletes every top-level node through the port (`demo_reset.rb:139-143`);
  - destroys the row and recreates it with a random password (`:145-154`, `:49`);
  - purges every trash entry with a cutoff of now + 1 h (`:183-193`).
- **Its refusal never looks at the account or the library's contents.** It checks only the seed, the port and co-tenants (`:68-88`).
- **Consequence on share/s3, case 1.** An operator sets the variable to their OWN (only) account. Their front page at once offers one-click sign-in to it. At 04:00 UTC every file in the library is moved to `.trash` and then removed, and their password is replaced.
- **Case 2.** A correctly minted demo on a library that already holds real files loses those files the second night: the first night's scan indexes them into the demo's catalog, and the next delete takes them.
- **The only guard** is the bold sentence at `docs/INSTALL.md:334`. The code elsewhere refuses misconfigurations of this class at boot (`registration.rb:43-55`, `mail_settings.rb:20-28`).
- **Possible interlocks** (each adds behaviour, so none is proposed as a simplification):
  - Record the demo on the row. Add a `users.demo` flag that only `DemoReset.create_account!` sets; `Demo.account` requires it; `setup` refuses an existing unflagged account. Both reasons `demo.rb:13-18` gives for "by address, not by id" still hold for a row flag (it survives the nightly re-mint, and reading it costs no query). The live OVH row would need marking in the same deploy.
  - Have `setup` refuse a library that is not empty on its first mint.

## Considered and rejected
- **One demo "policy" object instead of per-door checks.**
  - Today: one predicate, `Demo.demo?` (`demo.rb:53`), by address and with no query, plus per-door refusals whose response shapes differ by design:
    - redirect + flash (`registrations_controller.rb:143`, `handles_controller.rb:30-34`);
    - paranoid not-found (`passwords_controller.rb:20-30`);
    - form error (`projects_controller.rb:588-593`);
    - JSON 403 (`v1/devices_controller.rb:56,83`);
    - 413 or redirect (`files_controller.rb:1274-1291`, `projects/uploads_controller.rb:38-44`).
  - `demo.rb:19-22` records the per-door decision. Centralising would move branching behind a type.
- **Deriving `open?`/`first_owner?` from `Registration.state` once per request.**
  - `state` is already a four-valued union (`registration.rb:64-69`); `open?` (`:57-59`) and `first_owner?` (`:61`) are separate derivations over the same inputs.
  - A sign-up runs `User.exists?` three times (`registrations_controller.rb:135` via the before_action, `:90`, and `:129` inside Devise's `super`). The reads can disagree only inside the documented first-owner race (`registration.rb:18-20`, "recorded, not guarded").
  - `open?` keys on `== "open"` while `state` keys on `== "closed"`. They diverge only for an invalid mode, which `validate!` refuses at boot.
  - The change would be tidier, not materially simpler.
- **Confirmation columns** (`confirmed_at`, `unconfirmed_email`, `confirmation_token`).
  - These are Devise's state. The app reads them only through Devise predicates (`pending_reconfirmation?` in two views).
  - It writes `confirmed_at` at birth in five doors (`tinkerex.rake:22,32`, `demo_reset.rb:49`, `v1/test_users_controller.rb:22`, `user.rb:244-245`), plus `skip_confirmation!` for the first owner (`registrations_controller.rb:129`).
  - No app code defends against contradictory combinations, so there is nothing to re-model.
- **The passwordless account shape** (`encrypted_password` ""). Four small defences exist: `user.rb:127-133`, `:258-260`, `:273-276`, `registrations_controller.rb:77-85`. Each is argued, and the identity-keyed alternative is a recorded defect (`user.rb:266-272`).
- **`handle`.** Nullable, normalised, validated, unique-indexed, with the publish lock (`user.rb:155-206`). It is clean.
- **Tenant cleanup has ONE definition, not two.**
  - The definition is User's `dependent:` lines (`user.rb:2-98`). Completeness is checked against the live schema (`tenant_cleanup_test.rb:25-27`, `:168-215`), and parent edges by `structural_orphan_test.rb`.
  - `DemoReset` keeps no second list: `recreate_account!` calls `@user.destroy!` (`demo_reset.rb:149`) and says so (`:13-14`). Its port deletes (`:139-143`) are for bytes, not rows.
  - Side note, perf only: `has_many :nodes` is `dependent: :destroy` (`user.rb:3`) although `Node` has no callbacks. The argument `user.rb:12-13` makes for `remote_manifest_chunks`' `:delete_all` applies to nodes too. Account deletion is rare, so it is not raised.
- **One "from ENV or credentials" helper for key material.**
  - `SecretKeyBase.resolve` (`secret_key_base.rb:26-34`): ENV, stripped, blank counted as unset; then the credential; then a generated 0600 file; skipped under `SECRET_KEY_BASE_DUMMY`.
  - `EncryptionKeys.from_env` (`encryption_keys.rb:11-16`): only the keys present in ENV, which the railtie splats over credentials.
  - Both say "ENV wins", but the fallbacks differ on purpose: a generated encryption key would be data-bearing, and a nil splat breaks credential deployments. Two call sites with two rules; a shared helper would need a flag for each difference.
- **`DemoReset#purge_trash!` calling `TrashPurgeJob`'s private `purge_s3!`/`purge_share!` via `send`** (`demo_reset.rb:183-193`), re-implementing `#perform`'s adapter dispatch (`trash_purge_job.rb:62-72`).
  - The reset's s3 arm is the production path (OVH), and no test exercises it: `demo_reset_test.rb:20` pins share, and no demo test uses FakeS3.
  - A public cutoff-taking entry point on the job would remove both the `send` calls and the copied dispatch.
  - Below the bar here: it is small, the failure is loud and bounded (a failed job after the demo is already restored), and the job is S05's file. See Cross-subsystem notes.
- **A first-scan helper shared by every account-creating door.**
  - The sign-up form and `tinkerex:owner` enqueue the first scan (`registrations_controller.rb:90-93`; `tinkerex.rake:21-23`, with its own `!User.exists?` spelling).
  - `User.from_omniauth` (`user.rb:218-250`) never does, so an OIDC-created first account waits up to 15 minutes for the recurring scan (`recurring.yml:24-26`).
  - Low impact, and `scan_job.rb:133-140` records why the trigger is per door.
- **Removing `omniauth_signup`** (`user.rb:112-119`). Vestigial by its own comment; removal is a 24-file test sweep, so line count only.
- **Stale prose** (doc drift, not a simplification; recorded for whoever touches these files):
  - `demo.rb:46-47`: says POST /demo asks `available?`.
  - `demo.rb:7-8`: "the one place that reads it", while `tinkerex.rake:41` reads `DEMO_ACCOUNT_EMAIL` and normalises it on its own.
  - `demo_reset_job.rb:7-9`: says the job resolves the account without `Tinkerex::Demo`; `:20,23` have gone through it since `f275f0e3`.
  - `user.rb:121-126` and `registrations_controller.rb:72-76`: cite a "legacy device-token" / "v1" bootstrap that creates passwordless accounts. No such path exists in `app/`.
  - `user.rb:157-170`: `RESERVED_HANDLES`' own rule ("the app's own top-level paths") misses `demo` (`routes.rb:79`) and `pins` (`routes.rb:200`), both of which `HANDLE_RE` can mint. This is defence in depth only, and reserving `demo` would collide with `DemoReset::HANDLE`.

## Cross-subsystem notes
- **S01**: `Registration.validate!` SHOULD consume the single resolved LIBRARY_BACKEND reading.

  - Keep the `env["REGISTRATION"] == "open"` short-circuit first, and keep the refusal keyed on the operator's REGISTRATION value (`registration.rb:35-42`).

  - `SINGLE_LIBRARY_BACKENDS` (`registration.rb:24`) restates by name the fact that Opportunity 1 spells by class (`demo_reset.rb:75`); one declaration next to S01's reading could serve both.

- **S18**: `V1::TestUsersController` (`test_users_controller.rb:14-26`) mints confirmed accounts outside `Tinkerex::Registration`. On share/s3 that is the exposure `registration.rb` refuses at boot. - **S20**: under Opportunity 1, `landings_controller.rb:11-14` keeps its "a find_by and a COUNT" cost on share/s3 and drops the COUNT on chunk_remote. The landing's own gate (`Landing.enabled? = Demo.enabled?`, `landing.rb:67`) is untouched.
- **S23**: the interlock in the Safety note would be a `users` column, and the schema is S23's.
