## The row's questions, answered briefly
- **Scoping.** One shared shape already. Every action goes through `current_user.maker_*`, and nested parents are found the same way. Nothing to change.
- **Strong params.** Each controller has its own list, and the lists genuinely differ by model. The web inventory door says it shares v1's list (inventory_items_controller.rb:156-158).
- **Serialization.** Fourteen hand-written serializers. The overlap is small and nothing depends on it; see Considered and rejected.
- **Error mapping.** One shared map in the base controller. Three controllers add their own handlers, and each has a real reason. The exception is the map's `ArgumentError` entry (Opportunity 2).
- **Login response and the sync-grant failure.** Sound.
  - `sync` is nil exactly when `!syncable?`, decided by one guard, so a response can never pair `library.syncable: false` with a grant.
  - "503 and no maker device" depends on ordering: the grant is brokered before `Device.register!`. That order is written out twice, and both doors are pinned (device_login_test.rb:155-186).
- **Web and v1 doors writing the same model: one rule or two?**
  - **Two, for four rules.** Ledger project scope, ledger delta bounds, BOM stock-line unit and task completion stamp are enforced only by the web doors. That is drift, not variation (Opportunity 1).
  - **Everywhere else the difference is real.** File attachments, BOM design-file targets and project destroy differ from v1 for recorded reasons (see Considered and rejected).

## Opportunity 1: Rules only the web doors enforce — move each into the model or funnel both doors already call
1. Verdict: recommend
2. Evidence:
   **(a) The inventory ledger.** `Maker::InventoryTransaction.apply!` is the single funnel for every stock change. It has four callers:
   - web adjust (inventory_items_controller.rb:116);
   - web initial quantity (:147);
   - web BOM consume (projects/bom_lines_controller.rb:83);
   - v1 adjust (v1/maker/inventory_items_controller.rb:35).

   Two of its rules live only in the web adjust door:
   - **Project provenance.**
     - Web: inventory_items_controller.rb:109-114 says "A FOREIGN PROJECT ID IS DROPPED, NOT REFUSED — find_by (not find) against the user's own projects". This is pinned by test/integration/web/inventory_test.rb:258-271.
     - v1: `project_id: params[:project_id]` is passed straight into apply! (v1/maker/inventory_items_controller.rb:38).
     - The model deliberately keeps the project as a soft reference: `belongs_to :project, optional: true` with no ownership check (inventory_transaction.rb:10-19). Its comment says "a foreign or since-deleted project renders as '—'".
     - The ledger page does not do that. It preloads with an unscoped `includes(:project)` (inventory_items_controller.rb:51), then renders `t.project ? link_to(t.project.name, project_path(t.project)) : "—"` (inventory_items/show.html.erb:88). `Project#to_param` is the slug (project.rb:159).
     - No v1 test sends a `project_id` to adjust. cross_tenant_fk_test.rb covers supplier, location, item and task references only.
   - **Delta bounds.**
     - Web: inventory_items_controller.rb:121-138 has `MAX_DELTA = BigDecimal("999999999.999")` and `parse_delta`, which accepts only finite, non-zero deltas that fit the column. Its comment records that an Infinity row breaks quantity_cached == SUM(delta) "silently ... only deleting the item recovers".
     - The test that pins this says "at both doors" (inventory_test.rb:213-256). Both doors it means are web doors.
     - v1 passes `delta: params.require(:delta)` (:37). The model checks only `numericality: true` (inventory_transaction.rb:21), and the column is decimal(12,3) (schema.rb:224).

   **(b) The unit of a BOM stock line.**
   - Web: projects/bom_lines_controller.rb:37-42 says "A STOCK LINE IS COUNTED IN ITS ITEM'S UNIT ... (found in review)" and sets `attrs[:unit] = item.unit if item`.
     - The rule was added by 734e45e0 (2026-09-04), which touched only the web door.
     - It is pinned only on the web side (web/project_bom_test.rb:226-234).
   - v1: bom_lines_controller.rb:29-33 permits `:unit` alongside `:inventory_item_id`, and create and update save it as sent (:11, :18).
     - The column default is "each" (schema.rb:106).
     - The model checks only that the unit is in the allowed list (bom_line.rb:13).
   - The shipped desktop app sends its composer's unit dropdown for every kind of line, stock lines included (tinkerex-client client/maker-app/src/projects.js:421-432). The dropdown's first option is "each" (:25).
   - Some readers count a stock line's quantity in the item's unit:
     - Consume (projects/bom_lines_controller.rb:83; its flash at :85);
     - Consume's confirmation text (_bom_lines.html.erb:74);
     - `BomRollup#estimated_cost` and `#short` (bom_rollup.rb:22-36);
     - the panel's "short" flag (_bom_lines.html.erb:38).
   - Other readers print the line's own unit:
     - _bom_lines.html.erb:64;
     - public/projects/_bom.html.erb:58;
     - bom_csv.rb:47;
     - v1 `line_json` (:38) and `rollup_line_json` (boms_controller.rb:82).

   **(c) The task completion stamp.** It is derived from the status in three controller spellings:
   - v1 create: `task.completed_at ||= Time.current if task.status == "done"` (tasks_controller.rb:16).
   - v1 update: stamps only when the stamp is nil, and clears it on any other status (:23-28).
   - Web update: always re-stamps on done and clears otherwise (projects/tasks_controller.rb:48-53). Its comment names the split (:44-45): "`Time.current`, not v1's `completed_at ||=` ... this is not a fourth spelling".

   Two more facts about tasks:
   - Web create (:20-29) permits `:status` (:104-106) but stamps nothing.
   - The model's `complete!` (task.rb:44-46) has no production caller. Only task_test.rb:100 calls it.

   The house idiom for a column derived on the model: `before_validation :ensure_slug` in Project (project.rb:129), and `:ensure_logged_at` in BuildLogEntry (build_log_entry.rb:16).
3. Current complexity or invalid states:
   **(a) Cross-tenant disclosure.**
   - Any device-token holder can post an adjust to their own item with `project_id: N` set to another tenant's project. The ledger row stores N.
   - Their own web ledger page then shows that project's name and slug.
   - By walking N, they can list every tenant's project names, private ones included. This works on any deployment with more than one user. chunk_remote accepts REGISTRATION=open (§8).
   - The shipped client cannot trigger this: `adjust_inventory(delta: i64)` sends no project_id (maker.rs:1105-1118). It takes a hand-built request.
   - The model comment ("foreign ... renders as '—'") holds only for a project that has been deleted.

   **(a) Bad deltas.**
   - The v1 door posts zero-delta rows, which the web refuses.
   - It also accepts deltas that do not fit the column. SQLite stores them beyond the declared precision; Postgres overflows into an unmapped 500.
   - The web test also lists non-finite deltas. Whether a JSON body can get those into the ledger through v1 is not verified here.

   **(b) A stock line's unit can disagree with its item.**
   - A stock line created or edited through v1 keeps whatever unit the client sent, or "each".
   - Such a row prints "4 each" on the project page, the public page and the published CSV. Consume, meanwhile, subtracts 4 g and its confirmation says "4 g".
   - Lines made on the web drift too, when someone later edits the item's unit. Both inventory doors permit `:unit` (inventory_items_controller.rb:160-164; v1 :58-63), and the line's unit is a copy written once.

   **(c) The task state is maintained by each writer.**
   - Status and completed_at form a two-column state.
   - Any writer that is not one of the three spellings can produce an invalid pair: done with no stamp, or todo with a stamp. Examples are a web create with status done, the console, or a future door.
   - The two spellings also disagree on done → done: v1 keeps the stamp, the web re-stamps.

   **Common cause.** Each rule was added at the door being worked on. 734e45e0 and 84a2df67 both describe their rule as "at the door", and both put it in the web door only. The v1 door, written earlier, writes the same models through the same funnel.
4. Proposed representation and why it is simpler: each rule moves to the object both doors already call, and the doors keep only their own UX.
   ```ruby
   # (a) Maker::InventoryTransaction — the ledger's one funnel
   MAX_DELTA = BigDecimal("999999999.999")      # moved from InventoryItemsController; the column is decimal(12,3)
   validates :delta, numericality: { other_than: 0, in: -MAX_DELTA..MAX_DELTA }, on: :create   # Infinity and NaN fail the range
   def self.apply!(item:, user:, delta:, reason: "adjusted", project_id: nil, note: nil)
     project_id = user.maker_projects.where(id: project_id).pick(:id) if project_id.present?   # dropped, not refused
     # ... unchanged ...
   end

   # (b) Maker::BomLine — a stock line has no unit of its own
   before_validation { self[:unit] = stock_item.unit if stock_item }   # the stored copy stays a valid unit for a later retarget
   def unit = stock_item&.unit || super                                  # readers see the item's unit, even after the item's unit is edited
   private def stock_item = (inventory_item if inventory_item_id.present?)
   # Maker::InventoryItem#release_bom_lines (:109): lines.update_all(part_name: name, unit:, updated_at: ...)  # the unit goes with the line, like name and supplier

   # (c) Maker::Task
   before_save :stamp_completion, if: -> { new_record? || will_save_change_to_status? }
   def stamp_completion = self.completed_at = (status == "done" ? (completed_at || Time.current) : nil)
   def complete! = update!(status: "done")
   ```
   Why this is simpler:
   - Each rule exists once, on its model, instead of once per door.
   - The v1 controllers pick the rules up without new code. v1 tasks_controller.rb loses its seven derivation lines.
   - The web doors lose their special cases (bom_lines :37-42, tasks :48-53). Where they keep a pre-check for friendlier messages, it reads the model's constant.
   - Any future door (an addon, an import, the console) gets the rules for free.

   A smaller alternative for (b): move only the write rule into the model, and backfill existing stock lines. It is simpler, but it still drifts when an item's unit is edited.
5. Smallest credible implementation scope. Each step lands on its own, in this order:
   1. (a), owned by S19.
      - inventory_transaction.rb: add MAX_DELTA, the create-only validation and the project scope in apply!.
      - inventory_items_controller.rb: `parse_delta` reads `Maker::InventoryTransaction::MAX_DELTA`. The `find_by` at :114 can stay as UX or go.
      - Correct the model comment at :10-19.
      - No v1 code change.
   2. (b), owned by S16 and S19.
      - bom_line.rb: as above.
      - inventory_item.rb:109: the release carries the unit.
      - projects/bom_lines_controller.rb:41-42: delete the lookup and the override, keeping the "Pick a stock item" refusal at :36.
      - v1 bom_lines_controller.rb:6: add `bom.lines.includes(:inventory_item)`. Optionally do the same in boms_controller.rb:36, whose rollup already loads per line.
   3. (c), owned by S16.
      - task.rb: add the callback.
      - v1 tasks_controller.rb: delete :16 and :23-28, so create and update become `save!` and `update!(task_params)`.
      - projects/tasks_controller.rb: delete :48-53.
6. Regression risks and migration concerns:
   **(a)**
   - v1 adjust starts answering 422 for zero and out-of-range deltas. A zero adjust from the desktop app is newly refused, as it already is on the web.
   - A foreign project_id is silently dropped and the response is still 201. That is the web's recorded choice. Refusing instead would be a decision, and it would then have to become the web's answer too.
   - `on: :create` is required. inventory_transaction_test.rb:55-58 asserts that `update!(delta: 0)` raises ReadOnlyRecord. An unconditional validation would raise RecordInvalid first.
   - Rows that already carry a foreign project_id stay until cleaned. Fix them with a one-off update that nulls project_ids not owned by the row's user, or make the view render only a project the viewer owns (S19's choice).

   **(b)**
   - Wire: a stock line's `unit` in v1 responses becomes the item's unit, and a unit the client sends for a stock line is ignored, just as the web composer's is.
   - The desktop composer's unit select then has no effect for stock lines (a client follow-up).
   - No new queries on web or public pages, which already preload `:inventory_item` (projects_controller.rb:254, projects/boms_controller.rb:15, public_project.rb:190). The v1 index needs the `includes`.
   - Editing an item's unit now relabels its lines immediately. This is intended.

   **(c)**
   - On the web, done → done stops re-stamping. The UI never sends it: _task.html.erb:7 offers only the other statuses.
   - `complete!` on a task that is already done keeps its original stamp. It has no production caller.
   - Done tasks created in test fixtures get a stamp.

   **Backend legs:** none of the three steps touches FileLayer. The share, s3 and chunk_remote legs change only by the added tests, which are identical on all three.
7. Existing and additional validation required:
   - Existing pins:
     - (a): web inventory_test.rb:213-271; v1 inventory_items_test.rb:29-46; inventory_transaction_test.rb:55-64.
     - (b): web project_bom_test.rb:226-234 and :270-284; v1 bom_lines_test.rb; referential_integrity_test.rb:73-145.
     - (c): web project_tasks_test.rb:84-164; v1 tasks_test.rb:40-47; task_test.rb:100-105.
   - New tests, each with the mutation it must fail under:
     - **(a) Foreign project id.** On v1, an adjust carrying another user's project_id answers 201 with project_id nil. The owner's ledger page must not contain the foreign project's name. Fails when the scope line in apply! is deleted. Add a model test of apply! too.
     - **(a) Bad deltas.** On v1, a delta of 0 answers 422, and so does 1e10. Also probe `{"delta": 1e400}` and `"Infinity"` and assert that no row is written. Fails when `other_than` or the range is dropped.
     - **(a) Immutability.** The model test `update!(delta: 0)` still raises ReadOnlyRecord. Fails when `on: :create` is dropped.
     - **(b) Unit.** On v1, a stock line posted with `unit: "each"` against a "kg" item answers `unit: "kg"`, and the line reads "g" after the item's unit is edited to "g". Fails when `def unit` is deleted. A released line keeps the item's unit; fails when `unit:` is dropped from the release's update_all.
     - **(c) Task stamp.** Creating a task with status done stamps it, done → todo clears the stamp, and done → done keeps the original stamp. Set up inside `travel_to(3.days.ago)` and assert equality, not presence; §15 warns that `.to_i` comparisons cannot fail. Fails when the callback is deleted, which also turns the existing v1 and web status tests red.
8. Confidence:
   - **High** for (a)'s project scope and for (b). Each was traced from the door through the model to the view that renders it, but none was executed (this was a read-only audit). Confirm (a) with one request before filing it as a security issue.
   - **Medium** for whether non-finite deltas can reach the ledger through v1's JSON.
   - **High** for (c), with a small payoff: completed_at's only reader is the v1 JSON, which the desktop app deserializes and never displays.

## Opportunity 2: Retire `rescue_from ArgumentError` from V1::BaseController — the engine-era entry now maps only bugs and misconfiguration to 422
1. Verdict: recommend
2. Evidence:
   - **The entry.** base_controller.rb:37 is `rescue_from ArgumentError, with: :unprocessable`, and the handler at :44 renders `e.message` back to the client.
   - **Its history.**
     - 50e11933 (2026-07-15) added it with this comment: "A rejected-but-well-formed request (a malformed manifest hash, a move that would create a cycle, a version that isn't part of the named conflict — all raise ArgumentError) is a client error (422) ... Keep the raisers narrow so this never masks a genuine bug". All three named raisers were sync-engine endpoints.
     - 161d3b20 moved the five rescues into the engine's base controller.
     - 9658a573 (Arc A) rebuilt this class on ActionController::API, copied the five rescues back and dropped the rationale.
     - Arc D Part 2 then removed every endpoint the rationale named.
   - **No intended producer remains.**
     - There is no `enum` anywhere in app/models, so no enum assignment can raise.
     - There is no `raise ArgumentError` in app/models or in Maker::Previews.
     - Every 422 asserted under test/integration/v1 comes from a model validation (RecordInvalid) or from the explicit stale_version render (previews_controller.rb:99-101).
   - **The one explicit producer left is a misconfiguration.**
     - `FileLayer.build` raises `ArgumentError, "unknown LIBRARY_BACKEND ..."` (file_layer.rb:203). `@current ||= build` retries it on every call (:127-129).
     - v1 reaches it through DevicesController#sync_grant_for (:113) and #library_info (:100), and through PreviewsController#refuse_stale_version! (:96), whose own rescue at :102 names only NotFound and FetchError.
     - So a misconfigured deployment answers POST /v1/devices/login with 422 `{"error":"unknown LIBRARY_BACKEND \"chunk\""}`.
     - A chunk_remote deployment missing SYNC_PUBLIC_URL fails the same call through `LibraryBackendCheck::Error` (lib/library_backend_check.rb:90, :145) and answers 500. Two misconfigurations get two different answers.
   - **Ruby's own errors are caught too.** Arity drift and missing or unknown keywords raise ArgumentError, and come back as 422s carrying the interpreter's message. Examples: `Enqueue.call(user:, node_id:, name:, version_id:, ...)` (enqueue.rb:79) and `SyncGrant#call(user, device_name:)`.
   - **The house rule says this should not be rescued.**
     - move_node.rb:58-64: "Projects::AttachmentsController rescues this one and lets bare ArgumentError 500, which is what a programming error should do".
     - attach_to_project.rb:381-387: a too-wide rescue is "a machine for turning bugs into outage messages that no test can see. It caught bare ArgumentError until a review ...".
     - project_intake.rb:799-803 makes the same point.
     - architecture_invariants_test.rb:957 gives, as reason 3 for never rescuing NotImplementedError: "laundering a real s3 MISCONFIGURATION at FileLayer.build into a routine-looking response".
   - **It is the only one.** This is the only class-level `rescue_from ArgumentError` in app/controllers. The web's inventory_items_controller.rb:136 rescues locally, around one BigDecimal parse.
3. Current complexity or invalid states:
   - The map has five entries. Four have live producers:
     - RecordNotFound;
     - ParameterMissing;
     - RecordInvalid;
     - RecordNotUnique (`find_or_create_by!` races, and index_maker_file_attachments_uniqueness at schema.rb:178).
   - The fifth's producers left with the engine.
   - Its only effect now: a programming error or misconfiguration in any of the 15 controllers on this base reads as "your request was invalid". It sends internals to the client and never reaches error tracking as a 500.
   - So a programming error gets two answers across the app: 500 on the web, 422 on v1.
4. Proposed representation and why it is simpler:
   - Delete the line. The map then lists exactly the domain errors that have live producers.
   - A future v1 action with a genuine client-input ArgumentError gets a named subclass and its own `rescue_from`, following the MoveNode::InvalidName precedent.
5. Smallest credible implementation scope:
   - app/controllers/v1/base_controller.rb:37: one line, plus the test below.
   - If S01's Opportunity 1 lands, the FileLayer.build producer moves to boot as well, and the rescue would have no explicit producer at all.
6. Regression risks and migration concerns:
   - Any request that hits an ArgumentError today gets 500 instead of 422. That is the intent.
   - The Rust client maps any non-2xx from a maker call to `Error::Server`.
   - `is_retryable` does treat 500 as retryable, but `with_retry` wraps only chunk PUT and GET (tinkerex-client lib.rs:369-384, 818, 838). No maker call starts retrying.
   - Rails already converts ArgumentErrors that user input could cause upstream:
     - bad encoding becomes a 400 BadRequest;
     - time-zone-aware datetime casts rescue ArgumentError to nil;
     - decimal casts rescue string parse errors.
   - Backend legs: no effect.
7. Existing and additional validation required:
   - Existing: every v1 422 test must stay green on all three legs. They are all RecordInvalid-based.
   - New, a v1 integration test:
     - Make `FileLayer.current` raise ArgumentError, with a stub adapter or with LIBRARY_BACKEND=bogus plus `FileLayer.reset!`.
     - Log in, and assert the login is not answered 422.
     - The test env sets `show_exceptions = :rescuable` (config/environments/test.rb:62), so the assertion is `assert_raises(ArgumentError)`.
     - It fails when line 37 is restored.
   - Optional, a static pin in architecture_invariants_test.rb (S26) that no controller declares `rescue_from ArgumentError`.
     - It needs a negative case showing that a named subclass is allowed.
     - Otherwise a broader regex would pass vacuously over the MoveNode precedent.
8. Confidence:
   - High on the facts. The history and the producers were read directly.
   - Medium-high that no hidden producer exists. This rests on inspection, not on running the three legs.

## Considered and rejected
- **A shared serializer layer, or `as_v1_json` per model.** The duplication is small and nothing depends on it:
  - `attachment_json` appears three times, identically (items:72-75, file_attachments:36-39, projects:55-58).
  - There are two build-log shapes (projects:51-53 and build_log_entries:31-35). Both satisfy the only client, whose `BuildLogEntry` reads id, body, entry_type and logged_at (maker.rs:306-313).
  - The tag hash appears twice in tags_controller (:6 and :11).
  
  This would be line count only.
- **A generic CRUD concern for the eight index/show/create/update/destroy resources.** It would move branching behind a new type. Ordering, filters, the `full:` shapes and the nesting genuinely vary between them.
- **Folding DevicesController#login and #create into one `enrol!`.**
  - Two client types read two shapes (RegisterResponse vs DeviceResponse, tinkerex-client lib.rs:58-75 and 603-609).
  - The grant-before-register order is pinned for both doors.
  
  It would save about four lines.
- **`sync_grant_for` gating a ChunkRemote-specific call on `syncable?`** rather than §14a's class-check precedent. It is exact today, with one syncable backend. Changing it is hypothetical extensibility.
- **Removing the top-level `head_seq` from the login answer.** Nothing writes users.head_seq any more, but §14e records it as "NOT DEAD CODE TO SWEEP", and the Rust RegisterResponse requires the field (lib.rs:64).
- **Deleting `touch_seen!`.**
  - It writes devices.last_seen_at on every authenticated request, and nothing in this app reads the column. Deleting it is one line.
  - But stamping last_seen_at is one of the auth steps that §14j's parity note lists (authentication.rb:24-26), so it is a decision for both repos together.
  - The payoff is low.
- **Requiring `taskable_type` and `taskable_id` together, or neither, at the v1 door.** That would add a validation, not simplify anything. task.rb:50-60 records the half-filled state as deliberately tolerated.
- **FileAttachmentsController#resolve_parent (:26-30).**
  - It takes the first parent key present anywhere in the params, path or body. A body `item_id` therefore overrides the route's `project_id`.

- **File attachments and BOM design-file lines, v1 vs web.** The difference is real variation, not drift.
