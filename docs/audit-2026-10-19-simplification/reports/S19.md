## Opportunity 1: Let `Maker::InventoryTransaction` own what a postable ledger row is, instead of one of its four doors
1. Verdict: recommend
2. Evidence:
   - The model that states the invariant does not enforce its precondition. `inventory_transaction.rb:21` `validates :delta, presence: true, numericality: true`; `:54-57` keeps `quantity_cached == SUM(delta)` by `update_all(["quantity_cached = quantity_cached + ?", delta])`. ActiveModel 8.1 numericality parses a string with `parse_float(Kernel.Float(raw_value), ...)` (numericality.rb:82) and counts anything non-nil as a number (:99), so "Infinity", "-Infinity", "NaN" and "1e400" all **pass** `numericality: true`, and 0 passes too.
   - The rule lives in ONE controller. `inventory_items_controller.rb:123-138` holds `MAX_DELTA` and `parse_delta` (finite, non-zero, `abs <= 999999999.999`). It is applied at `:101` (adjust) and `:144` (initial quantity). The same controller re-checks `REASONS` at `:104-107`, which the model already validates at `:22`. It also scopes the project at `:109-114` ("A FOREIGN PROJECT ID IS DROPPED, NOT REFUSED").
   - The v1 door passes everything straight through. `v1/maker/inventory_items_controller.rb:35-39`: `apply!(item:, user: current_user, delta: params.require(:delta), reason: params.fetch(:reason, "adjusted"), project_id: params[:project_id], note: params[:note])`. The web comment at `inventory_items_controller.rb:98-99` says the web action is "mirroring the v1 API's own adjust action ... field-for-field". It does not mirror it: the web refuses zero, non-finite and out-of-column deltas and drops a foreign project, while v1 accepts all of them.
   - A fourth door, BOM consume (`projects/bom_lines_controller.rb:83`, `delta: -line.quantity`), feeds a quantity validated only `greater_than: 0` (`bom_line.rb:12`). ActiveModel compares the parsed value, and Infinity > 0.
   - The corruption mechanism has already been measured through this exact `apply!`. Commit 499ceddf says an Infinity row stored as Infinity, the cached balance stayed put, `rebuild_quantity_cached!` then wrote Infinity back, the immutable ledger left no repair short of deleting the item, and NaN reached the DB as NULL and returned a 500. Its fix "serves both doors (adjust, the initial quantity)", meaning the two **web** doors. The SQLite adapter explains the split: the INSERT binds `BigDecimal#to_f` (sqlite3/quoting.rb:104-107), while the increment's `update_all` quotes a non-finite numeric as the string literal `'Infinity'` (:53-60).
   - A foreign project leaks on the read side. `belongs_to :project, ... optional: true` (`inventory_transaction.rb:19`) is unscoped. `InventoryItemsController#show` preloads it (`:51`, `includes(:project)`), and `show.html.erb:88` renders `link_to(t.project.name, project_path(t.project))`. So a row posted through v1 with another user's `project_id` shows **that user's private project name and slug** on the poster's own ledger page. The model comment at `inventory_transaction.rb:16-17` claims "a foreign or since-deleted project renders as '—'". That is true for a deleted project, which Project nullifies (`project.rb:126`). It is false for a foreign project that still exists. Commit 84a2df67 made the same claim and assumed the web door was the only writer.
3. Current complexity or invalid states: The definition of a valid ledger post is split three ways:
   - the model owns `reason`;
   - the web controller owns delta validity and project tenancy, and re-owns `reason` so it can redirect;
   - v1 and BOM consume own nothing.

   That split permits states the model's own comments say cannot exist:
   - an immutable Infinity/1e400 row whose balance never moved, so `quantity_cached` and `SUM(delta)` disagree permanently (`show`'s running-balance walk at `:55-56` then prints garbage);
   - a NaN request that returns 500;
   - zero-delta no-op rows (v1 only);
   - ledger rows pointing at another tenant's project, which the web page then discloses.

   The divergence exists because each new door has to remember to copy a private controller method. Two of four did not.
4. Proposed representation and why it is simpler: put the rule where the invariant is stated and where all four doors already meet. Every door then becomes a translator of `RecordInvalid`:
   ```ruby
   # app/models/maker/inventory_transaction.rb
   MAX_DELTA = BigDecimal("999999999.999")   # moved from the web controller; the column is decimal(12,3)
   validates :delta, presence: true, numericality: { other_than: 0, in: -MAX_DELTA..MAX_DELTA }
   # (`in:` is RANGE_CHECKS -> Range#include?, which is false for +/-Infinity and NaN; "1e400" parses to Infinity)

   def self.apply!(item:, user:, delta:, reason: "adjusted", project_id: nil, note: nil)
     transaction do
       locked = Maker::InventoryItem.where(id: item.id, user_id: item.user_id).lock.first!
       # Provenance is optional: a project that is not the item owner's is DROPPED, not refused,
       # at every door (the rule InventoryItemsController#adjust used to apply alone).
       project_id = project_id.presence && Maker::Project.where(id: project_id, user_id: locked.user_id).pick(:id)
       txn = locked.transactions.create!(user:, delta:, reason:, project_id:, note: note.presence)
       item.reload unless item.equal?(locked)
       txn
     end
   end
   ```
   The web `adjust` then becomes `txn = apply!(... delta: t[:delta], reason: t[:reason].presence || "adjusted", project_id: t[:project_id], note: t[:note])`, using `signed(txn.delta)` for the flash, plus `rescue ActiveRecord::RecordInvalid => e` mapped to the existing alert redirect. `parse_delta`, `MAX_DELTA` (with its 7-line comment), the REASONS re-check and the project lookup all go, about 30 lines. v1 needs **no edit**, because `V1::BaseController` already maps `RecordInvalid` to 422 (`v1/base_controller.rb:36`), the same answer v1 already gives an invalid reason. The project check is a normalisation inside `apply!`, not a re-run validation. It therefore adds no `if: fk.present?` lock (§14d), and it keeps project_id the soft reference the model comment insists on: ledger rows are never re-saved (`before_update` raises), and Project's `:nullify` still clears deleted ones.
5. Smallest credible implementation scope:
   1. `app/models/maker/inventory_transaction.rb`: the `delta` validation and `MAX_DELTA`; project scoping and `note.presence` in `apply!`; correct the false "foreign ... renders as '—'" sentence (`:16-17`).
   2. `app/controllers/inventory_items_controller.rb`: `adjust` rescues `RecordInvalid`. `post_initial_quantity!` rescues it too, to keep its pinned silent skip (`inventory_test.rb:252-255`); surfacing the error instead is a UX choice. Delete `parse_delta`/`MAX_DELTA`/`:104-107`/`:109-114`, and update the stale "field-for-field" comment.
   3. No change to `V1::Maker::InventoryItemsController`.
   4. S16 follow-up, one line: `Projects::BomLinesController#consume` should rescue `RecordInvalid` into its flash. Otherwise a bad line quantity gives a 500 (better than the current silent corruption, but still a 500).
   5. Optional one-off census of existing rows: `project_id` whose project's `user_id` differs from the row's `user_id` can be nulled with `update_all`, the same path Project's `:nullify` already uses beneath the immutability guard. Non-finite rows can only be reported; deleting the item is the only repair.
6. Regression risks and migration concerns:
   - API: v1 `adjust` answers 422 instead of 201 for 0, ±Infinity, NaN, 1e400 and out-of-column amounts. A foreign `project_id` is now stored as null, matching the web. The desktop client sends `delta: i64` and never `project_id` (tinkerex-client `maker.rs:1105-1125`), so the only change it can observe is a zero delta.
   - Tests that must change: `inventory_transaction_test.rb:57` asserts `ReadOnlyRecord` from `txn.update!(delta: 0)`. With `other_than: 0`, validation runs before `before_update`, so it would raise `RecordInvalid` and the test would go red for the wrong reason. Change it to a valid delta (e.g. 1) so it still proves immutability.
   - Web flash text: the three `/Enter a non-zero/` assertions (`inventory_test.rb:221, 232, 248`) need either a custom validation message or new regexes. The reason test matches `/reason/i` and passes unchanged.
   - Query count: `apply!` gains one PK lookup on `maker_projects` when `project_id` is present. The web door loses its own `find_by`, so it nets zero. `page_query_budget_test` measures `GET` show, which is unaffected.
   - Backends: no FileLayer involvement, so share, s3 and chunk_remote run identical code and new tests add equally to all three legs.
   - Data: rows already posted through v1 with a foreign project keep disclosing it until the census or cleanup runs. The fix is write-side; a read-side `t.project.user_id == @item.user_id` check in `show.html.erb:88` is optional belt-and-braces if the census finds any.
7. Existing and additional validation required:
   - Behaviour pinned today:
     - `test/integration/web/inventory_test.rb:196-282`: posts, zero, non-numeric, non-finite at both web doors, foreign project dropped, bad reason.
     - `inventory_test.rb:319-341`: initial quantity.
     - `test/models/maker/inventory_transaction_test.rb` (all).
     - `behavioral_edges_test.rb:39-58`: `apply!` reload and return value.
     - `structural_orphan_test.rb:200-224`.
     - `test/integration/v1/maker/inventory_items_test.rb:29-46`.
   - New tests:
     - (a) Model: each of `%w[Infinity -Infinity NaN 1e400 0]` makes `apply!` raise `RecordInvalid`, with the ledger count and `quantity_cached` unchanged. Mutation: dropping `in:` turns the ±Infinity/NaN/1e400 cases red; dropping `other_than: 0` turns "0" red.
     - (b) v1: `POST /v1/maker/inventory_items/:id/adjust` with the same five strings (`as: :json`) answers 422 and leaves the ledger unchanged. **Run this first: it should be RED on today's code.** That is the probe for the gap this audit could only read.
     - (c) v1: adjust with another user's project answers 201 and stores `project_id` as nil. A web GET of the item page, signed in as the poster, must not contain the foreign project's name (`assert_select "td.col-project", text: /<name>/, count: 0`). Mutation: drop `user_id: locked.user_id` from the scoping and both assertions go red.
     - (d) S16: consuming a stock line whose quantity was planted as Infinity (`update_columns`) posts no ledger row.
8. Confidence: high for the divergence and the ledger corruption. The code path from `params.require(:delta)` to the INSERT has no check, the ActiveModel and SQLite adapter sources confirm the four values pass validation and split between INSERT and increment, and 499ceddf measured the outcome through this same `apply!`. Medium-high for the cross-tenant name/slug disclosure: it follows directly from the unscoped `belongs_to`, the preload and `show.html.erb:88`, but it has not been run. Test (c) is the probe.

## Considered and rejected
- **Drop `quantity_cached` and derive the balance from the ledger.** Rejected: the cache is read in SQL by `low_stock`, the `SORTS["quantity"]` sort, home's attention list and `BomRollup`, so deriving it means a grouped join or correlated subquery on every list. Its only writer is one atomic SQL increment inside `apply!`'s locked transaction, plus a repair method. The disagreement risk is input validation (Opportunity 1), not the cache design.
- **`attr_readonly :quantity_cached`.** Rejected: neither door's permit list includes the column (web `:160-164`, v1 `:58-63`). `rebuild_quantity_cached!` writes through `update_column`, which a readonly attribute refuses. About 8 test fixtures seed the column via `create!`. This would harden a door no production path opens.
- **`apply!`'s row lock is redundant with the atomic increment, and `item.equal?(locked) == false` is always true.** Rejected: line-level. The lock also provides `first!`'s owner and existence check. Not material.
- **Derive `user:` from the item inside `apply!`.** Rejected: the redundant argument permits `txn.user_id != item.user_id`, but every caller passes `current_user` with a `current_user`-scoped item, so the state is unreachable, and the change touches about 31 call sites. Opportunity 1 scopes the project by `locked.user_id`, which sidesteps the question.
- **A cycle guard on `Location#parent_id`.** Rejected: v1 `PATCH` (`v1/maker/locations_controller.rb:18-22`) can set `parent_id` to the location itself or to a descendant, because `parent_belongs_to_user` (`location.rb:21-25`) checks ownership only. But nothing walks the tree: the only reader is `location.parent.name`, one hop, at `locations/index.html.erb:18-19`. No loop is reachable, so the guard would be hypothetical.
- **A shared `*_belongs_to_user` validator or concern.** Rejected: these are four-line methods; the derived guards (`cross_tenant_fk_test`, `structural_orphan_test`, `tenant_cleanup_test`, `referential_integrity_test`) already cover the set; and §14d makes the `dependent:` partner deliberately per-edge (nullify vs `release_bom_lines`). This would move branching behind a new type.
- **Tidy `InventoryItem#release_bom_lines`.** Rejected: it is §14d's invariant. Statement order and the `[nil, ""]` filter are load-bearing and the comments forbid folding it into `dependent:`.
- **A tenancy validation on `Maker::Tagging` (tag, taggable and user agreement).** Rejected: every writer is scoped. `Taggable#apply_pending_tag_list` uses `user.maker_tags` plus `taggings.find_or_create_by!(user:)` (`taggable.rb:41-46`), and v1 `TaggingsController` scopes both item and tag to `current_user` (`v1/maker/taggings_controller.rb:6-8`). No door accepts a foreign tag or taggable id.
- **Unify the two tag systems (Taggable vs `Maker::Item`'s own taggings).** Rejected: different interfaces (a `tag_list` string vs add/remove one tag), and `taggable.rb:8-10` records why. Not material.
- **A `low_stock?` predicate** (defined three times: scope `inventory_item.rb:34`, `index.html.erb:73`, `show.html.erb:11`) and **a quantity-format helper** (`number_with_precision(..., precision: 3, strip_insignificant_zeros: true)` repeated about six times). Rejected: stylistic; all copies agree.
- **Noted, not a simplification:** `Settings::TagsController#index` counts every tagging, including `Maker::Item`'s (`settings/tags_controller.rb:8`), while `/tags/:name` lists only projects, models and inventory (`tags_controller.rb:12-22`). A tag worn only by desktop-catalog items reads "1 thing" in settings but "Nothing wears this tag yet." on its own page.
- **Noted, not a simplification:** `suppliers/index.html.erb:18` renders `supplier.url` as an href with no scheme check (`supplier.rb:21` validates only `name`). The data is per-user and never shown to anyone else, so it is self-only.
