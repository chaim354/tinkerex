## Opportunity 2: UploadBatch owns the request's files and every per-file refusal — one filtered list, one refusal table, one stat-then-enqueue
1. Verdict: recommend
2. Evidence:
   - The batch catches only two of the port's per-file refusals. The loop rescues only `UnsupportedOperation` and `FetchError` (`upload_batch.rb:54-64`). Both writable adapters' `write` also raise `FileLayer::NotFound` for conditions that belong to one file:
     - Share: non-leaf name `share.rb:742`; reserved or OS-clutter path (`.DS_Store`, `._x`, `.git/**`) `:788`; over `FileLayer::MAX_BYTES` (256 MB, `file_layer.rb:119`) `:831`; parent gone `:814/:821`.
     - S3: `:1173`, `:1221`, `:1264`, `:1249/:1254`.

     Nothing caps an upload before the port (no MAX_BYTES check in any controller).
   - So one such file in the middle of a selection escapes the loop:
     - `FilesController#create` answers "File not found." through `rescue_from` (`files_controller.rb:130-135`). The earlier files are already written and previewed, but the intake nudge (`:837`) and the notice never run for them, and the later files are never attempted.
     - `Projects::UploadsController` has no `NotFound` arm (`:30-36`), and ApplicationController has no `rescue_from`. The result is a 500 after the earlier files were written and attached. A single build-log upload of a phone video over 256 MB also 500s.

     The concern's own header (`:9-15`) names the property this breaks: "ONE FILE'S FAILURE MUST NOT LOSE THE OTHERS … a batch that silently drops a file is worse than one that refuses loudly." The demo-cap comment (`files_controller.rb:1267-1270`) relies on the same property: "UploadBatch isolates per file only what the port can discover mid-batch". A size over the cap or a reserved name is exactly that kind of discovery.
   - Separate channels exist only to re-raise for a single file. `errors` is described at `upload_batch.rb:27-34` and filled at `:41`, `:56`, `:63`. Each caller copies the same line: `raise errors.first if uploads.size == 1 && errors.any?` (`files_controller.rb:828`, `projects/uploads_controller.rb:63`).
   - There are three copies of "which params entries are uploaded files". The loop filters at `upload_batch.rb:47` and both demo caps repeat the predicate (`files_controller.rb:1281`, `projects/uploads_controller.rb:41`). The callers, however, decide single versus batch on the raw count (`files_controller.rb:816, 828, 839, 844`; `projects/uploads_controller.rb:48, 63`).
   - `upload_batch.rb:51` calls `enqueue_preview`, which the concern does not define. Each includer defines an identical private copy (`files_controller.rb:1240-1251`, `projects/uploads_controller.rb:141-148`). `library_output.rb:220-234` is already "THE ONE STAT-THEN-ENQUEUE … (stage 4, S4-4 review: this was briefly the fourth copy)" and `maker/text_save.rb:104` uses it. `project_folder_intake.rb:16-18` records the two controller copies as a known "SMALLER trade".
3. Current complexity or invalid states:
   - The batch's idea of "this file was refused" is an exception allowlist that does not match what the port actually refuses per file. That allows the state "files 1-2 written, file 3 refused, files 4-5 never tried" to be answered with "File not found." or a 500.
   - "How many files" has two answers. With `["", real]` (the `include_hidden` marker, or a hand-made POST) the request takes the batch branch: it redirects back instead of to the file page, and JSON gets a 422 "one file per JSON upload".
   - `refused` (a Hash keyed by name) and `errors` (an Array) run in parallel and can disagree in size, because two same-named refusals collapse into one key.
   - Any new includer must remember to define a private `enqueue_preview`. If it does not, the `NoMethodError` fires after a successful write, outside the rescue list, and abandons the batch.
4. Proposed representation and why it is simpler:
   ```ruby
   module UploadBatch
     REFUSED_BECAUSE = { FileLayer::UnsupportedOperation => "a file of that name already exists",
                         FileLayer::FetchError           => "the library could not be reached",
                         FileLayer::NotFound             => "the library cannot store it" }.freeze # wording: product call
     def uploaded_files = Array(params[:file]).select { |u| u.respond_to?(:original_filename) }
     def demo_upload_refusal(files) =
       files.lazy.filter_map { |u| Tinkerex::Demo.upload_refusal(current_user, name: u.original_filename, size: u.size) }.first
     # [written, refused]. A ONE-file list re-raises, so its door's rescue_from answers exactly as before.
     def write_batch(files, parent_node_id:)
       written, refused = [], {}
       files.each do |upload|
         name = upload.original_filename
         info = FileLayer.current.write(current_user, parent_node_id:, name:, io: upload)
         Maker::Addons::LibraryOutput.enqueue_preview(current_user, info.node_id, name)
         yield(info, upload) if block_given?
         written << info
       rescue *REFUSED_BECAUSE.keys => e
         raise if files.one?
         refused[name] = REFUSED_BECAUSE.find { |klass, _| e.is_a?(klass) }.last
       end
       [written, refused]
     end
   end
   ```
   - One list feeds the demo cap, the loop and the single/batch answer.
   - One table decides what counts as a per-file refusal and adds the missing `NotFound`.
   - The single-file rule lives in one place, so `errors` and both copied `raise` lines go.
   - The concern names its preview helper instead of borrowing one from its includer.
   - Statuses and the per-door `rescue_from` copy stay where they are.

   2. `files_controller.rb`:

## Considered and rejected
- **One browser flow for both backends.** The idea: `uploader_controller.js` would also drive `uploadPortFile` and a separate attach, so `Projects::UploadsController` and `_upload_control`'s port_writable branch could go. Rejected for four reasons:
  - It turns the demo's whole-selection cap (`files_controller.rb:1267-1270`) into a per-file cap on the live s3 demo box.
  - It replaces one multipart POST with 2N JSON requests.
  - It drops the server flash on share/s3.
  - It brings in the uploader's lost-feedback reload (see Defects below).

  The asymmetry it would remove is the §15 one (bytes go through Rails only where nothing can presign), and that asymmetry is deliberate.
- **A shared `uploadFile(file, door)` for the two JS ternaries** (`importer_controller.js:119-121`, `measure_controller.js:517-524`), and reusing `chunk_upload.js#postJSON` in `uploader_controller.js:57-76`. These are two three-line copies (measure's comment even names its twin), so the only gain is line count.
- **One success JSON shape for both doors, dropping the unread fields.** Today create answers `{node_id, notice}` and finalize answers `{version_id, seq, notice}`. Nothing reads `version_id`/`seq` (`files_controller.rb:964`) or begin's `missing` (`:928-929`). Rejected: `lib/chunk_upload.js` already turns both answers into `{nodeId, notice}` in one place (`:28-44`, `:46-63`), and `UploadFinalized` belongs to S01.
- **Treating the demo cap as a per-file refusal inside the loop.** Rejected because it violates the recorded whole-request rule (`files_controller.rb:1267-1270`), which `demo_guards_test.rb:213-216` pins.
- **One shared `rescue_from` table for both upload controllers.** Their copy and redirect targets differ on purpose, and S01 reached the same conclusion. Opportunity 2 adds only the missing `NotFound` arm.
- **Unifying the three clobber wordings.** They are the port message (single file, FilesController), "a file of that name already exists" (any batch), and "Couldn't upload that file — …" (single file, Projects). This is product copy, and two of the three are pinned (`upload_batch_test.rb:163-175`, `project_upload_attach_test.rb:77`). The divergence is noted, not proposed.
- **A ChunksMissing retry in `uploadChunkFile`.** There is no retry today: finalize answers `{error: "chunks_missing", missing}` (`files_controller.rb:965-966`) and the client gives up. The flow is a straight line with no state to simplify, so adding a retry would be a feature.
- **One intake sweep per chunk_remote batch.** Today `finalize_upload` sweeps once per file (`:962`) while `#create` sweeps once per batch (`:833-837`). Rejected: the protocol is per file, so this would need a new endpoint, and the sweep is idempotent and capped (`project_intake.rb:314-326`).
- **Defects found (in boundary; not simplifications):**
  - `uploader_controller.js:45-51` reloads immediately after a partial failure, so "Uploaded 2; failed: …" can never be read.
  - It also discards the server's `notice` (`:30` reads only `nodeId`). A chunk_remote top-bar upload therefore never says where the sweep filed the file, while share/s3 does (`files_controller.rb:867`). That contradicts `#finalize_upload`'s own comment (`:953-958`, "a chunk_remote maker gets the same feedback a share maker gets"), which holds only for Save-to-library.
  - It has no busy guard, so a second selection during an upload starts a second concurrent loop, which its own header (`:11-15`) says must not happen.
  - `project_folder_intake_test.rb:7-14` cites a "ChunkTest below" that no longer exists. `FilesController#finalize_upload`'s intake and notice (`:957-963`) have no request test on the chunk_remote leg; `measure_export_test.rb:267-269` calls that branch a rendered-attribute claim.

(`files_controller.rb:130-135`), and a JSON one gets a bare 404, which the importer reports as "(already present)" (`importer_controller.js:131`).
