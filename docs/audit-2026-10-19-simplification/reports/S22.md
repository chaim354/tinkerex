## Opportunity 1: The 3D viewer's lifecycle — one engine record, one token, rest on connect, one import per engine (Gerber's lifecycle, plus the one rule the vendored engine needs)
1. Verdict: recommend

2. Evidence
   - **No rest on connect.** `modelviewer_controller.js:35-40`: `this.disposed = false; this.generation = 0; if (this.lazyValue) return`. Gerber's sibling resets the stage on connect: `gerber_controller.js:79-83`, "AT REST, WHATEVER THE MARKUP SAYS. A Turbo Drive back-navigation restores the page from a snapshot taken WITH the stage open". That was measured on the Gerber stage in af536baa ("tools=2, buttons=10"). Turbo clones the live body before the new page renders (turbo.js:4087-4094 `cacheSnapshot` → `snapshot.clone()`; :2617 `cloneNode(true)`). A restore renders that clone with no request (:3006-3008 `shouldIssueRequest` → `!this.hasCachedSnapshot()`). No view sets `turbo-cache-control` (grep is empty). `preview.css:187-190` shows the stage and actions and hides the poster and launch button whenever `--ready` is set.
   - **The engine appends a canvas without clearing.** o3dv.js:3964 has `EmbeddedViewer` constructor `this.canvas=document.createElement("canvas"),this.parentElement.appendChild(this.canvas)`. `selectSource()` (`:213-215`) reloads only on the `--ready` class, which a restore keeps. `boot()` (`:104`) builds a new engine whenever `this.viewer` is unset.
   - **The engine runs one import at a time and silently drops a second one.** o3dv.js:3964 has `ThreeModelLoader.LoadModel(e,t,n){this.inProgress||(this.inProgress=!0, …)}`. Its two resets run after the callbacks: `n.onModelFinished(i,a),this.inProgress=!1` and `n.onLoadError(i),this.inProgress=!1`. `EmbeddedViewer.LoadModelFromInputFiles` runs `this.viewer.Clear()` … `this.progressDiv!==null&&(this.parentElement.removeChild(this.progressDiv),this.progressDiv=null)` before it calls `LoadModel`. The running import's later callbacks then dereference the field that was just nulled: `onImportStart:()=>{this.progressDiv.innerHTML=…}`, `onModelFinished:(n,i)=>{this.parentElement.removeChild(this.progressDiv),…}`, `onLoadError:n=>{…this.progressDiv.innerHTML=i,…}`. `Importer.ImportFiles` calls `onImportStart` from the fetch completion (`this.LoadFiles(e,{onReady:()=>{n.onImportStart(),…}})`).
   - **The controller's model of the engine assumes the opposite.** `:51-55` says "A SOURCE SWITCH … `LoadModelFromUrlList` clears the viewer itself, so switching reuses the one EmbeddedViewer". `:80` says `++this.generation // invalidate any in-flight load (rapid switches / keyboard nav)`. `:93-97` reassigns `this.modelLoaded`/`this.modelFailed` per load and claims "a completion that belongs to a SUPERSEDED load cannot report itself as the current one".
   - **The callbacks go through controller fields that outlive their engine.** `:117-118` has `onModelLoaded: () => this.modelLoaded?.()` and `onModelLoadFailed: () => this.modelFailed?.()`. `teardown()` (`:56-65`) calls `Destroy()`, but `ThreeModelLoader.Destroy(){this.RevokeObjectUrls(),this.importer=null}` does not stop a running import. The same `teardown()` empties the stage with `replaceChildren()` (`:63`).
   - **Two tokens answer one question.** `disposed` (`:36,:43`, checked at `:92,:106,:137,:200`) and `generation` (`:37,:80,:219`). `generation` is reset to 0 in `connect()`.
   - **Nothing drives any of this.** `o3dv_test.rb:108-128` switches only after `ready`. No test under test/ calls `go_back` (grep is empty). That includes Gerber: its rest-on-connect (`gerber_controller.js:83`) is pinned by nothing.

3. Current complexity or invalid states. The lifecycle is spread across seven fields: `disposed`, `generation`, `viewer`, `resizeObserver`, `modelLoaded`, `modelFailed` and `OV`. The two DOM flags are written independently at six sites. Each state below follows from the lines cited above.
   - (a) **Back to a file page whose viewer was open.** The DOM says open and ready: `--ready`, `data-modelviewer-state="ready"`, the old dims ("20 × 10 × 5 mm") over a blank cloned `<canvas>`. The fresh controller has no engine. The launch button is hidden by `--ready`, Reset is a no-op (`!this.viewer`), and Fullscreen enlarges a blank box. Only ✕ Image recovers. On the model page, using the switcher in that state boots a second engine whose canvas is appended after the cloned one, so the model draws below the stage box.
   - (b) **Model page: switching source while an import is running wedges the engine.** The window is the whole fetch and parse, which for a STEP file includes loading the 7.7 MB OCCT wasm. Arrowing through the closed switcher, which the `:80` comment names as handled, is exactly this path. The new request is silently dropped after the running import's progress element was thrown away. That import's next callback throws an unhandled TypeError (`this.progressDiv` is null), so `inProgress` never resets and the engine ignores every later request. The controller stays at `loading` under `--ready`, with the canvas still `display:none` from `onLoadStart`. Every further switch is a no-op until ✕ Image.
   - (c) **A released engine's late failure fails the current load.** Sequence: ✕ Image while A is still fetching, pick B, View in 3D. A's import keeps running on the destroyed engine. When it fails, its `onModelLoadFailed` reaches `this.modelFailed`, which now belongs to B's load. That calls `fail(currentGen)`, which tears down B's engine mid-import and shows "failed".
   - (d) **✕ Image or leaving the page during an import logs an error.** The orphaned import's `onModelFinished` later calls `removeChild` on a progress div that `teardown()` already removed. The result is an uncaught NotFoundError, possibly on the next page. This is cosmetic.

4. Proposed representation and why it is simpler. One staleness token, initialised once and only ever incremented. One engine record (or none) that holds everything the engine owns. The engine's callbacks close over that record, so a released engine can only reach its own promise. A load waits for the engine's running import before asking for another. `rest()` is called on connect, as in Gerber.
   ```js
   initialize() { this.generation = 0 }                  // never re-issued, even across a reconnect
   async load() {
     this.adoptSelectedSource()                          // unchanged: chosen <option> → values
     const gen = ++this.generation
     this.element.classList.add("model-viewer--ready")   // before the engine measures the stage (unchanged)
     this.state("loading")
     try {
       const OV = await (this.module ||= import("online-3d-viewer"))
       if (gen !== this.generation) return
       const engine = (this.engine ||= this.construct(OV))   // synchronous: one engine per open
       // ONE IMPORT PER ENGINE — ThreeModelLoader drops a request made while one runs, after
       // EmbeddedViewer has discarded the running import's progress element, which then throws.
       await engine.importing?.catch(() => {})
       if (gen !== this.generation) return                    // superseded while queued: never reaches the engine
       engine.importing = new Promise((resolve, reject) => {
         engine.settle = { resolve, reject }
         engine.viewer.LoadModelFromUrlList([this.urlValue])
       })
       await engine.importing
       if (gen !== this.generation) return
       this.loaded(engine)                               // colours, dims, "ready", focus: today's bodies
     } catch (e) { this.fail(gen, e) }
   }
   construct(OV) {                                       // callbacks close over THIS engine, never a controller field
     const engine = {}
     engine.viewer = new OV.EmbeddedViewer(this.canvasTarget, { /* unchanged options */
       onModelLoaded: () => engine.settle?.resolve(),
       onModelLoadFailed: () => engine.settle?.reject(new Error("the importer could not read this file")) })
     engine.observer = new ResizeObserver(() => engine.viewer.Resize())
     engine.observer.observe(this.canvasTarget)
     return engine
   }
   release() {                                           // today's teardown(), on the record
     const engine = this.engine; this.engine = null
     engine?.settle?.reject(new Error("released"))       // lets a queued, now-stale load exit
     engine?.observer.disconnect(); engine?.viewer.Destroy()
     this.canvasTarget.replaceChildren(); if (this.hasDimsTarget) this.dimsTarget.textContent = ""
   }
   connect()    { this.rest() }                          // a Turbo-restored open viewer has no engine
   disconnect() { this.generation++; this.release() }
   showPoster() { this.generation++; this.rest(); /* focus the launch button */ }
   rest()       { this.release(); this.element.classList.remove("model-viewer--ready")
                  this.element.removeAttribute("data-modelviewer-state") }
   ```
   What gets deleted: `disposed`, the per-load `modelLoaded`/`modelFailed` reassignment and the comment defending it, and the separate `viewer`/`resizeObserver` fields (a `get viewer()` accessor can stay for the test probe). Each invalid state above becomes unrepresentable. The DOM can no longer claim "open" without an engine behind it (a). A request can never reach a busy engine (b). An old engine cannot reach a new load (c). What stays unchanged, deliberately: a switch still reuses the one engine (the `:51-55` window-resize-listener reason). `--ready` still goes on before the engine is constructed. Colours, unit factor, dims, up-axis and the named URL are untouched (files-preview.md :359-545).

5. Smallest credible implementation scope
   1. `app/javascript/controllers/modelviewer_controller.js` is the whole fix: about 30 lines net. It adds no new values, targets or actions and changes no markup, CSS or route. `reset`/`applyColors`/`showDims` read the engine record.
   2. Tests (below): `test/system/o3dv_test.rb`, `test/system/gerber_test.rb`, and a shared helper in `test/system/support/web_helpers.rb`.
   3. Docs: files-preview.md:541-545 should say the restore rule (Gerber's sentence at :277) and the one-import-per-engine rule once. Also update the controller header (:19-24) and the `:51-55` comment ("clears the viewer itself" holds only for an idle engine).
   4. Optional, for (d) only: give each engine its own mount `<div>` so `release()` can detach the engine's DOM instead of pulling its progress div out from under a running import. `.model-viewer-stage` is one of the 52 addon-shared classes (design-system rule 12; spec 2026-09-03 §10). So add an overriding `.model-viewer-stage > .model-viewer-mount` rule and never retarget `.model-viewer-stage > div`.
   5. Optional, not required: drop the always-true `lazy` value and the log-only `format` value (see "Considered" 2-3).

6. Regression risks and migration concerns
   - It is client-only: no data, API, schema or route change. The byte route and its s3 presigned cross-origin fetch are the same on share, s3 and chunk_remote, so the backend legs see identical markup and run counts.
   - UX changes: Back shows the poster, which is Gerber's behaviour and what files-preview.md :277 already promises for the board. A switch during an import briefly shows the superseded model (the engine paints it as it finishes) before the latest choice replaces it. A switch during a hung import waits until the XHR errors; ✕ Image is still the escape, since it releases the engine and a relaunch builds a fresh one, exactly as today.
   - `o3dv_test.rb:147`'s probe reads `c.viewer`; keep a getter or change that one line.
   - The smallest possible stopgap for (b) alone is to disable the switcher while loading. It changes the UI and leaves (a) and (c) in place.

## Considered and rejected
- **One shared lifecycle module or base class for the 3D, Gerber and Measure viewers.** The coordinator asked whether the three viewers share one lifecycle model; they share three partial ones. Gerber has all of it (generation bumped on launch, dismiss and disconnect; one shared pending render; adopt-behind-generation; rest on connect). The 3D viewer has half of it (Opportunity 1). KiCanvas has none and needs none: it imports eagerly, inserts an embed that owns its own loading UI in a shadow root, and has no poster or launch. I still reject a shared runtime module. The expensive steps differ (a reusable stateful engine, a fetch+parse kept across ✕ Image, a geometry poll). The DOM vocabularies differ (`model-viewer--ready` vs `measure-view--ready`, and three state attributes the tests drive). After Opportunity 1 and F-S09-1, each controller carries about ten clear local lifecycle lines with its own reason. The pattern that keeps getting missed (rest on connect) is better pinned by one shared Turbo-Back test helper used by all three suites (New 1/4 above, plus F-S09-1's New 2). Revisit if a fourth launchable viewer appears.
- **The vestigial `format` value.** It appears at `modelviewer_controller.js:27,73,201`, `_model3d.html.erb:1,16`, `files/show.html.erb:146`, `public/files/view.html.erb:81` and `models/show.html.erb:56,71`, and is asserted at files_flow_test.rb:282,339,359 and models_flow_test.rb:151-154,230. It was the dispatch key of the retired Three.js viewer (the `UP_AXIS` table and the loader `switch`, removed in 9a4cefc7). Since then its only reader is a `console.warn` label: Online3DViewer picks the importer from the URL's extension. The row asked about "STL/3MF via three vs STEP via o3dv": there is no app-side dispatch any more. All nineteen formats go through o3dv. 3MF/FBX/DAE/WRL/AMF use the bundle's own three r176 loaders, and STEP/IGES/BREP/FCStd go to the OCCT wasm worker under public/o3dv/0.18.0. The host's three 0.185.1 pins are an addon contract that no repo file imports. Removing `format` alone is dead-plumbing cleanup and below the bar. Do it alongside Opportunity 1 if those templates are touched. The tests' named-URL assertions, not the format ones, carry the load-bearing invariant.
- **The always-true `lazy` value** (`_model3d.html.erb:14`, `models/show.html.erb:53`). The eager branch at `modelviewer_controller.js:38-39` is unreachable. This is the same kind of item as `format`: an optional companion to Opportunity 1, not a finding by itself.
- **One `sources` array for the 3D viewer.** Today one file is represented as element values and many files as per-option data attributes, copied into the values in `load()` (`:70-79`; `models/show.html.erb:51-76`). The copy is four lines in one place and already atomic, so this would only move the shape around. The model page is S07's.
- **Gerber stage state** (layers/single/hidden/side/sides/home/size/rendered/pending). This is already the reference: one render, kept; toggles keyed by that render's ids, adopted only behind the generation check; `home` read once; the side falls back in `show()`. The `layers` union (`{name,url}` | `{name,url,archive:true,members}`) with a server-decided `single` could in principle mix an archive with loose layers, which the server never builds. `filesFor` + `.flat()` handles any mix generically. The server-side assembly is F-S10-2's `Viewer`. No change.
- **KiCanvas.** Its `ready` means "embed inserted", not "rendered" (kicanvas_test.rb:52-54 says so). On a Turbo restore, the cloned `<kicanvas-embed>` upgrades and starts loading just before the fresh controller replaces it. That is one duplicate fetch, not a contradictory state a user can act on. Below the bar. A synchronous `stageTarget.replaceChildren()` before the `await` would remove it if anyone cares.
- **Build scripts vs bin/build-codemirror.** They share one model in spirit: one bundle, one pin, built bytes committed, no CDN, `preload: false` for the lazy bundles. They use three pin mechanisms, each suited to its source:
  - an enumerated whole-tree pin list (codemirror, tracespace);
  - upstream's own exact pins (o3dv: the cached packument shows online-3d-viewer@0.18.0 declaring `three: 0.176.0`, `fflate: 0.8.2` exactly, and the bundle carries `__THREE__="176"`);
  - upstream's lockfile at a pinned commit via `npm ci` (kicanvas).

  A shared shell helper would save about ten boilerplate lines each, which is line count only. Noted, not recommended: bin/build-kicanvas is zsh where the others are bash, and it has no refuse-to-build guard (the others check exports or CDN strings). bin/build-o3dv's "PINNED" relies on upstream declaring exact versions, so re-check that at every bump.
- **Strict locals vocabulary.** The names are consistent across the six partials (`name`, `blob_url`, `named_url`, `download_url`, `thumbnail`+`thumbnail_url`). The remaining repetition is already claimed elsewhere. The readiness re-test `thumbnail&.status == "ready" && thumbnail.asset.attached?` (`_gerber:63`, `_model3d:39`, `_static:18`) is covered by F-S08-2's `showable?`. The colours/unit-factor defaults are covered by F-S10-2's `Viewer`. Not re-recommended.
- **Vendored three/three-core/fflate/OrbitControls/3MFLoader and jszip/buffer/process/jszip-buffer-chunk.** These are addon contracts and hand-repointed jspm artefacts, documented in importmap.rb. The brief excludes restructuring vendored code.
