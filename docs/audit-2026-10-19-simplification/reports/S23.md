## Opportunity 1: Make `SchemaMap::EDGES` complete by check, not by memory — classify every `*_id` column, so a reference nobody draws can no longer slip past both guards that derive from EDGES

1. Verdict: recommend
2. Evidence
   - `lib/schema_map.rb:25-32` states the hole: "WHAT NOTHING HERE CATCHES … a NEW app-level reference that nobody adds to
     EDGES", justified by "no naming convention to key on (… `manifest_id` points at a column that is not even a primary key …)".
     Repeated at `test/schema_map_test.rb:16-17`.
   - `test/models/structural_orphan_test.rb:20-22, 28-31`: "THE CASE LIST IS DERIVED FROM SchemaMap::EDGES … an unenforced pointer
     nobody considered is exactly how these thirteen accumulated." The subject set is the AUTHORED list, so a pointer nobody draws
     is never considered. `SchemaMap#problems` (`lib/schema_map.rb:286-322`) checks only that authored edges name real columns,
     agree with `add_foreign_key`, and that LAYOUT places every table.
   - The premise of the caveat died with the engine tables (2026-08-25, `lib/schema_map.rb:104-112`: `manifest_id`/`chunk_hash`
     lived in them). Measured on `db/schema.rb` at HEAD: 54 primary-schema `*_id` columns besides `user_id`. One is
     `nodes.node_id`, an edge TARGET. Of the other 53: 48 are already edge sources; 4 are deliberate non-edges documented only as

     hold a node id are named `node_id` or `*_node_id`.
   - `lib/tasks/schema_map.rake:6-12` aborts the regeneration while `problems` is non-empty, i.e. a rule placed in `problems` stops
     a developer at the exact step the stale-page test (`test/schema_map_test.rb:25-34`) sends them to.

4. Proposed representation and why it is simpler

   NOT_EDGES = {
     "nodes.current_version_id"          => "a version on the sync server (chunk_remote); this database has no versions table",
     "remote_manifest_chunks.version_id" => "a version on the sync server; no local table",

   tables.select { |t| t["db"] == "primary" }.each do |t|      # Solid Queue's active_job_id is vendor schema

## Consistency of the three proposed schema changes (do not duplicate; assessed against the schema's conventions)

**F-S05-1 — partial `nodes (user_id, storage_path) WHERE deleted = true`: fits.**
- **Name.** The default name collides with the live-row index, so the custom `…_tombstones` suffix is right. It matches the
  schema's other custom names (`idx_maker_previews_unique`, `index_maker_models_on_auto_node_id`).
- **Predicate.** `deleted = true` mirrors the existing `deleted = false` literal (`20260716025826_add_share_columns_to_nodes.rb:29`).
  Partial indexes are adapter-agnostic (§14e). The column order is tenant-first like every `nodes` index. It would be the
  schema's first NON-unique partial index, which is fine.
- **Prefix guard** (`architecture_invariants_test.rb:1268-1310`). It passes: a partial index is never read as a superset, and no
  non-partial index starts with `(user_id, storage_path)`. But the comment at `:1289-1291` ("two indexes on EXACTLY the same
  columns … Zero such pairs exist today") becomes stale. The new pair is legitimate (complementary predicates), so amend that
  comment in the same slice before someone "fixes" it.
- **Schema map.** S05's step "regenerate `docs/schema-map.html`" is a no-op. The payload carries no index list, and `annotate`
  (`schema_map.rb:393-394`) picks the unique index for the `cu` badge. The page cannot show either partial predicate (`parse`
  drops `where:`, `:414-416`), so it states `nodes.storage_path` as unconditionally "unique across (user_id, storage_path)" —
  the opposite of §14a's point. That is a small accuracy fix inside this row, below the bar on its own.

**F-S02-1 — `nodes.trash_root_id`: fits structurally, with two convention conflicts to fix before it lands.**
- **Name.** All 20 columns that hold a `nodes.node_id` are `node_id` or `*_node_id`, while a bare `*_id` means an integer
  reference to some table's `id` (`project_id`, `parent_id`, …). `nodes` has BOTH an integer `id` and a string `node_id`, so
  `trash_root_id` genuinely reads as `nodes.id`. Use `trash_root_node_id` (string).
- **Edge.** It is a reference into `nodes.node_id` and belongs in EDGES (`nodes.trash_root_node_id → nodes.node_id`, app,
  share/s3 only). Nothing forces that today; Opportunity 1 would.
- **Index.** `(user_id, trash_root_node_id)` is tenant-first and passes the prefix guard (`index_nodes_on_user_id` is its prefix
  and is exempt). Prefer the schema's existing partial shape `WHERE trash_root_node_id IS NOT NULL` (precedents
  `20260825150100_add_auto_catalog_to_maker_models.rb:23`, `20260908120000_add_unique_folder_claim_to_maker_projects.rb:11`):
  it indexes only trash rows, so the scan's and the mirror's live-row inserts pay nothing, and both adapters use it for `= ?`.
- **Backfill.** It must be self-contained — a migration-local `MigrationNode < ActiveRecord::Base`, never `Node` or
  `FileLayer::Subtree` — the rule the rederive migrations state (`20260826180000_rederive_widened_text_roles.rb:7-12`).
- **Backend overloading.** One more share/s3-only column on `nodes`, NULL on chunk_remote mirror rows, consistent with
  `storage_path`/`content_hash`. Say so on the map label. The column records MEMBERSHIP, not existence: after TrashPurgeJob
  removes an entry (§14a: the purge "never touches the row") the members still name it. That is today's NotFound "purged?"
  behaviour, which is fine.
- **Guards.** No new table, so TenantCleanupTest is unaffected; the stale-page test forces regeneration.

**F-S11-1 — `maker_addon_files.revision`: fits.**
- **Name, type and default.** `integer, null: false, default: 1` matches `maker_addon_states.revision` exactly and agrees with
  `maker_addon_state_revisions.revision` and `maker_boms.revision`.
- **Backfill.** A correlated UPDATE via `execute` is the shape `20260813000100_create_maker_addon_state_revisions.rb:28-37` set
  (the connection, not the model), and it is adapter-agnostic.
- **Tenant scoping.** `maker_addon_files` is one of the two maker tables with no `user_id`, scoped through a real FK to a
  user-owned parent. A per-row column changes nothing there, and neither cleanup guard is touched.
- **Index.** None is needed: the ORDER BY runs over one state's rows after the `(addon_state_id, node_id)` unique index, and
  `latest_output_folder` already sorts a joined set (`addons_controller.rb:681-682`).
- **Schema map.** `revision` is not `*_id`. It is a composite `(addon_state_id, revision)` reference the map cannot draw, like
  `maker_releases.bom_revision`, so no EDGES line; the page regenerates.
- **Test caveat.** The backfill test's state must sit at revision ≥ 2. Otherwise "skip the UPDATE" leaves the default 1 equal to
  the expected value and the mutation stays green (the default-equals-expected vacuity §15 records for `.to_i`). S11's test 3
  says so; its test 4 must too.
- **Precedent tension.** The revisions migration's header (`:12-14`) refuses a COUNT column. This is a per-row fact written once,
  by the one writer, inside the save transaction — not a second count — so it is consistent.

  - 34 tables carry `user_id`: all 32 `maker_*` tables except `maker_addon_files` and `maker_addon_state_revisions` (scoped
    through a real FK to `maker_addon_states`), plus `devices`, `nodes`, `remote_manifest_chunks` and `user_identities`.
  - 12 of the 34 have a DB FK to `users`, not 13.
  - The asymmetry is deliberate as POLICY (tinkerex#152, `structural_orphan_test.rb:9-17`, `tenant_cleanup_test.rb:9-15`: SQLite
    rebuilds a table to add an FK; the property tests cover all 34). It is accidental per TABLE, an authoring style: `maker_file_links`
    (2026-09-07) and `maker_shelves` (2026-08-25) use `t.integer :user_id`, while `maker_pins` (2026-10-08) uses
    `t.references … foreign_key: true`. It is harmless and not worth a rebuild.
  - Same-tenant references: 10 of the 20 structural edges whose child carries `user_id` have a hand-written `*_belongs_to_user`
    check. The other 10 rely on doors building through a `current_user`-scoped parent, which every door I traced does (v1
    bom_lines, boms, build_log_entries, collections, taggings, file_attachments; web bom_lines, print_runs, connections, sheets,
    blocks; ReleaseSnapshot). The one reachable cross-tenant write is F-S19-1's.
- **Content-token columns.**
  - `nodes.content_hash` (share/s3: the Reconciler, indexed for move pairing, content-determined per §14a's identity ladder) and
    `nodes.current_version_id` (chunk_remote: keys `remote_manifest_chunks`) are backend-exclusive and mean different things, so
    keep them apart.
  - `maker_previews.version_id` is a real, repointed content token. `maker_file_attachments.version_id` is unwritten
    (Opportunity 2). `maker_release_files.content_token` is the same concept under the right name.
  - Two readers spell the per-backend union outside the port (`gerber_archive.rb:87`, `three_mf_manifest.rb:90`); F-S10-1 folds
    them into one door.
- **`nodes` three-backend overloading.**
  - Shared: `node_id`, `parent_node_id`, `name`, `kind`, `deleted`, `size`, `mtime`.
  - share/s3 only: `storage_path`, `content_hash`.
  - chunk_remote only: `current_version_id`. `mode` and `symlink_target` are WRITE-ONLY (`changelog_sync.rb:218, 232`; no
    reader).
  - Dead everywhere: `updated_seq` — contrary to the row's premise, chunk_remote does not use it either.
  - A deployment runs one backend, so the cross-backend combinations cannot co-occur. The trash discriminator (deleted + NULL
    path) is §14a's mechanism and stays.
- **JSON columns.** Each has one owner, and its readers are total or guarded (`Sheet#cells`/`#columns`,
  `ProjectKind.layout_for(overrides: self[:panels])`, `print_settings.present?`, `metadata.present?`). Nullability is inconsistent
  (only `maker_addon_states.data` is `NOT NULL default {}`), but no reader would shrink by more than a nil-check, and no shape
  is shared across tables.
- **Schema-map generator.**
  - The derived half is sound except that partial predicates are dropped (see F-S05-1 above).
  - The authored half's completeness is Opportunity 1.
  - Stale prose: `schema_map.rb:16, 46-48, 269`; `schema_map_test.rb:92-94`.
- **Do the existing guards catch a new COLUMN?**
  - Schema-map stale-page test: yes, for any column (it forces regeneration).
  - Schema-map `problems`: no, for an undrawn reference (Opportunity 1).
  - StructuralOrphanTest: no; it inherits EDGES.
  - TenantCleanupTest: table-level only. It would catch a new user-scoped TABLE, not a column.
  - `legacy_columns_dropped_test.rb`: not a derived guard at all. It is a hand list of four June-2026 auth columns and two
    tables, and catches nothing new. The repo memory's fourth derived guard is `template_hygiene_test.rb`, not this.

## Considered and rejected
- **Uniform FKs to `users`** (add them to the 22 tables, or drop the 12). tinkerex#152 decided against it: a table rebuild per
  table on SQLite, and an orphan census that was never run. The property guards cover all 34 tables, and the mixed state has no
  consequence (see above).
- **A shared same-tenant validation macro in `ApplicationRecord` plus a guard derived from EDGES.**
  - It would cover the 10 structural edges with no `*_belongs_to_user` check.
  - Preventive only: every door already builds through a scoped parent, and the one reachable leak is F-S19-1.
  - It would add an `exists?` per save on high-volume rows (taggings, collection items, release files). Below the bar.
- **Derive `maker_file_attachments.role` instead of storing it.** The evidence for it:
  - eight re-derivation migrations (2026-07-28 → 2026-09-08, about 570 lines);
  - eight migration-test files (about 965 lines; `seed_pcb_filing_rules` seeds rules only), each driving its migration's hand-copied extension list against real rows;
  - all of that exists only to move stored roles when `ROLE_BY_EXT` widens.

  S06 rejected it: v1 sets the role from the client, and EntryPhotos writes "image". I add a stronger reason to store it: the
  stored role is what keeps `Project#cover_node_id` query-free per index card (`project.rb:168-171, 189-192` forbid a query there). A
  derived role would need node names on that page. A cheaper relief for future widenings is one idempotent "re-derive `other`
  rows from the current `ROLE_BY_EXT`" task instead of a migration-plus-test pair each time (S06's call). Cross note below on the
  desktop client's roles.
- **Merge `nodes.content_hash` and `nodes.current_version_id` into one `content_token`.** Different value spaces with different
  secondary uses (move pairing needs content-determined values; manifests key on the version id), and each adapter reads its own
  column once.
- **Rename `maker_previews.version_id` to `content_token`** (as `maker_release_files` does). It is naming only. The wire would
  need aliasing (v1 previews params and JSON keys), and the misreading it guards against (an edge into `versions`) became
  impossible when `versions` was dropped.
- **An explicit tombstone-kind column on `nodes`.** It would duplicate §14a's NULL-path mechanism (S05 and S03 rejected it on the
  same ground; F-S02-1's column is a different fact).
- **Status + timestamp pairs** (`maker_projects.status`/`archived_at`, `maker_tasks.status`/`completed_at`). Already recorded as
  F-40/X6 in `docs/AUDIT-2026-08-19.md:993-1019`: ACCEPTED, still open as a product decision. One new fact for that record: the
  shipped desktop client offers "archived" as a status (`tinkerex-client/client/maker-app/src/index.html:119`) and never sends
  `archived_at`, so desktop-archived projects carry `archived_at` NULL, while every web reader decides from `status`.
- **`NOT NULL default '{}'` on the nullable JSON columns.** It would save one nil-check per reader at most.
- **Derive `maker_models.origin` from `auto_node_id IS NOT NULL`.** One writer keeps the two together; documented as
  belt-and-braces in `model-intake.md:117-118`.
- **Composite FKs** (`(user_id, parent_id) → parent(user_id, id)`) to make same-tenancy structural. A rebuild per table on SQLite
  and per-parent unique indexes; #152's objection applies a fortiori.
- **Split `nodes` per backend.** Massive churn, with no state that can actually co-occur.
