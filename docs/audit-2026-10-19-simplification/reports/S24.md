4. Proposed representation and why it is simpler. One job owns the ordered list and runs it, with one trigger per backend:
   ```ruby
   module Maker
     # WHAT RUNS AFTER THE CATALOG CHANGES, IN WHAT ORDER — the one statement of it (§14f, §14k).
     # share/s3: Library::ScanJob#perform runs it inline, strictly after the reconcile.
     # chunk_remote: config/recurring.yml's one `library_sweep` entry (sweep_all! below).
     class LibrarySweepJob < ApplicationJob            # name is the owner's call
       STEPS = [ Maker::ProjectDiscoveryJob, Maker::ProjectIntakeJob, Maker::ModelIntakeJob ].freeze # THE ORDER IS THE RULE
       Failed = Class.new(StandardError)

       queue_as :background
       # ONE semaphore per user, SHARED with ProjectIntakeJob (whose only remaining perform_later is
       # ChangelogSync's nudge), so a nudge and a sweep never file one user's folders at once.
       limits_concurrency to: 1, key: ->(args) { args[:user_id] }, group: "maker_library_sweep",
                          duration: 15.minutes, on_conflict: :discard

       def perform(user_id:)
         failed = STEPS.filter_map do |step|
           step.perform_now(user_id:)
           nil
         rescue StandardError => e   # a later step still runs (today's independence and ScanJob's rescues, kept)
           Rails.logger.error("Maker::LibrarySweepJob: #{step.name} failed for user #{user_id}: #{e.class}: #{e.message}")
           step
         end
         raise Failed, "#{failed.map(&:name).join(', ')} failed for user #{user_id}" if failed.any? # a failed row on chunk_remote, as today
       end

       def self.sweep_all!   # THE one inverse gate
         return if FileLayer.current.capabilities.scannable?
         User.find_each { |user| perform_later(user_id: user.id) }
       end
     end
   end
   ```
   ```ruby
   # Library::ScanJob#perform: observer.call; warn_unreadable; then
   def sweep(user)   # replaces discover_projects / intake_project_folders / intake_models
     Maker::LibrarySweepJob.perform_now(user_id: user.id)
   rescue StandardError => e   # never wraps observer.call (UnsafeScan still propagates)
     Rails.logger.error("Library::ScanJob: the reconcile SUCCEEDED but the library sweep failed for user #{user.id}: #{e.class}: #{e.message}")
   end
   ```
   ```yaml
   library_sweep:                      # replaces project_discovery, project_folder_intake and model_catalog_intake
     command: "Maker::LibrarySweepJob.sweep_all!"
     schedule: every 15 minutes
   ```
   Why it is simpler:
   - The order exists once, as data (`STEPS`), and holds on all three backends.
   - The backend split exists once: ScanJob's `scannable` gate plus the sweep's inverse gate. It is no longer one plus four.
   - The step jobs lose all scheduling knowledge. Each is just a command (`perform`), which is what its own header already says `#perform` is.
   - `#chain_intake` disappears, and with it the gate whose deletion re-arms §14f. Discovery never enqueues a filer, because the next step in the same run is the filer. This is strictly faster than today's chain, which waits for an enqueue.
   - This is not S05's rejected "collapse ScanJob's three steps into a list" (S05.md:129). That idea only re-spelled an order share/s3 already enforces. Here the list is the vehicle that gives chunk_remote an order at all, and it removes three schedule entries, four gates and a chain.

## Considered and rejected
- **One recurring entry for both the share/s3 scan and the chunk_remote sweep, dispatching on capability.** `recurring.yml:107-115` argues that the two 15-minute figures are different constraints, a floor versus an arbitrary choice. `boot_scan_test.rb:16-25` also pins `scan_all!` as the single entry point the boot hook and the schedule share. Merging them would couple two cadences the authors deliberately decoupled.
- **ERB in recurring.yml to emit entries per backend.** That would be a sixth reading of `LIBRARY_BACKEND` (S01's finding), and it would gate on a name rather than a capability, which is the Phase 3 trap `scan_job.rb:157-168` records.
- **A generic per-user fan-out helper** for `scan_all!`, `purge_all!`, the sweeps and `pull_all!`. The gates are deliberately three different kinds: a capability, the inverse capability, and a class check (§14a keeps the last). A helper would move branching behind a type.
- **Collapsing ScanJob's three steps into a list without the chunk_remote trigger.** S05 rejected this (S05.md:129) and I agree: on its own it only saves lines. Opportunity 1 is different because the list is what chunk_remote lacks.
- **Computing CSP `connect_src` once at boot instead of the per-response lambda (`content_security_policy.rb:53-56`).** The initializer cannot autoload app constants (the §14a lesson, `:40-41`). Per-leg tests and test-double ports rely on the per-response resolution. S01's boot fix already removes the user-visible failure: an unknown backend would 500 every response, `/up` included.
- **A per-request random CSP nonce instead of `session.id`.** A session-stable nonce is what Turbo Drive visits need once the policy enforces. Anonymous pages are already handled (`:136-138`, pinned by `content_security_policy_test.rb:126-142`).
- **Setting `RAILS_MAX_THREADS` once in the Dockerfile** instead of in compose and deploy (3 for Puma, 5 for the pool, 16 in compose and deploy). This is config deduplication with no correctness gain. Solid Queue runs forked (`puma/plugin/solid_queue.rb:26-48`), so job threads never share Puma's pool. A bare `docker run` has no sidecars to proxy, so the "3 starves" concern does not arise there.
- **Folding the Dockerfile's renderer stages.** Each stage is one renderer with an argued architecture story. The only "duplication", the unconditional F3D runtime libraries on arm64, is argued at `:192-193`.
- **Compose versus deploy.yml duplication.** Every sidecar touchpoint is already single-sourced by `Tinkerex::Sidecars` and `sidecar_hygiene_test`. The remaining shared knobs differ by network naming (`ADDON_SOURCE_URL`, `CHUNK_REMOTE_URL`) or are a single value.
- **.env.example vs INSTALL.md vs LibraryBackendCheck's lists.** `install_docs_test.rb` pins both directions that matter: code to table (including `LibraryBackendCheck::*_REQUIRED`), and compose plus `.env.example` to table. The only unguarded direction, a compose `:?` variable missing from .env.example, is cosmetic.
- **Importmap pins vs vendored bundles.** Version annotations are comments, and the build scripts pin the real versions. `lazy_bundles_test` and `ci_hygiene_test` pin the load-bearing parts: preload and the single CodeMirror pin.
- **Routes: the `handle` constraint is repeated nine times in the public scope.** A `constraints(handle: …) do` block would only reduce lines. The derived Active Storage shadow (`routes.rb:39-41`) is correct as is (§15).
