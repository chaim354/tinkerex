## Opportunity 1: Make `bin/ci` compare the backend legs' RUN counts, replacing a rule that only a person checks
1. Verdict: recommend
2. Evidence:
   - CLAUDE.md:1267-1276 (§15): the three legs "must report identical run counts", followed by: "**`bin/ci` PRINTS the three counts and never COMPARES them** — the rule has always relied on a human reading them". CLAUDE.md:342-343 (§13) says the same.
   - `config/ci.rb:276-278`: `CI.run do selected.each { |gate| GATES.fetch(gate).call(self) } end`. Nothing runs after the gates. Only the chunk_remote leg captures its output (`config/ci.rb:209`, `:212`, `tee tmp/chunk-remote-full.txt`). `test` (`:77-81`) and `test-s3` (`:83-93`) capture nothing, so not even the inputs for a comparison exist.
   - The human step is restated in every close-out document, and one copy is already wrong:
     - `.claude/commands/execute-plan.md:85-87`: "read the three backend legs' run counts … `bin/ci` prints them and never compares them".
     - `.claude/commands/finish-branch.md:28`: "All gates must pass: style, scan, test, **test-share**, test-s3, system". `test-share` does not exist and `test-chunk-remote` is missing. This is the same stale list CLAUDE.md:1263-1266 records fixing in its own copy.
     - `finish-branch.md:29-30`: "must report identical **run/assertion** counts". Assertions always differ by design, so this instruction fails on every run.
     - `git grep "run counts"` finds the step restated in about 20 plan files under `docs/superpowers/plans/`. Some of them design tests around it, for example `2026-08-31-project-folder-scan-button.md:30`: "Why one test file, not three: the three CI legs … must report identical run counts".
   - On whether the tinkerex#131 flap can be expressed as a tolerance: it does not need one. CLAUDE.md:1273-1274 puts the flap in assertions (±2) and skips (±1), not runs. The memory note backend-legs-structural-assertion-deltas.md covers 17 logged runs: run counts were always identical, s3 always had +7 assertions, chunk_remote about +160, and skips were 32/33/8. It adds: "each close-out re-asks whether +161 is a bug". No test defines itself conditionally on the backend: there is no class-level `if/unless … ENV/FileLayer/LIBRARY` in `test/**/*_test.rb`. So runs are deterministic per code revision, and the check can be exact equality.
3. Current complexity or invalid states: the three leg results are independent states, and all three can report green while they disagree, which is the exact condition §15 calls a real bug. Enforcement belongs to nobody. It is spread across CLAUDE.md, two command files and every plan, and the copy `/finish-branch` actually loads is the one that names a gate that does not exist and compares a number that always differs. In GitHub CI the legs are separate jobs (`ci.yml:211-269`), and no comparison happens anywhere.
4. Proposed representation and why it is simpler: `config/ci.rb`, already the declared single definition of "green", owns the rule. Each leg tees its own log. After the gates run, the backend legs that ran are compared on runs only:
   ```ruby
   BACKEND_LEGS = %w[test test-s3 test-chunk-remote].freeze      # CLAUDE.md §15
   leg_log = ->(gate) { "tmp/ci/#{gate}.log" }

   "test" => ->(ci) do
     ci.step "Tests: Rails (share backend)", "bash", "-c", <<~'SH'
       set -uo pipefail                       # tee must not mask the suite's status (:138-145)
       d=$(mktemp -d); trap 'rm -rf "${d:?}"' EXIT
       env LIBRARY_BACKEND=share LIBRARY_PATH="$d" bin/rails db:test:prepare test 2>&1 | tee tmp/ci/test.log
     SH
   end
   # test-s3 the same; test-chunk-remote's existing `tee tmp/chunk-remote-full.txt` → tmp/ci/test-chunk-remote.log

   CI.run do
     legs = BACKEND_LEGS & selected
     FileUtils.mkdir_p("tmp/ci"); legs.each { |g| FileUtils.rm_f(leg_log.(g)) }   # no stale logs
     selected.each { |gate| GATES.fetch(gate).call(self) }
     if legs.size >= 2
       runs = legs.to_h { |g| [ g, LegRuns.read(leg_log.(g)) ] }                   # nil = no summary
       unless runs.values.uniq.size == 1 && runs.values.first
         results << false
         failure "Backend legs disagree on RUN count (§15)", runs.map { |g, n| "#{g}=#{n || 'no summary'}" }.join("  ")
       end
     end
   end
   ```
   with a ten-line plain-Ruby `LegRuns.parse(text)` that returns the last `^(\d+) runs, \d+ assertions, …` match. Assertions and skips are deliberately not compared. They differ by structure and they flap; runs do neither. The result: the rule has one owner. The human step and its restatements in two command files and two CLAUDE.md passages go away, and the contradictory `finish-branch.md` lines go with them. A divergence fails `bin/ci` with a table instead of relying on someone noticing three numbers in scrollback.
5. Smallest credible implementation scope, in order:
   1. A new `lib/ci/leg_runs.rb` (plain Ruby, loadable from `bin/ci` with only `config/boot`) and its unit test.
   2. `config/ci.rb`: move `test` and `test-s3` to the `bash -c` heredoc form already argued at `:138-145`, adding `pipefail` and `tee`. Repoint the chunk_remote full-suite tee. Add `BACKEND_LEGS` and the post-run comparison.
   3. Docs, same commit: CLAUDE.md §15 bullet (1267-1276) and the §13 comment (342-343). CLAUDE.md sits exactly at `MAX_LINES` = 1,360, and this change removes lines, so lower the ratchet. Also `execute-plan.md:85-87`; `finish-branch.md:28-30` (replace the hand list with "every gate `bin/ci --list-ci` names; `bin/ci` compares the legs"); and, while there, its stale "`paths:` allowlist" paragraph at `:96-101` (`ci.yml:50-72` is now a denylist).
   4. Optional second step, for GitHub CI: each leg job exports `runs` as a job output, and a `legs-agree` gate/job `needs:` the three. Because `ci_hygiene_test.rb:134-155` asserts set equality, this must be a gate in `config/ci.rb`. Step 1 already covers §15's definition of green ("bare `bin/ci`"), and run counts depend on the code and the backend, not on the machine.
6. Regression risks and migration concerns:
   - Behind `tee`, the `test` and `test-s3` output loses TTY colour and arrives in bursts. The chunk_remote leg already pays this. A small Minitest reporter that writes the count to a file avoids it, but it touches `test_helper` (S27).
   - Dropping `pipefail`/`PIPESTATUS` would report green over a red suite. `config/ci.rb:138-145` records that this trap already caught out an earlier plan.
   - A leg that fails before it starts tee-ing leaves no log. The up-front `rm_f` turns that into "no summary", which reads as disagreement instead of a stale agreement.
   - No data, API or UI change. Backend legs stay equal, because the new unit test is backend-agnostic and adds the same runs to all three.
   - If Opportunity 2 lands too, both edit the same three commands, so do them in one change.
7. Existing and additional validation required:
   - Existing tests that stay as they are: `ci_hygiene_test.rb:134-155` (no new gate in step 1), `importmap_audit_test.rb:109` (greps the `ci.step … Importmap` line), `bin_sync_server_test.rb:67` (the keys `config/ci.rb` sources).
   - New unit tests, each with the mutation that proves it carries weight:
     - (a) Equal runs with unequal assertions and skips (the +7/+160, 32/33/8 shape) agree. Mutation: parse assertions instead of runs → red.
     - (b) A log with no summary line is a disagreement. Mutation: treat nil as 0 or as agreeing → red.
     - (c) With two summaries in one log, the last wins. Mutation: take the first match → red.
   - End-to-end, once: add `TEST=test/models` to the `test-s3` command and run `bin/ci test test-s3`. It must go red naming both counts. Then restore with `git checkout --`.
   - Also plant a failing test under the new `test` command and confirm the step is red, which proves `tee` does not swallow it.
8. Confidence: high. The rule text, the place of the flap (assertions and skips, not runs), the lack of any backend-conditional test definitions, and the absence of any existing comparison are all verified. Medium only on the CI-side step 2, which is optional.

## Opportunity 2: One definition per gate — `ci.yml` jobs carry runner plumbing only, never gate behaviour
1. Verdict: recommend
2. Evidence:
   - The claims: `config/ci.rb:3-5` ("exactly one definition of what each gate does") and `ci.yml:132-133` ("config/ci.rb is the single definition of what each gate does").
   - `ci.yml:221-222`, `:234-235`, `:251-252`, `:279-280`: `env: RAILS_ENV: test` on the four test-shaped jobs. `config/ci.rb:77-93`, `:208`, `:237-241` do not set it. `git log -S` traces the line to the initial scaffold (`ff07b265`, 2026-06-09), so it is residue, not a decision.
   - Why that changes behaviour:
     - activerecord-8.1.3.1 `databases.rake:22` declares `task load_config: :environment`, and `:553` declares `test:prepare` with `prepare: :load_config`. So `bin/rails db:test:prepare` boots the full app in the current `RAILS_ENV`. The test run itself is a child process (`railties … test_unit/runner.rb:50-54`, `system("rails", test_command, …)`).
     - `config/initializers/library_backend_check.rb:20-25` runs `LibraryBackendCheck.check!` "unless Rails.env.test?".
     - Locally, then, `bin/ci test`, `test-s3`, `test-chunk-remote` and `system` each boot development and run the boot guard against that leg's configuration: share's touch-probe, s3's knob presence, chunk_remote's `CHUNK_REMOTE_REQUIRED` at `lib/library_backend_check.rb:90`, fed from `tmp/sync-server.env`. In GitHub CI the same four gates boot test, and the guard never runs.
   - `ci.yml:218-219` and `:231-232` run `ci/ensure-resvg.sh` before `bin/ci test` and `bin/ci test-s3`. It does not run before `test-chunk-remote` (`:237-269`), which runs the same full suite, nor before `system-test`, nor in local `bin/ci`. On the Linux image it is a no-op, because `ci/runner/Dockerfile:162` bakes resvg. Its fallbacks (`ensure-resvg.sh:19` brew; `:24-25` `cargo install` with `$HOME/.cargo/bin`) are written for the Mac and cannot work on the runner: brew is absent, and `CARGO_HOME` is root-owned for uid 1001 (`ci.yml:261-265`).
   - `ci.yml:254` `SYNC_PORT: "3002"` restates `config/ci.rb:149` `PORT="${SYNC_PORT:-3002}"`.
   - The guard: `ci_hygiene_test.rb:140-146` says it "pins that ci.yml never hand-rolls a command", but it only counts `bin/ci <gate>` invocations. A job with extra `run:` steps or behaviour-changing `env:` passes.
3. Current complexity or invalid states: a gate's real definition is three things put together: the `config/ci.rb` command, the job and step `env:` in `ci.yml`, and the pre-steps in `ci.yml`. Local and CI therefore run different boot sequences under the same gate name. A knob added to `CHUNK_REMOTE_REQUIRED` without `bin/sync-server` emitting it turns local `bin/ci` red and leaves CI green. That is the reverse of finish-branch.md:108-109's "if CI fails on something `bin/ci` passed, that difference is itself the finding", and it is invisible from either side. The difference has already misled a reader in this audit: S01's report, line 85, validates F-S01-1 on "CI's development boot (`db:test:prepare`)", which only happens locally. The resvg precondition is non-uniform: it covers 2 of the 3 full-suite legs, and it is a third pin of resvg 0.47.0.
4. Proposed representation and why it is simpler: a gate job is checkout(s), then `bundle install --quiet`, then `bin/ci <gate>`, plus only the runner plumbing that says where things are on this box: `TINKEREX_SYNC_DIR`, `CARGO_TARGET_DIR`, `CARGO_HOME`, `RUSTUP_HOME`, `RUBOCOP_CACHE_ROOT`, and the cache/artifact `uses:` steps. Anything that changes what a gate tests lives in `config/ci.rb`:
   ```ruby
   # config/ci.rb — if the test env is the intended one, say so HERE, where local runs it too
   'env RAILS_ENV=test LIBRARY_BACKEND=share LIBRARY_PATH="$d" bin/rails db:test:prepare test'
   ```
   Delete the four `RAILS_ENV` blocks, the `SYNC_PORT` line and the two `ensure-resvg` steps from `ci.yml`. Extend the existing contract test so its stated intent is what it checks:
   - every `run:` in a gate job is `bundle install --quiet` or exactly one `bin/ci <gate>`;
   - job-level and `run:`-step `env` keys are a subset of an argued `RUNNER_PLUMBING_ENV`, the same "exception as data" shape as `LOCAL_ONLY_GATES` (`config/ci.rb:244-255`).
   The result: `bin/ci <gate>` on a laptop and in a CI job is one definition again, and the guard enforces that rather than only the gate name.
5. Smallest credible implementation scope:
   1. Decide the environment once.
      - Conservative: add `RAILS_ENV=test` to the four test-shaped commands in `config/ci.rb`, so local matches CI. This loses only the incidental local dev-boot of the guard, which nothing asserts and which `test/lib/library_backend_check_test.rb` covers.
      - Stronger: drop it everywhere, so CI also runs the guard per leg. This needs one measured CI run first, because a development-env boot on a fresh runner (dev DB config, credentials) is unmeasured.
   2. `ci.yml`: remove `RAILS_ENV` (×4), `SYNC_PORT`, and the two `ensure-resvg` steps.
   3. `test/ci_hygiene_test.rb`: extend the `:134-155` contract and add a planted-fixture test in the shape of `:324-380`.
   4. Hand `ci/ensure-resvg.sh` itself to S29 (delete it, or keep it as a manual Mac helper).
6. Regression risks and migration concerns:
   - The direction choice above.
   - Without the `ensure-resvg` step, a future image that lost resvg would no longer write the step-summary warning. Today that warning covers only two legs, and its install paths cannot succeed on this fleet. The better net is the renderer-parity point under "Considered and rejected" #1.
   - F-S01-1's dev-boot validation must then come from a test, not from `db:test:prepare`.
   - No data, API or UI change, and run counts are unaffected.
   - It edits the same `config/ci.rb` lines as Opportunity 1, so land the two together.
7. Existing and additional validation required:
   - Existing: `ci_hygiene_test.rb:134-155` (set equality and one invocation), `:168-186` (fork guard on every job), `:188-197` (setup is the only local-only gate). All are unaffected.
   - New fixture assertions:
     - A gate job with `env: RAILS_ENV: test` is an offender.
     - A gate job with an extra `run: ci/ensure-resvg.sh` is an offender.
     - Negative controls: `TINKEREX_SYNC_DIR`/`CARGO_HOME` on a gate job and `DEPENDENCIES_HASH` on a `uses:` step stay green. Without these, a predicate that flags everything also passes.
   - Mutations: re-add `RAILS_ENV: test` to one real job → red; re-add the resvg step → red; delete an entry from `RUNNER_PLUMBING_ENV` → `test-chunk-remote`'s job goes red.
8. Confidence: medium. The facts are verified against the gem sources and the initializer. The value is moderate: no shipped bug yet, but a live local/CI split in the subsystem's central claim, and it has already misled one reader.
