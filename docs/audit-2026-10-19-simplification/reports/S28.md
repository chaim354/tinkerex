2. **Evidence**

## Opportunity 2: Each write phase names its own "unfiled" record (one helper), instead of threading payload + path through five raise sites

1. **Verdict:** recommend

2. **Evidence**
   - `bin/log:87-92` says the payload rides on the exception and "`api` ... attaches the payload at the
     ONE raise site". At HEAD, five sites construct a payload-carrying `Unreachable`: `:185` and `:189`
     (api), `:396-399` (label attach), `:411` (create_task) and `:563-564` (note). Four of them re-wrap an
     `Unreachable` they caught, merging with `e.payload || payload` / `e.path || path`, and the
     precedence of those merges is load-bearing (`:388-395`).
   - **The mechanism the comment names cannot fire in the most common outage.** A write verb's first wire
     call is always a READ: workspace and project resolution (`:120-141`) or the board (`:259-287`). When
     Kaneo is down, `api` attaches `body = nil`. What saves the record is a per-verb rescue, and each of
     those was added after a measured loss:
     - 234abebd: "an `open` against a dead server reported 'nothing to file' — silently turning a write
       into a no-record".
     - 0aae5900: "A non-JSON 2xx on a write was therefore losing its payload and reporting 'nothing to
       file'".
     - da5244f9: the label-vs-create spool trap, and note's issue number becoming "unrefilable".

     The rule "THE PAYLOAD IS BUILT BEFORE ANY WIRE CALL" (`:363-368`) is enforced only by a comment.
   - **The unpatched instance is `close`** (`:587-603`), which has no rescue of its own. A failed PUT
     after a good board read spools `{"status": "done"}` under `# endpoint: /api/task/status/<opaque id>`.
     No issue number appears in the entry or in the error message. It is the same defect
     note's rescue (`:556-562`) was written to fix, reappearing in a verb that never got the
     patch. No test drives it: the only close-outage test (`test/log_cli_test.rb:1264-1269`)
     covers the read failure.
   - **The spool's `# endpoint:` line is overloaded.** `spool!` (`:632-637`) says it "is what tells a label
     attachment from a task create", but it records whichever request FAILED:
     - an open/arc/deploy against a dead server spools a task-create body under
       `# endpoint: /api/auth/organization/list`;
     - a garbled 2xx on the create is filed under `/api/task`;
     - a 5xx on the create is filed under `/api/task/<pid>`;
     - a note is filed under `/api/auth/organization/list (issue #128)`.

     The test for the resolution case (`log_cli_test.rb:582-593`) asserts only the title.

3. **Current complexity / invalid states**
   - `Unreachable#payload` and `#path` are two independently nullable fields filled from different places:
     `api` fills them for the write call itself, and the verb's rescue fills them for everything before it.
   - The pair can therefore be contradictory (a POST body beside the path of a GET that failed) or
     incomplete (close: a body that names nothing).
   - Writing a correct new write verb requires knowing that `api`'s auto-attach does NOT cover the
     server-down case, which is the opposite of what `:87-92` tells the reader.

4. **Proposed representation and why it is simpler**
   The verb states what it would leave unfiled around each write phase, resolution reads included. One
   helper puts that record on the exception passing through, and `main` spools the record or nothing:
   ```ruby
   Unfiled = Struct.new(:what, :payload)          # one record; it is also the spool entry
   class Unreachable < StandardError
     attr_accessor :unfiled                       # nil => a read failed: nothing to file
   end

   def filing(what, payload)                      # payload is evaluated BEFORE any wire call
     yield
   rescue Unreachable => e
     e.unfiled ||= Unfiled.new(what, payload)     # innermost phase wins if anyone ever nests
     raise
   end

   def create_task(title, body:, labels:, closed: false)
     payload = { title: title, description: body, priority: "no-priority",
                 status: closed ? CLOSED_STATUS : OPEN_STATUS }
     task = filing("create #{title.inspect} (#{labels.join(', ')})", payload) do
       parse(api(:post, "/api/task/#{project_id}", payload), "/api/task")
     end
     labels.each do |name|                        # a SIBLING phase, never nested in the create
       attach = { name: name, color: "#666666", workspaceId: workspace_id, taskId: task.fetch("id") }
       filing("##{task['number']} was created but its #{name.inspect} label was not attached", attach) do
         api(:post, "/api/label", attach)
       end
     end
     task
   end
   # note:   filing("comment on ##{number}", payload) { api(:post, "/api/comment/#{task_for(number).fetch('id')}", payload) }
   # close:  task = task_for(number)                     # stays outside: a read failure still spools nothing
   #         filing("close ##{number}", { status: CLOSED_STATUS }) { api(:put, ...) }
   # api:    the `rescue Unreachable` re-wrap goes; the transport rescue raises a plain Unreachable
   # spool!: "# unfiled: #{command} — #{unfiled.what}" + the pretty JSON payload; the endpoint line goes
   ```
   Why this is simpler:
   - One mechanism replaces an auto-attach plus four compensating rescues.
   - The payload-before-wire rule becomes structural, because Ruby evaluates the argument before the block.
   - The label trap (`:388-395`; `log_cli_test.rb:679-686`) cannot form, because the label phase is a
     sibling of the create phase rather than nested in it.
   - Every spool entry says what it is in the record's own terms (#N, label, comment). A close entry
     becomes refilable through the single door with `bin/log close N`.
   - The two properties C2 was protecting survive. Reads never open a phase, so they spool nothing by
     construction. Nothing lives in module state, because the record rides the exception.

5. **Smallest credible implementation scope (in order)**
   1. `bin/log`: add `Unfiled`, the accessor and `filing`; remove `api`'s re-wrap (`:178-185`).
   2. `bin/log`: `create_task` uses two sibling phases and deletes both rescues (`:384-411`).
   3. `bin/log`: `note` gets one phase and deletes its rescue (`:556-565`).
   4. `bin/log`: `close` gets a phase around the PUT only.
   5. `bin/log`: `setup` gets a phase around each definition POST, for parity with today's spooling.
   6. `bin/log`: `main`/`spool!` print `what` and spool it; the `# endpoint:` line is dropped.
      Optional: `status` prints each entry's header and counts entries rather than files.
   7. `test/log_cli_test.rb`: re-express the `"/api/label"` assertion (`:688`) as the attachment record,
      and add the tests in field 7.

   No interface changes: commands, exit codes 0/2/3/4/5 and the spool path all stay as they are
   (CLAUDE.md:374-376 is unaffected).

6. **Regression risks and migration concerns**
   - The spool text changes. Only humans read it; `status` only globs the directory.
   - The stderr message on a label failure must keep "#N was created" and the quoted label name
     (`log_cli_test.rb:674-677`).
   - `||=` (innermost wins) must stay if a caller ever nests phases. The label test (`:687-693`) pins
     this, by refuting `"description"` in the spool.
   - `close`'s resolution read must stay OUTSIDE its phase, so a read failure still spools nothing
     (`:1259-1263`).
   - No backend-leg dependence: `bin/log` runs as a no-Rails subprocess, so the three legs see identical
     behaviour.
   - §14j's environment stripping is untouched.

7. **Existing and additional validation required**
   - Existing tests that pin the behaviour: `log_cli_test.rb:285-303, 355-368, 374-390, 398-416, 421-431,
     582-593, 659-697, 783-793, 1264-1269`.
   - New test (a): `close 10` with a good board and `PUT /task/status` answering 502 must leave a spool
     entry naming `#10`. Mutation: remove close's phase → nothing is spooled → red.
   - New test (b): `open` against the dead default port must leave an entry that names the create and does
     NOT contain `/api/auth/organization/list`. Mutation: put the failed request's path back into the
     header → red.
   - New test (c), optional, a funnel at test level: for every `SUBCOMMANDS` key outside a hand-written
     list of non-spooling verbs (`show search status setup close`), a run against a dead port leaves a
     spool file. Mutation: remove note's phase → red. A new write verb that forgets `filing` then fails
     by default.

8. **Confidence:** medium. The mechanism and both defects (close's anonymous entry, the contradictory
   endpoint line) are concrete and checked against the code. The payoff is confined to outage paths, and
   the refactor touches the code with this file's densest regression history; the existing
   mutation-checked spool tests are what make it safe.

## Considered and rejected
- **A typed Kaneo wire model (Task, Board, SearchRow values).** Each response shape is read in exactly
  one place: the board in `task_index`, search rows in `search`, label rows in `label_index`, orgs and
  projects in their resolvers. The only two-shape hazard, search's `taskNumber` against the board's
  `number`, is confined to `search` and pinned by `log_cli_test.rb:846-873`. Nothing guesses between
  shapes (contrast F-S04-1), so this would only move existing reads behind types. The real duplication
  of the wire model is `bin/migrate-record` (Opportunity 1).
- **One "build an issue from a template" path for arc/deploy/note.** It already exists: open, arc and
  deploy all go through `create_task` (`:373`), and the bodies are one-line strings (`:448`, `:529`).
  note and close are single-call writes with nothing to share.
- **Deriving `dispatch` from `SUBCOMMANDS`.** Stylistic. The `else raise` arm (`:756-760`) already makes
  drift loud.
- **Splitting the outcome model further.** It is already one model: verbs return `EXIT_*`, helpers raise
  `UsageError`/`Unreachable`, and `main` maps them once (`:669-734`). A wart remains: `Unreachable` also
  covers not-found (`:286`), slug misconfiguration (`:125`, `:137`), gh failures (`:429`, `:436`) and
  setup verification (`:493`). So `note 9999 "x"` exits 3 with "Kaneo is unreachable — no issue #9999"
  and spools an entry nobody can file. A separate NotFound outcome would be more honest, but it changes
  exit-code semantics that `/finish-branch` reads and that `log_cli_test.rb:1096-1108` pins. That is a
  behaviour change, not a simplification.
- **A write-ahead spool (journal before the first wire call, delete on success).** It gives "spool by
  construction", but it adds new failure modes:
  - the spool can be unwritable while Kaneo is reachable;
  - deleting one entry from an appended per-branch file forces a file per entry;
  - Ctrl-C after the server accepted the write leaves a stale entry.

  It would also rewrite most of the spool tests. Opportunity 2 gets the same guarantee for less.
- **A `refile`/`clear` verb.** The spool has no transition from spooled to filed inside the tool: a human
  re-runs the verb and `rm`s the file. Plans already misdescribe this (`2026-10-16-landing-format-wall.md:1445`
  says "file it with `bin/log status`"). But a new verb is feature work, and NO auto-replay is a
  recorded decision (CLAUDE.md:375; spec 2026-08-26 §5.2).
- **Spool scope is the checkout, not the repository. NOT a simplification, but a real ownership gap,
  flagged for a separate small fix.** This answers the row's question of whether `status` and the spool
  can disagree:
  - `status` always agrees with its own directory. But `spool_dir` (`:605`) defaults to the RUNNING
    checkout's `tmp/log-pending`, and 28 worktrees exist under `.claude/worktrees/`.
  - So a record spooled in one worktree is invisible to `bin/log status` in every other checkout. That
    includes the start-of-run checks in `/finish-branch` and `/deploy`.
  - The spool is deleted when that worktree is removed, and since `tmp/` is gitignored (`.gitignore:16`),
    a worktree whose only change is a spool file looks clean to git.
  - A default under `git rev-parse --git-common-dir`, falling back to `tmp/`, would make the backlog the
    repository's. It changes behaviour, so it is not counted here.
- **`status` counts files, not entries.** It prints "1 unfiled record(s)" for a branch file holding
  several. Cosmetic; can ride along with Opportunity 2.
- **Retiring `bin/verify-fix-log`.** It shares no model with `bin/log`: it is bash plus git over one
  frozen markdown ledger with 50 rows. CLAUDE.md:1350 cites it as standing practice, so removing it is a
  line-count change plus a CLAUDE.md edit. Keep.
- **Retiring `arc --from-file`/`--closed`** (`:449-451`, `:456`, `:462-470`). These were built for the
  STATUS.md import (851577f4), whose splitter was deleted when that import finished (8ec505c1), and no
  workflow uses them now. But five tests use `--from-file` as scaffolding to drive `create_task` without
  a gh stub (`log_cli_test.rb:621-697, 907-961, 1014-1024`), and no state model changes, so this is a
  minor line-count item. It is an optional ride-along with Opportunity 1, not counted.
- **Test-quality asides (not simplifications):**
  - (i) The real-spool guard (`log_cli_test.rb:434-451`) computes the branch with
    `git branch --show-current`, which prints "" on CI's detached checkout, while `bin/log` writes
    `detached-<sha>.md` there. In CI the guard compares a file that can never be written, so it cannot
    fail there (§14e's vacuous-guard shape). Locally it works.
  - (ii) The usage test's list (`log_cli_test.rb:79`) omits `close`.
