## Opportunity 1: render.mjs's exit-code wire -- make the declared outcome table true (exit 3 is unreachable; "not a Gerber" exits 1 inside node's crash report)

1. Verdict: recommend

2. Evidence
- The declared wire, render.mjs:35-37: "EXIT CODES ARE THE WIRE: 0 + SVG on stdout, 2 for a usage error, 3 when
  nothing parsed, 4 when there is nothing to draw. Anything else is node itself failing". And :39-41: "3 AND 4 ARE
  SEPARATE BECAUSE THE RUBY SIDE ANSWERS THEM DIFFERENTLY. A file that will not parse is a RenderError".
- The exit-3 arm, render.mjs:54-58: `const rendered = renderLayers(plot(await read(files)))` then
  `if (rendered.layers.length === 0) { ... "no layer could be parsed" ... process.exit(3) }`.
- Why it can never fire: :49-52 already exits 2 when `files.length === 0`, and tracespace's `read` (bundle line 16)
  is `async function cs(e){let n=e.map(ps),l=await Promise.all(n),...;for(let{id:a,filename:i,parseTree:s}of l)
  {...o.push({id:a,filename:i,type:p,side:d})...}return{layers:o,...}}` -- exactly one layer per input path, or a
  rejection. `plot` (`ds`) and `renderLayers` (`hs`) both hand `layers:n` back unchanged. So
  `rendered.layers.length === files.length >= 1` on every path that reaches :55.
- Where "will not parse" really goes: `ps` calls `Ol(t)` = `Tr().feed(e).result()`, and `result()` is
  `if(l===null)throw new Error("File type not recognized")` (bundle line 8). That rejection escapes the top-level
  `await read(files)` -> node's uncaught-exception exit, code 1 -- the code the header reserves for "node itself
  failing".
- The Ruby reader, gerber.rb:84-97: `NOTHING_TO_DRAW = 4` -> `Unsupported`; otherwise
  `raise RenderError, "tracespace failed (#{status.exitstatus}): #{err.to_s[0, 300]}" unless status.success?`.
  Codes 1, 2 and 3 are one answer; only the first 300 bytes of stderr tell them apart.
- The test that records the false mechanism, gerber_test.rb:212-220: "render.mjs exits 3 with "no layer could be
  parsed" on an empty render" over `assert_raises(RenderError) { svg_for("\x00\x01\x02 not a gerber at all", ...) }`.
  It passes via exit 1 and cannot tell. (Since 3 is unreachable, wherever this case runs rather than skips, its
  green IS the proof that "not a Gerber" travels as node's crash exit.)
- The sibling tool already has the needed shape: stl-thumbnailer main.rs:6-14 -- one handler,
  `eprintln!("stl-thumbnailer: {e:#}")`, one exit code.

3. Current complexity or invalid states
- The wire declares an outcome (3) the tool cannot produce and omits the one it does produce (unparseable input ->
  1). "This file is not Gerber/Excellon" and "tracespace or node crashed / OOM'd / failed to load a module" share a
  code, so no caller can answer them differently without parsing a stack trace -- the separation the header says
  the codes exist for.
- Diagnostics: the throw sits on bundle line 8, a single 85,723-character minified line. Node's fatal-exception
  report prints `<file>:<line>` and then the throwing source line before the message, so the 300 characters
  gerber.rb keeps (and GeneratePreviewJob stores in `maker_previews.error`) are expected to be the path plus ~250
  characters of minified JavaScript, not "File type not recognized" (Node's report format; not executed here).
- The policy hook is missing: pdf.rb:49-63 answers "content is not the claimed format" with `unsupported` because
  `failed` is the state Enqueue re-enqueues; whether a non-Gerber `.gbr` (GIMP's brush format uses the same
  extension) should get the same answer cannot even be expressed today without matching on stderr.

4. Proposed representation and why it is simpler
Each outcome gets its code at the one place it can arise, and every failure writes one line (main.rs's shape):

    const fail = (code, why) => { process.stderr.write(`render.mjs: ${why}\n`); process.exit(code) }
    if (!["layer", "board"].includes(mode) || files.length === 0) fail(2, "usage: ...")
    let parsed
    try { parsed = await read(files) }            // the ONLY place "not Gerber/Excellon" can arise
    catch (e) { fail(3, `no layer could be parsed: ${e.message}`) }
    const rendered = renderLayers(plot(parsed))   // a throw here stays exit 1: tracespace failed on input it recognised
    // svg selection and the exit-4 viewBox check (:59-76) unchanged

The unreachable `layers.length === 0` arm is deleted and the header's table becomes true without adding a state.
Optional: wrap plot/render in a catch that writes one line and exits 1, so a minified-source dump never reaches
`maker_previews.error` either. Ruby needs no change: 4 stays `Unsupported`, everything else stays `RenderError` --
now with a readable reason, and with 3 available should S08 want pdf.rb's policy.

5. Smallest credible implementation scope
1) tools/gerber-svg/render.mjs: the catch around `read`; delete :55-58; rewrite :35-45 to the real table
   (0 SVG / 2 usage / 3 not Gerber-or-Excellon / 4 nothing to draw / anything else = node or tracespace failed).
2) test/services/maker/previews/gerber_test.rb:212-220 (S08's file): correct the comment; assert code and reason.
3) No change to gerber.rb, gerber_zip.rb, the job, or files-preview.md (which names only exit 4, :336-339).
4) Not part of this recommendation (S08's policy call): whether 3 maps to `Unsupported` per pdf.rb:49-63.
   render.mjs:39-41 records RenderError as the intent today and gerber_test.rb pins it.

6. Regression risks and migration concerns
- Ruby behaviour unchanged: every non-4 code is still RenderError -> `failed`. Board mode: one unrecognised member
  fails the board with 3 instead of 1 -- the same rule gerber_controller.js:142-147 applies to a missing layer.
- Streams stay separate (gerber.rb:70-73 relies on it); the exit-4 check and the unparseable-viewBox fall-through
  (render.mjs:63-76) are untouched. `run_node`'s `out.include?("<svg")` check is untouched.
- The catch also classifies an I/O failure reading the temp file as 3; the one-line message keeps the real reason.
- Existing `failed` rows keep their old error text until re-rendered; no migration; no backend-leg dependence.
- `process.exit` straight after a stderr write can drop the line on macOS (async pipes); exits 2/3/4 already do
  this today, and Linux (prod, CI) pipes are synchronous.

7. Existing and additional validation required
- Existing, unchanged: gerber_test.rb:104-111 (empty layer -> Unsupported), :134-144 (node not runnable),
  :159-193 (timeout + process-group kill), :214-220 (garbage -> RenderError); gerber_zip_test.rb's render cases.
- New, in :214-220: `assert_match(/failed \(3\)/, error.message)` and `assert_match(/not recognized/, error.message)`.
  Mutation 1: remove the try/catch -> exit 1 -> red on the code. Mutation 2: restore a `layers.length === 0` check
  instead of the catch -> still exit 1 -> red. Needs node + the committed bundle (the CI image has node,
  ci/runner/Dockerfile:86-99); skips elsewhere like every other render case.
- Optional: a board-mode case (one MINIMAL_GERBER member + one garbage member) -> RenderError carrying `(3)`.

8. Confidence: medium. High on the mechanism -- read straight from the bundle (one layer per input or a rejection;
the parser's throw) plus node's standard exit 1 for an uncaught error. The stderr-content consequence follows
Node's fatal-exception format but was not executed. The payoff is a true wire and readable failures rather than a
behaviour change, so it is modest; blast radius is one script and one assertion.

## Opportunity 2: One resvg declaration per image that pins what actually renders; retire ci/ensure-resvg.sh and make a missing preview toolchain red in CI

1. Verdict: recommend

2. Evidence
- Three literal pins, none of which pins the dependency closure: Dockerfile:107
  `RUN cargo install resvg --version 0.47.0 --root /out`; ci/runner/Dockerfile:162
  `RUN cargo install resvg --version 0.47.0 --root /usr/local`; ci/ensure-resvg.sh:24
  `cargo install resvg --version 0.47.0`. None passes `--locked`.
- The repo's own measured rule for exactly this, ci/runner/Dockerfile:175-181: "`--locked` IS NOT OPTIONAL ...
  `cargo install` IGNORES a committed Cargo.lock unless told otherwise: the build log read `Locking 37 packages to
  latest compatible versions` ... a renderer whose dependencies drift silently between image rebuilds would change
  stored previews with nothing recording that it happened." Applied to stl-thumbnailer (:205) and to neither resvg
  install.
- What "0.47.0" leaves floating: the published resvg-0.47.0.crate ships a Cargo.lock (tiny-skia 0.12.0, usvg 0.47.0)
  while its Cargo.toml asks for caret ranges (`tiny-skia = "0.12.0"`, `usvg = "0.47.0"`); without `--locked` each
  image build resolves the rasterizer and the parser to whatever patch release is current that day.
- The script on today's fleet: every job runs in the image (ci.yml:103-104), which installs and verifies resvg
  (ci/runner/Dockerfile:162-163), so ensure-resvg.sh always exits at :14-17 ("already present"). Its brew arm (:19)
  is unpinned and the image has no brew; its cargo arm (:24) cannot succeed as the job user, whose CARGO_HOME is the
  root-owned image default (ci.yml:261-263, "read-only here -- cargo cannot fill its registry"); its GITHUB_PATH line
  (:25) names `$HOME/.cargo/bin`, not the image's CARGO_HOME.
- It guards two of the three backend legs: ci.yml:218-219 (`test`) and :231-232 (`test-s3-backend`);
  `test-chunk-remote` (:237-269) and `system-test` (:271-281) never call it and have resvg anyway -- because the
  image, not the script, provides it.
- The equality it is cited for is unenforced: ci/runner/Dockerfile:141-142 "resvg is pinned to 0.47.0, matching
  ci/ensure-resvg.sh's own cargo fallback, so the two cannot disagree" -- no test reads either value and the
  production Dockerfile is not mentioned. The neighbouring binary has already drifted the same way: pdfium-cli is
  v0.2.0 native in CI (ci/runner/Dockerfile:166) and v0.11.0 webassembly in production (Dockerfile:117-119).
- The class it watches one instance of, ci.yml:112-116: stl-thumbnailer was absent on the Mac runner, so "the STL
  preview path had never once run in CI -- ci/ensure-resvg.sh's "green about less than you think", silently, for a
  different binary than that script watches".
- The pattern is being taught forward: docs/adding-a-preview-format.md:24-27 tells the next format author to "add an
  idempotent install to the self-hosted CI legs in .github/workflows/ci.yml".

3. Current complexity or invalid states
- "Which resvg does this repo mean" has three owners with three semantics (top crate pinned in two images; any
  version / brew-latest / top crate pinned in the script), and even the agreeing "0.47.0" literals admit different
  tiny-skia/usvg patch versions per image build -- a production image and the CI image built on different days can
  rasterize the same SVG differently, with no THUMBNAIL_REVISION bump anywhere.
- The script presents as CI's resvg gate but is a no-op wherever CI runs; in the one case it would matter (an image
  that lost resvg) it can only print a non-fatal step summary, for one binary, in two of three legs. A missing
  stl-thumbnailer, pdfium, vipsthumbnail or node degrades its tests to skips with no signal at all.

4. Proposed representation and why it is simpler
- One owner of CI's toolchain: the runner image. Delete ci/ensure-resvg.sh and its two workflow steps.
- One effective pin per image: `cargo install resvg --version 0.47.0 --locked` in both Dockerfiles, held equal by
  one hygiene assertion (ci_hygiene_test.rb already reads ci/runner/Dockerfile at :486):

      installs = %w[Dockerfile ci/runner/Dockerfile].flat_map { |f| File.read(Rails.root.join(f)).scan(/cargo install resvg (.*)$/) }.flatten
      assert_equal 2, installs.size                          # the scanned set is not empty (§14e)
      assert_equal 1, installs.map { |a| a[/--version (\S+)/, 1] }.uniq.size
      assert installs.all? { |a| a.include?("--locked") }

- One gate for the class: when `ENV["CI"]` is set, a test that FAILS (never skips) unless every renderer the image
  promises answers `available?` -- SvgRasterizer (resvg), Stl, Pdf, ImageThumb, Gerber (node + bundle) -- with Mesh
  named as deliberately absent (no F3D in the CI image).
Net: three resvg declarations plus an imperative fallback become two declarative ones a test keeps equal, and a
one-binary, two-leg warning becomes one red gate over all five toolchains.

5. Smallest credible implementation scope (order matters)
1) New CI-only presence test (e.g. test/preview_toolchain_test.rb) -- land first; confirm green on the live image.
2) test/ci_hygiene_test.rb: the resvg-pin assertion above.
3) Dockerfile:107 (S24) and ci/runner/Dockerfile:162: add `--locked`; reword ci/runner/Dockerfile:141-142 to name
   the hygiene test instead of the script.
4) Delete ci/ensure-resvg.sh and ci.yml:218-219, :231-232.
5) docs/adding-a-preview-format.md:24-27: "install it in the Dockerfile and ci/runner/Dockerfile at one version,
   and add it to the CI presence test".
Rebuild the CI image (ci/runners/README.md, "Rebuilding the image") and redeploy for step 3.

6. Regression risks and migration concerns
- `--locked` installs the published lock's tiny-skia/usvg. If either live image was built against later 0.12.x /
  0.47.x patches, PNG output can move with no revision bump; compare the fixtures' PNG bytes from old and new image
  before deploying and bump the SVG-family THUMBNAIL_REVISIONs only if they differ (measure-view.md revision rules).
- The presence test turns ensure-resvg.sh:4's "NON-FATAL BY DESIGN" into a red gate. That design dates from a
  developer-Mac runner whose toolchain the repo did not control; every job now runs in a repo-built image
  (ci.yml:103-104), so a missing binary is an image defect -- "a gate that is not a gate" in the script's own words
  (:8). If the live image predates ci/runner/Dockerfile (e.g. lacks node), step 1 goes red at once: that is the gap
  it exists to surface -- rebuild before step 4.
- A future macos/windows job loses the brew/cargo fallback; ci_hygiene_test already forces such jobs behind
  preflight, and the presence test makes the missing toolchain an explicit decision rather than a silent skip.
- App runtime, data and the three backend legs are untouched (the CI-only test skips outside CI, so run counts
  still match across legs).

7. Existing and additional validation required
- Existing: svg_rasterizer_test.rb:49-60, gerber_test.rb:134-144, stl_test.rb:24-26 show `available?` answers
  honestly for a missing binary -- the property the presence test relies on.
- Hygiene mutations: one Dockerfile at `--version 0.46.0` -> red; `--locked` dropped from one -> red; one install
  line deleted -> red on the count (the non-empty guard).
- Presence mutations: `CI=1 RESVG_BIN=/nonexistent bin/rails test <file>` -> red naming SvgRasterizer;
  `CI=1 NODE_BIN=/nonexistent` -> red naming Gerber; `CI=1 STL_THUMBNAILER_BIN=/nonexistent` (set before boot --
  Stl::BIN is read at load, stl.rb:21) -> red naming Stl.

8. Confidence: medium. High on every fact (read in the files, the workflow and the cached resvg crate). Medium on
value: on today's fleet the risk is latent (the image does carry resvg 0.47.0), but the two concrete cases next
door -- STL never ran in Mac-era CI; pdfium already differs between the two images -- show the per-binary,
two-image model drifts in practice.

## Considered and rejected
- An explicit "nothing drawn" outcome for stl-thumbnailer (empty mesh / non-finite bounds -> an exit-4 analogue
  mapped to `unsupported`). `render_stl` returns `Ok(blank PNG)` for both (lib.rs:87-88, :106; render.rs:72-82 pins
  the empty case), so the row goes `ready` on a background-only tile. Below the bar: Gerber's exit 4 exists because
  an empty `.gbo` is ORDINARY (render.mjs:39-45); an empty or NaN STL is not. (Aside: under `cargo test`'s debug
  profile, euc's `debug_assert!` at triangles.rs:97 panics on non-finite coordinates, so lib.rs:88's "never panics"
  holds only for release builds -- which is what ships.) The earlier audit's S35 SKIP of lib.rs stands.
- The absolute near plane in `auto_frame` (lib.rs:195, `0.01` against a scale-relative eye distance) looked as if it
  would blank sub-centimetre models exported in metres. It does not: euc 0.5.3 does no near/far clipping
  (triangles.rs:146-158 only depth-tests the interpolated z against a buffer initialised to 1.0, lib.rs:104) and the
  depth mapping is monotonic for any positive distance. No defect.
- `anyhow::Result` collapsing "not an STL" and "PNG encode failed" into exit 1 -- consistency-only for STL (both rare,
  both honestly `failed`); the Gerber half earned Opportunity 1 because its table is declared and false.
- One output convention for both tools (stl-thumbnailer writes a file, render.mjs writes stdout) -- style; each Ruby
  wrapper handles its one tool and no outcome differs.
- A wall-clock bound for stl-thumbnailer -- gerber.rb:99-108 argues the asymmetry (input capped by
  MAX_PREVIEW_BYTES; euc cost linear in triangles, README.md:66-68).
- Shipping one tracespace bundle for browser and node (byte-identical today) -- recorded rule:
  bin/build-tracespace:138-143, files-preview.md:280-285.
- Sharing render.mjs's read -> plot -> renderLayers -> (layer | board.top) with gerber_controller.js:142-147 /
  :257-266 -- three library calls in two runtimes with different inputs (paths vs `File` objects) and needs (top only
  vs both sides + toggles). Layer type/side identification exists only inside tracespace (`oi`, bundle line 16; no
  Ruby copy -- grep of app/ for copper/silk/side finds none), and single-vs-board is decided by the server for both
  surfaces (files_controller.rb:575 `@gerber_single`; the Registry choosing Gerber vs GerberZip). Nothing to remove.
- A crate-side revision constant or a source-digest guard tying tools/stl-thumbnailer to `Stl::THUMBNAIL_REVISION`
  -- adds a second edit site (the S35 verdict) or fires on comment-only edits; measure-view.md:365-368 puts "ship
  both or neither" on the Rails side deliberately.
- Collapsing the crate's [lib]/[[bin]] split now that no desktop core links it -- tests/render.rs needs the library
  entry point. But the "AND the Tauri desktop core" claims (Cargo.toml:5, README.md:3-8, lib.rs:6-7) are false
  (../tinkerex-client has no reference; its d21c50c moved the crate out as server-side) -- correct them in passing.
- `w * SSAA` u32 overflow / unbounded allocation for absurd sizes (lib.rs:100-101) -- unreachable: Ruby always
  passes 512 (128 in tests).
- `auto_frame` scanning the flattened `verts` (3 per face) instead of `mesh.vertices` for bounds -- trivial cost,
  line-count only.

## Cross-subsystem notes
- gerber.rb:62-67 (S08) writes the layer as `layer.<ext>`, while render.mjs:10-12 requires that "the caller writes
  each member under its real basename" because tracespace identifies a layer from its name. KiCad's
  `*-Edge_Cuts.gbr` / `*-F_Cu.gbr` carry identity in the basename, which the viewer keeps (gerber_controller.js:168
  `new File([...], name)`) and the thumbnail drops; low impact for a single layer (drawn in currentColor), but it can
  change the board shape / viewBox an outline layer is drawn in.
- pdfium-cli differs between images: v0.2.0 `pdfium-linux-x64` in CI (ci/runner/Dockerfile:165-168) vs v0.11.0
  `pdfium-webassembly-linux-${TARGETARCH}` in production (Dockerfile:116-120) -- CI's PDF thumbnail tests exercise a
  binary production does not ship (S24 / CI owner).
- Dockerfile:98 (S24) builds stl-thumbnailer with `cargo build --release`, no `--locked`; `cargo build` honours a
  consistent committed lock, so no live drift, but `--locked` would make a manifest/lock mismatch fail the build, as
  ci/runner/Dockerfile:175-181 argues.
- stl.rb:7-10 (S08) says the crate "also runs in the Tauri desktop core ... this server-side path is the universal
  fallback" -- false; the server is the only path.
- Five copies of one subprocess shape (Tempfile in -> out path -> capture3 -> `success? && exist? && size?` -> ensure
  delete -> ENOENT -> RenderError): stl.rb:55-73, pdf.rb:65-87, image_thumb.rb:43-61, mesh.rb:83-103,
  svg_rasterizer.rb:82-98 (S08).
- Three conventions for the `*_BIN` override: constant frozen at load (stl.rb:21, pdf.rb:38, image_thumb.rb:30,
  mesh.rb:31), memo + `reset_bin!` (svg_rasterizer.rb:20-22), read per call (gerber.rb:34) (S08).
- `available?` spawns a process on every GeneratePreviewJob run (generate_preview_job.rb:107 -> Stl runs the binary,
  Gerber runs `node --version`), unmemoized (S08).
- gerber.rb's node subprocess has a wall-clock bound but no heap bound; the recorded 104 s probe ended at the kernel
  OOM killer, which under SOLID_QUEUE_IN_PUMA could as easily choose Puma. `node --max-old-space-size=...` would keep
  the failure inside node (-> RenderError); worth measuring against MAX_EXTRACTED_BYTES (S08).
