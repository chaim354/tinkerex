## Opportunity 1: Stored attachment roles follow the vocabulary by ONE rule with one owner, not by a hand-copied migration per widening (and the two widenings that never got one heal)
1. Verdict: recommend
2. Evidence:
   - The column is a write-time snapshot. `maker_file_attachments.role` defaults to `"other"` (`db/schema.rb:174`); it is written from `role_for(name)` at attach time (`project_intake.rb:673`, `model_intake.rb:163`, `attach_to_project.rb:128,315`, `models/attachments_controller.rb:23`, `projects/uploads_controller.rb:138`), as `"image"` by the two photo doors (`entry_photos_controller.rb:16`, `uploads_controller.rb:138`), and from the client through v1 (`v1/maker/file_attachments_controller.rb:33`). Nothing rewrites a row afterwards: `ProjectIntake#attach` plucks existing node ids and rejects them (`project_intake.rb:669-671`). The code says so itself: "An attachment row's role is a snapshot taken when the row was written … a stale row would misfile it" (`project_folders.rb:15-17`).
   - Readers act on the stored value: `Project#derived_cover_node_id` (`project.rb:198-201`) through `HERO_ROLES` — electronics prefers `%w[pcb image model]` (`project_kind.rb:110-113`, added 8973e8ee, 2026-09-07); `Model#derived_cover_node_id` (`model.rb:109-114`); `ModelsController#show` `@by_role` → gallery and instructions (`models_controller.rb:50`, `models/show.html.erb:103,128`); every v1 attachment JSON (`v1/maker/projects_controller.rb:57`, `items_controller.rb:74`, `file_attachments_controller.rb:38`).
   - So every widening of `ROLE_BY_EXT` has to reach stored rows by hand: 9 data migrations 2026-07-28 → 2026-09-08 (651 lines) plus 9 tests (1,114 lines), carrying 111 hand-copied extension entries. Seven restate ONE rule — an `other` row whose extension now has a role takes it (`20260728124303:35-41`, `20260729035422:29-35`, `20260826130000:46-51`, `20260826180000:57-61`, `20260906140000:50-57`, `20260907120100:57-70`, `20260908120100:60-67`); one is the only reclassification in history (`lbrn2` vector→laser, `20260730153103:41-46`); one seeds filing rules only (`20260906120000`).
   - Two widenings never got their row half. `nc`/`tap`/`ngc` joined `gcode` in 77c29bc3 (2026-07-31; `file_attachment.rb:71`) beside `RederiveLaserRoles`, which moves `lbrn2` only. The 24 `pcb` extensions joined in efb7455e (2026-09-06; `file_attachment.rb:172-176`) with `SeedPcbFilingRules`, which has no attachment class at all (`20260906120000:48-68`). No migration in `db/migrate/` names `nc`/`tap`/`ngc` or re-derives a `pcb` role (grep). `ProjectIntake` had auto-attached every project-folder file since 2026-07-31, so a Gerber attached between then and 2026-09-06 still says `other` — and the electronics hero added the next day prefers exactly `pcb`.
   - The migration tests pin each historical copy to TODAY's table. Per key: `rederive_roles_migration_test.rb:96-116` (with a `SUPERSEDED` allowlist the `lbrn2` move forced), document `:69`, code `:99`, laser `:83`, widened text `:125`, bench `:170`, image `:99`. As EQUALITY with today's role set: `seed_pcb_filing_rules_migration_test.rb:129-131` ("exactly the pcb role") and `rederive_model_roles_migration_test.rb:109-111`. So `file_attachment.rb:167-171` — "`.xnc` … adding it later is a one-line edit here with no other consequence" — is false at HEAD: that one line turns the pcb migration's test red, and existing `.xnc` rows would stay `other` without yet another migration. `files-preview.md:13`'s "Add an extension in `ROLE_BY_EXT` only" is false for existing data in the same way.
   - "Derived" is already defined by heuristic, migration by migration: "only rows holding the PRIOR role are touched (a role set deliberately is never rewritten)" (`20260906140000:14-17`), with the stated limit that `down` "cannot tell a row `up` re-derived from one that was `image` all along" (`20260908120100:20-23`).
3. Current complexity or invalid states:
   - Representable and reachable today: an attachment stored `other` while `role_for(name)` is `pcb` or `gcode` (27 extensions). For a project whose Gerbers were attached between 2026-07-31 and 2026-09-06 and whose maker later set its kind to electronics, the hero falls back to an image, a model or the first attachment instead of the board; v1 clients are told `other`. Not measured on live data (read-only audit); the path is traced end to end above.
   - The rule "stored roles follow the vocabulary" has no owner. It lives in N self-contained migrations, each re-deciding which rows count as derived and each coupling history to the present through its test. A widening that forgets it fails silently, and two have.
4. Proposed representation and why it is simpler:
   - Make `other` mean, explicitly, "nothing classified this name when the row was written" — the one stored state the vocabulary can still improve — and give `Maker::FileAttachment` one method that re-classifies those rows against the CURRENT `ROLE_BY_EXT`, run by a sweep (the argument `Maker::AttachmentReaper`'s header makes: a sweep, not a hook).
     ```ruby
     # Maker::FileAttachment — beside role_for, the one owner of the vocabulary
     def self.classify_unclassified!(user)
       rows = user.maker_file_attachments.where(role: "other")
                .joins("JOIN nodes ON nodes.user_id = maker_file_attachments.user_id " \
                       "AND nodes.node_id = maker_file_attachments.node_id")
                .pluck("maker_file_attachments.id", "nodes.name")
       rows.group_by { |_id, name| role_for(name) }.except("other")
           .sum { |role, pairs| where(id: pairs.map(&:first)).update_all(role:) }
     end
     ```
   - Wired per user into the existing daily `Maker::AttachmentReaperJob` (DB-only, backend-neutral, per-user failure isolation already there), plus a rake task for an immediate run after a widening deploy. One query per user per day, and zero writes in steady state.
   - Simpler because one rule has one owner and reads the one vocabulary. An additive widening needs no migration and no test, so the `.xnc` promise becomes true for rows. The two missed widenings heal on the first run. The per-migration "which rows are derived" decision disappears: it is the same `other` rule that 7 of the 8 role re-derivations used. Writers are unchanged, and the recorded decision to STORE the role stands, so the cover stays query-free per card (`project.rb:168-171,189-192`).
   - Limits, stated: a reclassification (the `lbrn2` shape, 1 of 9 events) still needs a migration. An extension removed from `ROLE_BY_EXT` is not demoted.
5. Smallest credible implementation scope:
   1. `app/models/maker/file_attachment.rb`: the method (~10 lines).
   2. `app/jobs/maker/attachment_reaper_job.rb`: one per-user loop, copying `reap_all!`'s rescue. Alternatively, its own `config/recurring.yml` entry if the reaper's charter should stay "dead nodes only".
   3. `lib/tasks/`: `maker:classify_roles` (optional, for an immediate run).
   4. Tests (field 7).
   5. Docs: `files-preview.md:72-75` and `:490-498` (the role half no longer arrives by migration), `project_folders.rb:15-17`.
   6. Relax the two EQUALITY pins (`seed_pcb_filing_rules_migration_test.rb:129-131`, `rederive_model_roles_migration_test.rb:109-111`) to the per-key form the other seven use ("every copied extension still has this role"). Otherwise the next pcb or model addition turns a test of an already-run migration red. Those files are S23's.
6. Regression risks and migration concerns:
   - Data: the first run rewrites the stale `other` rows to their vocabulary role. That covers the 27 extensions above, plus any v1 row a client set to `other` for a now-known extension — the same overwrite all seven from-`other` migrations already performed. Derived covers (no chosen cover) of affected projects and models may change, which is the intent (electronics → board). No schema change, nothing destroyed, and no `down` (the same posture as the reaper).
   - API: the v1 `role` value changes for those rows and becomes more accurate; the shape is unchanged. UI: the model page's gallery and instructions groups may gain rows.
   - Latency: up to 24 h between a widening deploy and stored rows following, where a migration was immediate. The rake task covers it.
   - Backend legs: DB-only and identical on share/s3/chunk_remote; the new tests run on all three, so run counts stay equal.
7. Existing and additional validation required:
   - Existing: the `file_attachment_test.rb` role pins; `project_kind_test.rb:568-573` (hero lists); `importer_test.rb:106-114` (persisted roles are the server's); the attachment-reaper tests; the 9 migration tests (unchanged except the two pins).
   - New, derived from the table rather than copied:
     - For every `(ext, role)` in `ROLE_BY_EXT`, an `other` row on `f.<ext>` becomes `role`.
     - A deliberate non-`other` row (`instructions` on a `.log`, a build-log `image`) is untouched.
     - A row whose node is missing is untouched.
     - A second run returns 0.
   - Mutations:
     - Drop `where(role: "other")` → the deliberate-role case goes red.
     - `.except("other", "pcb")` → the derived sweep goes red on the 24 pcb extensions.
     - Remove the job wiring → a job test (a stale `other` `.gbr` row, `perform`, assert `pcb`) goes red.
   - End to end: an electronics project holding an `other` Gerber attachment and a photo shows the photo as its hero before the sweep and the board after it. Mutation: skip the sweep → red.
8. Confidence: high on the defect (git history, migration grep and reader trace agree). Medium-high on the remedy: hosting it in the reaper job or on its own schedule is the owner's call (S06 owns the files).

## Opportunity 2: The filing map stores the user's DEVIATIONS from the vocabulary's default, not a per-user copy of the vocabulary
1. Verdict: recommend
2. Evidence:
   - Every user holds a materialized copy. `FilingRules.seed!` inserts one row per `ROLE_BY_EXT` key plus `BEYOND_ROLE_BY_EXT` (`filing_rules.rb:48-60`) — 128 rows per user at HEAD (126 + 2) — and `FilingRules.for` then reads only those rows (`filing_rules.rb:62-65`).
   - The copy is written on READ: by the sweep's first `FilingRules.for` (`project_intake.rb:505`, `project_folders.rb:119`) and by a GET, because `FilingRulesController#index` calls `seed!` (`settings/filing_rules_controller.rb:19`). The hub must not seed, so it counts raw rows (`settings_controller.rb:1-12`: "a bare count must not seed 82 filing rules"). A user with no project folder who has never opened /settings/filing therefore reads "0 rules" while 128 defaults apply. The budget tests pre-create rows to keep `seed!`'s insert out of the measurement (`page_query_budget_test.rb:1316-1320,1338-1340`).
   - The `exists?` guard admits two states it cannot handle: an emptied map re-seeds ("an accepted gap", `filing_rules.rb:28-37`), and a user holding any one row is never completed — the partial map pinned by `filing_rules_test.rb:81-95`.
   - Each widening needs a top-up migration, because the guard forbids topping up on read (`project-intake.md:244-246`, `files-preview.md:490-498`). That has happened for 4 of 4 widenings since the table was created on 2026-09-04: `20260906120000` (pcb), `20260906140000:40-47`, `20260907120100:47-54`, `20260908120100:50-57`. Each carries a self-contained copy of the new keys and a test that pins the copy to today's vocabulary (`seed_pcb …_test.rb:129-131` by equality, bench `:170`, image `:99`), and the two `BEYOND_ROLE_BY_EXT` keys are re-spelled in `20260907120100:27-33`.
   - The default derivation is already spelled twice in `app/`. `seed!` inlines `ROLE_FOLDERS.fetch(role)` (`filing_rules.rb:52-55`). `default_folder_for` (`project_folders.rb:102-104`) is documented as "Used by Maker::FilingRules.seed!" (`:98-101`; `project-intake.md:247-249`), but grep finds no production caller — only tests, 36 references.
3. Current complexity or invalid states: storage cannot tell "the vocabulary's default" from "the user's choice". So:
   - (a) A new key cannot reach existing users without a migration.
   - (b) "Removed" is encoded as absence, which is also how "never seeded" and "newer than my seed" look. Hence the guard, the reseed gap and the partial map.
   - (c) Reading must write (GET seeds), and the one reader that must not write (the hub) disagrees with the one that does.
4. Proposed representation and why it is simpler: derive the default once at load, and store only deviations, with `folder: nil` meaning "I removed this default".
   ```ruby
   class Maker::FilingRules
     BEYOND_ROLE_BY_EXT = { "kicad_sch" => "pcb", "kicad_pcb" => "pcb" }.freeze
     DEFAULT = Maker::FileAttachment::ROLE_BY_EXT
                 .transform_values { |role| Maker::ProjectFolders::ROLE_FOLDERS.fetch(role) } # raises at boot on an unmapped role
                 .merge(BEYOND_ROLE_BY_EXT).freeze
     def self.for(user) = DEFAULT.merge(user.maker_filing_rules.pluck(:ext, :folder).to_h).compact
   end
   ```
   - Removed: `seed!`, the `exists?` guard, and every write on read (the GET, the hub, the sweep). The hub and the page read the same `for`.
   - A new key reaches every user with no migration.
   - A removed default is a row, so it can never be resurrected; the /settings/filing promise ("files into other until you add a new one") holds by construction.
   - The partial map and the reseed gap become unrepresentable.
   - `default_folder_for` becomes `DEFAULT.fetch(ext, "other")`, or is removed.
   - The invariant's REASON (never overrule an edit, never resurrect a removal; `filing_rules.rb:2-7`) is kept. Only its MECHANISM, "by migration, once", is retired.
5. Smallest credible implementation scope (S06 owns these files):
   1. A migration: `change_column_null :maker_filing_rules, :folder, true`, plus a one-time, self-contained conversion. For each user who has rows, insert `(ext, NULL)` for every HEAD default key the user lacks (a 128-key literal, the last copy). Existing rows are kept verbatim as deviations, so no user's effective map changes on deploy. `down` deletes the NULL rows.
   2. `filing_rules.rb`: add `DEFAULT` and the new `for`, delete `seed!`. `filing_rule.rb`: `folder` may be nil only for a `DEFAULT` key.
   3. `settings/filing_rules_controller.rb`, its routes (`param: :ext`) and `_folder_card.html.erb`:
      - `index` groups `FilingRules.for`.
      - `destroy` writes `(ext, nil)` for a default key and deletes a custom row.
      - `create` keeps today's Remove-then-Add UX by refusing an ext the effective map already files; otherwise it upserts.
      - `update` upserts.
   4. `settings_controller.rb`: the count becomes `Maker::FilingRules.for(current_user).size`.
   5. `project_folders.rb`: `default_folder_for` → `DEFAULT`. `project_intake.rb` is unchanged: it reads `for`, and the `BOARD_LAYER_EXT` fallback (`:549`) still applies when `gbr` is removed.
   6. Docs: `project-intake.md:235-249`, `files-preview.md:20-31,490-498`, and the headers of `filing_rules.rb`, `filing_rule.rb` and `project_folders.rb`.
6. Regression risks and migration concerns:
   - Behaviour: defaults become live for keys a user has not touched.
     - For additive widenings that is the point: it is what each top-up migration did by hand.
     - A future reclassification or `ROLE_FOLDERS` rename would now reach untouched users; today it reaches only users seeded after it. The author of such a change has to decide that explicitly, where today the outcome depends on whether a migration gets written.
     - Converted users are unaffected, because their existing rows stay as deviations.
   - Data: the conversion must record removals (default keys the user lacks), or a removed rule is resurrected; new test (4) pins this. On SQLite, `change_column_null` is a table copy, but on a small table.
   - Routes/UI: chip actions are keyed by ext instead of id, and tenancy becomes structural (only `current_user`'s rows are ever touched). The two foreign-id tests become "a crafted ext touches only your own rows".
   - Backend legs: DB-only and identical on all three.
7. Existing and additional validation required:
   - Existing:
     - `filing_rules_test.rb` (rewrite the seed cases).
     - `project_folders_test.rb:100-119`, and `project_intake_test.rb`'s custom-rule filing case.
     - `settings_filing_test.rb` (cards, add/remove/update, KiCad, reserved names).
     - `settings_hub_test.rb:66` (the count).
     - `page_query_budget_test.rb:1266-1349`: still constant, and without the pre-seed workaround.
   - New, each with the mutation that turns it red:
     - (1) A user with deviations still resolves a default key they never touched. Mutation: `for` reads rows only.
     - (2) Removing `.stl` leaves `folder_for(user, "x.stl") == "other"` across reads and renders no chip. Mutation: `destroy` deletes the row instead of writing nil, so `.stl` goes back to `models`.
     - (3) GET /settings/filing, GET /settings and `FilingRules.for` write zero rows. Mutation: re-add a seed call.
     - (4) A user missing `.stl` before the conversion still files `.stl` into `other` after it. Mutation: skip the NULL inserts.
8. Confidence: medium. The mechanism is small and the evidence is all in the code, but the change rewrites the settings routes and makes future default changes live — both choices the owner should accept explicitly. The conversion is the one data step, and its `down` is cheap.

## Considered and rejected
- **Derive `maker_file_attachments.role` at read time, or store it only when it was set deliberately (NULL = derived).** S06 and S23 rejected this (AUDIT §5).
  - New evidence weakens their "v1 permits a client-set role" reason: the only v1 client sets the role from a drifted guess (cross note 2), not a decision.
  - It does not defeat the other reason. `Project#cover_node_id` must stay query-free per index card (`project.rb:168-171,189-192`; `projects_controller.rb:63` loads attachments only), and deriving there needs node names.
  - Opportunity 1 gets freshness while keeping the role stored.
- **A `role_source` / pinned column to tell deliberate roles from derived ones.** It cannot be backfilled honestly: a v1 row whose role equals `role_for` looks identical either way. It needs a schema change plus about 10 writer sites, and the `other` rule already matches what 7 of 8 historical re-derivations did.
- **One master per-extension table (role, renderer, viewer, measurable, inline, photo, backup).** That is a relocation; the facts genuinely differ.
  - Recorded as different facts: `files-preview.md:487-489` ("a role is where a file files, not whether it renders"), `:196-200` (inline vs role), `:263-272` (`VIEWABLE_3D_EXTS` vs renderers), and the KiCanvas section.
  - Every pair that IS one fact is already derived: `TEXT_EXTENSIONS`→`TextThumb`/Registry/`preview_kind`, `GERBER_EXTS`/`Gerber::EXTENSIONS` from `pcb`, `IMAGE_EXTS`, `EXT_FAMILIES`. See the appendix.
- **Declare each renderer's geometry builder once, and derive `MEASURABLE_EXTS`, `Geometry::REVISIONED_BY`, the four `kind == "geometry"` render arms, the four `payload_revision` arms and `Svg`/`Dxf`'s `available_for?` from it** (S09.md:72; AUDIT.md:714). The duplication is real, but:
  - the lists agree at HEAD and are held together by GeometryTest and the drive-each-entry test (`file_preview.rb:27-28`);
  - the rewrite would mostly move four identical branches behind a type;
  - the invalid state it would close (a PNG stored as `geometry`/`render`/`model_glb`) is reachable only by hand-crafted requests (cross note 1), and a door-side guard closes it.
- **The importer's `roleFor` (`importer_controller.js:8-18`) → a `data-importer-roles-value` built from `ROLE_BY_EXT` on `models/new.html.erb:16`.**
  - It is a real drift at HEAD: `MODEL_EXT` is the 2026-07-21 list, so 13 model extensions (gltf glb ply off dae wrl 3ds fbx 3dm amf iges igs brep) count as "other".
  - But it only changes the summary text, the title fallback when there is no zip, and the cover pick when there is no image (and the server's `derived_cover_node_id` covers that last case). It is recorded and accepted (`files-preview.md:74-75`, `importer_test.rb:106-110`) and S07 judged it below the bar. The fix is cheap if someone is in the file.
- **Derive `Registry::FORMAT_RENDERERS` from each renderer's `EXTENSIONS`, and `ImageThumb::EXTENSIONS` from `IMAGE_EXTS`.**
  - Both agree at HEAD (image 10 = 10, Mesh 14 = 14), and `renderer_contract_test.rb:61-69` reddens the harmful direction. That makes it line-count only (S08 concurred).
  - Also, an image-role extension libvips cannot decode would be a legitimate divergence.
- **`KICANVAS_EXTS` (= `ProjectKind::KICAD_EXTS`) vs `BEYOND_ROLE_BY_EXT`'s keys.** They coincide today but are different facts (which viewer vs which filing key), the same "agreement is not identity" shape §14a records for `scannable`/`port_writable`.

- **`GerberArchive::EXT` / `GerberZip::EXTENSIONS` ("zip") and `ThreeMfManifest::EXT` / `ThreeMf::EXTENSIONS` ("3mf").** These are one-string name tests for different readers; trivial.
