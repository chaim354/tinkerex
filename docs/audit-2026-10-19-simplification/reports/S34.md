## Opportunity 1: A spinner turns only inside a poll cell. Key the animation on the cell, and delete public.css's list of containers that do not poll
1. Verdict: recommend
2. Evidence
   - **One fact, "will anything resolve this spinner?", is decided by the markup and then written again by hand in CSS.**
     - The markup decides it. `thumbs_controller.js:15` declares `static targets = ["cell"]`. `:31-34` defines `pendingIds()` as `this.cellTargets.filter((c) => c.querySelector(".thumb-spinner") || …)`, and `:38-39` stops with `if (ids.length === 0) return`. A cell is `data-thumbs-target="cell"` (`files_helper.rb:88-90`, `thumb_cell_data`) inside a `data-controller="thumbs"`.
     - The CSS writes it again. `components.css:315-319` makes every `.thumb-spinner` turn (`animation: thumb-spin .8s linear infinite`). `pages/public.css:41-42` then stops it for a hand-kept list: `.public-files .thumb-spinner, .public-photos .thumb-spinner, .public-tiles .thumb-spinner { animation: none; }`. Its own comment (:38-40) records that the list has already grown once: "`.public-tiles` JOINED THE PAIR … the rule that is easiest to forget is this one".
   - **The two already disagree, in four places.**
     - Public: two of the six sites that render `files/thumb` are missing from the list.
       - `public/projects/_build_log.html.erb:29-33` (`div.entry-photos`). It has rendered the thumb since 6c1b9b3e, the same commit that wrote the list with only `.public-files` and `.public-photos` on it.
       - `public/projects/_block_panel.html.erb:50-52` (`a.block-thumb`). Its own comment (:41-43) says "a pending thumbnail reads as a static badge (files/_thumb plus pages/public.css)".
       - The result: a pending build-log photo or image-block thumbnail turns forever for a visitor. It also does so on the owner's preview, because `projects/preview.html.erb:10` renders the same body.
       - The four covered sites are `_files.html.erb:37,52`, `_photos.html.erb:15,23`, `_folder_panel.html.erb:46,57` and `_folder_panel.html.erb:66,81`.
     - Private: both image pickers.
       - `projects/_page_intro.html.erb:30-44` and `projects/_block_editor.html.erb:52-66` mount `data-controller="thumbs"` over `button.image-pick` elements (`:37`, `:59`). The buttons carry `data-node-id` but no `data-thumbs-target="cell"`, so `cellTargets` is empty and `poll()` returns at once. A pending spinner in either picker turns until the page is reloaded.
       - The commit message of f218c38a says the opposite: "both image pickers mount their own thumbs controller like the hero, so a pending preview stops spinning without a reload".
       - `projects/_attachments.html.erb:186-189` names this exact shape as the one to avoid: "a controller instance over no cells".
   - **Pending rows are most common exactly where nothing polls.** The public render backfills missing rows (`public_project.rb:425-431`, files-preview.md:606-609), so the first visit after an upload meets `pending` rows.
   - **Four more files state that the list covers every public spinner:** `files-preview.md:602-606`, `public_project.rb:425-428`, `public/projects/_files.html.erb:14-18` and `_block_panel.html.erb:41-43`.
   - **No test can see any of this.** The only spinner assertion checks markup (`maker_page_thumbnails_test.rb:129`). `public_project_test.rb:464` asserts that the controller is absent, not that the animation stopped.
   - **The repo's own rules point at this fix.**
     - `preview.css:85-87`: "STYLED OFF `data-group` AND `data-state`, NEVER OFF CLASSES OF THEIR OWN … a parallel set of class names would be a second vocabulary for one fact, free to disagree with the first".
     - `components.css:327-331` keeps `.thumb-failed` in components.css because it is "A STATE OF THE COMPONENT, so it lives here and not in a page sheet".
3. Current complexity or invalid states
   - Every surface that renders `files/thumb` without a poll needs a second edit in a page sheet, and nothing ties the two edits together.
     - Two of the six public sites were missed. One was missed at birth (6c1b9b3e).
     - Prose in four files promises a guarantee that the CSS does not give.
   - The list knows only public containers. A private mount with no cell (the two pickers) gets the same never-ending spinner, and there is no place to record it as an exception.
   - The invalid state that exists today: a spinner that animates, promising an answer, in a region no poll will ever visit.
4. Proposed representation and why it is simpler

   The spinner reads the poll's own test for "pending". No rule names a container.
   ```css
   /* components.css, replacing :315-318 */
   .thumb-spinner { width: 14px; height: 14px; border: 2px solid transparent;
     border-top-color: var(--thumb-ink); border-right-color: var(--thumb-ink); border-radius: 50%; }
   /* IT TURNS ONLY WHERE THE POLL WILL ANSWER IT: inside a cell thumbs_controller reads (cellTargets,
      whose spinner IS the pending predicate). Anywhere else -- every public surface (the poll door is
      session-authed) and any mount with no cell -- nothing will replace it, so it is a still ring. */
   [data-thumbs-target~="cell"] .thumb-spinner { animation: thumb-spin .8s linear infinite; }
   ```
   - Delete `pages/public.css:35-42`.
   - A new public partial, or a private mount that forgets its cell wiring, then shows an honest still ring with no edit anywhere else. Adding the wiring is what makes the spinner turn, and it is also what makes the thumbnail resolve.
   - A stricter variant also requires the controller: `:is([data-controller~="thumbs"] [data-thumbs-target~="cell"], [data-controller~="thumbs"][data-thumbs-target~="cell"]) .thumb-spinner`.
     - The second arm covers `models/show.html.erb:116-118`, where the controller element is its own cell.
     - No current render site needs the stricter form.
5. Smallest credible implementation scope
   1. `components.css:315-319`: move `animation` onto the cell-scoped selector. This is one rule in S20's file.
   2. `pages/public.css:35-42`: delete the comment and the rule.
   3. Update the prose that names public.css as the mechanism: `files-preview.md:602-606`, `public_project.rb:425-428`, `public/projects/_files.html.erb:14-18` and `public/projects/_block_panel.html.erb:41-43`.
   4. Add the tests below.
   - Nothing else changes: no markup, controller, route or addon.
   - The pickers' real fix is S15's (see the cross-subsystem notes): put `thumb_cell_data` on their buttons so that they poll. With this rule in place, that change also brings their spin back.
6. Regression risks and migration concerns
   - Visible changes:
     - The two public sites that are not covered today, and the two pickers, become still rings. That is the intended state.
     - Every other spinner is unchanged. I checked all 17 private `files/thumb` render sites one by one (15 explicit, plus `files/_grid` and `_list` through their relative `render "thumb"`). Apart from the two pickers, each of the 15 sits inside a cell under a thumbs controller, wired either by `thumb_cell_data` or by a raw `data-thumbs-target="cell"`.
   - Coupling: the CSS now names a Stimulus target.
     - If the target in `thumbs_controller.js` is renamed, every spinner stops. That failure is safe: they become still rings and polling is unaffected.
     - The private half of the new system test catches it. `stimulus_hygiene_test` does not read CSS.
   - Addons are unaffected. No bundle renders `.thumb-spinner` or any Stimulus wiring (grep of `../tinkerex-addons/addons`), and `.thumb-spinner` is not one of the 52 contract classes.
   - Cascade: the rule stays in the same layer as today. The only other `animation` rule is the reduced-motion `!important` at `application.css:178-180`, which does not change.
   - Data, API and the backend legs are unaffected. This is CSS only, and it behaves the same on share, s3 and chunk_remote.
7. Existing and additional validation required
   - These must stay green: `maker_page_thumbnails_test.rb:129` (spinner markup), `public_project_test.rb:464` (no poll on /u/:handle), and the 375px sweep in `shell_test.rb:214`.
   - New system test, checking both directions:
     - Set up a published project with a build-log photo and an image block whose nodes have `pending` rows.
     - On the public page, assert that every `.thumb-spinner` has `getComputedStyle(el).animationName == "none"`.
     - On the Library grid, with a pending row, assert `"thumb-spin"`.
     - Today the public half is red: the `.entry-photos` and `.block-thumb` spinners report `thumb-spin`.
     - Mutation 1: put `animation` back on the bare `.thumb-spinner`. The public half goes red.
     - Mutation 2: drop the cell-scoped rule. The private half goes red.
     - The reduced-motion rule does not change `animationName`, so the check is unaffected by it.
   - Optional cheap guard in `css_hygiene_test`: no page sheet sets `animation` on `.thumb-spinner`, so the list cannot come back. Mutation: restore `public.css:41-42`, and the guard goes red.
8. Confidence: high.
   - I traced both public misses and the pickers' empty `cellTargets` by reading the markup and the controller, and the cascade involved is ordinary.
   - Not observed in a browser, because this review was read-only.

## Opportunity 2: Make the `hidden` attribute authoritative once, in `@layer base`, instead of restating `[hidden]` in each component
1. Verdict: recommend
2. Evidence
   - **The attribute is the one fact "this element is hidden", and CSS overrides it by default.** Templates, Stimulus controllers and the addon bundles all write it; `lib/file_chooser.js:237-238` calls it "the house idiom". But any author `display` beats the UA's `[hidden] { display: none }`, so the attribute works only on a component that restates it.
   - **There are 6 restatements, covering 7 selectors in 3 sheets.**
     - In this row's sheet:
       - `tools.css:71`: `.box-toc-list li[hidden]`.
       - `tools.css:97`: `.addon-card[hidden], .box-group[hidden]`.
       - Only `.addon-card` needs it, because it has `display: flex` (:17). `li` and `.box-group` (:84) have no author `display`, so two of the three are belt and braces.
       - They serve the addon bundles' filter: `addons/boxes/filter.js:50-58` and `openscad/filter.js:62-70` set `card.hidden`, `group.hidden` and `item.hidden`.
     - In S20's sheets:
       - `components.css:215-220`, `.tab-pane[hidden]`, with the comment "Any component given a `display` must restate this if anything ever hides it with the attribute".
       - `components.css:450-453`, `.flash[hidden]`. Without it, an empty "Problem" box showed on every openscad load (`shell_test.rb:156-169`).
       - `components.css:553-558`, `.filechooser-back[hidden]`, with the comment "met a second time" (`repo_browser_test.rb`).
       - `shell.css:115-117`, `.topbar-upload-caption[hidden]`.
   - **They already disagree, live, on the YAML layout drawer.**
     - `components.css:181` declares `.layout-drawer { position: sticky; …; display: flex; … }`.
     - `projects/_layout_drawer.html.erb:2` says "Hidden until 'Edit as YAML'", and `:8` renders `<aside class="layout-drawer" hidden …>`.
     - `layout_editor_controller.js:430-436` toggles the attribute, and the toggle button carries `aria-expanded="false"` (`_layout_bar.html.erb:46`).
     - No `.layout-drawer[hidden]` rule exists. So from the moment edit mode opens, the drawer (Copy, Apply and an empty textarea) renders below the panel grid, and "closing" it leaves it on screen.
     - The tests check only the attribute: `project_layout_editor_test.rb:48` asserts `aside.layout-drawer[hidden]`, and `page_editor_test.rb:146-147` asserts `:not([hidden])` after the click.
   - **The JS believes a reset exists, and none does.**
     - `file_chooser.js:237-238`: "`el.hidden`, not `style.display`: the house idiom (readme_controller.js, layout_editor_controller.js), and the one the app's own reset already honours."
     - The commit that wrote that sentence, fc29cc20, also had to add `.filechooser-back[hidden]`.
     - `git log -S'[hidden]'` over application.css, components.css and shell.css shows that no such reset ever existed. The pre-2026-09 application.css had the same two tools restatements.
     - The spec puts "the reset" in application.css's base layer (spec 2026-09-03 §4.1, line 80).
   - **The addon bundles already work around it.** tinkerex-addons@d3ab6fd, `addons/boxes/editor.js:170-177`: "REMOVED RATHER THAN `hidden`, WHICH IS DECORATIVE ON THIS ELEMENT. The host's `.btn` rule sets `display` … Probed, not reasoned … a bundle cannot add a third (it ships no CSS), so it removes the node instead."
   - **Exposure:** roughly 290 selectors across our sheets set a visible `display` (an approximate count: components 81, projects 48, tools 33, preview 32, files 23, shell 20, and others). Only 7 of them restate `[hidden]`.
3. Current complexity or invalid states
   - One bit has two owners: the attribute, which everything writes, and each component's `display`, which wins by default.
   - Correctness depends on a per-component restatement that has been discovered only after a shipped bug. Four bug stories are recorded, and the drawer is a fifth that nobody has found yet.
   - The addon bundles can use `hidden` only on the classes this repo happens to restate. On every other class it is "decorative".
   - Invalid states this permits:
     - an element with `hidden` that is visible and focusable (the drawer today; the Back button and the tab panes before their fixes);
     - a control marked `aria-expanded="false"` next to a region that is visible.
4. Proposed representation and why it is simpler
   ```css
   /* application.css, @layer base, after the box-sizing reset (:154) */
   /* THE `hidden` ATTRIBUTE IS AUTHORITATIVE -- the house idiom (file_chooser.js) needs nothing else.
      `!important` in an EARLY layer is the cascade's own tool for this, not a fight with it: important
      declarations reverse layer order, so this beats every component, shell, page and vendor rule,
      and no component restates `[hidden]`. `until-found` keeps its own UA behaviour. */
   [hidden]:not([hidden="until-found"]) { display: none !important; }
   ```
   - Then delete the seven selectors: `tools.css:71` and `:97`; `components.css:215-220`, `:450-453` and `:553-558`; `shell.css:115-117`.
   - The result:
     - "Hidden" has one definition.
     - The drawer is fixed with no edit to components.css.
     - Every addon-shared class honours `hidden`. The boxes workaround can stay, because it remains correct.
   - This is not F-S20-1's pattern found again. F-S20-1 is one rule block duplicated across two triggers; this is markup state that a CSS declaration silently overrides.
   - The obvious alternative is a seventh restatement, `.layout-drawer[hidden]`. That is the pattern that produced the defect.
5. Smallest credible implementation scope
   1. `application.css` base layer: add the one rule. The file is S20's.
   2. `tools.css:71` and `:97`: delete. These are this row's.
   3. `components.css:215-220`, `:450-453` and `:553-558`, and `shell.css:115-117`: delete the rules and their comments. These are S20's. Deleting them is optional, since they become inert, but it is what leaves a single definition.
   4. `docs/invariants/design-system.md`, under "The cascade": add one rule saying that `hidden` is authoritative in base and that components never restate it.
   5. Add the tests below.
6. Regression risks and migration concerns
   - The risk is CSS that deliberately shows an element carrying `hidden`, which the rule would now hide. I checked:
     - the eight `hidden` elements in five templates (`_upload_control` ×2, `_block_editor:33`, `_layout_drawer:8`, `_topbar_upload` ×3, `files/show:99`);
     - the eight attribute writes in five JS files (`readme`, `file_chooser`, `layout_editor` ×3, `tabs` ×2, `upload_pick`);
     - every `hidden` in the addon bundles.
   - None relies on CSS overriding the attribute. The drawer is the only behaviour that changes, and it changes to what its comment documents.
   - Lexxy's own `[data-dropdown-panel][hidden] { display: none }` agrees with the new rule. A grep found no code that sets `style.display` while `hidden` is set.
   - `!important` is already established here:
     - `application.css:179` uses it in the base layer for reduced motion.
     - `css_hygiene_test` has no rule against it, and design-system.md rule 1 still holds because the rule is layered.
     - An unlayered vendor `!important` would lose to it, and none targets `[hidden]`.
   - Addons: `hidden` becomes strictly more effective, and no bundle depends on it being ignored.
   - Data, API and the backend legs are unaffected.
7. Existing and additional validation required
   - These must stay green once the restatements are deleted. Together they prove the base rule covers each former restatement:
     - `shell_test.rb:161` (the hidden-flash probe);
     - `repo_browser_test.rb`, "the browser offers no Back at its root";
     - the page_tabs suite (one pane at a time);
     - `system/topbar_upload_test.rb` (the top-bar caption);
     - the box filter in `system/box_sections_test.rb` (it types into `input.box-search`, which hides cards and groups).
   - New test in `page_editor_test.rb`:
     - Call `open_editor`, then `assert_no_selector "aside.layout-drawer"` (Capybara counts visible elements only).
     - Click "Edit as YAML" and `assert_selector`; click it again and `assert_no_selector`.
     - Today the first assertion is red.
     - Mutation: delete the base rule, and the test goes red.
   - New test generalising the probe at `shell_test.rb:161`:
     - Inject `<button class="btn" hidden>`, `<aside class="layout-drawer" hidden>` and `<div class="addon-card" hidden>`, and assert none of them is visible.
     - Mutation: delete the base rule. With the restatements gone, all three go red.
   - New `css_hygiene_test` assertions: the base layer carries the rule, and no other sheet declares `[hidden] { display: none }`.
     - Mutation 1: delete the rule, and the test goes red.
     - Mutation 2: re-add `.addon-card[hidden]`, and the test goes red.
8. Confidence: medium-high.
   - The cascade behaviour (an author normal rule beats a UA normal rule) is certain, and this codebase has measured it three times.
   - The drawer defect is inferred from that behaviour, not observed, because this review was read-only.
   - The open question is ownership: the rule's home, and four of the seven selectors, belong to S20.
