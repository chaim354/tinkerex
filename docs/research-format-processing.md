# File-Format Processing & Preview — Library Survey

> **HISTORICAL — not re-verified.** Written before the repository split of 2026-08-20, when the
> sync engine and the Rust client still lived here (they are `chaim354/tinkerex-sync` and
> `chaim354/tinkerex-client` now). Kept for its reasoning and its measurements; it does not
> describe what this repository contains today. The current map is `docs/README.md`.


> **Purpose.** Survey the libraries that can parse / convert / render / thumbnail every file
> format the maker app handles (CLAUDE.md §1: 3D **STL / 3MF / OBJ**, CAD **STEP / IGES** +
> native Fusion/FreeCAD/SolidWorks, LightBurn **`.lbrn2`**, plus the vector formats **SVG / DXF**
> that show up as laser/CNC source), so the **Previews** pillar (a server job that turns a file
> version into a thumbnail/GLB — `Maker::Preview`, CLAUDE.md §4/§12-step-9) can be built on a
> **permissive-only** toolchain.
>
> **Hard constraint (CLAUDE.md §9): permissive licenses only — MIT / Apache-2.0 / BSD.**
> **GPL/AGPL is DISQUALIFIED** for anything we bundle or ship or depend on. **LGPL/MPL** is a
> *qualified yes*: usable **only** if dynamically linked / invoked as a separate process (the
> same posture CLAUDE.md §9 already takes for OCCT-derived tooling and for FUSE drivers — keep
> the copyleft code out of *our* binary). The framing gap this closes: `feature-set-and-workflows.md`
> §3 item 10 ("Preview an STL/3MF/CAD file in-browser" — **not built**).

## 0. TL;DR — the recommended permissive toolchain

| Format | Recommended path | Why | License posture |
|---|---|---|---|
| **SVG** | **resvg** (Rust CLI/lib) → PNG | pure-Rust, no system deps, MIT/Apache | ✅ permissive — bundle freely |
| **`.lbrn2`** | **lbrn2-to-svg** (TS) → SVG → **resvg** → PNG | XML→SVG is small + auditable; reuse the SVG path | ✅ MIT |
| **3MF** | **extract embedded `Metadata/thumbnail.png`** first; fall back to **F3D** (BSD) render | most slicer-exported 3MF *already* carries a PNG → zero render | ✅ BSD / pure-zip |
| **STL / OBJ** | **F3D** headless (`--output`) → PNG; optional GLB via F3D/Assimp | one BSD binary covers all meshes; offscreen-capable | ✅ BSD-3 |
| **STEP / IGES** | **F3D** (links OCCT) headless → PNG/GLB, *as a separate process* | OCCT is LGPL → process-isolate (don't statically link into our app) | ⚠️ LGPL via subprocess only |
| **DXF** | **ezdxf** (Python) → SVG (matplotlib backend) → **resvg** → PNG | MIT; **avoid its PyMuPDF PNG backend (AGPL)** — go via SVG | ✅ MIT (SVG backend) |
| native **Fusion/SldWrks** | **none** (proprietary) → store "no preview", suggest exporting STEP/STL | closed binary formats; no permissive parser | n/a — unsupported by design |

**Common rendering strategy (see §8):** normalize *everything* to a **thumbnail PNG** (the universal,
cheap, web-safe artifact — the `Maker::Preview` `kind: thumbnail`), and — for true 3D formats —
optionally also emit a **web-friendly GLB** (`kind: model_glb`) for an interactive Three.js viewer in
the web/Tauri UI. **Render server-side / headless** (the job model the data layer already assumes:
`Maker::Preview` is generated by a server job), with **Three.js used only client-side** to display the
GLB. Rasterization (SVG/lbrn2/DXF→PNG) is pure-CPU and trivially server-side; mesh/CAD rendering uses
F3D offscreen (CPU/OSMesa or GPU if present).

## 1. LightBurn `.lbrn2` → SVG/PNG

`.lbrn2` is LightBurn's XML project format (vector shapes + cut settings + embedded raster images +
text-as-backup-path). There is no "official" library; the maker community has a couple of parsers.

| Library | Lang | What it does | License | Maturity | As a server job |
|---|---|---|---|---|---|
| **jlucaso1/lbrn2-to-svg** | TypeScript | Parses lbrn2 XML → typed objects → SVG (rects/ellipses/paths/groups, embedded bitmaps as base64 `<image>`, text via BackupPath outlines, CutSetting stroke colors, Y-up→Y-down fix) | **MIT** ✅ | Small but functional — ~6★, ~27 commits, actively maintained, no tagged release yet ([repo](https://github.com/jlucaso1/lbrn2-to-svg)) | Run via Node/Bun/Deno (it ships as a library + supports all three runtimes); call from a Ruby job over a thin Node CLI shim, output SVG, then rasterize with resvg |
| *roll-our-own XML parser* | Ruby (Nokogiri, MIT) | lbrn2 is plain XML — for the **subset we care about** (the shapes for a thumbnail) we can parse it directly in-process with Nokogiri and emit SVG, avoiding a Node dependency | **MIT** (Nokogiri) ✅ | Nokogiri is extremely mature; the lbrn2→SVG mapping is the work | Pure in-Ruby in the job — **no extra runtime**. Best long-term home; lbrn2-to-svg is the reference implementation to port from |

**Recommendation.** Phase-1 quickest win: shell to **lbrn2-to-svg** (MIT) for correctness, OR (preferred,
fewer moving parts) port its shape-mapping into a small in-Ruby `Maker::Lbrn2ToSvg` using Nokogiri.
Either way the output is SVG → reuse the SVG→PNG path (§4). lbrn2's structure (CutSetting colors,
BackupPath text) is documented by the reference repo's README/source, our primary source.

## 2. 3MF → thumbnail

3MF is a ZIP container (OPC) of XML mesh + relationships. **Crucially, the spec lets a 3MF embed a 2D
thumbnail** (JPEG/PNG) referenced by an OPC relationship, and **most slicer-exported 3MF files already
carry one** — PrusaSlicer/Bambu write `Metadata/thumbnail.png` (a slight spec deviation; the spec's
canonical location is via the `…/metadata/thumbnail` relationship). So the cheapest 3MF preview is
**extract the embedded PNG — no rendering at all.**

| Library | Lang | What it does | License | Maturity | As a server job |
|---|---|---|---|---|---|
| **(zip extraction)** Ruby `Zip` (rubyzip, BSD-2) | Ruby | Open the 3MF as a zip, read `Metadata/thumbnail.png` (or resolve the OPC thumbnail relationship) | **BSD-2** ✅ | Trivial + mature | In-process; near-zero cost; covers the common case |
| **3MFConsortium/lib3mf** | C++ (C/Py/Go/etc. bindings) | Full 3MF read/write; `HasPackageThumbnailAttachment()`/`GetPackageThumbnailAttachment()` to pull the embedded thumbnail; also exposes the mesh for rendering | **BSD** ✅ | The 3MF Consortium's reference implementation — very mature ([repo](https://github.com/3MFConsortium/lib3mf)) | As a CLI/FFI to extract the thumbnail *correctly* (resolves the relationship vs. guessing the path) |
| **three.js `3MFLoader`** | JS | Parses 3MF mesh in-browser | **MIT** ✅ | Mature (part of three.js) | Browser-side display; not the server thumbnail path |
| **F3D** | C++ | Renders the 3MF *mesh* to a PNG if no embedded thumbnail exists | **BSD-3** ✅ | Mature (§3) | Headless fallback render |

**Recommendation.** **Try the embedded thumbnail first** (rubyzip read of `Metadata/thumbnail.png`, or
lib3mf for spec-correct relationship resolution); **fall back to an F3D mesh render** when absent. This
makes 3MF the *easiest* high-value 3D format (most files preview for free).

| Library | Lang | What it does | License | Maturity | As a server job |
|---|---|---|---|---|---|
| **F3D (f3d-app/f3d)** | C++ (+`libf3d` C/Py/Java/JS) | Fast minimalist 3D viewer + **headless thumbnail generation**; loads glTF/STL/STEP/PLY/OBJ/FBX/3MF; fully CLI-controllable (`f3d model.stl --output thumb.png`); PBR/raytrace optional | **BSD-3-Clause** ✅ | Mature, active (Kitware-adjacent, FOSDEM 2026 talk); built on VTK + OCCT + Assimp ([repo](https://github.com/f3d-app/f3d)) | **The recommended common renderer.** Invoke the CLI offscreen (OSMesa/EGL for headless CI/servers); one binary covers STL/OBJ/3MF/STEP. Note its **OCCT/Assimp deps are LGPL/BSD** — process isolation keeps that copyleft out of *our* binary |
| **three.js `STLLoader`/`OBJLoader`** | JS | Parse + render meshes | **MIT** ✅ | Very mature | **Client-side** Three.js viewer; for *server* rendering would need `headless-gl` (CPU WebGL, no GPU) — heavier/flakier than F3D, so reserve for the browser |
| **numpy-stl** | Python | Parse STL meshes (no renderer) | **BSD** ✅ | Mature | Mesh stats / custom matplotlib render; lower-level than F3D |
| **ADMesh** | C | STL repair/inspect (no render) | **GPLv2** ❌ | Mature | **DISQUALIFIED** for bundling (GPL) — don't depend on/ship |
| **OpenSCAD** | C++ | CSG modeler; can render PNG via CLI | **GPLv2** ❌ | Mature | **DISQUALIFIED** (GPL) as a bundled dependency |

**Recommendation.** **F3D headless** is the single best permissive renderer for all mesh + CAD formats —
adopt it as the common 3D thumbnail engine. Keep **three.js** strictly client-side for interactive GLB
viewing. Avoid ADMesh/OpenSCAD (GPL).

## 4. SVG → PNG (the rasterization backbone)

The SVG→PNG step is reused by lbrn2 and DXF, so its license matters a lot.

| Library | Lang | What it does | License | Maturity | As a server job |
|---|---|---|---|---|---|
| **resvg (linebender/resvg)** | Rust (CLI + C lib) | SVG → raster (PNG); pure-Rust, no system deps, ~1600 regression tests, CLI < 3MB | **MIT OR Apache-2.0** ✅ | Mature — ~3.9k★, 55 releases ([repo](https://github.com/linebender/resvg)) | **Recommended.** Ship the `resvg` CLI (or bind the C lib); `resvg in.svg out.png`. Deterministic, sandboxable, no GNOME/cairo baggage |
| **librsvg** | C/Rust (GNOME) | SVG → raster via cairo | **LGPLv2.1 / GPLv2** ⚠️/❌ | Very mature | LGPL → would have to invoke `rsvg-convert` as a **separate process** (and it drags cairo + GNOME deps). resvg avoids all of this — **prefer resvg** |
| **CairoSVG** | Python | SVG → PNG/PDF | **LGPLv3** ⚠️ | Mature | LGPL (and Python). Subprocess-only if used; resvg is simpler |
| **sharp** (libvips) | JS/native | Raster pipeline; SVG in via librsvg | **Apache-2.0** (but SVG path pulls **librsvg LGPL**) ⚠️ | Very mature | The SVG decode still routes through librsvg → same LGPL caveat |
| **rsvg / ImageMagick / `image_processing` gem** | Ruby | `image_processing` (~> 2.0, **already in the Gemfile**, MIT) wraps **libvips** or **ImageMagick** | gem **MIT** ✅; backends vary | Mature | Use `image_processing` for **resize/crop/encode of the PNG** we already produced (it's great at raster→raster); do **not** rely on it for SVG decode (that path = librsvg/IM-rsvg, LGPL) |

**Recommendation.** **resvg** for SVG→PNG (clean permissive, zero system deps). Then use the existing
**`image_processing` ~> 2.0** gem (MIT) only for the *raster* finishing pass (downscale to thumbnail
dimensions, encode). This keeps the one copyleft-adjacent component (librsvg) entirely out of the picture.

## 5. DXF → SVG/PNG

DXF (AutoCAD interchange) shows up as laser/CNC source. **DWG** (the binary sibling) is the licensing
minefield — the only full parser is GPL.

| Library | Lang | What it does | License | Maturity | As a server job |
|---|---|---|---|---|---|
| **ezdxf (mozman/ezdxf)** | Python | Read/write DXF; **SVG export via a matplotlib backend**; (also PNG/PDF via a **PyMuPDF** backend — see caveat) | **MIT** ✅ | Very mature, well-documented ([site](https://ezdxf.mozman.at/)) | Run as a small Python CLI → **emit SVG** (matplotlib backend, BSD/PSF), then resvg→PNG. **AVOID ezdxf's PyMuPDF/PNG backend — PyMuPDF is AGPL** ❌ |
| **dxf-parser (JS)** | JavaScript | Parse DXF → JSON (no render) | **MIT** ✅ (commonly) | Moderate | Node CLI → build SVG ourselves; lower-level than ezdxf |
| **LibreDWG** | C | DWG **and** DXF read/write | **GPLv3** ❌ | Mature | **DISQUALIFIED** — GPL. (This is why **DWG has no permissive path**; only DXF does, via ezdxf) |

**Recommendation.** **ezdxf → SVG (matplotlib backend) → resvg → PNG.** Explicitly do **not** use
ezdxf's PyMuPDF PNG path (AGPL). DWG is unsupported (no permissive parser).

## 6. STEP / IGES + native CAD (Fusion / FreeCAD / SolidWorks)

The open CAD interchange formats (STEP/IGES) are all served by **OpenCASCADE (OCCT)** under the hood —
which is **LGPL-2.1-with-exception**. That's a *qualified* yes: use OCCT-derived tooling **as a separate
process / dynamically**, never statically linked into our shipped binary (exactly the §9 posture).

| Library | Lang | What it does | License | Maturity | As a server job |
|---|---|---|---|---|---|
| **OpenCASCADE (OCCT)** | C++ | The CAD kernel — reads STEP/IGES/BREP, tessellates to mesh | **LGPL-2.1 + exception** ⚠️ | Industry standard | The engine *under* the tools below; isolate as subprocess |
| **F3D** | C++ | Renders STEP/IGES directly (links OCCT) → PNG/GLB headless | **BSD-3** (app) ✅, OCCT dep LGPL ⚠️ | Mature (§3) | **Recommended.** `f3d part.step --output thumb.png` as a subprocess → keeps the LGPL dep process-isolated. Single binary already covering meshes |
| **occt-import-js** | C++→WASM (JS/Node) | Imports STEP/IGES/BREP → JSON mesh (the data → build GLB or render) | **LGPL-2.1-only** ⚠️ | Active ([repo](https://github.com/kovacsv/occt-import-js)) | Node module → produce a GLB for the Three.js viewer; LGPL via the WASM module (separable) |
| **FreeCAD (headless)** | C++/Python | Full CAD app; `freecadcmd` scripting reads STEP/IGES → export STL/mesh/thumbnail | **LGPL-2.0-or-later** ⚠️ | Very mature | Heavyweight; subprocess `freecadcmd`. Use only if F3D's STEP coverage is insufficient |
| **CadQuery / build123d** | Python | Parametric CAD over OCCT; can import + tessellate STEP | **Apache-2.0** (CadQuery) ✅ / build123d Apache ✅ — but **OCP/OCCT runtime is LGPL** ⚠️ | Active ([cadquery](https://pypi.org/project/cadquery/), [build123d](https://github.com/gumyr/build123d)) | Pythonic STEP→mesh→GLB; the *wrapper* is Apache but it loads LGPL OCCT at runtime → still subprocess-isolate |
| **Fusion 360 / SolidWorks native** (`.f3d`, `.sldprt`) | — | **Proprietary closed formats** | n/a ❌ | — | **No permissive (or any FOSS) parser.** Store `status: failed` / "no preview"; UX nudge: export STEP/STL. FreeCAD native `.FCStd` *is* openable (it's a zip of BREP) via FreeCAD/OCCT |

**Recommendation.** **F3D (subprocess)** for STEP/IGES thumbnails (reuses the same renderer as meshes;
LGPL OCCT stays process-isolated). For an interactive web GLB of a CAD part, **occt-import-js**
(Node/WASM) → GLB. **Native Fusion/SolidWorks are unsupported** (proprietary); FreeCAD `.FCStd` is
feasible via FreeCAD but deprioritized.

## 7. Licensing-risk callout (read before adding any dependency)

**✅ Safe to bundle/ship (permissive — MIT/Apache/BSD/PD):**
resvg (MIT/Apache), lbrn2-to-svg (MIT), Nokogiri (MIT), rubyzip (BSD-2), lib3mf (BSD), F3D (BSD-3),
three.js (MIT), numpy-stl (BSD), ezdxf (MIT, *SVG/matplotlib backend only*), dxf-parser (MIT),
`image_processing` gem (MIT), CadQuery/build123d *wrappers* (Apache).

**⚠️ LGPL/MPL — use only via subprocess / dynamic link, never statically linked into our binary:**
OpenCASCADE/OCCT (LGPL-2.1+exc), occt-import-js (LGPL-2.1), FreeCAD (LGPL-2.0+), librsvg (LGPL/GPL),
CairoSVG (LGPLv3). **F3D, occt-import-js, FreeCAD are *invoked as separate processes* anyway**, which
satisfies the dynamic-link condition and keeps copyleft out of *our* shipped artifacts (same model as
the user-installed FUSE drivers, §9). **CadQuery/build123d are Apache wrappers but load LGPL OCCT at
runtime — treat them as LGPL for distribution purposes (subprocess).**

**❌ DISQUALIFIED — GPL/AGPL, do NOT depend on, bundle, or ship (CLAUDE.md §9):**
- **LibreDWG** (GPLv3) — the only full DWG parser → **DWG is unsupported by design**.
- **ADMesh** (GPLv2), **OpenSCAD** (GPLv2) — STL tooling; F3D/numpy-stl cover our needs permissively.
- **PyMuPDF / MuPDF** (AGPL) — ezdxf's PNG/PDF raster backend → **use ezdxf's matplotlib SVG backend
  instead**, then resvg→PNG. (Easy trap: the obvious `ezdxf → PNG` one-liner pulls AGPL.)
- General rule: when a Python tool offers "PDF/PNG export", **check the raster backend** — PyMuPDF
  (AGPL) and Ghostscript (AGPL) hide here.

**Proprietary (no FOSS parser at all):** Fusion 360 `.f3d`, SolidWorks `.sldprt/.sldasm`,
native Fusion/Inventor → **unsupported; prompt the user to export STEP/STL/3MF.**

## 8. Recommended common rendering approach

1. **Normalize to two artifacts**, matching the `Maker::Preview.kind` enum already designed
   (`thumbnail` / `model_glb` / `render`):
   - **`thumbnail`** — a PNG (e.g. 512×512, padded square) for *every* previewable format. This is the
     universal, cheap, list-grid-friendly artifact and the **only** thing Phase 1 must produce.
   - **`model_glb`** — *optionally*, for true 3D/CAD formats, a web-friendly **GLB** for an interactive
     **Three.js** viewer. Generated later (Phase 3+).
2. **Server-side / headless for generation** (the data model already assumes a server job): rasterizers
   (resvg) are pure-CPU; F3D renders offscreen (OSMesa/EGL — no GPU required, GPU used if present). This
   keeps the browser thin and the output cacheable/CDN-able via ActiveStorage→S3/R2.
3. **Client-side Three.js only for *display*** of the GLB (the existing CLAUDE.md §4 plan: "Three.js
   (browser)"). The server never runs WebGL.
4. **Pipeline shape per format** (all converge on PNG):
   - SVG → resvg → PNG → `image_processing` resize → store.
   - lbrn2 → (lbrn2-to-svg / in-Ruby) → SVG → resvg → PNG.
   - DXF → ezdxf(SVG) → resvg → PNG.
   - 3MF → embedded-PNG extract (rubyzip/lib3mf) **or** F3D render → PNG.
   - STL/OBJ → F3D → PNG.
   - STEP/IGES → F3D (subprocess) → PNG; later occt-import-js → GLB.
5. **Degrade gracefully:** unknown/proprietary/failed → `Maker::Preview.status = failed` with an
   `error`; the UI shows a generic file-type icon. Never block the catalog on a missing preview.
6. **Tooling availability is environment-dependent:** resvg + Ruby are always present; **F3D, Node,
   Python tools are optional external binaries** — the job must detect their absence and mark `failed`
   (not crash). Phase 1 deliberately picks a format whose toolchain (resvg, pure-Ruby) is
   self-contained.

**Net:** **resvg is the only hard dependency for Phase 1** (SVG and/or lbrn2). F3D unlocks all 3D/CAD in
a later phase as one BSD binary. Everything stays MIT/Apache/BSD in *our* shipped code; the only
copyleft (OCCT, via F3D/occt-import-js) is always a separate process.
